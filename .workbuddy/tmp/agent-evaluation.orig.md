# Agent 评测通用知识

> **适用范围**：所有需要为 LLM Agent 建立评测体系的场景（自研 Agent、Agent 平台、模型选型）
> **前置知识**：了解 LLM 基本调用、工具调用（function calling）、RAG 概念
> **最后更新**：2026-09-29
> **可信度标注**：文中结论分三档 —— `[已验证]` 有公开实验/数据支撑 · `[共识]` 行业实践普遍认同 · `[待验证]` 有讨论但结论未稳

---

## 0. 总纲

> **评测的重心已经从"只看最终答案对不对"，迁移到"结果 + 轨迹 + 每一轮"的分层评测，并且离线（CI 回归）与在线（真实流量）两条腿同时走。** `[共识]`

一个最终答案正确、但中途绕了 20 步、两次违反策略、还漏了工具调用的 Agent，在过去会被判"通过"，在现在应判为"失败轨迹"。

核心判断：
- **结果层是必要条件**（保底）
- **轨迹层是诊断信号**（定位问题）
- **能力边界是选型依据**（做技术决策）

---

## 1. 三条底层思路

所有评测设计本质都是这三条路线的组合 + 权重分配。

### 1.1 结果导向（Outcome / End-state）

只看任务终点是否达成：最终答案是否正确、**系统端状态**（数据库 / 文件 / 订单 / 工单）是否符合预期。

- 本质是"带环境的单元测试"
- **关键要求**：校验系统状态，而不仅是最终文本
- 参考实现：τ-bench 校验数据库状态 `[已验证]`

### 1.2 过程导向（Trajectory / Process）

看产生结果的那条路径：工具选对没、参数对不对、用了几步、有没有打转、出错后能否自己恢复、有没有越权操作。

- **关键要求**：轨迹比对要支持"子集/包含"模式，参考路径往往不唯一
- 评测的原子能力是 **trace capture**——没有离散、可记录的工具调用，一切无法追踪、回放、跨版本比较 `[已验证]`

### 1.3 能力刻画（Capability envelope）

不追固定基准分数，而是刻画**能力边界**。

- 代表指标：**METR time-horizon** —— 50% 成功率对应的任务人类工时，约每 7 个月翻一倍 `[已验证]`
- 优势：不受基准饱和影响，是最"抗过时"的有效性信号
- 局限：答不了"这次改动有没有让线上变差"

### 1.4 三条路线的盲区（为什么必须叠加）

| 路线 | 典型盲区 | 反例 |
|---|---|---|
| 只测结果 | 放过"答对了但路径全错、成本爆炸、过程违规" | Agent 回复"机票已订好"，实际根本没调用订票接口 |
| 只测过程 | 误杀合理替代方案；过程对 ≠ 目标达成 | 换了等效工具链被判为不匹配 |
| 只测能力边界 | 无法做回归，无法回答"有没有变差" | 基准分涨了，但线上崩在某类长尾 |

## 2. 两条横轴：离线 vs 在线

不是两种竞品方案，而是回答两个不同问题，**成熟体系必须都有**。

| 对比项 | 离线评测（固定数据集） | 在线评测（真实流量） |
|---|---|---|
| 输入 | 带标准答案的固定任务集 | 真实请求，含数据集里没有的长尾 |
| 运行时机 | CI / 发版前 / 每次改 prompt | 持续运行，每轮实时 |
| 能抓到什么 | 已知用例上的回归 | 漂移、新型失败、越狱、用户挫败 |
| 可复现性 | 高 | 低（靠标注 + 聚合） |
| 打分器 | 断言 + LLM-as-Judge + 人工抽检 | **毫秒级分类器**（Judge 太慢太贵，跑不动全量） |
| 成本 | 一次性 + 每次 CI 重跑 | 需要常驻基础设施 |

**关键结论**：离线告诉你"没有在昨天的任务上变差"；在线告诉你"在没见过的输入上会怎样"。
真正让 Agent 变强的信号，来自**在线层标出来的数据回流**到离线集、微调集和奖励函数——这个闭环比把离线集做大更有效。 `[共识]`

## 3. 评测流程：六环节 + 一条闭环

### ① 定义成功标准（最关键、最常被跳过）

把"什么叫这个任务做完了"写成**机器可判定**的定义。三种口径按强度递增：

1. 只看最终文本 —— 最弱，容易假通过
2. 最终文本 + 系统端状态 —— **推荐默认**
3. 多轮对话下的最终状态 —— 客服 / 订票类场景必须

### ② 构建数据集（黄金集 / 场景注册表）

- 版本化管理的 YAML / JSON 用例集即可起步，**不需要商业平台**
- 按任务类型、难度、语言、工具条件**分层**
- 设置**抗污染机制**：避免答案泄漏进 prompt 或检索库
- 建立**数据集刷新协议**：定期从线上补新样本、退役过时样本

### ③ 接入环境与工具

这是所有系统化评测的**前提条件**：

- 工具调用必须**离散、可记录**
- 环境状态必须**可重置、可校验**
- 企业场景要构造**真实工作负载**（多步 API 编排、合规文档抽取、自愈数据管道），而不是只跑公开基准

### ④ 采集轨迹（trace capture）

记录完整序列：

```
模型调用 → 工具调用(名称+参数) → 状态转移 → 中间产物 → 重试
→ 记忆读写 → 子 Agent 交接 → 每步 token/费用/耗时
```

建议对齐 **OpenTelemetry span 语义**（`agent.trajectory.step`、`gen_ai.agent.name`、`gen_ai.agent.graph.node_id`、工具名、模型名），便于跨框架对比。 `[共识]`

### ⑤ 三层打分

按 **确定性断言 → LLM-as-Judge → 人工** 的成本递增顺序组合（详见第 5 节）。

### ⑥ 聚合、切片与门禁

- **不要只报一个总分**：按任务类型 / 难度 / 语言 / 模型版本 / 工具条件切片，防止"总体 95% 掩盖某语言只有 70%"
- **发布门禁**四项阈值：成功率、关键安全项、延迟、成本
- **一次只改一个变量**：模型、prompt、检索器、工具实现不要同时换；必要时用因子实验

### 闭环

```
线上每轮标注 → 回流刷新数据集 → 更新 CI 回归门禁 → 再发版
```

**这条回路才是评测体系真正的产出，而不是那个分数。**

## 4. 评测维度清单

### 4.1 L1 · 结果层（Outcome）

| 维度 | 怎么测 | 设计要点与陷阱 |
|---|---|---|
| 任务完成率 | 校验**系统端状态**，不仅是最终文本 | 最常犯的错是只看最后的文本。先写"状态断言"，再考虑文本断言 |
| 事实性 / 有据性 | 无参考 RAG 指标：faithfulness、context precision/recall、answer relevancy | 要同时评"检索到的东西对不对"和"回答有没有超出检索内容"。只测 faithfulness 会漏掉"检索失败但回答看似合理" |
| 格式与契约 | JSON Schema 校验、必填字段、枚举值、类型约束 | 成本最低收益最高。建议在**工具边界做类型约束校验**，把这类失败结构性消除，而非事后解析兜底 |

### 4.2 L2 · 轨迹层（Trajectory）

| 维度 | 怎么测 | 设计要点与陷阱 |
|---|---|---|
| 工具调用准确率 | 逐次比对工具选择正确性 + 参数正确性 | 必须区分"选错工具"与"选对工具但参数错"，两者修复手段完全不同 |
| 步数 / 循环检测 | 实际步数 vs 最短必要步数；标记重复的相同动作 | **循环是隐藏最深的失败模式**——20 步和 3 步的 Agent 都只返回一条答案。必须做 **per-step 成本归因**才能暴露 |
| 轨迹匹配度 | 与参考轨迹比对，严格模式 / 子集模式 | 参考路径不唯一，务必提供子集模式，否则大量误杀 |
| 错误恢复能力 | 注入工具故障 / 无效输入，观察是否识别失败并重试 | **"静默失败"比"报错失败"危险得多**。建议单独设指标并进门禁 |
| 对抗鲁棒性 | 畸形输入、边界用例、提示注入 | 要作为一等评测目标，而非上线后的应急项 |

### 4.3 L3 · 轮次层（Per-turn，在线）

| 维度 | 怎么测 | 设计要点与陷阱 |
|---|---|---|
| 单轮语义标签 | 毫秒级分类器逐轮打标：越狱尝试、系统提示词泄露、政策违背、用户挫败 | 这些事件**不改变状态码、延迟和 token 数**，在日志和 trace 里完全不可见。必须专门做逐轮分类并落库 |
| 多轮漂移 | 观察长对话中意图衰减、上下文丢失、约束被遗忘 | 离线单轮数据集天然测不到，要在真实多轮会话上采样 |

### 4.4 横切维度

| 维度 | 怎么测 | 设计要点与陷阱 |
|---|---|---|
| 可靠性 / 一致性 | `pass@k`（k 次至少成功一次）与 `pass^k`（k 次全部成功）**分开看** | 生产关心 `pass^k`。工具型 Agent 的主要风险就是结果不稳，这是 τ-bench 的核心设计动机 |
| 成本 | 直接成本 / 千任务、人工复核成本、错误返工成本，**三项分开算** | Agent 循环会吃掉大量模型调用。成本常被排除在评测外，但它和正确率一样是硬指标 |
| 延迟 | P50 / P95 / P99 + 冷启动开销 | **平均值没有意义**，SLA 由最差分位定义 |
| 上下文利用 | 在 1.5× 典型上下文负载下测试；构造跨文档交叉引用任务 | 多数 Agent 在上下文利用率 >80% 后明显退化，要测出自有场景的拐点 |
| 多智能体协同 | 子任务交接、跨 Agent 状态共享、冲突消解、死锁/环依赖熔断 | 多 Agent 架构下此项非可选 |
| 安全合规 | 把 OWASP LLM Top 10（提示注入、护栏绕过、过度授权）做成 **CI 一等目标** | **目前评测生态最大的空白**——多数框架默认不集成，需自己补 |

## 5. 打分器设计

### 5.1 三种打分器对比

| 打分器 | 优势 | 局限 | 最佳用途 |
|---|---|---|---|
| 确定性断言 | 快、可复现、易自动化 | 判不了主观质量 | 工具调用、schema、政策规则、成本上限 |
| LLM-as-Judge | 可扩展到主观输出 | 有模型偏见、会漂移 | 有用性、相关性、引用准确性 |
| 人工标注 | 上下文与安全判断最可靠 | 慢、贵、一致性差 | 判分器校准、事故复盘、高风险流程 |

### 5.2 LLM-as-Judge 的硬性设计要求

- [ ] **评分维度编码化**：写成结构化评分 prompt（如 relevance / faithfulness / completeness / safety 四维打 0–1 并附理由），而不是"你觉得好不好"
- [ ] **Judge prompt 本身版本控制 + 回归测试**——它实际上是"什么叫好输出"的机器可读规格。**无 rubric 的 Judge 结果不可复现** `[已验证]`
- [ ] **要求引用证据**：让 Judge 先指出被评回答中的具体依据再打分，显著降低幻觉式好评
- [ ] **防止冗长偏见**：rubric 里给出示例，明确"长 ≠ 好"
- [ ] **与人工盲评定期校准**：报告一致率 / 精确率 / 召回率
- [ ] **结构化输出**：用 Pydantic / JSON Schema 强制输出结构，避免解析失败

评分维度参考模板：

```python
from pydantic import BaseModel

class EvalResult(BaseModel):
    relevance: float      # 0-1 回答与问题的相关度
    faithfulness: float   # 0-1 回答是否基于给定上下文
    completeness: float   # 0-1 是否覆盖问题所有方面
    safety: float         # 0-1 是否包含有害内容
    evidence: str         # 必填：评分所依据的原文片段
    reasoning: str        # 评分理由
```

### 5.3 组合策略（成本递增漏斗）

```
确定性断言（便宜，覆盖大部分硬失败）
      ↓ 过滤
LLM-as-Judge（中等成本，评质量）
      ↓ 低置信 + 高风险样本
人工标注（最贵，用量最少）
```

在线侧用**毫秒级分类器**替代 Judge，因为 Judge 跑不动全量流量。
最佳实践：**主动学习**（只标 Judge 不确定的样本）+ **分层标注**（先 LLM 粗筛，再人工精标）。

## 6. 2026 主流基准速览

用于选型与外部对标，**不能替代自有领域评测集**。

| 基准 | 测什么 | 2026 前沿水平 | 可信度提示 |
|---|---|---|---|
| SWE-bench Verified | 真实 GitHub Issue 修复 | ~80%–88% | 接近饱和，有污染争议；部分失败源于测试用例本身有问题；OpenAI 已因确认污染停止报送 |
| SWE-bench Pro | 仓库级工程任务（更难） | ~23%–59%（视 scaffold） | 抗污染设计更可信；Verified 上 ~80% 的模型在 Pro 上掉到 ~23% |
| GAIA | 通用多步推理 + 工具 + 浏览 | L1 ~82% / L2 ~73% / L3 ~65% | 存在 **scaffolding shock**：外部骨架可带来约 30 分差距，报分必须带骨架说明 |
| τ-bench | 多轮工具交互 + 政策约束 | ~55%–72%（retail ~60-72% / airline ~55-68%） | 最接近生产客服场景；强调多次运行一致性与 DB 状态校验 |
| WebArena | 浏览器端到端任务 | ~72%（人类 78.24%） | 漏洞已修补，剩余差距是真实能力差 |
| OSWorld | 桌面级 Computer Use | ~72%（人类 ~72%） | 已修补 BenchJack 类漏洞，Agent 首次追平人类基线 |
| BFCL v3 | 纯函数调用准确率 | 88%–94% | 前沿模型在孤立工具调用上已很强——说明瓶颈不在调用本身，在多轮压力下的选择 |
| AgentBench | 8 个环境的综合能力 | ~85% | 已饱和，参考价值下降 |
| MLE-Bench | Kaggle 式 ML 工程任务 | ~25%–38% | 端到端自主 ML 研究的开放前沿 |
| Aider Polyglot | 多语言改代码-跑测试循环 | ~70%–82% | 真实的 edit-and-test 循环，不是玩具补全 |

### 读榜单的正确姿势

分数分布本身说明问题：

- **孤立工具调用**：前沿模型优秀（BFCL >90%）
- **有界轨迹任务**：够用（τ-bench、SWE-bench）
- **开放式 OS / Web 操作**：**仍然基本不能用**（OSWorld、GAIA L3）

> 基于 MMLU 类分数选模型来做 Agent，是 2026 年明确不成立的赌注。 `[已验证]`

另外：**所有固定基准都会饱和**，这是结构性属性（SWE-bench Verified 已接近 70%+，正是因此催生了 SWE-bench-Live）。所以外部基准只能用于选型，不能替代自有评测集。

## 7. 常见陷阱清单

1. **优化演示而非代表性负载** —— 简单 prompt 出漂亮分数，但决定运营风险的是困难用例：缺权限、重复请求、被污染文档、工具中断
2. **答案泄漏进 prompt / 检索库** —— 测出来的是记忆能力，不是解决能力
3. **一次改多个变量** —— 模型、prompt、检索器、工具实现同时换，然后把提升归因到单一因素
4. **只测最终文本** —— 会放过过程中的循环、违规调用和危险中间行为。只评最终文本的框架应当被质疑
5. **把 95/100 当成"下限就是 95%"** —— 必须按任务类型、用户群、语言、模型版本、工具条件切片报告
6. **忽略成本与隐私** —— Agent 一次任务可能跑几十次模型调用；trace 里可能含客户数据、凭证，送去做 Judge 或可观测前必须先脱敏
7. **把每条线上分歧都变成测试用例** —— 不先复核就入库，会让评测集变噪，甚至把用户的不安全行为当成标准答案
8. **忽略随机性** —— 单次运行的高分不代表稳定，工具型 Agent 必须看多次运行一致性（`pass^k`）
9. **把回归全压在离线集上** —— 上个月写的用例集不包含这个月出现的新失败模式
10. **混淆 workflow 与 agent** —— 步骤固定的是 workflow，不该用 agent 的方式评测（逐轮分类、轨迹诊断都过度了）

## 8. 最小可行评测框架（MVP）

从零开始搭，按性价比排序：

- [ ] **① 版本化的场景注册表** —— 先用 YAML/JSON 管用例，不急着上平台
- [ ] **② 工具调用日志 + 轨迹落库** —— 没有这一层后面全是空谈；对齐 OTel span 语义
- [ ] **③ 两层指标栈** —— 代码断言（硬失败）+ 带结构化 rubric 的 LLM-as-Judge（质量），Judge prompt 纳入版本控制
- [ ] **④ CI 回归门禁** —— 成功率 / 关键安全项 / 延迟 / 成本四项设阈值，低于阈值阻断发布
- [ ] **⑤ 数据集刷新协议** —— 线上标注定期回流，退役过时样本，防止评测集腐化
- [ ] **⑥（进阶）在线逐轮分类器** —— 毫秒级、可跑全量，捞出 trace 里看不见的越狱 / 泄露 / 政策违背
- [ ] **⑦（进阶）安全专项** —— OWASP LLM Top 10 做成 CI 一等评测目标，这是目前最大的生态空白

**发布门禁参考阈值**（需按业务风险面自行标定）：

| 指标 | 参考阈值 | 说明 |
|---|---|---|
| 常规任务成功率 | ≥ 90% | 低于此值先查任务设计和失败模式，不要急着上线 |
| `pass^k`（k=3/5） | 与单次成功率差距 ≤ 5pt | 差距大说明不稳定 |
| 关键安全项 | **0 容忍** | 越狱成功、提示词泄露、越权操作 |
| P95 延迟 | 由 SLA 反推 | 平均值不作为门禁 |
| 单任务成本 | 不超过预算上限 | 含人工复核与返工 |

## 9. 开放问题 / 待补充

- **在线评测的落地成本**：毫秒级分类器如何训练、标注成本如何控制、如何避免分类器自身漂移
- **多 Agent 归因**：多 Agent 协作失败时，如何归因到具体 Agent 或具体交接环节
- **长时任务评测**：跨越数小时到数天的任务，如何设计可判定成功标准与断点重放
- **评测集腐化**：如何量化"数据集还能反映当前分布"的程度
- **成本-准确率联合优化**：目前普遍分开报告，缺少统一的联合指标
