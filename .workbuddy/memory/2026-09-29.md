## Agent 评测方法论梳理（行业实践 + 本项目对照）

用户要求总结当前市场上 Agent 评测的思路（流程 / 维度 / 设计方法）。做了行业调研（LangSmith、DeepEval、Braintrust、Arize Phoenix、FutureAGI、Strands Evals 等 2026 年实践），并对照本项目既有资料：

- `docs/agent_evaluation.md`：已定义 L0–L6 七层评测、硬门禁、RAG 分层评测、数据集分层（smoke/regression/challenge/safety/holdout）、Mock/Replay/Live 三种执行模式、CI 三档（PR/nightly/发布前）。
- `evals/graders.py`：目前仅 4 个确定性 grader（requirement_completeness、itinerary_executability、budget_constraint_score、source_coverage_score），`grade_travel_state()` 的 `overall` 为简单算术平均。
- `evals/datasets/`：travel_tasks 120 条、rag_qa 60 条、mcp_tool_tasks 60 条，共 240 条。

### 归纳出的核心结论（后续可复用）

1. 评测单位从 (input, output) 变为 trajectory（含工具名/参数/返回、中间推理、节点、状态变化）。
2. 流程是五阶段闭环：离线评测 → CI 门禁 → 线上 Trace 评测 → 误差聚类(Error Feed) → 优化回流，同一条 rubric 贯穿全部阶段。
3. 评分器三层分工：确定性检查（先跑、免费、可复现、失败即阻断）→ LLM-as-Judge（3–5 维、1–5 分、写死 criteria、pin 模型版本、按 (trace, rubric, judge_model) 哈希缓存分数）→ 人工校准（结构化标注 schema 回灌）。
4. Judge 必须校准四类偏差（位置/冗长/自我增强/格式），与人工算 Cohen's kappa，< 0.6 不可用于自动打分。
5. 门禁是 AND 逻辑：hard_gate AND quality >= threshold AND cost <= budget，安全类指标必须为零，不做加权平均。
6. 轨迹六维度：工具选择、参数抽取、结果利用、错误恢复、计划一致性、任务完成。不要求唯一调用顺序。
7. 一致性指标不能漏：pass@1 与 pass^k 同时报告（τ-bench 参考：单次 <50%，pass^8 <25%），另加 steps-to-first-error、cost per completed task。
8. 数据集构建铁律：线上每次回归 → 一条永久用例；期望优先表达为约束而非唯一自然语言答案；holdout 不参与调参。
9. 公开 benchmark 只作基线验证与模型选型，不作验收标准；注意 Goodhart's law 与 reward hacking（SWE-bench top-30 中约 19.78% 的 "solved" 语义上不正确）。

## 项目评测链路设计分析（已完成，产出 docs/agent-eval-design.md）

通读了 app/ 的实际实现后完成了评测链路设计分析。**关键代码事实（后续复用，不要重复挖掘）**：

### 架构
- 入口 `POST /chat/stream/{conversation_id}`（`app/api/v1/chat.py:211`），SSE + `astream_events(version="v2")`。
- `create_travel_planner_graph(model_factory, checkpointer)`（`app/agents/graphs/travel_planner_graph.py:115`）—— **model_factory 已经是可注入参数**；但 `create_travel_agent()`（`travel_agent.py:29`）硬编码 `get_llm`，未向外暴露。加个透传参数即可获得模型层 mock 点。
- 8 个步骤节点，每个 `add_edge(step_name, END)`，START 按 `current_step` 条件路由 → **一轮对话只推进一步**（本项目独有强不变量）。
- `current_step` 只由 `app/tools/state_transition.py` 的工具通过 `Command(update=...)` 写入；LLM 不能直接改状态。
- 每步有硬前置 `requires`，由 `_missing_requirements()`（graph:66）在节点入口门禁。
- 构建：qwen-max（dashscope compatible-mode，temp 0.7，max_tokens 8000，streaming）。checkpointer 优先 Postgres，3s 超时降级 MemorySaver。

### 发现的问题
1. **无轨迹落库**：`app/observability/tracing.py` 只有 `trace_operation()` 写日志字符串。但 `chat.py:97` 已在消费 `on_tool_start`/`on_tool_end`/`on_chain_start`/`on_chain_end`，**加旁路 tee 写 JSONL 即可**。
2. **capability 词表两套**：`mcp_tool_tasks.jsonl` 用 registry 真实 capability（正确）；`travel_tasks.jsonl` 的 `expected_tools` 用 `destination/transport/itinerary/budget`——registry 里不存在（registry 只有 weather.realtime / date.current / search.web / map.poi / hotel.search / transport.train / transport.flight）→ 这 120 条的召回率**目前算不出来**。
3. **240 条数据集全部缺** `split` / `version` / `initial_state` / `metadata`。因"一轮一步"，没有 `initial_state` 就无法把用例定位到某一步。
4. **无 runner**：`evals/` 只有 `graders.py` + `datasets/`；`tests/test_evals/test_graders.py` 只测 grader 本身，agent 从未被跑过。
5. **`source_coverage` 是自证指标**：`build_itinerary_plan()` 恒给每个 item 挂 `SourceReference(source_type="planner")`，而 grader 判据是 `bool(item.get("sources"))` → **恒等 1.0**。应改为只统计外部来源。
6. **审批无代码强制**：`generate_order_tool` 不检查 `approval_decision`；`MCPToolGateway.list_tools` 的 `max_risk_level` 全仓库唯一调用点硬编码 `"read"`，风险过滤是死代码。
7. **`order_id` 写入未声明字段**：`generate_order_tool` 写 `order_id`，但该字段在 `TravelState` 被注释掉（`app/core/state.py:166`）→ 极可能被静默丢弃，待实测。
8. **重名工具**：`generate_itinerary_tool` / `summarize_budget_tool` 在 `planning_tools.py`（生产用，step_config:24 导入）和 `state_transition.py:309/376`（测试用，test_handoffs_flow_1.py:38 导入）各有一份 → **测试测 A，线上跑 B**。
9. `app/agents/routers/food_router.py` 全仓库无引用（遗留）；`destination_router` **在用**（经 `router_query.py:29` 的 `query_destination_info`）。
10. 嵌套 agent 两处：`query_transport_options` → transport_coordinator → flight/train/driving subagent；`query_destination_info` → destination_router。

### 设计结论
- 行程与预算是**确定性代码**生成（`build_itinerary_plan` / `estimate_budget`），**不要对内容做 LLM Judge**（那是在给代码打分）；真正该测的是"LLM 有没有在正确时机调这个工具、参数对不对、调用前有无完成确认"。
- 最高性价比断言：**参数保真** —— `query_transport_options(origin_city, destination_city, departure_date)` vs state 三字段。
- 沙箱注意：checkpointer 与 store 都持久化（`("user_profiles", user_id)`），**用例间会互相污染**，必须独立 `user_id` / `thread_id` 并在用例后清理。
- 落地 Phase 1：透传 model_factory → 旁路 trace → 修 source_coverage → 统一重名工具 → `evals/runner.py` → 先跑 L0/L2 确定性断言 → 四项硬门禁。

## Phase 2 前半落地（P0-2 词表 + 数据集 schema）

### 词表：单一来源 `app/mcp_core/registry.py`

原先只有一张 `工具名关键词 → capability` 解析表，现在补齐为三套并集（`KNOWN_TOOL_VOCABULARY`）：

| 常量 | 含义 |
|---|---|
| `MCP_CAPABILITIES` | 外部能力，**从解析表派生**（不手写第二份） |
| `INTERNAL_TOOL_CAPABILITIES` | 状态机工具，`internal.<domain>.<action>` |
| `FORBIDDEN_CAPABILITIES` | deny-list，已知危险但**未实现**的动作，独立成词表 |

**关键判断**：deny-list 必须独立成词表 —— 这样"数据集禁止 `payment.execute`"可被校验，
而"模型编了个 `pay.now`"会被识别为词表外未知值。若把两者混作"所有出现过的字符串"，
安全断言就退化成同义反复。

新增 `resolve_tool_id(name)`：把真实工具名（内部 / MCP）解析成语汇 ID，是轨迹断言
把"实际调用"与"期望调用"放到同一词汇的能力前提。

补的两处词表缺口：`map.route`（amap `maps_direction_*`）、`get-current-date`

### 关键代码事实

### Memory 架构总结与优化思路（面向用户汇报，未改代码）

把上一轮诊断重构为"分层 + 两条路径 + 六条思路"的框架，供后续改造引用：

- **分层**：工作层（`TravelState.messages`，单次 `ainvoke`）/ 会话层（`AsyncPostgresSaver`，键 `thread_id`，每节点自动快照）/ 长期层（`AsyncPostgresStore` + `UserProfile`/`TravelHistory` 两份 JSON，键 `user_id`，靠工具写入）。要点：工作层与会话层**共用同一 schema `TravelState`**，差别只在是否落库——这是最易混淆处；分层方向本身是对的。
- **根因判断**：问题不在"层数不够"，而在长期层的**数据形态是文档而非条目**。由此派生四条：只能增不能减、无时间/来源/置信度（`[-5:]` 的"最近"因 set 无序而失真）、整体覆盖写（并发丢更新）、挂不了 embedding（召回只能全量拼文本）。
- **两条路径**：读路径应有 5 环（召回→过滤→重排→预算截断→注入），实装只有第 5 环；写路径应有门禁（抽取→敏感检测→冲突消解→版本化），实装只有"LLM 自决调工具→并集合并→整体覆盖"。
- **六条优化思路（按改造顺序）**：① 长期层条目化（根）② 读路径补召回/重排/预算 ③ 注入改独立槽位 + 数据声明（顺带堵住跨会话提示注入）④ 写路径改图中显式 `extract_candidate_memories → write_memories` 节点 ⑤ 区分"本次约束"与"长期偏好"（本次需求留 state，不默认写长期）⑥ 可用性/一致性（区分空与错误、单例先 initialize 后赋值、启动不阻断、加 `schema_version`）。
- 交付形态：3 张内联示意图（三层职责、读路径缺口、写路径缺口）+ 6 条思路文字。多租户/RBAC/审计仍建议放最后。
