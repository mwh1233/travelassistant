# TravelAssistant 评测结构与评测体系设计

> **文档性质**：项目评测设计分析，描述当前实现并给出对齐通用方法的目标架构。
> **设计基准**：[D09 · 质量 · Agent 评测通用知识](../universal/D09-质量-评测.md)
> **项目现状依据**：`evals/`、`app/observability/trace.py`、`app/api/v1/chat.py` 与相关测试。
> **分析日期**：2026-09-29

---

## 1. 结论摘要

项目已经从孤立的评分函数发展为一条可运行的离线回归链路：版本化 JSONL 用例、确定性执行 harness、结构化轨迹采集、L0 与轨迹断言、数据集结构门禁，以及 JSON/Markdown 报告均已存在。确定性模式保留真实 LangGraph 拓扑与状态转移工具，只替换模型、记忆后端和非确定性依赖；因此它适合快速验证工作流与状态契约。

但现有链路仍是**以回归门禁为主的评测执行框架**，还不是 D09 所述的完整评测体系。主要边界如下：

- D09 的“结果层 / 轨迹层 / 轮次层”是评测粒度，“回归门禁 / 能力刻画 / 选型对标”是评测目的；项目当前的 L0 / L2 是代码执行套件命名，不能与 D09 粒度一一对应。
- 当前 Agent 端到端场景执行集中在 `trajectory_scenarios.jsonl`。另 240 条旅行、RAG、MCP 内容用例会参与结构校验，但 `runner` 尚未按这些数据集执行 Agent 并汇总行为指标。
- `evals/graders.py` 已有结果级评分和硬门禁实现，但 `evals/runner.py` 当前没有调用 `grade_travel_state`，这些评分未进入端到端 case verdict 或报告。
- 轨迹提供工具参数、结果摘要、状态写入、终态和总 token/调用/耗时信息；尚无工具返回值重放、完整逐步成本、成本金额、延迟分位数及父子 Agent 归因报告。
- 生产侧可选采集 trace，但在线逐轮分类、人工复核、失败样本回流与数据集刷新闭环尚未形成。

因此建议保留当前确定性回归作为 PR 主门禁，并沿 D09 的坐标系扩展结果评分、数据执行覆盖、轨迹诊断、在线反馈及发布指标，而不是把当前单一分数或单一套件包装成全量质量结论。

## 2. D09 评测结构：两个正交轴

评测结构回答两个不同问题：**评测观察到什么粒度**，以及**这次评测要支持什么决策**。任何报告和用例都应能放到以下矩阵中的一个或多个位置。

### 2.1 粒度轴

| 粒度 | 被观察对象 | TravelAssistant 中的典型判据 |
|---|---|---|
| 结果层（Outcome） | 最终答复与任务终态，尤其是结构化业务状态 | 行程/预算 schema、必需需求字段、用户预算约束、引用来源、审批及订单状态 |
| 轨迹层（Trajectory） | 从模型决策到工具、状态转移、错误恢复的执行路径 | 工具选择与参数、重复调用、一轮一步、回退清理、审批前置、工具错误恢复 |
| 轮次层（Per-turn） | 每轮话语的语义、策略遵循及上下文状态 | 意图与约束保持、提示注入/泄露、用户挫败、该澄清时是否提问、多轮修改是否正确 |

旅行规划图目前规定一次调用推进一个规划步骤。这使“本轮最多推进一步”和每个步骤的前置状态成为项目特有的强断言，也意味着评测输入必须准备对应的 `initial_state`。该工作流不等于完整的多轮语义评测：状态机正确并不能证明系统没有遗忘约束或被提示注入。

### 2.2 目的轴

| 目的 | 要回答的问题 | 适用于本项目的做法 |
|---|---|---|
| 回归门禁 | 代码、提示或配置变更是否破坏已知能力？ | 固定 smoke/regression/safety 集、确定性断言、关键失败零容忍 |
| 能力刻画 | 系统能力边界与随机稳定性如何？ | 按任务难度逐级扩展，重复运行观察 `pass@k` 与 `pass^k`，分析长任务与多轮能力 |
| 选型对标 | 哪种模型、提示、检索器或 Agent 编排更合适？ | 冻结外部工具输入后控制变量比较，报告质量、稳定性、成本和延迟 |

### 2.3 九宫格评测矩阵

下表是目标覆盖，不表示项目现有能力已经全部实现。

| 粒度 \ 目的 | 回归门禁 | 能力刻画 | 选型对标 |
|---|---|---|---|
| 结果层 | 系统状态、schema、预算/安全硬断言 | 重复运行成功率与稳定性曲线 | 与固定基准答案或业务目标比较 |
| 轨迹层 | 工具/参数契约、一步一轮、循环与越权门禁 | 可完成任务长度、故障恢复和复杂工具编排边界 | 冻结工具结果比较模型/提示/图版本的轨迹质量 |
| 轮次层 | 提示注入、策略违例、关键多轮状态回归 | 意图保持、约束保持与用户模拟任务成功率 | 比较模型在同一轮次剧本中的策略与对话质量 |

报告至少应注明覆盖了哪些矩阵单元。一个 `pass@1` 总数不代表结果、轨迹、轮次都已经评过；数据集通过 schema 校验也不代表样例被 Agent 执行。

## 3. 当前项目评测结构

### 3.1 代码与数据的职责分层

| 模块 | 当前职责 | 评测体系中的位置 |
|---|---|---|
| `evals/datasets/` | 四类 JSONL 共 250 条：旅行 120、RAG 60、MCP 工具 60、轨迹场景 10；含 split、version、initial_state、metadata 等字段 | 用例/场景注册表。内容数据与可执行轨迹场景当前覆盖不同 |
| `evals/checks.py` | L0 纯函数、schema、词表、状态写入契约等检查 | 低成本确定性断言与输入数据门禁 |
| `evals/harness.py` | 场景输入构造、工具替身、脚本化模型、内存 checkpointer/记忆服务、图运行及 trace 汇总 | 离线执行与隔离边界 |
| `evals/mock_llm.py` | 按场景脚本产出固定模型响应 | 确定性模型替身 |
| `evals/trajectory_checks.py` | 场景期望与通用轨迹不变量检查 | 主要为轨迹层回归判定 |
| `evals/graders.py` | 行程/预算/来源维度分数及硬门禁 | 结果层评分器；当前未由主 runner 接入 |
| `evals/runner.py` | suite 调度、重复执行、报告、退出码 | CLI 编排与回归门禁入口 |
| `app/observability/trace.py` | 消费 LangGraph 事件并生成结构化轨迹，可旁路写 JSONL | trace capture；离线评测必需，也可供生产观测使用 |
| `app/api/v1/chat.py` | `EVAL_TRACE_ENABLED` 开启时从 SSE 事件旁路采集线上轨迹 | 线上数据采集入口，当前不是在线评估器 |
| `tests/test_evals/` | 检查评分器、断言及其负向对照 | 评测基础设施自身的单元测试，不等价于评测数据集通过 |

### 3.2 当前执行链路

```text
JSONL 场景
  -> runner 选择 suite / mode / repeat
  -> harness 根据 initial_state 构造图输入
  -> 构建真实旅行规划图
       deterministic: 脚本化模型 + 非确定性工具 stub + 新 MemorySaver
       live:          真实模型与真实依赖
  -> astream_events
  -> TraceCollector 收集节点、工具参数/摘要、状态写入、错误与总成本
  -> trajectory_checks 对轨迹和终态运行断言
  -> runner 汇总 pass@1 / pass^k、失败和已知缺口
  -> JSON + Markdown 报告、可选 JSONL trace、退出码
```

现有命令入口及结果边界：

| Suite | 当前实际行为 | 不应据此推断 |
|---|---|---|
| `l0` | 运行确定性函数/契约/data 门禁 | 不代表 Agent 端到端结果质量 |
| `trajectory` | 执行 `trajectory_scenarios.jsonl` 并做轨迹断言 | 不代表其余 240 条旅行/RAG/MCP 内容用例已跑过 |
| `dataset` | 校验数据集结构与词表 | 不代表数据集语义正确或 Agent 行为通过 |
| `all` | 组合 L0、轨迹及 dataset 检查 | 不代表 D09 九宫格全覆盖 |

确定性 harness 的价值在于同一输入可以重复检查真实图拓扑、步骤路由、状态转移和断言逻辑，同时避免依赖外部 API 的随机性。它的 stub 返回值是固定的，因此也不能证明真实 MCP/RAG 服务的质量；当前执行模式中没有 D09 所说的录制工具响应 Replay 模式。

### 3.3 当前已具备的评测资产

- 数据用例已统一版本化 schema，并按 smoke、regression、challenge、safety、holdout 等 split 组织；数据集词表以 MCP registry 为单一来源，并覆盖内部工具 ID。
- 轨迹场景可声明初始状态、模型脚本、预期工具、参数保真、终态字段、调用上限、known gap 与 negative control。
- 轨迹不变量包含执行无异常、重复工具调用、一轮一步、工具候选集、审批前置及轨迹参数一致性等检查。
- Trace 记录带 schema version、case/run ID、数据版本/模型/提示版本字段、步骤、工具调用、状态写入、终态快照和 token/调用/总耗时统计。
- 回归失败会使 CLI 返回非零；已知缺口和负向对照单独报告，不混入普通回归失败统计。

### 3.4 现有安全用例与产品门禁的差别

轨迹断言已经检查高风险动作前置审批，且数据中把“未经审批生成订单”作为已知缺口场景。但将问题标注为 known gap 只是准确呈现当前失败，并不等于产品安全已被修复或发布风险已被接受。目标状态应是产品执行边界强制审批，同时 safety suite 对未经批准的操作保持零容忍；从 known gap 移除时应同步验证产品防护和回归断言。

## 4. 当前缺口与 D09 的映射

| D09 要求 | 项目状态 | 影响 |
|---|---|---|
| 成功标准以最终系统状态为主 | 有结构化终态与若干状态断言；结果 grader 未接入 runner | 端到端场景通过仍不能汇总行程/预算等结果质量分 |
| 版本化、分层数据集 | 已有四类数据集、统一 schema、split/version/metadata | 内容集多数尚未进入 Agent 执行和报告，覆盖率与行为质量未知 |
| 可重置、隔离、可重入执行环境 | deterministic harness 每场景使用新内存 checkpointer 和记忆服务 | 缺少跨运行持久化/续跑模型和统一 run 存储；live 外部依赖更难复现 |
| Mock / Replay / Live 三种模式 | 已有 deterministic（Mock）与 live | 缺少历史工具入参/返回值录制和 Replay，比较实验的控制变量有限 |
| 完整轨迹及逐步归因 | 已记录主要工具、状态写入与总成本；有调用父链原始 ID | 当前面向报告的字段没有完整多 Agent 父子归因、逐步 token/费用，也不保存完整工具结果 |
| 三层评分器 | 确定性断言充分起步，存在结果 grader | 无已接入的 LLM Judge rubric / 版本校准 / 人工复核流程 |
| 轮次层评测 | 有一步一轮状态机不变量及少量多轮数据 | 没有逐轮语义/安全分类、user simulator 执行器或意图保持指标 |
| 切片聚合与发布门禁 | 报告有 case、split、pass@1/pass^k 和退出码 | 缺少按任务、难度、风险、语言、模型/提示版本切片，以及成功率/安全/延迟/成本阈值体系 |
| 在线逐轮观察 | 可选生产 trace 旁路采集 | 没有毫秒级分类、标注队列、复核及线上失败回流；trace 开关不等于在线评测闭环 |
| 失败分类与数据集刷新 | 场景有 check ID、known gap、negative control | 缺少稳定版本化的互斥主因分类、线上样本人工确认与退役/刷新协议 |

还有一项数据解释风险：`split` 是数据组织字段，但当前 runner 没有对全部数据集按 split 执行并聚合行为表现。报告中显示某个 split 的轨迹结果，只能代表实际执行的轨迹场景子集，不能外推成该 split 全量数据成功率。

## 5. 对齐 D09 的目标评测体系

### 5.1 端到端数据流

```text
成功标准 / 失败分类 taxonomy / 指标与阈值版本
                    |
                    v
      版本化评测集与场景注册表
       | smoke / regression / safety / challenge / holdout
       v
     可复现执行环境与工具适配层
       | Mock -> Replay -> Live
       v
 Agent 执行 -> 结构化全链路 Trace -> 结果终态快照
                    |
                    v
       确定性断言 -> Judge -> 人工复核
                    |
                    v
  九宫格覆盖 + 按维度/版本切片的报告
       | 成功率/安全/稳定性/延迟/成本门禁
       v
      PR / nightly / 发布决策

生产会话 -> 脱敏 trace -> 逐轮轻量分类 -> 低置信/高风险样本复核
       -> 人工确认正确行为 -> 版本化数据集更新 -> 回归门禁
```

### 5.2 六环节设计

1. **定义机器可判定成功标准。** 对旅行规划优先验证结构化终态、需求约束和系统状态；文本评价用于表达质量，而不能替代状态断言。每个用例应声明必需字段、允许的替代路径、禁止行为及判定所需证据。
2. **维护版本化场景注册表。** 继续使用 JSONL，但明确 schema 版本、数据集版本、split、任务类型、难度、风险、初始状态、期望状态、工具约束和来源。holdout 用例隔离答案与调参过程；失败用例合并前必须人工确认。
3. **建设环境适配与隔离。** 每个 case 从固定初始状态开始，检查工具词表和状态前置，记录依赖模式。确定性 Mock 用于 PR；Replay 用于模型/提示/图版本的控制变量比较；Live 用于 nightly 或发布前外部行为抽查，不作为 PR 的唯一门禁。
4. **采集可归因轨迹。** 以 `case_id`、`run_id`、代码 SHA、dataset/prompt/model/tool 版本为主键上下文，保留节点与父子 span、工具参数及结果摘要、状态前后、错误/重试、模型调用、token、逐步耗时与成本。敏感内容在存储或外送前脱敏，并设置保留期限。
5. **使用分层判分漏斗。** 先运行便宜、稳定的硬断言；对自然语言质量、RAG 有据性等再用结构化 rubric 的 LLM Judge；高风险、低置信和 Judge/断言冲突样本进入人工复核。Judge prompt 与模型版本化，并以人工标注持续校准。任何安全硬门禁失败不得被平均分抵消。
6. **聚合、切片、决策并反馈。** 分别报告结果/轨迹/轮次指标，至少按 split、任务类型、难度、风险、模型/提示/代码版本切片；发布决策同时看成功率、安全零容忍项、延迟分位数和成本。线上失败经人工确认后再回流离线集。

### 5.3 评分模型

评测结果建议分开保留三个值，避免平均分掩盖安全失败：

- **硬门禁**：schema、系统状态契约、禁止能力、审批、关键事实无依据等布尔项。任一关键项失败时 case 不通过。
- **维度分数**：需求完整度、行程可执行性、预算约束、来源覆盖、工具准确性、恢复能力、轮次策略等。每个分数必须附指标版本和适用条件。
- **总体判定**：先判断硬门禁，再按预先定义的适用维度组合；明确“不适用”的分母规则。不把没有外部来源要求的纯启发式用例按来源覆盖低分惩罚，也不在缺少结果评分时用轨迹通过率冒充任务成功率。

随机性指标中同时报告 `pass@k`（多次运行至少一次通过）和 `pass^k`（多次运行全部通过）。回归门禁更关注稳定性及其与单次结果的差距；不得只报告一次通过率。

### 5.4 建议的失败分类

为每个失败 case 记录一个主因和可选次因，taxonomy 自身版本化。首批标签控制在可判定范围，例如：

| 维度 | 首批标签建议 |
|---|---|
| 结果 | `state_mismatch`、`required_field_missing`、`schema_invalid`、`constraint_violation`、`unsupported_claim` |
| 轨迹 | `tool_selection_error`、`tool_argument_error`、`unnecessary_tool_call`、`loop_detected`、`silent_tool_failure`、`recovery_failure`、`unauthorized_action` |
| 轮次 | `intent_drift`、`constraint_forgotten`、`prompt_injection_success`、`policy_violation`、`missed_clarification` |
| 运行质量 | `timeout`、`cost_limit_exceeded`、`latency_limit_exceeded`、`nondeterministic_failure` |

### 5.5 报告与门禁

PR 报告聚焦确定性 smoke/regression/safety 场景、硬失败、负向对照和与基线的差异。Nightly/发布报告扩展 Replay/Live、重复运行、Judge 与人工抽检，并展示下列按维度切片的指标：

| 指标族 | 建议报告项 | 门禁原则 |
|---|---|---|
| 结果 | 任务成功率、状态正确率、schema 合规率 | 以目标业务风险标定阈值，不以总平均掩盖关键任务退化 |
| 轨迹 | 工具选择/参数准确率、循环率、错误恢复率、越权率 | safety/越权为零容忍；工具轨迹有差异时保留可诊断证据 |
| 轮次 | 意图保持率、策略违例率、提示注入成功率 | 高风险安全项零容忍；分类器要报告校准表现 |
| 稳定性 | `pass@k`、`pass^k`、重复运行方差 | 多次运行设置与模型版本一并记录 |
| 延迟 | P50/P95/P99、超时率 | 由产品 SLA 反推门槛，不用平均值替代尾延迟 |
| 成本 | 每任务 token、模型/工具费用、Judge/人工成本 | 逐项报告并约束单任务上限，明确未计入成本 |

阈值应作为配置版本化并在实际基线上校准，不直接照搬通用参考值。每份报告需写明代码 SHA、数据集版本、执行模式、模型及参数、提示版本、重复次数、有效样本数和排除的 known gap。

## 6. 分阶段演进建议

### Phase A：闭合现有离线结果链路

- 在 trajectory outcome 上接入 `grade_travel_state` 或等价结果 grader，将硬门禁纳入每个适用 case 的最终 verdict；补足从场景声明到 grader 输入/分数的契约。
- 扩充可执行 runner，使旅行、RAG、MCP 内容用例不止做 schema 校验；如部分任务不能由同一 Agent 图直接运行，为数据集类型定义显式执行器及判分器，并报告执行覆盖数。
- 把数据集版本、split 和 schema 版本一致传入 trace 与报告；报告区分“结构校验样本数”和“行为执行样本数”。
- 让关键 safety 场景成为明确硬门禁；known gap 仅用于迁移期清单，不能计作已满足安全要求。

### Phase B：丰富轨迹与执行可复现性

- 给 trace 补齐有边界的父子 span 归因、逐节点/逐模型调用成本与延迟、重试信息及工具结果录制引用；完整工具返回数据需考虑脱敏和保留策略。
- 增加 Replay 模式与录制版本失效策略，使同一工具响应下可以比较模型、提示和图变更。
- 支持重复运行结果、按 split/type/risk/model/prompt 版本切片及指标基线对比；将稳定性、P95 延迟和单任务成本纳入 nightly/发布报告。

### Phase C：建立轮次与在线反馈闭环

- 增加固定剧本与可控 user simulator 的多轮场景，测意图/约束保持、澄清和中途修改行为。
- 将线上 trace 视为待分析事件，不直接当作评分。先实现脱敏、抽样、逐轮轻量分类及低置信/高风险人工复核队列。
- 通过人工确认正确行为、标注主因、更新版本化数据集并运行回归，形成“线上发现 -> 人工复核 -> 离线回归 -> 发布”的闭环。
- 对 Judge 与在线分类器做独立校准、版本控制和漂移检查；未达校准要求时仅作筛查，不直接作为自动门禁。

### Phase D：能力刻画与选型对标

- 建立 holdout 与 challenge 维护规则，定期按任务长度、前置依赖和故障注入扩展能力边界。
- 通过 Replay 冻结检索/工具响应，一次只变更模型、提示、RAG 或图编排中的一个变量；必要时做受控因子实验。
- 以稳定性、结果质量、安全、成本和尾延迟组成对标表；外部基准只用于补充，不替代项目真实工作负载。

## 7. 近期验收标准

达到下一阶段可称为“项目离线回归体系”的最低条件：

- [ ] 每个会进入回归判定的用例均有明确的结果、轨迹或轮次目标，并声明适用判分器。
- [ ] 报告分别列出数据结构校验量、实际执行量和通过量，不能将校验通过计作 Agent 成功。
- [ ] 结果级评分进入 runner；关键硬门禁失败必然令 case 和对应 suite 失败。
- [ ] `smoke`、`regression`、`safety` 至少能按 split 独立执行并报告；holdout 不参与提示调优的日常反馈。
- [ ] 失败结果能关联代码 SHA、数据集版本、执行模式、模型/提示版本及结构化 trace。
- [ ] 回归报告至少有按任务类型与风险的切片、重复运行稳定性指标；安全门禁不被平均分稀释。
- [ ] 每个 negative control 确认预期断言仍能失败；known gap 有责任归属、影响说明和退出条件。
- [ ] 生产 trace 与评测数据有脱敏、访问控制、保留期限和人工复核策略；线上样本未经人工确认不得直接成为黄金标准。
