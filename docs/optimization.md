# 旅行助手项目优化方案

> 适用背景：本项目为 2026 年 3 月左右构建的智能旅行规划助手，当前已经具备 Agent、RAG、MCP、长期记忆、SSE 流式响应等基础能力。随着 2026 年 Agent Runtime、MCP 标准化、多模态交互、RAG 评测和可观测性的发展，同样的旅行规划需求可以进一步升级为更稳定、可恢复、可评测、可交互的生产级系统。

## 1. 当前项目判断

### 1.1 已有优势

- 已经采用 LangChain/LangGraph 相关能力构建 Agent，具备多步骤旅行规划雏形。
- 已经拆出状态流转、目的地查询、交通查询、记忆工具、RAG 工具和 MCP 工具，具备模块化基础。
- 已经引入 Chroma、Hybrid Retriever、Reranker、Query Optimizer、Cache 等 RAG 优化组件。
- 已经接入 MCP Client，预留了天气、搜索、高德、12306、航班、酒店等外部工具服务。
- 已经有 Postgres Store、Checkpointer、Redis、LangSmith 等生产化组件的依赖和部分代码基础。

### 1.2 主要短板

- 主 Agent 仍偏「单 Agent 挂大量工具」模式，流程控制依赖提示词和工具调用，稳定性不足。
- 主流程使用 `MemorySaver`，没有充分使用已有的 Postgres checkpoint 能力，长会话恢复能力不足。
- 行程生成和预算汇总仍有明显模板化、硬编码逻辑，不能反映真实价格、距离、营业时间和用户约束。
- RAG 虽有检索链路，但缺少引用、数据新鲜度、检索质量评测和答案质量评测。
- MCP 工具接入偏配置式，缺少统一权限、审计、降级、超时、重试、schema 标准化和结果可信度标注。
- 前端交互仍以文本对话为主，旅行场景需要地图、卡片、时间轴、预算面板、语音和图片输入。
- 缺少系统性 Agent 评测，无法稳定判断改模型、改 prompt、改工具后效果是否变好。

## 2. 优化总目标

把当前项目从「能演示的旅行 Agent」升级为「可持续迭代的旅行规划系统」。

目标包括：

- 用户可以多轮表达需求、修改需求、回退步骤，并在中断后恢复。
- 系统可以调用实时工具获取天气、交通、酒店、POI、路线和价格信息。
- 系统输出的行程可解释、可编辑、可落地，而不是只生成一段漂亮文本。
- 关键决策有数据来源、约束依据和预算明细。
- 每次 Agent 调用、工具调用、RAG 检索和用户确认都能被追踪、评测和复盘。

## 3. 优先级路线图

### 阶段一：稳定主流程，减少幻觉和状态混乱

建议周期：1 周。

#### 3.1 把主 Agent 改成显式旅行规划图

优化内容：

- 将当前 `create_agent + middleware + tools` 的主流程改造成显式 `StateGraph`。
- 将旅行流程拆为固定节点：需求收集、目的地推荐、目的地确认、交通规划、住宿规划、餐饮规划、行程生成、预算汇总、最终确认。
- 每个节点只暴露当前步骤需要的工具，减少模型误调用工具的概率。
- 对每个节点定义明确输入、输出、前置依赖和失败分支。

如何改：

- 保留现有 `TravelState`，但补齐 `current_step` 与各步骤状态字段的类型约束。
- 新增一个主图构建模块，例如 `app/agents/graphs/travel_planner_graph.py`。
- 将 `app/agents/handoffs/step_config.py` 中的 prompt 配置迁移为每个节点的系统提示词。
- 将 `app/tools/state_transition.py` 中的状态更新工具逐步改为图节点内的确定性状态更新。
- 将回退工具保留为用户操作入口，但底层通过图状态恢复或重新执行节点实现。

修改原因：

- 旅行规划是强流程任务，不适合完全交给模型自由决定下一步。
- 显式图可以让每一步可测试、可恢复、可插入人工确认。
- 工具作用域收窄后，模型调用错误工具、跳步骤、状态不一致的概率会降低。

#### 3.2 主流程 checkpoint 切换到 Postgres

优化内容：

- 将主 Agent 的 checkpoint 从内存版 `MemorySaver` 切换到项目已有的 `AsyncPostgresSaver`。
- 以 `conversation_id` 作为 thread id，实现断点续跑、历史恢复和步骤回退。

如何改：

- 在 `app/agents/handoffs/travel_agent.py` 中使用 `get_checkpointer()` 替代 `MemorySaver()`。
- 确认应用启动时初始化 `app/core/checkpointer.py` 的生命周期。
- 在 SSE 接口 `app/api/v1/chat.py` 中继续通过 `configurable.thread_id` 传入 `conversation_id`。
- 为 checkpoint 初始化、恢复、失败重试补测试。

修改原因：

- 旅行规划常常不是一次完成，用户会隔一段时间回来继续修改。
- 内存 checkpoint 重启后丢失状态，不适合真实使用。
- Postgres checkpoint 可以为后续时间旅行、人工确认、错误复盘打基础。

#### 3.3 工具输出全面结构化

优化内容：

- 交通、酒店、天气、目的地、预算、行程等工具都返回 Pydantic 结构，而不是自由文本。
- 最终回复可以继续是自然语言，但中间数据必须结构化保存。

如何改：

- 在 `app/schemas` 或 `app/core/state.py` 中补充 `TransportOption`、`HotelOption`、`WeatherForecast`、`PoiOption`、`ItineraryCandidate`、`BudgetItem` 等模型。
- 改造 `query_transport_options`、`query_destination_info`、RAG 工具和 MCP 包装层，让它们返回结构化对象。
- 在最终生成回复前，由 synthesizer 节点把结构化数据渲染成 Markdown、JSON 或前端卡片事件。

修改原因：

- 文本结果难以校验、排序、去重、预算计算和前端展示。
- 结构化结果能支撑地图、时间轴、预算明细和多方案对比。
- 后续评测也需要稳定字段，而不是只评估自然语言。

## 4. 阶段二：提升规划质量

建议周期：2-3 周。

#### 4.1 用约束优化替代硬编码行程生成

优化内容：

- 将行程生成从模板逻辑升级为「约束规划 + LLM 解释」。
- 约束包括：旅行天数、预算上限、地理距离、营业时间、交通耗时、天气、儿童/老人强度、餐点时间、用户偏好、已去过景点。
- 输出多个候选方案，例如省钱版、舒适版、深度游版。

如何改：

- 将 `generate_itinerary_tool` 拆为两个部分：
  - 候选 POI/餐厅/酒店收集。
  - 基于约束进行路线和时间分配。
- 新增 `app/planner` 目录，放置确定性规划逻辑，例如评分、排序、时间窗检查、预算计算。
- LLM 只负责解释为什么这样安排，以及在多个可行方案中做偏好权衡。
- 每个行程项保存 `source`、`estimated_cost`、`duration_minutes`、`location`、`reason`。

修改原因：

- 纯 LLM 生成行程容易出现路线绕路、时间不可能、价格不可信等问题。
- 旅行规划本质是约束满足问题，确定性算法更稳定。
- LLM 适合处理偏好和表达，不适合作为唯一的计算引擎。

#### 4.2 预算系统接入真实数据和区间估算

优化内容：

- 替换 `transport_cost = 500 * total_people` 等固定估算。
- 按交通、住宿、餐饮、门票、市内交通、保险、杂费分别计算区间。
- 给出乐观、正常、保守三档预算，并标注价格来源和更新时间。

如何改：

- 新增 `BudgetEstimator` 服务。
- 交通费用来自航班/火车/自驾工具结果。
- 住宿费用来自酒店工具或城市均价数据。
- 餐饮和门票费用来自 RAG/搜索/POI 数据。
- 对缺失数据使用城市级 fallback，并在结果中标记 `estimated: true`。

修改原因：

- 用户最关心预算是否可信，硬编码估算会明显削弱项目说服力。
- 区间估算比单点价格更符合旅行场景。
- 明确来源和更新时间可以降低用户误解。

#### 4.3 RAG 增加引用、时效和评测

优化内容：

- RAG 返回结果必须带来源、文档片段、更新时间和置信度。
- 对过期信息进行提示，尤其是门票、开放时间、交通政策、酒店价格。
- 建立 RAG 测试集，评估检索命中率、答案忠实度和引用覆盖率。

如何改：

- 扩展 `Document.metadata`，加入 `source_url`、`updated_at`、`city`、`category`、`valid_until`。
- RAG pipeline 返回 `RetrievedContext`，而不是只返回 `Document`。
- 新增 eval 数据集，例如 30-50 个典型旅行问题。
- 用 LangSmith 或本地 pytest 记录不同 embedding、top_k、reranker 的效果。

修改原因：

- 旅行信息高度依赖时效，旧攻略很容易误导用户。
- 有引用的答案更可信，也更适合面试展示。
- 没有评测就无法判断 RAG 优化是否真的有效。

## 5. 阶段三：升级 MCP 和工具生态

建议周期：2-4 周。

#### 5.1 建立 MCP 工具网关

优化内容：

- 在 MCP Client 之上增加统一工具网关，负责注册、权限、schema、重试、降级、审计。
- 将不同 MCP server 的输出归一化为项目内部 schema。

如何改：

- 新增 `app/tools/tool_gateway.py` 或 `app/mcp_core/gateway.py`。
- 为每个 MCP 工具定义能力标签，例如 `weather.realtime`、`transport.train`、`transport.flight`、`hotel.search`、`map.poi`。
- 工具调用统一记录：输入参数、耗时、成功/失败、错误类型、返回摘要。
- 对关键外部工具设置 timeout、retry、fallback 和 circuit breaker。
- 对需要 API Key 的服务在启动时做健康检查。

修改原因：

- MCP 工具数量增加后，直接把所有工具挂给 Agent 会失控。
- 工具网关可以屏蔽不同服务协议和返回格式差异。
- 审计和降级是生产可用的关键，尤其是旅行价格和订单类场景。

#### 5.2 工具调用增加权限和人工确认

优化内容：

- 查询类工具可以自动调用。
- 写入类、下单类、支付类、发送通知类工具必须人工确认。
- 高风险操作需要显示确认摘要。

如何改：

- 给工具加 `risk_level`：`read`、`write`、`purchase`、`payment`。
- 在图节点中遇到高风险工具调用时中断，向前端发送 `approval_required` 事件。
- 用户确认后再恢复执行。

修改原因：

- 旅行助手如果未来接入预订和支付，不能让模型直接执行高风险动作。
- Human-in-the-loop 可以同时提升安全性和用户信任。
- 这也是 Agent 系统从 demo 到真实产品的关键边界。

## 6. 阶段四：产品体验升级

建议周期：3-6 周。

#### 6.1 从纯聊天升级到地图和时间轴交互

优化内容：

- 保留聊天入口，但主要结果以行程时间轴、地图点位、预算面板、交通卡片、酒店卡片展示。
- 用户可以拖拽调整行程顺序、删除景点、锁定酒店、重新计算预算。

如何改：

- SSE 事件从单一 token 扩展为多种事件：
  - `token`
  - `tool_call`
  - `tool_result`
  - `itinerary_delta`
  - `budget_update`
  - `map_marker`
  - `approval_required`
  - `done`
- 后端输出结构化行程 JSON，前端负责渲染。
- 用户对卡片的操作转成状态更新事件，再触发局部重算。

修改原因：

- 旅行规划是强可视化任务，纯文本难以比较和修改。
- 地图与时间轴能立即暴露路线是否合理。
- 局部编辑比反复聊天修改更高效。

#### 6.2 增加图片和语音输入

优化内容：

- 支持用户上传攻略截图、酒店截图、景点图片、聊天记录截图。
- 支持语音表达旅行需求，并可语音追问。

如何改：

- 新增图片解析接口，将图片中的地点、价格、酒店名、日期、偏好抽取成结构化数据。
- 新增语音输入通道，将语音转成文本后进入同一需求收集节点。
- 对图片解析结果加入用户确认步骤，避免 OCR 或视觉理解错误。

修改原因：

- 真实用户常从小红书、携程、美团、朋友聊天截图中收集旅行信息。
- 多模态输入能显著降低用户录入成本。
- 语音适合移动端和出行中修改计划。

## 7. 阶段五：可观测性和评测体系

建议周期：持续建设。

#### 7.1 建立 Agent 任务评测集

优化内容：

- 构建覆盖典型旅行需求的评测集。
- 评测 Agent 是否正确收集信息、调用工具、控制预算、生成可执行行程。

如何改：

- 新增 `tests/evals` 或 `evals` 目录。
- 设计典型任务：
  - 亲子游。
  - 周末短途游。
  - 低预算学生游。
  - 老人轻松游。
  - 美食优先游。
  - 雨天备选方案。
  - 指定交通方式。
  - 用户中途修改预算或目的地。
- 指标包括：字段完整率、工具调用正确率、预算误差、路线合理性、引用覆盖率、用户确认次数。

修改原因：

- Agent 系统的质量很难靠单次人工体验判断。
- 有评测集后，才能安全升级模型、prompt、RAG 和工具。
- 这部分也是项目面试展示中非常加分的工程能力。

#### 7.2 全链路 trace 和成本监控

优化内容：

- 每次对话记录模型调用、工具调用、RAG 检索、耗时、token、错误和用户反馈。
- 建立 dashboard 观察成功率、平均耗时、工具失败率、用户回退率和预算满意度。

如何改：

- 完善 LangSmith 配置和 trace metadata。
- 每个节点和工具调用附带 `conversation_id`、`user_id`、`step`、`tool_name`。
- 对外部 API 调用记录 latency、timeout、fallback、empty result。
- 将用户点击确认、回退、重新生成等行为作为反馈数据保存。

修改原因：

- 没有 trace 就无法定位 Agent 为什么给出错误方案。
- 成本和延迟会随着工具、模型、多模态能力增加而快速上升。
- 用户行为反馈可以反向优化推荐排序和 prompt。

## 8. 推荐落地顺序

### 最高优先级

1. 主流程改显式图。
2. Checkpoint 切 Postgres。
3. 工具输出结构化。
4. 替换硬编码预算和行程。

原因：

- 这些改动直接解决稳定性和可信度问题。
- 不依赖复杂前端，也不需要一次性接入大量新服务。
- 改完后整个系统会更像真实产品，而不是 demo。

### 第二优先级

1. MCP 工具网关。
2. RAG 引用和评测。
3. Agent eval 数据集。
4. LangSmith trace 闭环。

原因：

- 这些能力决定项目是否能持续迭代。
- 对面试或展示而言，能体现工程深度。
- 能降低后续接入更多工具和模型的风险。

### 第三优先级

1. 地图和时间轴 UI。
2. 图片输入。
3. 语音输入。
4. 下单/支付前人工确认。

原因：

- 这些能力提升产品体验明显，但依赖前两阶段的数据结构和流程稳定性。
- 如果先做 UI，容易被后端数据不稳定拖住。

## 9. 面试展示角度

如果这个项目用于面试，建议重点包装成以下几个亮点：

- **Agentic Workflow**：不是简单聊天机器人，而是有状态、有回退、有人工确认的旅行规划流程。
- **Tool-Augmented Planning**：通过 MCP 统一接入天气、地图、交通、酒店等外部能力。
- **Reliable RAG**：支持混合检索、重排、引用、时效检查和评测。
- **Long-Term Memory**：能够记住用户偏好、历史目的地、饮食限制和住宿偏好。
- **Evaluation-Driven Iteration**：用评测集和 trace 驱动模型、工具和 prompt 迭代。
- **Structured Product Output**：最终输出不是一段文本，而是可视化、可编辑、可重新计算的旅行计划。

## 10. 一句话总结

当前项目的方向没有过时，但实现还停留在「Agent 调工具生成文本」阶段。新的优化方向应该是：用显式规划图保证流程稳定，用 Postgres checkpoint 保证可恢复，用 MCP 工具网关保证外部能力可控，用结构化数据和约束优化保证行程可执行，用 RAG/Agent 评测保证每次迭代真的变好。
