## 0. 总纲

> **上下文工程的目标不是"在窗口里装更多信息"，而是"让关键信息在被用到的那一刻，以正确的形态、出现在正确的位置"。上下文长度与任务成功率不是单调关系——超过某个点后，增加内容会同时增加成本并降低召回精度；而这个"点"与模型、任务形态、信息冗余度强相关，必须自测，不可照搬外部数字。** `[共识]`

这个断言可被反驳：如果某类任务的信息密度极高且高度互相关联（例如整篇需要交叉引用的技术规范），那么"装得多"可能确实胜出，拐点不存在或位置极高。反驳者需要给出这类任务的判据（本文 §8 保留分歧）。

展开为五条要点：

| # | 判断 | 说明 |
|---|---|---|
| 1 | **context rot 是架构性质，不是实现缺陷** | Transformer 注意力两两计算，token 增加带来非线性增长的干扰项，特定信息召回精度随之下降 `[共识]`；换更大的窗口只能缓解，不能消除 |
| 2 | **首选的裁剪对象是"检索证据"，不是"对话历史"** | 证据是**可重新取回**的（JIT），历史是不可重新生成的（一旦压缩就丢信息）——可重建的东西才该被裁 |
| 3 | **冻结点越靠前，缓存命中率越高、单位成本越低** | 系统指令与工具定义放在前缀并保持逐字节稳定，是降低成本最直接的杠杆；反之，任何动态内容混进前缀都会整体失效 |
| 4 | **工具返回必须自带契约，否则它会以最占地方的方式进入上下文** | 结果必须含 状态 / 结论 / 范围 / 证据位置 / 下一步（`D00-地基-总纲.md` §9），缺一项就要靠模型反复追问，成本远高于多写几个字段 |
| 5 | **上下文利用率拐点必须自测** | 外部报告的数字对应的是别人的任务分布与模型版本，照搬等于把别人的拐点当自己的约束 `[待验证]` |

**术语纪律（承接 `D00-地基-总纲.md` §9）**：本文处理的是**一次调用窗口内的上下文**（context）。**状态**（一次运行内的结构化事实）、**记忆**（跨会话持久化的高显著度事实）、**检查点**（状态快照，用于恢复与重放）都在窗口之外，由 `D05-运行时-记忆与状态.md` 负责。上下文里"看起来像历史"的内容，可能是从记忆取回的、也可能是从来没持久化过的——两者必须分别设计。

## 1. 问题定义与边界

### 1.1 本文解决的问题

1. 单次模型调用的上下文里应该分成哪几个**槽位**，每个槽位装什么、由谁写入、按什么顺序放？
2. 上下文预算如何在槽位之间分配，冲突时谁让路？
3. context rot 在工程上如何应对——靠**压缩**、靠**按需检索**，还是靠**外置笔记**？
4. 子 Agent 隔离噪音的机制与代价是什么，什么时候值得拆？
5. 前缀如何冻结才能命中 prompt cache，动态内容如何安放？
6. 工具返回应该以什么形态进入上下文，才能既少占地方又不丢失必要信息？

- **不讨论工具契约本身**（入参 schema、错误约定、幂等）——那是 `D06-运行时-工具与协议.md`。本文只回答"工具定义与工具返回**如何进入上下文**"（数量预算、描述长度预算、返回摘要形态）。
- **不讨论 MCP（当前规范版本 `2026-07-28`）的协议行为**——`D06-运行时-工具与协议.md`。

## 2. 设计思路

### 2.1 第一性原理：注意力是有限且非均匀的资源，"装得准"是唯一可控的变量

模型对上下文的处理有三个架构性质：

```text
① 注意力两两计算 → token 越多，干扰项越多，特定信息的召回精度越低（context rot）
② 位置有偏     → 前缀（系统指令）与后缀（当前指令）得到更多注意，中段最容易被忽略
③ 缓存是前缀式 → 只有从头开始逐字节一致的部分才能命中缓存，动态内容混入即整体失效
```

**唯一推论**：既然总容量不可无限扩展、且中段会被稀释，工程上能做的只有三件事——**减少总量**（裁剪与压缩）、**提高命中**（把关键信息放到注意力高的位置）、**避免重复**（把可重建的东西移出窗口，按需取回）。

这三件事分别对应本文的三类手段：压缩（§3.3）、装配顺序（§4.3）、JIT 检索与结构化笔记（§3.2 / §3.4）。

### 2.2 不可回避的约束

| 约束 | 性质 | 对上下文设计的直接影响 |
|---|---|---|
| **上下文有硬上限** | 模型窗口是绝对上界 | 输出预留必须先扣掉，前六项在剩余空间里竞争 |
| **召回精度随长度下降** | 架构性质（context rot） | 不能靠"把全部材料都放进去"提高正确率；必须有裁剪判据 |
| **位置影响权重** | 注意力非均匀 | 关键约束不放中段；当前指令应靠近生成位置（后置） |
| **前缀缓存逐字节匹配** | 缓存实现机制 | 时间戳、随机 ID、动态排序混进前缀会让缓存 100% 失效——这是最常见的成本泄漏 |
| **信息不可无损压缩** | 压缩是有损的 | 摘要会丢信息；因此"可重建的信息"优先裁，"不可重建的信息"优先保 |
| **工具返回体积由下游决定** | 外部系统不受控 | 大返回必须先在下游侧截断/投影，再进上下文；不能靠压缩器兜底 |
| **成本与延迟随 token 线性（甚至超线性）增长** | 计费与注意力复杂度 | 每次调用都是成本事件；上下文策略是成本的第一大杠杆 |

### 2.3 由此推导出的核心取舍

**取舍一：宁可把材料外置、按需取回（JIT），也不预先全量装载。** 因为预载的信息大部分从未被用到，却全程占用预算并稀释注意力；而 JIT 的代价（多一次检索往返、可能取不到）是可度量、可优化的，预载的代价（注意力稀释）是不可逆的。

**取舍二：宁可让工具返回更长但自带契约，也不追求"返回简洁"而缺字段。** 因为缺字段会诱发对话式追问（多轮、多次调用、上下文反复膨胀），代价是返回体积的数倍；而 状态 / 结论 / 范围 / 证据位置 / 下一步 这五个字段是**可重建性的前提**——没有证据位置，就无法在后续轮次里只取片段而不是整篇。

**取舍三：宁可牺牲一点灵活性，也要让前缀逐字节冻结。** 因为缓存命中带来的成本下降是确定的、可测量的，而"前缀里放动态内容"带来的收益（通常只是省一次拼接）远小于损失。任何出现在前缀里的动态值（时间戳、随机数、动态排序、按热度变化的工具顺序）都必须被移到后段。

读者读完这三条取舍，应能自行推出后文的七槽位定义、预算分配规则与装配顺序：可重建的靠后并可裁、不可重建的靠前并保留、动态内容一律排除在前缀之外。

## 3. 通用方案

### 3.1 方案 A · 全量预载（Pre-load）

**机制**：在第一次调用前，把可能与任务相关的全部材料（文档、历史、工具说明）一次性装入上下文。

**适用条件**：材料总量远小于窗口、信息密度高且互相关联、需要多次交叉引用。

**代价**：token 成本与首字延迟随材料量线性上升；注意力被无关材料稀释，关键信息召回精度下降；材料的更新需要重装整个上下文。

**不适用场景**：材料总量接近或超过窗口的可用部分；材料中大部分与被问的问题无关；需要多轮迭代（每轮都带着全部材料）。

### 3.2 方案 B · JIT 检索（Just-in-time）

**机制**：上下文里只保留**指针**（路径、ID、摘要、可检索的索引），真正的内容在被需要的那一刻由工具取回。

**适用条件**：材料体量大于窗口可用部分；材料有稳定的可检索结构（文件、表、API）；模型有能力判断"现在需要什么"。

**代价**：多一次（乃至多次）工具往返，延迟上升；检索失败会成为新的失败模式；需要模型先"知道有什么"才能"取什么"，因此**索引本身必须在上下文里**——这是 JIT 最容易漏掉的一半。

**不适用场景**：材料小到可以直接放下（JIT 的往返成本高于收益）；材料无结构、无法按需定位；任务允许的延迟预算极小。

### 3.3 方案 C · 压缩与摘要（Compaction）

**机制**：当对话历史或证据超过阈值时，把较早的部分替换为结构化摘要（保留结论、已确认约束、未决问题、关键证据位置），丢弃原文。

**适用条件**：历史长度可控增长（单循环形态的必然结果）；摘要质量可验证（有明确"必须保留"的字段清单）。

**代价**：有损——细节一旦丢弃不可恢复；摘要本身也是模型输出，会漂移与引入错误，且**错误会被后续所有轮次继承**；压缩时机难选（太早丢信息，太晚已超预算）。

**不适用场景**：细节本身是任务对象（例如逐条比对）；需要对历史做审计（应外置为结构化笔记而非摘要）。

### 3.4 方案 D · 结构化笔记（External notes）

**机制**：把计划、已确认约束、中间结论、待办外置为一份**模型可读写的结构化对象**（而不是压缩成散文摘要），需要时整体或部分取回。

**适用条件**：长任务需要跨多轮保持"当前进度"；仍需保留逐条可检索的细节（摘要会丢，笔记不会）。

**代价**：需要模型主动维护笔记（增加每次调用的工具调用与上下文开销）；笔记本身可能腐化（写入重复、矛盾条目）；需要定义写入时机与去重规则。

**不适用场景**：短任务（维护成本高于收益）；任务没有"需要跨轮记住的结构化事实"。

### 3.5 方案 E · 子 Agent 隔离（Sub-agent isolation）

**机制**：把探索性、噪音大的子任务交给独立的子 Agent，子 Agent 在自己的上下文里做大量检索与试错，只把**结论 + 证据位置**返回主上下文。

**适用条件**：子任务的中间过程对主任务无价值（只有结论有价值）；子任务需要消耗大量检索预算但又不需要主线索感知。

**代价**：需要显式的返回契约（否则子 Agent 会把噪音原样带回来，隔离失效）；子 Agent 自身有成本，且其失败需要单独归因；上下文隔离意味着主线索失去可审计的中间过程。

**不适用场景**：中间过程本身需要被主线索审查（合规场景）；子任务与主线高度耦合、无法独立定义成功标准。

### 3.6 方案 F · 前缀冻结 + 缓存分层（Frozen prefix）

**机制**：把系统指令与工具定义组成一个逐字节稳定的前缀，并在其外层叠加可缓存层（例如稳定的检索索引、稳定的少量示例），使每次调用尽可能复用已计算的 KV 缓存。

**适用条件**：几乎全部场景（这是成本优化而非功能选择）；尤其适用于调用次数多的循环形态。

**代价**：前缀内容不能随请求变化——这限制了"按用户动态裁剪系统指令"这类做法；工具集变化会打断缓存，因此"按任务裁剪工具集"与"缓存复用"存在张力，需要按调用频率排序来决定哪些进前缀。

**不适用场景**：每次调用的前缀天然不同（例如每次都要注入不同的租户政策文本且这部分无法后置）——此时应重新审视是否真的必须放在系统指令里。

> **注意**：方案 A–E 是**内容策略**（装什么），方案 F 是**装配策略**（怎么放）。两者正交，任何内容策略都应在 F 的约束下落地。

## 4. 如何设计

### 4.1 上下文七槽位与预算分配

把窗口切成七个槽位，是让"装什么"变成可设计、可度量、可争论的前提。

| # | 槽位 | 装什么 | 谁写入 | 动态性 | 裁剪方式 |
|---|---|---|---|---|---|
| 1 | **系统指令** | 角色、政策、输出规范、术语口径 | 开发者 | 冻结 | 只增不删；任何改动都是版本变更并打断缓存 |
| 2 | **工具定义** | 工具名、描述、参数 schema | 开发者 | 冻结（按任务集裁剪） | 优先**裁剪工具集**，而不是压缩单个描述 |
| 3 | **检索证据** | 本轮取回的文档片段、外部数据 | 运行时检索器 | 高 | **最优先裁剪对象**——可重建 |
| 4 | **对话历史** | 用户轮次、模型回复、工具调用记录 | 运行时 | 高 | compaction / 摘要 / 外置为笔记 |
| 5 | **工作草稿** | 计划、中间结论、待办、已确认约束 | 模型 | 高 | 外置为结构化笔记，窗口内只留当前段 |
| 6 | **当前指令** | 本轮用户请求或子任务的明确指令 | 运行时 | 每轮变 | 固定，**后置**（靠近生成位置） |
| 7 | **输出预留** | 本轮生成所需的 token | 预留 | 固定 | **硬预留**，不可被前六项侵占 |

**预算分配原则**（顺序即优先级）：

```text
① 先扣输出预留 —— 它是硬约束，被侵占会导致截断
② 再放冻结前缀（槽位 1 + 2）—— 追求逐字节稳定，不追求短
③ 剩余空间按"可重建性"分配：不可重建的（已确认约束、当前指令）优先，
   可重建的（检索证据、历史）按需分配并允许被裁到 0
④ 槽位 5 只在"当前段"保留，历史段落外置为笔记
```

**注意力分布的经验规则**：关键约束（边界、禁止事项）不放中段——中段是全窗口注意力最低的区域；当前指令放最后；系统指令放最前。这就是槽位顺序固定为 1→2→…→6 的原因。

### 4.2 数据结构与接口形态

```python
from dataclasses import dataclass, field
from typing import Literal, Optional

SlotId = Literal["system", "tools", "evidence", "history",
                 "scratchpad", "instruction", "output_reserve"]

@dataclass(frozen=True)
class SlotSpec:
    slot: SlotId
    max_tokens: int                    # 必填：该槽位上限
    evictable: bool                    # 必填：是否可被裁剪（evidence/history 为 True）
    cacheable: bool                    # 必填：是否属于可缓存前缀（system/tools 为 True）
    notes: str                         # 该槽位的裁剪依据（写"由什么决定"）

@dataclass(frozen=True)
class ContextBudget:
    window_tokens: int                 # 必填：模型窗口总容量
    output_reserve: int                # 必填：硬预留，先从 window 中扣除
    slots: list[SlotSpec]              # 必填：槽位规格
    # 校验：sum(s.max_tokens) + output_reserve <= window_tokens

@dataclass(frozen=True)
class ToolResultContract:
    """工具返回即契约：五字段齐备才能按需取用而不必重跑。"""
    status: Literal["ok", "partial", "error"]   # 必填：状态
    conclusion: str                             # 必填：结论（可直接使用的部分）
    scope: str                                  # 必填：范围（这些结论覆盖了什么、没覆盖什么）
    evidence_ref: str                           # 必填：证据位置（可用于后续按需取回）
    next_hint: Optional[str] = None             # 选填：下一步建议（降低模型的空转）

@dataclass(frozen=True)
class AssemblyPlan:
    """一次调用的装配结果，用于可观测与回归。"""
    prefix_hash: str                   # 必填：冻结前缀的哈希（缓存命中诊断的关键）
    prefix_tokens: int
    slot_tokens: dict[SlotId, int]     # 必填：各槽位实际占用
    evicted: list[str]                 # 必填：本次被裁掉的内容标识
    truncated_evidence: bool           # 必填：证据是否被截断（截断即需标注）
```

**校验规则（应作为 CI 断言）**：

1. `sum(slot.max_tokens) + output_reserve <= window_tokens`。
2. `prefix_hash` 在相同配置下跨调用稳定（不稳定说明前缀里有动态值，缓存必然失效）。
3. 每次装配的 `slot_tokens` 落库，用于回归对比（口径由 `D11-质量-可观测性.md` 定义）。
4. 任何 `truncated_evidence = True` 的调用在结果中标记，避免把截断当成完整证据。

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 调整信号 |
|---|---|---|
| `output_reserve` | 由**该节点期望输出的最大长度**决定（结构化输出取其 schema 上界；自由文本取 P95 长度 × 安全系数） | 频繁出现输出截断 → 提高预留；预留长期用不满 → 空间被浪费，可下调 |
| `system` 槽位上限 | 由**政策与输出规范的必要长度**决定；策略是"只增不删" | 若系统指令频繁需要"按租户裁剪"，说明它混入了本该后置的内容 |
| `tools` 槽位预算 | 由**当前任务实际会用到的工具数**决定（见下条），而非"平台共有多少工具" | 工具定义占比持续超过总计的合理比例 → 先裁剪工具集，而不是压描述 |
| 工具数量上界 | 由**候选工具之间的语义可分性**决定：当两个工具的描述在语义上难以区分时，选择错误率上升 | 工具选择错误集中出现在某两个工具之间 → 合并二者或改名改描述，而不是继续加工具 |
| 工具描述长度 | 由**参数 schema 的必要复杂度**决定；描述应说明"何时用/何时不用"，而非复述参数名 | 模型反复问"该用哪个工具" → 描述缺"不适用场景"这一半 |
| `evidence` 槽位上限 | 由**剩余预算**与**单条证据的平均长度**共同决定；单条占满一半以上时，应先在下游投影字段 | 检索命中但答案错 → 往往是证据被截断，检查 `truncated_evidence` |
| 检索 `top_k` | 由单条内容的平均 token 数与剩余上下文预算共同决定；典型 3–10 | 超过 10 仍无改善 → 应先检查召回质量，继续加大只是稀释注意力 |
| compaction 触发阈值 | 由**历史槽位上限占用量**决定，不是固定轮数；同时设一个"最小保留轮数"避免刚聊两句就压缩 | 压缩后任务成功率下降 → 说明摘要丢了不可重建的信息，应改为结构化笔记（方案 D） |
| 前缀缓存 TTL | 由**调用间隔分布**决定：间隔短于 TTL 才有复用价值 | 缓存命中率长期偏低 → 先检查前缀是否混入动态值（`prefix_hash` 稳定性） |
| 上下文利用率拐点 | **必须自测** `[待验证]`：构造同一任务在多个上下文负载下的成功率曲线，取明显下降点 | 该值随模型版本变化；外部报告数字不可直接采用 |

### 4.4 分阶段实施路径

**最小可行版**：① 定义七槽位与各自的 `max_tokens`，先扣 `output_reserve`；② 工具返回强制五字段契约（`ToolResultContract`）；③ 系统指令与工具定义前置并保持稳定，动态内容一律后置；④ 只做一种裁剪——证据超限时截断并在结果中标注；⑤ **不做**：JIT 检索、compaction、结构化笔记、子 Agent 隔离。

**生产就绪版**：① `ContextBudget` 与 `AssemblyPlan` 落库，`prefix_hash` 稳定性进 CI；② 证据改为 JIT：上下文只放索引与证据位置，内容按需取回；③ 历史超限时走 compaction，且摘要字段清单（已确认约束 / 未决问题 / 关键证据位置）固定；④ 长任务引入结构化笔记，窗口内只保留当前段；⑤ 噪音大的探索性子任务下沉为子 Agent，返回契约限定为"结论 + 证据位置"；⑥ 自测本任务分布的上下文利用率拐点并写入配置；⑦ 上下文占用指标对接 `D11-质量-可观测性.md` 的采集口径，并纳入成本归因。

## 5. 检查清单

### 5.1 「最小可行」

- [ ] 七个槽位都有明确的 `max_tokens`，且 `sum(slots) + output_reserve ≤ window_tokens`
- [ ] 输出预留是硬预留，没有被前六项侵占
- [ ] 系统指令与工具定义在窗口最前，当前指令在最后
- [ ] 工具返回包含 状态 / 结论 / 范围 / 证据位置 / 下一步 五个字段
- [ ] 证据被截断时在结果中有明确标注（不把截断当完整证据）
- [ ] 检索证据可被裁到 0 而不影响任务可运行（说明裁剪优先级正确）

### 5.2 「生产就绪」

- [ ] `prefix_hash` 在相同配置下跨调用稳定，且有 CI 断言
- [ ] 前缀中不存在时间戳、随机 ID、动态排序等会让缓存失效的内容
- [ ] 每次调用的各槽位实际占用已落库，可用于回归对比
- [ ] 检索证据走 JIT：上下文只保留索引与证据位置，内容按需取回
- [ ] compaction 的触发阈值由历史占用量而非固定轮数决定，且摘要含固定的必保留字段
- [ ] 长任务有结构化笔记，窗口内只保留当前段

## 6. 常见陷阱

| # | 陷阱 | 现象与根因 | 埋伏阶段 → 规避方式 |
|---|---|---|---|
| 1 | 前缀里混入动态值 | **现象**：缓存命中率长期接近 0，成本远高于预期。**根因**：把时间戳、请求 ID、动态排序的列表、按热度变化的工具顺序拼进了系统指令或工具定义区 | **构建**，在**运营**期以"账单不符合预期"的形式爆发，且很难归因（功能完全正常） → 冻结前缀逐字节稳定；`prefix_hash` 进 CI，不稳定即报警 |
| 2 | 工具定义只写"怎么用"，不写"什么时候不要用" | **现象**：模型在多个语义相近的工具之间反复选错，或在不适用的场景调用某工具。**根因**：描述只复述参数名与功能，缺少"不适用场景"这一半 | **设计**，在**验证**期以"工具选择准确率上不去"的形式暴露 → 描述必须成对给出"何时用 / 何时不用"；两个工具难以区分时应合并，而不是加更多描述 |
| 3 | 只做压缩，不做外置 | **现象**：历史被反复摘要，任务越到后面越容易忘记早期已确认的约束。**根因**：把 compaction 当成唯一手段，忽略了摘要是有损的，且错误会被后续轮次继承 | **设计**，在**运营**期以"长任务后期约束遗忘"的形式爆发 → 不可重建的信息（已确认约束、禁忌）走结构化笔记，不走摘要；摘要只用于过程性内容 |
| 4 | 工具返回裸结果进上下文 | **现象**：大段原始数据进窗口，随后模型为了确认"这些数据覆盖了什么范围"再发起一次调用。**根因**：工具返回没有遵守契约（缺范围与证据位置），把压缩的责任推给了下游 | **构建**，在**运营**期以"调用次数比预期多一倍、token 超预算"的形式爆发 → 强制五字段契约；大返回必须先在下游投影/截断，不能靠上下文压缩器兜底 |
| 5 | 子 Agent 隔离失效 | **现象**：拆了子 Agent，主上下文反而更长——子 Agent 把中间过程原样带了回来。**根因**：只做了执行隔离，没做**返回契约**约束 | **设计**，在**验证**期以"上下文占用不降反升"的形式暴露 → 子 Agent 的返回值必须限定为结论 + 证据位置；中间过程只在子 Agent 自己的观测里保留 |
| 6 | 照搬外部"上下文利用率拐点"数字 | **现象**：按某篇文章的数字设定阈值，实际任务要么过早压缩、要么过晚。**根因**：拐点与模型版本、任务形态、信息冗余度强相关，不是通用常数 | **设计**，在**验证/运营**期以"离线指标正常但线上成功率低"的形式爆发 → 必须用本任务分布自测曲线；外部数字只作为量级参考 `[待验证]` |
| 7 | 关键约束放在中段 | **现象**：规则明明写了，模型还是违反。**根因**：注意力在位置上有偏，中段最易被忽略；把长清单平铺在中间，等于把约束放进了盲区 | **设计**，在**验证**期以"随机性违规"的形式暴露 → 约束前置（系统指令）与后置（当前指令）各放一次；长清单应改为结构化短条目 |

## 7. 反例

### 反例 1 · 把整份知识库预载进每一次调用

**做法**：为了让 Agent"什么都知道"，把全部领域文档一次性装入系统指令区。
**爆掉的方式**：token 成本立刻翻数倍；同时，具体问题相关的段落被大量无关内容稀释，回答质量不升反降。更隐蔽的是，前缀里包含了按热度排序的文档列表，导致缓存每次失效——成本再乘一层。修复要做三件事：改 JIT、冻结前缀、把索引与内容分离，等于把设计阶段欠的债一次性还清。

### 反例 2 · 用摘要代替结构化事实

**做法**：每超过 N 轮就把全部历史交给模型"总结一下"，然后丢弃原文。
**爆掉的方式**：某次摘要把"该用户的额度上限"写成了另一个数字（模型生成摘要时的常见漂移），此后所有轮次都基于错误约束执行，直到产生不可逆动作才被发现。根因是把不可重建的事实交给了有损压缩——正确做法是把这类事实外置为结构化笔记。

### 反例 3 · 工具返回直出原始数据

**做法**：一个查询类工具把下游返回的完整 JSON（数千 token）直接作为结果塞进上下文。
**爆掉的方式**：三轮之后上下文就撞上预算上限，触发压缩，而压缩把上一步刚取到的关键字段丢掉了；Agent 于是重新查询，形成"取回 → 压缩 → 丢失 → 再取回"的循环，成本直接翻倍而任务没有推进。根因是工具返回没有契约、没有证据位置，模型无法只取片段。

### 反例 4 · 把"上下文越大越好"当默认假设

**做法**：选用窗口最大的模型，并把所有能放的内容都放进去，理由是"反正放得下"。
**爆掉的方式**：单次任务成本上升一个数量级，而在长任务上成功率并未提高——因为瓶颈不是容量而是召回精度。团队后来做了对照实验才发现，把检索证据从"全量"改为"按需 5 条"后成功率反而略升、成本下降过半。这个实验本可以在设计阶段用自测拐点提前完成。

## 8. 开放问题

- **JIT 检索与预载的分界线在哪？** 有一派主张"能预载就预载"，理由是消除检索失败这一失败模式；另一派主张"默认 JIT，只在证明收益后才预载"。**两派前提不同**：前者面向延迟敏感、材料稳定且总量可控的场景，后者面向材料体量大或频繁变化的场景。目前缺少把"材料体量 / 窗口容量 / 往返成本"折算成统一判据的方法。
- **compaction 与结构化笔记能否统一？** 一种观点认为结构化笔记就是"有针对性的压缩"，可以用同一套机制实现；另一种认为二者的可靠性与审计性差异是本质的（摘要不可审计，笔记可审计），因此不应合并。**未收敛。**
- **子 Agent 隔离会不会削弱可观测性？** 隔离的代价是主线索看不到中间过程，而合规与调试往往正需要这些过程。是否应要求子 Agent 必须上报"可重放的轨迹摘要"，目前各框架没有统一做法 `[共识]`。
- **context rot 是否会被架构改进缓解？** 若未来模型在长上下文上的召回不再退化，本文大部分裁剪机制（compaction、JIT、子 Agent 隔离）的动机都会显著减弱。目前没有公开证据表明该退化可被根本消除，但这是一个会改变全部结论的变量。
- **上下文占用指标的口径何时稳定？** `D11-质量-可观测性.md` 需要采集各槽位占用，而 OTel GenAI semconv 仍在 Development（独立仓 `semantic-conventions-genai`，2026-06-12 迁出），属性名仍在变化。在口径稳定前，是否应先在自建字段上采集、避免绑定 semconv，尚无共识。
- **工具返回契约的五个字段是否足够？** "下一步建议"这一字段在部分实现中被认为会诱导模型跳过验证直接执行；是否应把它降级为可选且默认不填，需要更多实践数据 `[待验证]`。
