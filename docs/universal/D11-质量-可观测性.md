## 0. 总纲

> **Agent 可观测性的难点不在"采集不到数据"，而在数据采集齐全之后仍然回答不了"哪一个决策导致了这次失败"。因此 span 层级的设计优先级高于采集覆盖率：一个只覆盖 60% 但层级正确的 trace，比 100% 覆盖却全平铺的事件流更有价值。** `[共识]`

展开的要点：

- **归因的判据是唯一的**："这次运行产生的每一个副作用，能否回溯到产生它的那一次模型决策或工具调用？"能回溯，则层级设计合格；不能，则再多的字段也救不回来。
- **OTel GenAI semconv 仍在 Development，属性名会变。** `gen_ai.system` 已被 `gen_ai.provider.name` 取代，`prompt_tokens` / `completion_tokens` 已被 `input_tokens` / `output_tokens` 取代 `[已验证]`。**跟随 experimental 属性名会把文档里所有查询与看板变成持续返工项**，因此必须显式固定版本（§2.3）。
- **采样是一次不可逆的决策。** 采样丢掉的 trace 无法事后补采，因此采样策略必须由"哪些运行值得留"来定义，而不是由"存储预算平均分配"来定义。Agent 尤其如此——失败的、慢的、绕圈的运行才是最值得留的那些。
- **reasoning trace 是高价值也是高风险数据。** 它常包含未脱敏的中间推理与用户数据，采集即意味着把敏感内容的保留期问题引入系统（制度面归 `D16-交付-治理合规.md`）。
- **可观测性 ≠ 评测。** 本文负责"采集与呈现"，判定与门禁归 `D09-质量-评测.md`。把 trace 采集齐全不等于有了评测，把指标画成看板不等于有了门禁。

## 1. 问题定义与边界

### 1.1 本文解决的问题

1. **信号选型**：traces / metrics / logs 三类信号在 Agent 场景各承载什么，各自不能替代什么。
2. **层级设计**：workflow / agent / step / llm / tool / retrieval 等 span 的父子关系、命名与必填属性。
3. **指标口径**：延迟分位、token 用量、每步成本、工具错误率、循环检测、人工介入率如何定义与计算。
4. **成本归因**：按 trace / 租户 / 功能 / 模型四个维度切分成本，使"贵在哪"可回答。
5. **采样、脱敏与版本稳定性**：头采样与尾采样的取舍、Agent 场景的偏好、采集端脱敏与数据最小化，以及在 semconv 未稳定期如何以最低成本把遥测接下去（固定版本 + 显式 opt-in）。

### 1.2 本文不讨论什么

- **评测集、打分器、门禁阈值** → `D09-质量-评测.md`。本文只保证"数据能被拿到"，不负责"拿到后判定好坏"。
- **超时重试熔断、降级分级、级联失败隔离** → `D12-质量-可靠性.md`；本文只指出可靠性设计建立在可观测之上。
- **成本结构、单位经济学、缓存分层、批处理** → `D15-交付-成本性能.md`。本文只做成本**归因**，不做成本**优化**。
- **数据保留期、跨租户边界、审计要求的制度面** → `D16-交付-治理合规.md`；本文只讲技术形态的脱敏与最小化。
- **模型路由策略本身**（用哪个模型、什么档位）→ `D08-运行时-模型推理.md`；本文只要求路由标签可被切分。
- **检查点的存储与恢复重放** → `D05-运行时-记忆与状态.md`；**护栏规则的判定逻辑** → `D10-质量-安全护栏.md`（本文只定义安全事件应发什么遥测）。
### 1.3 与其他文档的边界切线

| 你可能想问 | 去哪篇 |
|---|---|
| 这些数据怎么判定好/坏、怎么设门禁阈值 | `D09-质量-评测.md` |
| 失败后怎么重试、怎么降级、怎么熔断 | `D12-质量-可靠性.md` |
| 怎么把成本降下来、单位经济学怎么算 | `D15-交付-成本性能.md` |
| 数据保留多久、怎么擦除、审计要留什么 | `D16-交付-治理合规.md` |
| 用哪个模型、开什么推理档位 | `D08-运行时-模型推理.md` |
| 状态快照怎么存、怎么恢复到某一轮 | `D05-运行时-记忆与状态.md`（检查点） |
| 护栏该拦什么、怎么设审批门 | `D10-质量-安全护栏.md` |
| 跨 Agent 调用怎么串成一条 trace | 本文 §3.3（协议面归 `D07-运行时-多智能体.md`） |

> **检查点 vs trace（最容易混淆的一对）**：检查点是**状态快照**，目的是"能从这一轮继续跑"，是可变状态的可恢复副本；trace 是**事件记录**，目的是"事后能解释发生了什么"，是不可变事实的序列。前者服务于恢复，后者服务于归因——**用 trace 做恢复会漏掉未记录的状态，用检查点做归因会丢失过程。**

## 2. 设计思路

### 2.1 第一性原理：一次 Agent 运行是一棵调用树，观测的任务是让这棵树可查询

一次运行由模型调用、工具调用、检索、子 Agent 调用、人工介入共同构成。它们之间存在严格的父子关系：一个工具调用由某次模型决策产生，一次子 Agent 调用由某个步骤产生。**归因就是沿着这棵树反向走：从异常结果出发，找到产生它的那一个节点。**

由这个原理直接推出三条结论：**① 平铺的事件流无法归因**——若所有事件同属一层，"哪一步导致了失败"就只能靠时间戳猜测，一旦有并发（并行工具、多 Agent）猜测立即失效；**② 上下文必须跨进程与跨服务传播**——工具可能是独立服务、子 Agent 可能是另一个进程、检索可能走外部系统，trace context 传播是层级设计的前提而非优化项；**③ 每个节点必须携带"它自己的成本"**，否则成本只能按整体摊派，而摊派无法回答"贵在哪一步"。

### 2.2 六个不可回避的约束

| 约束 | 性质 | 对设计的影响 |
|---|---|---|
| **GenAI semconv 仍是 Development** | 标准成熟度现实 | 属性名会变（已发生 `gen_ai.system` → `gen_ai.provider.name`、`prompt_tokens` → `input_tokens`）；必须固定版本并显式 opt-in，把迁移成本限制在一处 `[已验证]` |
| **成本与 token 由供应商返回，粒度不一** | 外部依赖 | 缓存读取/写入 token、reasoning token 常单独计价且并非所有供应商都返回；**缺失时必须记为"未知"而不是 0**，否则归因会系统性低估 |
| **trace 数据量随步数近似乘法增长** | 数据结构性质 | 每一步都携带上下文快照时，单条 trace 的体积随步数平方级膨胀；AI 负载产生的遥测体量显著高于传统服务 `[共识]` |
| **reasoning trace 可能含敏感内容** | 数据性质 | 采集即引入保留与脱敏问题；必须允许"采结构与统计、不采原文"这一档位 |
| **采样不可逆** | 工程现实 | 未被采样的运行无法事后重建；采样策略必须按"值得留的特征"定义，而不是按比例平均 |
| **跨进程/跨服务边界多** | 拓扑现实 | MCP server、子 Agent、外部工具都可能断开链路，形成多个孤立 trace |

### 2.3 由此推导出的三条取舍

**取舍一：宁可少记字段并固定 semconv 版本，也不要跟随 experimental 属性名。**

理由：跟随实验版本的代价不是一次改名，而是**所有查询、看板、告警规则、成本报表的同步返工**，且改名不产生报错、只产生空数据（静默失效）。固定版本 + 显式 opt-in 把"标准漂移"变成一次可控的升级动作（做法见 §4.3）。

**取舍二：宁可对慢的、失败的、非典型的运行全量保留（尾采样），也不要均匀采样把长尾丢掉。**

理由：Agent 的失败几乎都集中在长尾——绕圈、超步数、工具报错重试、人工介入。均匀头采样恰好把这些样本按比例稀释。**采样的目的是留下能解释问题的运行，不是留下有代表性的运行。**

**取舍三：宁可在采集端做不可逆的脱敏，也不要依赖展示端的权限过滤。**

理由：原始数据一旦落盘，其暴露面就由存储与下游决定，而不是由你的展示层决定。**在采集入口丢弃敏感字段，是唯一不依赖下游自律的方案。**

### 2.4 由上述推导出的结论

① **层级设计先于字段完备度**（由"归因靠反向走树"推出）；② **采样必须按特征而非比例**（由不可逆性 + 长尾集中推出）；③ **缺失的成本字段记为未知而非 0**（由供应商返回粒度不一推出）；④ **采集端脱敏为默认**（由落盘即扩散推出）；⑤ **采集与判定分属两个系统**（可观测性不产生门禁，门禁归 `D09-质量-评测.md`）。

## 3. 通用方案

### 3.1 采集方式

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · SDK 内嵌埋点** | 在业务代码里显式创建 span，完全控制层级与属性 | 自研编排器；需要精确的父子关系与自定义属性 | 侵入代码；埋点与业务逻辑耦合，遗漏点不可见；跨服务需自行传播上下文 | 快速原型；已有成熟框架的系统 |
| **B · 框架内置回调 / 自动埋点** | 依赖编排框架自带的 OTel 集成自动产生 span | 使用主流框架；希望零侵入起步 | 层级由框架决定；升级框架时埋点行为会变；**部分框架只覆盖模型调用、不覆盖检索与外部工具** | 有强自定义层级要求的系统 |
| **C · 代理式网关（LLM gateway）** | 在模型/工具出口处放代理，由代理记录请求、响应与 token | 多供应商、多团队共用出口；需要统一的用量与成本口径 | 只看到网络层，**看不到编排内部的层级**（谁调用了谁、为什么）；流式响应下的完整性处理复杂 | 需要归因到"哪一步"的场景（网关只能给"哪一次调用"） |
| **D · 组合（推荐落地形态）** | 框架/SDK 产生层级 + 网关补齐外部调用的用量与错误 + Collector 统一处理采样与脱敏 | 生产系统 | 需要一套 Collector 侧的配置治理；多处埋点可能重复计数，必须去重 | 极小规模系统（成本高于收益） |

**OCSF 的角色**：安全类事件（越权尝试、被阻断调用、异常外发）除 OTel 属性外常需按安全领域 schema 规范化，以便进入 SIEM；OWASP Agent Control Standard 建议以 OTel + OCSF 组合发出这类遥测 `[共识]`。实践建议：安全事件与业务 trace **共用 `run_id`，但落地在独立的信号通道**，避免安全查询与性能查询互相干扰。

### 3.2 三类信号的分工

| 信号 | 在 Agent 场景承载什么 | 不能替代什么 |
|---|---|---|
| **Traces** | 归因：一次运行的完整树、每步的输入输出摘要、模型与工具的时刻与耗时、错误与重试 | 不能替代指标：按 trace 存储做 P99 统计成本极高，且采样后分位失真 |
| **Metrics** | 趋势与告警：请求量、延迟分位（P50 / P95 / P99）、token 速率、每步成本、工具错误率、循环率、人工介入率、缓存命中率 | 不能替代 trace：聚合值无法定位到具体一次运行 |
| **Logs / Events** | 离散事实：护栏决策、状态转移、异常栈、配置变更、prompt 版本切换 | 不能替代 trace：日志没有父子关系，无法回答"谁调用了谁" |

### 3.3 span 层级设计

**推荐的层级（父子关系）**

```text
workflow / run            ← 一次用户请求的根 span（也可用 invoke_agent 作为根）
├── agent                 ← 一个 Agent 实例的完整执行（含多步循环）
│   ├── step              ← 循环的一轮（可选，视框架而定）
│   │   ├── llm           ← 单次模型调用（CLIENT span）
│   │   ├── tool          ← 单次工具调用（可能与 llm 并列，也可能在其下）
│   │   │   └── retrieval ← 工具内部的检索（若发生在工具内）
│   │   ├── retrieval     ← 直接发生的检索
│   │   └── human_input   ← 人工介入等待（必须单独成 span，否则延迟归因错误）
│   └── agent             ← 子 Agent 调用（嵌套的 agent span）
```

**命名与关键属性（属性名以 2026-09 时点 Development 版为准，落地时以固定版本为准）**

| 节点 | span 命名惯例 | 关键属性 |
|---|---|---|
| 模型调用 | `{gen_ai.operation.name} {gen_ai.request.model}`，如 `chat <model>` `[共识]` | `gen_ai.operation.name`、`gen_ai.provider.name`、`gen_ai.request.model`、`gen_ai.response.model`、`gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens`、`gen_ai.usage.cache_read.input_tokens`、`gen_ai.response.finish_reasons`、`gen_ai.response.id` |
| Agent 执行 | `invoke_agent {gen_ai.agent.name}` `[共识]` | `gen_ai.operation.name=invoke_agent`、`gen_ai.agent.name`、`gen_ai.agent.id`、`gen_ai.conversation.id`、`gen_ai.usage.input_tokens/output_tokens`（会话级汇总） |
| 工具调用 | `execute_tool {gen_ai.tool.name}` `[共识]` | `gen_ai.operation.name=execute_tool`、`gen_ai.tool.name`、`gen_ai.tool.type`、`gen_ai.tool.call.id`、`gen_ai.tool.call.arguments`、`gen_ai.tool.call.result`、`error.type` |
| 任意失败节点 | 继承父 span 名 | `error.type` + span status = ERROR 必须同时设置；只有其一会让错误在部分后端不可见 |

**四条设计要点**

1. **`gen_ai.request.model` 与 `gen_ai.response.model` 必须分开记录**——前者是请求值，后者是实际响应值。二者不一致即为别名漂移的唯一可观测痕迹（回指 `D08-运行时-模型推理.md` §4.2）。
2. **人工介入必须单独成 span**。把等待人的时间算进"Agent 延迟"会让可靠性优化方向完全错位（真正的等待在审批队列里，而不是在模型里）。
3. **每个 span 都要带能切分的维度**：租户、功能/场景、路由标签、模型快照号、prompt/工具 schema 版本。**切不出来的维度等于不存在**（与 `D08-运行时-模型推理.md` §2.4 第 ③ 条是同一约束的两侧）；同时**跨进程传播必须显式验证**——至少有一条测试证明子 Agent / 工具服务的 span 挂在同一条 trace 下（A2A `v1.0.1` 与 MCP `2026-07-28` 下的跨进程调用都需要应用侧显式传递上下文）。

### 3.4 采样方案

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 头采样** | 请求入口按比例决定是否采样，后续所有 span 继承决定 | 流量大、错误率低、只需要整体趋势 | **丢掉长尾**：慢的、失败的、绕圈的那些按比例被稀释；且入口无法预知本次是否会失败 | 以归因为主要目的的系统 |
| **B · 尾采样** | 全部 span 先缓冲，trace 结束后按策略决定保留（如"有错误""超时""步数超阈值""人工介入""高成本"） | **Agent 场景的默认选择** | 需要缓冲与集中决策（通常由 Collector 承担）；缓冲期内存开销大；跨服务时需保证同一 trace 的所有段都到达判定点 | 单机极小流量（直接全留即可） |
| **C · 分层组合** | 头采样打底保趋势 + 尾采样强制保留"值得留"的类别 + 安全事件 100% 保留 | 生产系统 | 策略需被治理（规则变更要有评审与版本号）；规则过宽会退化为"全留"，过窄会漏掉新失败模式 | 还没有基线、不知道什么算"值得留"的早期系统 |

**尾采样的保留策略清单（可直接作为规则集起点）**

- 有 `error.type` 或 span status = ERROR 的 trace
- 超过步数阈值（相对该功能的 P95 步数）或检测到循环（相同工具 + 相同参数重复调用）的 trace
- 出现人工介入的 trace
- 单次运行成本超过分位阈值的 trace
- **安全相关事件（被阻断调用、越权尝试、跨租户访问被拒）——不走采样，100% 保留**（回指 `D10-质量-安全护栏.md` §4.3）

### 3.5 成本归因方案

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · trace 级累计** | 把一条 trace 内所有模型调用的成本相加，得到"单次运行成本" | 最基础的起点；回答"哪些请求贵" | 只能到"这次运行贵"，无法回答"贵在哪一步" | 需要优化动作的场景 |
| **B · 步骤级打标** | 每个 llm span 记录自己的 token 与模型，成本按 span 聚合后再汇总到 trace | 需要定位到具体步骤 | 需要统一的 token 口径与定价表；缓存折扣、reasoning token 的分摊规则必须写清 | 供应商不返回细分 token 的场景（此时只能估算并标注） |
| **C · 多维属性化归因** | 在 span 上打租户 / 功能 / 模型 / 路由标签，成本可任意维度切片 | 多租户、多功能的系统；需要按客户核算 | 属性基数会膨胀（高基数标签导致存储与查询成本上升）；需要基数治理 | 未做基数治理的早期系统 |
| **D · 双层记账（推荐）** | 可观测侧按属性化口径出"分析账"，计费/账单侧用独立账本出"结算账"，两者定期对账 | 有真实结算需求的系统 | 两套口径存在偏差，必须定义对账规则；对账差异本身需要归因流程 | 无对外结算需求的内部系统（单套即可） |

**四个必须写清的归因规则**

1. **缓存读取/写入 token 的分摊**：缓存命中部分通常按折扣计价，若并入普通输入 token 会系统性高估成本；**reasoning token** 常单独计价且量级可观，**不得折入普通输出 token** 后就不管。
2. **重试与修复调用的归属**：结构化输出修复、降级重试产生的成本必须归属到**触发它的那个步骤**，而不是记成一个独立事项。**缺失值语义**同理：供应商未返回的字段记 `null`（未知），**不得记 0**——记为 0 会让归因持续低估并且看不出低估。

### 3.6 选型判据

```text
你现在要回答的问题是什么？
├── "整体有没有变慢/变贵" → 先做 Metrics（分位 + 趋势），成本用 trace 级累计
├── "这次为什么失败" → 必须有 Traces 且层级正确；采样走尾采样
├── "贵在哪一步 / 哪个租户" → 需步骤级打标 + 多维属性化归因（含定价表口径）
├── "安全上发生了什么" → 独立信号通道（OTel + OCSF），安全事件 100% 保留
└── "改动有没有让质量变差" → 这不是可观测性问题，去 D09-质量-评测.md
```

**顺序判据**：层级设计 → 采样策略 → 属性与基数治理 → 脱敏 → 看板。**顺序颠倒的典型症状**是：先做了漂亮的看板，后来发现无法下钻到单次运行，只能推倒重来。

## 4. 如何设计

### 4.1 步骤序列

| # | 步骤 | 产出物 |
|---|---|---|
| 1 | **明确要回答的问题清单**：把"上线后必须能回答的问题"写成 5–10 条（如"哪一步最贵""哪些运行超步数""人工介入率多少"） | 问题清单（每条能映射到某个信号与维度） |
| 2 | **冻结 semconv 版本**：选定版本号并显式 opt-in，写进依赖与文档 | 版本锁定记录 + 环境变量配置 |
| 3 | **定 span 层级与命名**：按 §3.3 画出本系统的调用树，标注哪些节点必须有、哪些可省 | 层级图 + 节点属性清单 |
| 4 | **定必填属性集**：为每个节点确定必填属性（含租户、功能、路由标签、版本） | 属性字典（含基数上限） |
| 5 | **实现上下文传播**：验证跨进程/跨服务（子 Agent、工具服务、检索服务）span 挂在同一 trace 下 | 传播验证用例 |
| 6 | **定采样策略**：尾采样规则集 + 安全事件例外 + 全量保留的兜底清单 | 采样规则（版本化配置） |
| 7 | **定脱敏与数据最小化**：确定哪些字段在采集端即被掩码/令牌化/摘要化 | 脱敏规则 + 字段白名单 |
| 8 | **定成本归因口径**：写明缓存 token、reasoning token、重试成本、缺失值的处理规则 | 归因口径文档 + 定价表版本 |
| 9 | **建看板与告警**：只建能对应步骤 1 问题的看板；告警只挂可行动指标 | 看板清单 + 告警规则 |
| 10 | **验证可回答性**：用一次真实故障复现，检验是否能在 3 次下钻内定位到根因节点 | 演练记录（**唯一**能验证可观测性是否合格的测试） |

### 4.2 数据结构与接口形态

span 属性集（`!` 为必填；字段名按 semconv 固定版本取值，非 GenAI 属性的 `*` 表示自定义扩展位）：

```yaml
# 每个 span 都必须带的通用属性
common:                                  # ! 所有 span 共有
  tenant_id: string                     # ! 租户标识（多租户系统必填，用于隔离与归因）
  feature: string                       # ! 功能/场景标签（成本与质量的切片维度）
  run_id: string                        # ! 一次运行的标识（等价 gen_ai.conversation.id 的用途）
  route_version: string                 # ! 模型路由表版本（回指 D08-运行时-模型推理.md）
  prompt_version: string                # ! 提示/工具 schema 版本，用于回归归因
  deployment_version: string            # ! 应用版本，用于发布对比

llm_span:                               # ! 每次模型调用
  gen_ai.operation.name: "chat"
  gen_ai.provider.name: string          # ! 旧名 gen_ai.system，已弃用 `[已验证]`
  gen_ai.request.model: string          # ! 请求值
  gen_ai.response.model: string         # ! 实际响应值；与请求值不同即别名漂移
  gen_ai.usage.input_tokens: int        # ! 旧名 prompt_tokens
  gen_ai.usage.output_tokens: int       # ! 旧名 completion_tokens
  gen_ai.usage.cache_read.input_tokens: int | null      # 缺失记 null，不记 0
  gen_ai.usage.cache_creation.input_tokens: int | null
  gen_ai.usage.reasoning.output_tokens: int | null      # 思考 token 常单独计价
  gen_ai.request.reasoning_effort: string | null        # 扩展位 *：推理档位
  gen_ai.response.finish_reasons: list[string]
  error.type: string | null             # 失败时必须与 span status=ERROR 同时设置

tool_span:                              # ! 每次工具调用
  gen_ai.operation.name: "execute_tool"
  gen_ai.tool.name: string
  gen_ai.tool.type: string              # function | extension（MCP 工具）等
  gen_ai.tool.call.id: string
  gen_ai.tool.call.arguments: string | null   # 采集端脱敏后可为摘要
  gen_ai.tool.call.result: string | null      # 同上
  tool.idempotency_key: string | null   # 扩展位 *：用于识别重复调用（循环检测）
  error.type: string | null
```

> **内容捕获（prompt / 消息体 / 工具参数）应作为独立开关**：默认关闭，按需开启。开启后必须与脱敏规则联动，因为这是 PII 与密钥最容易泄漏的位置 `[共识]`。

「运行摘要」结构（供看板与下钻使用，可从 span 聚合得到）：

```python
from dataclasses import dataclass
from typing import Literal

@dataclass
class RunSummary:
    run_id: str                        # !
    tenant_id: str                     # !
    feature: str                       # !
    outcome: Literal["success", "failed", "aborted", "pending_human"]  # !
    steps: int                         # ! 循环轮数
    llm_calls: int                     # !
    tool_calls: int                    # !
    input_tokens: int                  # ! 仅含已上报部分时须置 cost_incomplete
    output_tokens: int                 # !
    cost_estimate: float | None        # ! 由 span 级成本聚合；含定价表版本
    cost_incomplete: bool              # ! 存在 null 字段时为 True（禁止静默低估）
    latency_ms: int                    # !
    human_wait_ms: int                 # ! 人工介入等待必须单列，不计入 Agent 延迟
    loop_detected: bool                # ! 相同工具+参数重复调用
    degraded: bool                     # ! 是否走了降级路径（回指 D12-质量-可靠性.md）
    guardrail_blocks: int              # ! 被护栏阻断次数（回指 D10-质量-安全护栏.md）
    trace_sampled_tail: bool           # ! 是否由尾采样保留（用于评估采样偏差）
```

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 误用后果 |
|---|---|---|
| **semconv 版本** | 由"迁移成本 vs 新属性收益"决定；锁定后只在计划升级时变更，并以 `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` **显式选择**而非依赖默认值 | 跟随 experimental → 查询与看板静默失效（改名不报错、只丢数据） |
| **采样方式** | 由"是否以归因为主"决定：需要归因 → 尾采样；只看趋势 → 头采样 | 以归因为目的却用头采样 → 长尾被稀释，"为什么失败"永远答不上 |
| **尾采样缓冲窗口** | 由该功能的 P99 运行时长决定：窗口必须大于 P99，否则 trace 在判定前就被丢弃 | 窗口小于 P99 → 最慢的那批恰好被丢弃，而这正是最该留的样本 |
| **保留期** | 由合规要求与排障需求共同决定（制度面归 `D16-交付-治理合规.md`）：排障期通常远短于审计期 | 按单一保留期一刀切 → 要么排障时数据已删，要么为审计长期保存全量明细 |
| **属性基数上限** | 由存储与查询成本决定：**高基数字段（原始参数、原始 URL、用户 ID）不得作为标签维度** | 基数失控 → 存储成本与查询延迟同时恶化，且通常先表现为"看板变慢"而非报错 |
| **循环检测阈值** | 由"同一工具 + 相同参数的重复调用次数"决定；阈值应接近业务上合理的重试次数上界 | 阈值过高 → 资源在黑盒里被烧完才发现；阈值过低 → 正常的重试被误判 |
| **人工介入率口径** | 由"人是否真的阻断过流程"定义，而不是"是否展示过确认界面" | 口径过宽 → 该指标失去诊断价值（一切都要确认的系统读数为 100%） |

### 4.4 分阶段实施路径

**最小可行（能归因到节点）**

- 冻结并记录 semconv 版本，显式 opt-in。
- 三层 span 到位：`invoke_agent` → `llm` / `execute_tool`，父子关系正确。
- 每个 span 带 `tenant_id` / `feature` / `run_id` / 模型快照号 / `prompt_version`。
- 失败时同时设置 `error.type` 与 span status = ERROR。
- 成本按 trace 级累计；缺失字段记 `null` 并在下游标记 `incomplete`。
- 内容捕获关闭；只记摘要与统计。
- 有一份"3 次下钻定位根因"的演练记录。

**生产就绪**

- 尾采样规则集上线并版本化，含安全事件 100% 保留的例外。
- 步骤级成本归因可用，定价表有版本号，重试与修复调用的成本归属规则写明。- 跨进程（子 Agent、工具服务、检索服务）trace 已连成一条链，并有验证用例。
- 高基数标签有上限与治理规则；看板的下钻路径不超过 3 层。- 脱敏在采集端完成，字段白名单有维护人；内容捕获按环境分级。
- 存在"可观测性覆盖度"自检：新增的每个外部调用点是否都能在 trace 中看到。
- 安全事件走独立信号通道（OTel + OCSF），与业务 trace 以 `run_id` 关联；每次降级在 trace 与指标中都可计数（与 `D12-质量-可靠性.md` 的降级路径联动）。

**落地检查点**：能回答"上一次成本异常是哪一次运行、贵在哪个 span、用了哪个模型快照与路由版本"——答不出说明归因链未闭合。

## 6. 常见陷阱

### 陷阱 1 · 跨进程断链

**现象**：子 Agent 与工具服务的调用在本端看得到，但它们是独立的 trace，无法拼成一次运行。
**根因**：上下文传播没有显式实现——跨进程（MCP `2026-07-28` 下的工具服务、A2A `v1.0.1` 下的子 Agent）不会自动继承 trace context。
**埋伏阶段**：构建。
**规避**：把传播写进调用协议并在集成测试中断言"子调用挂在同一条 trace 下"；这是**必须被测试覆盖**的项，不能靠"应该会传过去"。

### 陷阱 2 · 采样按比例均匀，丢掉全部失败样本

**现象**：看板上成功率、延迟都正常，但一旦出事，找不到能做根因分析的 trace。
**根因**：头采样按比例丢弃，而失败与慢运行在长尾中占比极低；采样不可逆，丢失后无法补采。
**埋伏阶段**：运营（引入点在设计）。
**规避**：改尾采样并显式保留"错误 / 超步数 / 循环 / 人工介入 / 高成本"五类（§3.4）；同时把"被保留的 trace 是否仍有偏"作为一项自检（`RunSummary.trace_sampled_tail`）。

### 陷阱 3 · 高基数属性炸掉存储与查询

**现象**：上线一段时间后看板变得非常慢，存储成本超预算；排查发现 trace 上带了原始 URL、原始参数或用户 ID 作为标签。
**根因**：把"想看到的信息"与"想按它切分的信息"混为一谈。标签（维度）与字段（详情）的成本模型完全不同。
**埋伏阶段**：设计。
**规避**：只有会被用来分组/过滤的值才做标签；原始内容与高基数值只作为 span 内的字段（且经脱敏）。给每个属性的基数设上限并在写入时校验。

### 陷阱 4 · 采集端不脱敏，靠展示端权限兜底

**现象**：prompt 原文、工具参数、用户标识全部落进遥测存储；对外展示时靠角色权限限制。
**根因**：把脱敏当成展示问题而不是数据问题。数据一旦落盘，暴露面由存储、备份、导出、下游集成共同决定。
**埋伏阶段**：设计。
**规避**：在采集入口做不可逆脱敏（掩码/令牌化/摘要化）；内容捕获作为独立开关按环境分级；这一条与 OWASP Agent Control Standard 对遥测的要求方向一致 `[共识]`。

### 陷阱 5 · reasoning trace 全量留存

**现象**：为便于调试把模型思考内容全量落库，事后被合规或安全评审指出含敏感推理与用户数据。
**根因**：reasoning 内容看起来"只是模型的中间步骤"，实际上它经常复述输入中的敏感信息；其保留期与访问控制要求与普通指标完全不同。
**埋伏阶段**：运营（引入点在设计）。
**规避**：默认只采**结构与统计**（思考 token 数、时长、是否触发），原文按需开启并绑定保留期与访问审计（制度面归 `D16-交付-治理合规.md`）。

## 7. 反例

### 反例 1 · 先做看板后做层级

**做法**：项目启动时先接入一个观测平台，画出成功率、延迟、token 趋势三张图，认为可观测性已完成。
**爆掉的方式**：第一次真实故障时，图上显示"某功能成功率下降 6%"，但点进去全是平铺事件，无法判断是模型、工具还是检索导致的。团队开始加日志、加字段，两周后发现要定位根因必须重构埋点——**而历史数据已经无法回溯**。爆点发生在第一次需要根因分析的时候，而那时通常已经上线且流量在涨。

### 反例 2 · 成本按整体摊派

**做法**：账单按功能模块平均分摊，或者只统计总 token，不做到步骤级。
**爆掉的方式**：成本超标时无法归因，只能"全局优化"：缩小上下文、降低模型档位——这些动作会同时损害质量最高的那条路径，而又无法证明损害在哪。**结果是成本降了 20%、成功率降了 8 个点，且没人能把它归到具体改动**（观测口径回指 `D15-交付-成本性能.md`）。

### 反例 3 · 人工等待混入 Agent 延迟

**做法**：审批与澄清的等待时间被算进 Agent 的总耗时。
**爆掉的方式**：优化会议上看的是"Agent 太慢"，于是去压模型延迟与推理档位；真正的瓶颈（审批排队）完全没被触碰。压制模型能力换来的延迟改善远小于人的等待时间，**质量却实实在在地降了**。这个错误会让整个可靠性优化方向错位（可靠性归 `D12-质量-可靠性.md`）。

## 8. 开放问题

- **固定 semconv 版本 vs 保持最新：** 一派主张**锁定版本**并计划升级，理由是查询与看板成本可控、变更是一次动作；另一派主张**跟随最新**，理由是早期版本属性覆盖不足，锁死会长期缺字段、事后补数据的成本更高。前者假设"分析口径已稳定"，后者假设"字段需求还会变"。**没有跨团队的通用答案。**
- **多 Agent 场景的尾采样可行性：** 尾采样要求一条 trace 的所有段都到达同一个判定点。当子 Agent 跨组织边界（A2A `v1.0.1`）或跨云时该前提可能不成立，**代替方案（本地判定 + 汇总对账？）尚无共识。**
- **reasoning trace 的采集边界：** 采"结构不采原文"会丢失最有价值的调试信息，采原文又引入保留与访问问题。能否找到既可调试又不落敏感原文的中间形态（例如本地短期缓存 + 只上传判定结果），**缺少可复现的实践证据。**
- **可观测性的成本上界：** Agent 负载的遥测体量显著高于传统服务 `[共识]`，但"每美元业务成本对应多少遥测成本"这一比值没有公开基线，导致预算无法论证。
- **采集与判定的接口标准：** 目前"把 trace 交给评测系统"没有通用契约，各平台自定格式，导致评测侧重复解析。是否需要类似 trace → eval 的标准接口？**标准层面尚无动作。**
