## 0. 总纲

> **状态、检查点、记忆是三种生命周期完全不同的对象——状态在一次运行内被高频读写、检查点是某一时刻状态的完整物化快照、记忆是跨会话持久化的高显著度事实。把它们塞进同一个 schema、同一个存储、同一套淘汰策略，是 Agent 系统最常见的结构性错误；三者的读写频率、一致性要求与保留期互不兼容，强行合并后必然有一方被牺牲。** `[共识]`

具体表现有三类：**把记忆当状态用**（每轮整体重放、状态随会话线性膨胀，撞上上下文预算与序列化成本）· **把检查点当记忆用**（恢复语义与回忆语义互相污染，两者都无法独立演进）· **把三者当一层存**（高频状态与低频记忆共用索引与备份，成本被最坏的那一方拉高）。

三条可操作的结论：

1. **状态追求"可重建"**：给定输入与检查点，能确定性地重建到某一步；因此在运行结束或失败后可按需丢弃。
2. **检查点追求"可重放"**：不仅恢复数值，还要能重放副作用与外部调用（见 §4.2 的 `idempotency_index`）。
3. **记忆追求"可遗忘"**：写入有门槛、保留有 TTL、删除可证（法律意义上的擦除留待 `D16-交付-治理合规.md`）。

三者唯一可以共用的东西是**序列化格式与版本字段**，而不是存储、索引与生命周期。

## 1. 问题定义与边界

### 1.1 本文解决的问题

一句话：**把"运行中变化的东西"（状态）、"用来恢复与调试的东西"（检查点）、"跨会话要记住的东西"（记忆）分成三个独立设计对象，并给出各自的字段、存储、写入与淘汰规则。**

这三个词在行业讨论中经常被混用（"把记忆存进 state""用 checkpoint 做长期记忆"），因此第一件事是把边界钉死：

| 维度 | 状态（state） | 检查点（checkpoint） | 记忆（memory） |
|---|---|---|---|
| **定义** | 一次运行内、编排器维护的结构化事实 | 状态在某一执行步的完整物化快照 | 跨会话持久化、经显著性筛选的事实 |
| **生命周期** | 一次运行（run / session 内） | 与运行同寿，可长期归档 | 跨会话、跨运行，长于任何单次运行 |
| **作用域** | 当前任务 | 当前任务（用于恢复 / 重放 / 时间旅行） | 用户 / 租户 / 组织级 |
| **读写频率** | 每步读写（高） | 每步或每 N 步写一次（中），恢复时读（低） | 写入低、每会话取回一次（低） |
| **一致性要求** | 强（同一步骤内自洽） | 强 + **原子性**（不能存半个状态） | 最终一致（允许合并延迟） |
| **可丢弃性** | 运行结束即可丢弃 | 可归档，但可丢弃 | **不可随意丢弃**（用户预期它被记住） |
| **是否进上下文** | 部分字段经装配进提示 | 不进上下文（是存储对象） | 取回后经注入进上下文 |
| **淘汰方式** | 隐式（运行结束） | TTL / 归档策略 | 显著性衰减 + TTL + 显式删除 |
| **对应本文节** | §4.2、§4.3 | §3.2、§4.2、§4.4 | §3.4、§4.3、§4.5 |
| **归属文档** | 本文 | 本文（与 `D11-质量-可观测性.md` 划界） | 本文 |

> **一句话记忆法**：状态是"现在是什么"，检查点是"当时是什么"，记忆是"上次说过什么"。

### 1.2 本文不讨论什么

- **不讨论单次窗口内的上下文装配与裁剪**——那是 `D04-运行时-上下文工程.md` 的职责；本文只决定"哪些状态字段值得被装配"，不决定"怎么装"。
- **不讨论工具如何读写状态**——工具侧的读写接口契约归 `D06-运行时-工具与协议.md`；本文只定义状态 schema 与被读写字段的语义。
- **不讨论 trace 的采集、span 层级与采样**——那是 `D11-质量-可观测性.md` 的职责；本文只澄清检查点与 trace 的用途差异（§1.3）。
- **不讨论数据擦除的合规流程、多租户隔离策略、加密与密钥管理**——归 `D16-交付-治理合规.md`；本文只定义"可被擦除"所需的结构前提（每条记忆可定位到主体与来源）。
- **不讨论具体向量库或图数据库产品的选型**——本文给的是分层与策略，不背书具体供应商。

### 1.3 与其他文档的边界切线

| 你可能想问 | 去哪篇 |

**检查点 vs trace 的划界（高频混淆点）**：

| 对比项 | 检查点（checkpoint） | 轨迹（trace） |
|---|---|---|
| 目的 | **恢复与重放**运行 | **观测与评测**运行 |
| 内容 | 状态的结构化物化（可继续执行的最小集合） | 步骤序列（输入、工具、输出、耗时、token、成本） |
| 可否由它继续执行 | **可以**（这是它的定义） | 通常不可以（缺少完整状态） |
| 保留粒度 | 每步或每 N 步，可去重 | 每步，稠密 |
| 主要消费者 | 编排器、恢复逻辑 | 人、评测系统、告警 |
| 归属 | 本文 | `D11-质量-可观测性.md` |

> 二者可以**同源**（同一个执行步同时产出检查点与 span），但**不可互相替代**：用 trace 恢复执行会缺状态，用检查点做评测会缺过程。

## 2. 设计思路

### 2.1 第一性原理：三种对象的生命周期由"谁在什么时候需要它"决定

设计的起点不是"存什么字段"，而是三个问题：**谁需要它**（编排器 / 恢复逻辑与调试者 / 未来的会话）· **什么时候需要**（几乎即时 / 失败或回溯时 / 可能几周后）· **需要多久**（一次运行内 / 可归档但有限 / 用户预期长期）。

由此推出三条相互独立的存储设计，而不是一张大表。**读写频率差决定索引与备份策略，保留期长短决定存储介质与成本模型，一致性要求强弱决定事务边界。** 三者一旦合并，成本与复杂度就会被最坏维度支配。

### 2.2 不可回避的约束

| 约束 | 性质 | 对设计的强制影响 |
|---|---|---|
| **模型不能"按主键读"中间状态** | 架构性 | 状态里放的内容，只有被**装配进上下文**模型才看得见；不能假设模型能查询状态表。因此状态要么被投影进提示，要么通过工具暴露（回指 `D06-运行时-工具与协议.md`） |
| **上下文预算有限且注意力会稀释** | 架构性 | 记忆再全，一次也只能注入少数高显著度条目；因此记忆设计的核心是**取舍与排序**，而非容量（回指 `D04-运行时-上下文工程.md`） |
| **序列化有物理成本** | 工程性 | 状态越大，每步快照的写放大越严重；检查点必须支持**增量或去重**，否则长任务会被快照拖垮 |
| **副作用不可天然回滚** | 外部世界 | "重放"不是重跑一遍代码，而是**重放已记录的结果**；这要求工具有幂等键或结果可录制（回指 `D06-运行时-工具与协议.md`、`D12-质量-可靠性.md`） |
| **非确定性** | 模型性质 | 同一检查点恢复后继续运行，结果可能不同；因此"可重放"要区分**确定性重放**（录制结果）与**可重复重放**（同输入同结果，通常不成立） |
| **删除有法律与用户预期** | 合规 | 记忆结构必须可定位到主体与来源，否则无法执行擦除（`D16-交付-治理合规.md`） |

### 2.3 由此推导出的核心取舍

**取舍一：宁可状态显式且可序列化，也不把真相藏在对话历史里。** 若状态的唯一载体是 message 列表，那么"当前计划到第几步""已确认哪些约束"只能靠模型从历史里重新推断，既不可校验也不可恢复。显式字段的代价是 schema 维护成本，收益是状态可断言、可分片、可迁移。**对话历史是叙述，状态是事实。**

**取舍二：宁可接受检查点的存储与写放大成本，也不追求"无缝恢复"的魔法。** 有些实现试图只存"变更日志"并声称能重建任意点，但一旦涉及外部副作用或非确定性步骤就无法重建。显式快照 + 幂等键是更笨但更可靠的路。代价是存储，收益是恢复的可验证性——**恢复能力必须可被演练证明，而不是被声称。**

**取舍三：宁可记忆写入门槛高导致偶尔"忘事"，也不让检索噪声淹没上下文。** 记忆的价值来自信噪比。写入过松会引入大量低显著度条目，检索时挤占上下文、引入矛盾、放大注入面。**默认不写、符合显著性判据才写**，比"先都写下来再靠检索排序"更稳——因为检索排序在矛盾条目上不可靠。

## 3. 通用方案

状态、检查点、记忆各有多条主流路线。下面是四种被广泛采用的整体方案，覆盖从"最简"到"最重"。

### 3.1 方案 A · 单一类型化状态对象（typed single state）

**机制**：整个运行维护一个强类型对象（字段 / 类型 / 必填 / 默认值固定），每步由节点返回对该对象的更新、编排器做浅合并；检查点即该对象的整体序列化。**适用条件**：步骤数中等、状态字段稳定、运行内并发写少；单 Agent 或 supervisor 单写者模型。
**代价**：字段膨胀时对象变大、整体快照写放大明显；并发写需额外合并策略；类型变更需迁移（§4.2）。**不适用场景**：长时任务（快照体积失控）、多写者并发（合并冲突频繁）、字段随任务类型剧烈变化。

### 3.2 方案 B · 分域状态 + 归约函数（scoped state with reducers）

**机制**：状态按作用域拆分（如"全局设置 / 计划 / 局部临时 / 外部引用"），每个域声明自己的合并语义（覆盖、追加、求并、求和），并行分支写同一域时由归约函数合并。**适用条件**：有并行分支（多工具 / 多 Agent）、不同域的更新频率差异大，需要把"高频小字段"与"低频大字段"分开。
**代价**：需为每个域定义归约语义，定义不当会出现"覆盖丢数据"或"追加无限增长"；检查点需分别管理各域的持久化与回放顺序。**不适用场景**：更新几乎全为覆盖语义、无并发的简单场景（引入归约属过度设计）。

### 3.3 方案 C · 事件溯源 / 追加日志（event sourcing）

**机制**：状态不直接存储，而存为**不可变事件序列**（append-only），当前状态是事件的折叠结果；检查点 = "事件序列 + 一个折叠出的快照"，恢复 = 从最近快照重放其后事件。**适用条件**：需要审计（谁在何时改了什么）、时间旅行调试、精确重建任意历史点、写入以"事实"而非"当前值"为主。
**代价**：读放大（重建状态需重放）、事件 schema 演进复杂（旧事件必须永远可解析）、存储随运行时间线性增长、快照压缩需专门设计。**不适用场景**：以当前值读取为主、无审计需求；对延迟极度敏感且状态读取频繁。

### 3.4 方案 D · 分层记忆外置 + 应用内状态（memory service offload）

**机制**：应用内只保留运行态（方案 A 或 B），跨会话记忆委托给外部分层记忆服务；各层独立 TTL 与写入门槛，写入走"显著性筛选 → 合并去重 → 冲突消解 → 时间衰减"，读取走"按需取回 → 注入上下文"。**适用条件**：有明确跨会话记忆需求（助手、客服、个性化），需要把记忆容量与运行期状态解耦。
**代价**：引入外部依赖与一致性延迟；记忆质量高度依赖写入策略（阈值、合并、衰减）的调参；厂商自报基准数字不可作为选型唯一依据。**不适用场景**：纯单次任务、无跨会话身份，或数据不允许出本地边界。

**分层记忆六层（各层存什么 / 典型 TTL / 写入门槛）**：

| 层 | 存什么 | 典型 TTL | 写入门槛（显著性地板） | 检索命中方式 |
|---|---|---|---|---|
| **工作（working）** | 当前推理的临时草稿与中间结果 | 一次运行 / 数分钟 | 不筛选，随用随弃 | 不检索，直接在用 |
| **会话（session）** | 本次会话的已确认事实（当前语境、临时偏好） | 会话结束或数小时 | 低：会话内出现即记 | 会话内直接引用 |
| **情节（episodic）** | "某次发生的事"：任务、结果、时间、参与方 | 数天至数周 | 中：任务有明确结果或结论 | 按时间 / 相似场景召回 |
| **语义（semantic）** | 去情境化的事实与偏好（"用户偏好靠窗座位"） | 数月，随衰减 | 高：多次出现或用户显式确认 | 按相似度召回 |
| **图（graph）** | 实体及其关系（人、地点、项目、约束之间的边） | 长，随实体衰减 | 高：需能连到已有实体 | 多跳关系查询 |
| **程序（procedural）** | 可复用的技能 / 流程 / 提示模板 | 长，版本化 | 高：被验证有效的稳定流程 | 按任务类型匹配 |

> 分层命名与"写入时合并去重 + 遗忘策略"的做法，与 Mem0 / Zep-Graphiti / Letta 的公开实践一致 `[共识]`；这些厂商公布的记忆基准提升数字**均为自报**，只能作 `[共识]` 或 `[待验证]`，不得作 `[已验证]`。
> **注意**：六层不是"必须全建"。缺少图查询需求时，图层的收益不及它带来的实体对齐成本；缺少可复用技能沉淀时，程序层是空壳。**从会话 + 情节 + 语义三层起步是多数系统的合理最小集。**

### 3.5 选型判据

```
是否需要审计 / 时间旅行 / 精确重建历史点？
├─ 是 → 方案 C（事件溯源），并是否同时需要跨会话记忆？
│        ├─ 是 → C + D
│        └─ 否 → C
└─ 否 → 是否存在并行分支 / 多写者？
         ├─ 是 → 方案 B（分域 + 归约）
         └─ 否 → 方案 A（单一类型化状态）
是否跨会话需要记住用户？
├─ 是 → 叠加方案 D（并按 §3.4 六层裁剪）
└─ 否 → 不引入记忆层
```

| 判断问题 | 若回答为 | 建议 |
|---|---|---|
| 单次运行的步骤数是否超过约 50 步或耗时超过数分钟？ | 是 | 倾向 B 或 C，避免整体快照写放大 |
| 是否需要"回到第 N 步重放"用于调试？ | 是 | 倾向 C（或 A/B + 显式检查点序列） |
| 是否有并行分支写同一批字段？ | 是 | 必须引入归约（B），否则覆盖丢数据 |
| 是否跨会话必须记住用户？ | 是 | 叠加 D，且先定写入门槛再谈检索 |
| 是否存在不能出边界的敏感数据？ | 是 | 记忆层本地化或延后（`D16`） |

## 4. 如何设计

### 4.1 步骤序列（每步标产出物）

```text
① 枚举"运行内必须持久化的事实"      → 产出：状态字段清单（含用途与消费者）
② 划域（全局/计划/临时/外部引用）     → 产出：状态域划分表 + 每域合并语义
③ 定 schema（字段/类型/必填/版本）    → 产出：状态 schema（含 version 字段）
④ 定检查点粒度与存储                 → 产出：检查点触发策略 + 原子写入方案
⑤ 定记忆分层与裁剪                   → 产出：启用哪几层 / 各层 TTL 与写入门槛
⑥ 定写入流水线                       → 产出：筛选→去重→冲突消解→衰减 的规则
⑦ 定取回与注入                       → 产出：取回时机 + 注入槽位（回指 D04）
⑧ 定遗忘与擦除前提                   → 产出：衰减/淘汰规则 + 主体可定位字段（D16 接口）
```

每一步都有产出物，缺一步就会在后面变成隐性约定（隐性约定 = 无法评审 = 无法迁移）。

### 4.2 数据结构与接口形态

**状态对象（示意，字段名中性化）**：

```python
from typing import Literal, Optional
from pydantic import BaseModel, Field

class StateEnvelope(BaseModel):
    schema_version: str                      # 必填：状态 schema 语义化版本，迁移判据
    run_id: str                              # 必填：本次运行唯一标识
    step: int = 0                            # 必填：当前执行步，检查点与重放的对齐基准
    goal: str                                # 必填：任务目标（运行内不变，恢复后据此重建意图）
    plan: list["PlanItem"] = []
    confirmed_constraints: dict[str, str] = {}   # 运行内已确认、不可推翻的约束，便于断言
    scratch: dict[str, object] = {}              # 临时中间结果；可丢弃，不进跨会话恢复语义
    external_refs: dict[str, str] = {}           # 外部系统句柄/ID；只存引用，不存大对象
    memory_refs: list[str] = []                  # 注入过的记忆条目 ID，便于溯源与回滚投毒

class PlanItem(BaseModel):
    id: str
    desc: str
    status: Literal["pending", "running", "done", "failed"] = "pending"
    evidence_ref: Optional[str] = None       # 证据位置（回指 D06 工具契约）
```

**检查点对象（示意）**：

```python
class Checkpoint(BaseModel):
    checkpoint_id: str                       # 必填：唯一 ID，恢复入口
    run_id: str
    step: int
    created_at: str                          # ISO8601 UTC
    schema_version: str                      # 必填：与 StateEnvelope 一致，迁移校验用
    state: StateEnvelope
    idempotency_index: dict[str, str] = {}   # 已执行副作用的幂等键 → 结果，用于确定性重放
    parent_checkpoint_id: Optional[str] = None   # 链式检查点，支持时间旅行与分支
```

**记忆条目（示意）**：

```python
class MemoryRecord(BaseModel):
    memory_id: str
    layer: Literal["session", "episodic", "semantic", "graph", "procedural"]
    content: str                             # 必填：去情境化后的事实文本
    subject_key: str                         # 必填：主体定位键（用户/租户），擦除前提 D16
    source_run_id: str                       # 来源运行，便于回溯与投毒排查
    salience: float                          # 0–1，写入与衰减的依据
    confidence: float                        # 0–1
    created_at: str
    last_accessed_at: str                    # 衰减按访问时间而非创建时间
    ttl_class: Literal["short", "medium", "long"]
```

**接口形态（最小集）**：`write_memory(candidate) -> WriteResult`（返回"写入 / 合并 / 拒绝 + 理由"）· `retrieve_memory(query, k) -> list[MemoryRecord]` · `checkpoint(state, idem_index) -> Checkpoint`（原子写）· `restore(checkpoint_id) -> (StateEnvelope, idem_index)`。

> 关键：`write_memory` **必须返回拒绝理由**。没有拒绝理由的写入接口，等于把写入门槛藏进了实现里，无法评审也无法调参。

### 4.3 关键参数与取值依据

本节的写法遵循"参数由什么决定"，不写"建议设为 X"。

| 参数 | 由什么决定 | 取值信号 |
|---|---|---|
| **检查点间隔（每步 / 每 N 步）** | 单步耗时 × 状态序列化成本 vs 可接受的重放代价。重放代价 = 一次失败平均要重做多少步 | 若单步快且便宜 → 每步；若快照昂贵 → 每 N 步 + 关键节点强制。**决定因素是"重放的可接受代价"，不是存储便宜** |
| **状态对象体积上限** | 上下文预算与快照写放大 | 状态里的大对象应外置为引用（`external_refs`）；体积上限由"每步快照写入延迟是否可接受"反推 |
| **记忆写入门槛（显著性地板）** | 检索噪声容忍度与上下文预算 | 门槛越高越精确但越容易忘事；由"一次会话平均注入条目数 × 单条 token"是否能塞进预算决定（回指 `D04`） |
| **各层 TTL** | 该层事实的有效期与用户预期 | 偏好类（语义）随衰减长期保留；情节类过期即降权；会话类随会话结束清空。TTL 由"事实半衰期"决定，不由存储成本决定 |
| **时间衰减速率** | 事实类型（偏好变化快慢）与访问频率 | 按 `last_accessed_at` 而非 `created_at` 衰减，否则常用记忆会被误淘汰 |
| **合并去重的相似度阈值** | 误合并（丢信息）与漏合并（重复）的成本差 | 宁漏合并勿误合并：误合并会永久丢失一条事实，漏合并只是检索时多一条 |
| **取回条数 k** | 单条平均 token 与剩余上下文预算 | 与 `D04-运行时-上下文工程.md` §4.3 同口径：先查召回质量，再决定是否加大 k |
| **注入槽位** | 记忆类型（事实/偏好/流程） | 偏好进系统约束槽；事实进检索槽；流程进工具/技能槽（回指 `D04`） |

### 4.4 分阶段实施路径

| 阶段 | 做什么 | 不做什么 |
|---|---|---|
| **最小可行** | 单一类型化状态（含 `schema_version`、`step`、`run_id`）+ 每步整体检查点写库 + 恢复接口 + 一个"会话层"记忆（键值或简单向量） | 不做图、不做程序层、不做事件溯源、不做衰减 |
| **生产就绪** | 状态分域 + 归约；检查点支持链式与原子写；记忆扩到 情节/语义 层并带显著性、合并去重、冲突消解、按访问时间衰减；擦除前提字段齐备；恢复演练纳入例行 | 不追求"无缝"恢复，接受重放代价并**实测**恢复成功率 |
| **规模化** | 检查点冷热分层与压缩、事件溯源叠加审计、图/程序层按需启用、记忆投毒检测（`D10`） | 不在没有审计需求时上事件溯源 |

### 4.5 写入、遗忘与检索的落地细则

**写入流水线（四道闸）**：

1. **显著性筛选**：候选事实满足至少一条 —— 用户显式要求记住、跨会话稳定（偏好/身份）、被重复观察到 ≥ N 次、影响后续决策。不满足则**默认丢弃**。
2. **合并去重**：与已有条目比对，命中相似度阈值则合并（保留来源与时间），否则新增。合并采用"保留双方来源 + 取较新值 + 记冲突标记"。
3. **冲突消解**：同一主体同一维度的矛盾事实，按"用户显式确认 > 近期观察 > 早期观察 > 推断"的优先级;无法判定时**保留双方并标记冲突**，注入时提示模型存在分歧，而不是静默取一条。
4. **时间衰减**：`salience` 按 `last_accessed_at` 衰减；落到地板以下进入淘汰候选，宽限期后物理删除（擦除流程归 `D16-交付-治理合规.md`）。

**遗忘与压缩（分类处理）**：

| 该忘什么 | 怎么忘 |
|---|---|
| 工作 / 临时中间结果 | 运行结束即弃，不落持久层 |
| 过期的情节（旧任务的细节） | 衰减到地板后淘汰，保留统计摘要 |
| 被推翻的偏好 | 冲突消解后旧值降权并标记 superseded，宽限后删 |
| 高频但低价值的对话 | 压缩为情节摘要，丢弃逐轮原文 |
| 敏感数据 | 按主体擦除（结构化定位），非"覆盖写"式删除 |

> **压缩 ≠ 遗忘**：压缩是保留语义、丢弃形式（回指 `D04-运行时-上下文工程.md` 的 compaction）；遗忘是放弃语义。两者触发条件不同，不要用同一个机制。

**检索与注入（何时取回 / 注入哪个槽位）**：

- **取回时机**：会话开始（拉主体长期事实）、任务类型切换（拉相关程序/情节）、状态显式请求（工具触发）。**不做"每步都检索"**，那是上下文噪声的主要来源。
- **注入槽位**（与 `D04-运行时-上下文工程.md` 的槽位对应）：偏好与硬约束进**系统约束槽**；相关事实进**检索槽**；可复用流程进**技能/工具说明槽**。
- **注入纪律**：注入条目必须可溯源（`memory_refs`），以便发现注入导致的偏误或投毒时可回滚（`D10-质量-安全护栏.md`）。

## 5. 检查清单

### 5.1 「最小可行」

- [ ] 状态对象可完整序列化，且带 `schema_version`、`step`、`run_id` 三个字段
- [ ] 运行结束后，状态可以既不污染下一次运行，也不被下一次运行读取
- [ ] 检查点写入是原子的（不存在"读到一个半截状态"）
- [ ] 存在一条可执行的恢复路径，且**至少演练过一次**失败恢复
- [ ] 记忆写入接口会返回"写入 / 合并 / 拒绝"及理由，不是无条件写
- [ ] 三条边界被显式区分：状态不承担跨会话回忆，检查点不承担评测，记忆不承担运行内工作集

### 5.2 「生产就绪」

- [ ] 状态按作用域分域，且每个域声明了合并（归约）语义
- [ ] 检查点支持链式 / 时间旅行，且与 `schema_version` 迁移策略配套
- [ ] 状态 schema 的每次变更都有迁移脚本，旧检查点仍可恢复或明确拒绝
- [ ] 记忆分层有明确裁剪（启用哪些层），每层有 TTL 与写入门槛
- [ ] 写入门槛、合并阈值、衰减速率均可配置且**有默认理由**（写清由什么决定）
- [ ] 衰减按 `last_accessed_at` 计算
- [ ] 冲突事实保留双方并标记，而非静默取一条
- [ ] 每条记忆可定位到主体与来源运行（擦除与投毒排查前提）
- [ ] 恢复成功率、检查点大小、记忆注入条目数进入监控（回指 `D11`）；检查点与 trace 采集同源但存储分离

## 6. 常见陷阱

### 陷阱 1 · 把对话历史当唯一状态

**现象**：没有显式状态对象，靠 message 列表推断"当前进度""已确认约束"。
**根因**：起步时图省事，把 LLM 的对话上下文当成了状态容器。
**埋伏阶段**：设计（②）——设计状态 schema 时直接跳过。
**规避**：把必须持久化与断言的事实显式化为字段；对话历史只作叙述，不作事实源。

### 陷阱 2 · 检查点与 trace 混用

**现象**：用 trace 做恢复，或用检查点做评测/归因。
**根因**：二者都"记录了每一步"，被误认为同一种东西。
**埋伏阶段**：设计（②）——观测与持久化没有分开设计。
**规避**：按 §1.3 的对比表划界；二者可同源产出，但存储、粒度、消费者分开。

### 陷阱 3 · 状态整体快照导致写放大

**现象**：长时任务运行变慢，检查点写入成为瓶颈，且快照体积随步数线性膨胀。
**根因**：每步都整体序列化一个大状态，且状态里内联了大对象。
**埋伏阶段**：构建（③）——检查点实现时未做增量或引用外置。
**规避**：大对象外置为引用；检查点支持每 N 步 + 关键节点强制；状态分域以隔离高频小字段。

### 陷阱 4 · 记忆写入过松，检索被噪声淹没

**现象**：注入了很多"记忆"，模型反而更容易跑偏、出现矛盾。
**根因**：写入没有显著性门槛，"都先存下来靠检索排序"。
**埋伏阶段**：设计（②）——记忆层只定义了容量，没定义门槛。
**规避**：默认不写 + 四条显著性判据（§4.5）；把"一次会话注入条目数"纳入监控。

### 陷阱 5 · 恢复后重复副作用

**现象**：从检查点恢复后，之前已执行的订票 / 下单 / 写库动作被重复触发。
**根因**：检查点只保存了"状态值"，没保存"已执行哪些副作用及其结果"，缺少幂等索引。
**埋伏阶段**：设计（②）——检查点结构未包含幂等索引。
**规避**：检查点内带 `idempotency_index`；工具侧必须有幂等键（回指 `D06-运行时-工具与协议.md`）。

### 陷阱 6 · schema 变更无迁移，旧检查点静默失效

**现象**：加了字段之后，历史检查点恢复报错或恢复出错误状态。
**根因**：状态 schema 被视为内部实现细节，未版本化、无迁移。
**埋伏阶段**：构建（③）——schema 未纳入版本管理与门禁。
**规避**：`schema_version` 进检查点；恢复时校验版本，能迁移则迁移、不能则明确拒绝（回指 `D13-交付-部署运行时.md` 的版本与灰度）。

## 7. 反例

### 反例 1 · "把整段会话塞进状态，每次恢复都重放"

**做法**：状态对象里内联完整对话历史，检查点即整体快照。
**爆掉的方式**：两周后进入长会话场景，单次检查点写入从毫秒级涨到秒级，任务超时；同时上下文被历史淹没，模型开始遗忘当前目标。**在运营期以"越用越慢 + 越用越糊涂"的形式爆掉。**

### 反例 2 · "用向量库当记忆，写入不设门槛"

**做法**：每轮对话后把整段回复向量化入库，检索时 top-k 注入。
**爆掉的方式**：一个月后，检索召回的多是陈旧的、被用户后来推翻的表述；模型在矛盾条目间摇摆，出现"记错用户偏好"的投诉。**在运营期以"记忆越全越不准"的形式爆掉，且难以归因——因为每条记忆看起来都无害。**

### 反例 3 · "检查点做成了 trace 的别名"

**做法**：用观测系统里的 span 序列充当"检查点"，声称能恢复。
**爆掉的方式**：真正需要恢复时发现 span 里只有输入输出，没有中间状态与计划进度，无法继续执行；团队临时补状态，导致两套事实不一致。**在验证/运营交界处（④→⑤）以"声称能恢复但恢复不出来"的形式爆掉。**

### 反例 4 · "状态不分域，多分支并行写同一对象"

**做法**：多工具 / 多 Agent 并行，都直接写同一个扁平状态。
**爆掉的方式**：后写的覆盖先写的，出现"某工具的产出凭空消失"；覆盖语义下 trace 里也看不出丢失。**在构建期埋下，在并发量上来后以"偶发数据丢失、无法复现"的形式爆掉。**

## 8. 开放问题

- **检查点能否等价于"确定性重放"？** 一派主张：只要录制所有外部结果 + 幂等键，检查点就能确定性重放，可"从任意步继续"。另一派主张：模型的非确定性使"同检查点 → 同后续"不成立，重放只能保证**外部效果一致**而非**轨迹一致**，调试价值有限。两派把重放分别定义在副作用层与语义层，**前提不同，未收敛**；本库暂取"恢复用前者、调试用后者"，但未验证该拆分能否覆盖真实故障。
- **记忆分几层才够？** 一派主张六层齐全（不同类型记忆无法共用一套检索）；另一派主张三层（会话/情节/语义）即可（图层与程序层维护成本高于增量收益）。**分歧实质是"记忆质量上限由层数还是由写入策略决定"，尚无定量证据。**
- **遗忘该由谁触发？** 自动衰减派主张无需用户干预；显式管理派主张记忆必须可被用户查看、编辑、删除。二者对"用户预期"的假设不同，无统一结论。
- **检查点的保留期该多长？** 留久可回溯但放大存储与擦除成本，留短则失去事后追责。通常需按合规与业务风险联合标定。
