## 0. 总纲

> **Agent 开发的瓶颈已经从"模型会不会用工具"转移到"工程链路是否完整"。链路由五个阶段构成——定义 → 设计 → 构建 → 验证 → 运营，每个阶段末尾有一道门禁；不通过门禁就进入下一阶段，是绝大多数 Agent 项目返工的根因。** `[共识]`

具体表现：

- 跳过①定义，直接进②③写代码 → 做出来的东西没有成功标准，无法判断"能不能上线"，也无法评测。
- 跳过④验证，直接上⑤运营 → 靠用户投诉当测试，靠回滚当灰度。
- 有链路但没有门禁 → 每个阶段都在"差不多就行"的状态下流转，问题在最后一环集中爆炸。

本知识库的目标，就是**给链路的每一块配一篇"标准答案 + 设计方法 + 检查清单"**。

## 1. 为什么需要"链路视角"，而不是"组件视角"

### 1.1 当前状态

本目录 README 现有的主题索引是**组件视角**：评测、记忆、工具与 MCP、规划、多智能体、安全、可观测性、成本——按"技术模块"切分。

组件视角是必要的，但不完整，缺三样东西：

| 缺失 | 后果 |
|---|---|
| **总纲** | 没有共同术语和边界定义，8 篇文档之间必然重叠、必然出现同一概念两种叫法 |
| **定义阶段** | 缺"这个任务该不该用 Agent""自主度给到几级"的判断标准，技术选型全凭手感 |
| **交付阶段** | 缺部署、人机协作、治理，文档在"能跑通"处戛然而止，到不了生产 |

### 1.2 组件视角会产生的三类典型失败

1. **边界重叠**：「工具调用与 MCP」和「多智能体协同」都会讲工具契约与错误约定；「Agent 安全」和「治理合规」都会讲权限最小化。两篇文档各写一遍，读者不知道该信哪篇。
2. **顺序错乱**：先写「多智能体协同」，再发现连单 Agent 的上下文预算都还没定，协同协议设计无参照。
3. **没有门禁**：文档之间只有"相关"，没有"先决"。读者读完不知道自己的项目现在卡在哪一步。

### 1.3 解法

**用链路（阶段 + 门禁）作为主轴，用文档作为链路的横切产物。** 链路是唯一的、有序的；文档按链路阶段归位，每篇文档的"输入/输出"就是它上下游的门禁产物。这样边界由链路天然决定，不需要人为约定。

## 2. 从市场方案中抽象出的开发链路

### 2.1 抽象方法

不是照抄某一家框架的分层，而是从三组互相独立的来源中取交集：

| 来源组 | 代表 | 抽取的东西 |
|---|---|---|
| **厂商方法论** | Anthropic《Building Effective Agents》《Effective Context Engineering》、OpenAI Agents SDK 四原语（Agent / Handoff / Guardrail / Session） | 「什么该做 Agent、什么该做 workflow」「上下文是一等公民」「护栏是原语不是补丁」 |
| **运行时框架** | LangGraph、Claude Agent SDK、Google ADK、Microsoft Agent Framework、CrewAI、Pydantic AI | 「状态图 / 检查点 / 人机回环」「沙箱与工具执行」「多语言与协议互操作」 |
| **标准与合规** | MCP、A2A、OpenTelemetry GenAI semconv、OWASP LLM/Agentic Top 10 + Agent Control Standard | 「协议层怎么接」「遥测怎么发」「红线在哪里」 |

三者交集处就是"跨框架都成立"的部分——这才够格写进通用知识库。

### 2.2 五阶段链路

| 阶段 | 核心问题 | 关键产物 | 门禁（不通过不进入下一阶段） |
|---|---|---|---|
| **① 定义** | 这个任务该用 Agent 还是 workflow？成功长什么样？ | 任务契约（目标 / 边界 / 可用工具 / 完成条件）、自主度分级、风险分级 | **契约四要素齐全**：目标、边界、工具、完成条件能写成一句话且可验证 |
| **② 设计** | 用什么编排？上下文预算多少？ | 编排模式选型、状态 schema、上下文装配策略 | **预算与拓扑冻结**：上下文预算有数、循环有上界、失败有归口 |
| **③ 构建** | 状态怎么存、工具怎么接、模型怎么选？ | 状态定义、工具契约、协议接入、模型路由 | **接口冻结**：工具 schema 与状态 schema 进入版本管理，改动需评审 |
| **④ 验证** | 凭什么相信它？哪里会致命？ | 评测集与门禁、威胁模型与护栏、trace 语义 | **红线全 0 + 评测门禁达标**：越权率、跨租户泄漏率等硬门禁为 0 |
| **⑤ 运营** | 怎么上、怎么活、怎么不烧钱？ | 灰度与隔离方案、交互协议、成本与 SLO、治理与审计 | **灰度可回滚 + SLO 有定义 + 成本有上界** |
| **↺ 迭代** | 失败怎么回流成改进？ | bad case 分类、回流路径、验收标准 | **每条失败都有归口**：要么改契约、要么改上下文、要么改工具，不允许"重试一下就好了" |

> 关键点：**迭代不是第六个阶段，是从⑤回到①②③的回边。** 把迭代当独立阶段，会导致"迭代"变成没有输入输出的空话。

### 2.3 每个阶段的对标标准

| 阶段 | 首选对标物（写文档时必须核到的版本） |
|---|---|
| ① 定义 | Anthropic《Building Effective Agents》；OWASP Top 10 for Agentic Applications（ASI01–ASI10，2025-12） |
| ② 设计 | Anthropic《Effective Context Engineering》；OpenAI Agents SDK 四原语；LangGraph 状态图模型 |
| ③ 构建 | MCP 2026-07-28；A2A v1.0.1；各框架当前版本 |
| ④ 验证 | 本库 `agent-evaluation.md`；OpenTelemetry GenAI semconv；OWASP Agent Control Standard |
| ⑤ 运营 | OTel GenAI semconv；OWASP Agentic Top 10 的 ASI08/ASI10；A2A 的签名与多租户 |

## 3. 文档地图：18 篇

### 3.1 编号与命名规则

**文件命名格式固定为：`{编号}-{层级}-{主题}.md`**，全部存放在 `docs/universal/` 下。

示例：`D00-地基-总纲.md`、`D14-交付-人机协作.md`

| 字段 | 取值 | 说明 |
|---|---|---|
| **编号** | `D00`–`D17` | 表示**阅读与依赖顺序**，不是重要性排序；编号一经分配不再变更 |
| **层级** | `地基` / `运行时` / `质量` / `交付` / `迭代` | 五层分组，表示该文档在链路中服务的目标 |
| **主题** | 2–6 个汉字 | 该文档的唯一主题词，与编号一一对应 |

五层的含义：

| 层级 | 服务目标 | 包含 |
|---|---|---|
| **地基** | 想清楚 | D00–D03 |
| **运行时** | 做出来 | D04–D08 |
| **质量** | 证明它可信 | D09–D12 |
| **交付** | 上生产 | D13–D16 |
| **迭代** | 活下去 | D17 |

编排规则：

- 一篇文档一个主题，**一个主题只允许有一篇文档**。发现重叠时，先回本文改边界，再动文档。
- 跨文档引用的写法固定为 `` `D06-运行时-工具与协议.md` ``（带编号的完整文件名），不使用相对链接以外的简写。

- **必备**：缺了它，写不出一个"能被评测、能被信任"的 Agent。表现为——缺少本文档会导致工程上无法做决策，只能拍脑袋。

这个判据是可验证的：把某篇文档抽掉，问"下一个要做决定的人会不会卡住"。会卡住就是必备。

## 4. 每篇文档的规格（统一模板）

### 4.1 十三节结构

所有文档统一按以下顺序组织。**第 5、6、7 节是每篇文档的主体，必须写得最厚**——它们分别回答"为什么这么设计""行业上有哪些做法""具体怎么落地"。缺节需在文首显式说明原因。

| # | 章节 | 内容要求 | 篇幅参考 |
|---|---|---|---|
| 1 | **页眉** | 文档编号 / 层级 / 文件路径 / 适用范围 / 前置知识 / 对标版本 / 最后更新 / 可信度标注 / 来源规范 | 10 行 |
| 2 | **对标版本表** | 本主题涉及的外部标准与框架，含版本号、稳定性、迁移风险、对应本主题的哪一节 | 5–10 行 |
| 3 | **总纲** | 一段话讲清本主题的核心判断，并标可信度。必须是**可被反驳的断言**，不能是"很重要"这类废话 | 10–20 行 |
| 4 | **问题定义与边界** | 要解决的具体问题；显式写出**本文不讨论什么**，以及与其他 D 编号文档的边界切线 | 20–30 行 |
| 5 | **设计思路** | **为什么这么做**：第一性原理、不可回避的约束（注意力机制、token 成本、非确定性、外部系统的物理限制）、由此推导出的取舍逻辑。要让读者理解"规则背后的原因"，而不是记住规则 | 40–80 行 |
| 6 | **通用方案** | **行业上有哪些做法**：至少 3 种主流方案，每种写清 机制 / 适用条件 / 代价 / 不适用场景；给出选型判据（决策树或判断表）。禁止"只有一个正确答案"的表述 | 60–100 行 |
| 7 | **如何设计** | **具体怎么落地**：可执行的步骤序列、数据结构与接口形态、关键参数与其取值依据、伪代码或结构示意、分阶段实施路径。读者应能照着做出第一版 | 60–100 行 |
| 8 | **检查清单** | 可直接勾选的条目，分「最小可行」与「生产就绪」两档 | 20–30 行 |
| 9 | **常见陷阱** | 陷阱 + 根因 + 规避方式 + **在链路的哪个阶段埋下** | 30–50 行 |
| 10 | **反例** | 具体的错误做法及其代价，写成"如果这样做，会在什么时候以什么形式爆掉" | 20–30 行 |
| 11 | **开放问题** | 未收敛的分歧。**有争议的地方保留分歧，不要强行统一**；不得为空 | 10–20 行 |
| 12 | **参考来源** | 可追溯，含日期；区分官方规范 / 论文 / 厂商博客 | 10–20 行 |
| 13 | **修订记录** | 日期 / 变更 / 说明 | 3–5 行 |

**篇幅目标**：必备文档 ≥300 行；进阶文档 ≥250 行。**下限是硬约束**——低于下限说明 §2 设计思路 / §3 通用方案 / §4 如何设计 三节写得不合格。上限为参考值：进阶约 400 行、必备约 450 行；当主题的"必覆盖项"无法在区间内写完时允许超出，但**超过 600 行应检查是否存在应拆分或应归属其他 D 编号的内容**。

### 4.2 写作硬约束

- **对标版本必须写明**：不同版本的结论可能相反（例如 MCP 在 2026-07-28 前后是两套架构）。不写版本号的结论视为无效。
- **对标不是在文末列一堆链接**，而是在正文相应结论后面直接标出处与版本。
- **可信度标注不可省**：厂商博客的基准数字一律 `[共识]` 或 `[待验证]`，不得 `[已验证]`。
- **保留分歧**：行业未收敛的做法写清"两派各自的前提"，不要合成一个看似中立的第三条路。
- **禁止项目细节**：见 §7.1。

## 6. 阅读与写作顺序

| 层级 | 文档 | 顺序理由 |
|---|---|---|
| **地基** | D00 → D01 → D02 → D03 | D00 定边界（本文）；D01 定模板；**D02 是整个链路的起点**——没有任务契约与自主度分级，后面所有设计都失去判据；D03 决定拓扑，是 D04–D08 的共同前提 |
| **运行时** | D04 → D05 → D06 → D07 → D08 | 上下文决定状态怎么切（D04→D05）；状态决定工具怎么调（D05→D06）；工具与协议定了才谈得上多 Agent（D06→D07）；模型层是对前四者的优化，放最后 |
| **质量** | D09 → D10 → D11 → D12 | D09 已定下本文库的写法：坐标系、对比表、清单、可信度标注，其余文档对齐它的格式；安全与可观测是两条独立的验证腿；可靠性建立在可观测之上（不知道哪一步失败就谈不上降级） |
| **交付** | D14 → D13 → D15 → D16 | 交互协议先于部署（因为部署形态由交互协议决定：流式长连接还是异步任务）；成本性能需要 D08 与 D13 都就位；治理合规放最后，因为它约束前面全部 |
| **迭代** | D17 | 迭代闭环需要全部文档作为输入，最后写 |

**依赖关系不是任意的**：每一层内部的箭头都代表"后一篇的输入是前一篇的输出"。跨层可以并行（例如 D10 与 D11 无依赖），但**跨层不可倒置**。

## 7. 三条必须显式取舍的张力

### 7.1 通用知识 vs 项目落地：**通用库里不写项目细节**

本目录的收录原则已经写明"不收录单个项目的业务逻辑"。因此：

- 通用文档只写方法论、模式、清单、陷阱。
- **项目与通用知识的映射不写进本目录**。若要保留映射，另建项目侧文档（例如 `docs/` 下），在通用文档里只留一个中性化的"落地检查点"小节。
- 理由：一旦通用文档里出现 `TravelState` 或某个业务字段名，这篇文档就不能被下一个项目复用，本目录的前提即失效。

**这条张力在所有 16 篇待写文档里都会出现，必须提前定规矩。**

### 7.2 标准稳定性 vs 时效性

多处标准仍在 Development（OTel GenAI semconv）。两种极端都不对：

- 只写稳定标准 → 文档落后一整代，读者拿到的是过时结论。
- 只写最新实践 → 半年后文档全是错的。

**采取的规则**：正文以"当前最新版本"为准，但**每条结论必须带稳定性标记与迁移风险**；同时提供最小改动路径（例如 semconv 用环境变量显式 opt-in 而不改代码结构），使结论随版本漂移时只需改一处。

### 7.3 完备性 vs 可执行性

18 篇文档是完备性目标，但完备性会拖慢落地。取舍原则：

- **必备 12 篇**是可用性下限，未写完之前不建议启动演进型项目。
- **进阶 6 篇**可以按项目实际撞墙顺序补齐（例如撞到成本问题再补 D15）。
- 每篇文档内部同样分"最小可行"与"生产就绪"两档清单，允许读者只取前半。

## 8. 验收标准：什么叫"这篇文档写完了"

一篇文档达到以下全部条件，才可从 ⬜ 改为 ✅：

1. 页眉八个字段齐全，文件路径与实际存放位置一致。
2. 总纲里有一句**可被反驳**的核心判断，并标明可信度。
3. 对标版本表填写完整，每个外部标准的版本号可核验。
4. **§5 设计思路**写清了第一性原理与约束，读者能复述"为什么"，而非只看到规则。
5. **§6 通用方案**至少 3 种，每种都写了机制、适用条件、代价、不适用场景，并提供选型判据。
6. **§7 如何设计**给出了可执行步骤、数据结构或接口形态、关键参数取值依据，读者能照着做出第一版。
7. 检查清单可勾选，且分「最小可行 / 生产就绪」两档。
8. 至少 3 条常见陷阱，每条带根因与埋伏阶段。
9. 开放问题非空——如果一条开放问题都没有，说明查得不够深或写得过于笼统。
10. 全文无项目业务细节（见 §7.1）。
11. 每条数字符合 `数值（来源 · 日期 · 自报/复现）` 格式。
12. 必备文档 ≥300 行，进阶文档 ≥250 行（上限超出时按 §4.1 说明处理）。
13. README 的主题索引已同步更新。

## 9. 术语表（跨文档唯一口径）

| 术语 | 口径 |
|---|---|
| **上下文（context）** | 模型这一次推理能看到的全部 token：系统指令、工具定义、检索内容、历史、草稿、当前指令 |
| **上下文工程** | 对上下文的**装配、压缩、检索、冻结**做工程决策的实践，是 prompt engineering 在循环场景下的演进 |
| **状态（state）** | 一次运行内、编排器维护的结构化事实（目标、计划、进度、已确认约束） |
| **记忆（memory）** | 跨会话持久化的、经过筛选的高显著度事实，与状态严格分开 |
| **检查点（checkpoint）** | 状态快照，用于恢复与重放，不是记忆 |
| **轨迹（trajectory）** | 一次运行产生的完整动作序列（含工具调用、参数、结果），评测与观测的原子单位 |
| **工具契约（tool contract）** | 工具返回必须包含 状态 / 结论 / 范围 / 证据位置 / 下一步，而不只是一个裸结果 |
| **门禁（gate）** | 阶段末尾的通过条件，未通过不得进入下一阶段 |
| **护栏（guardrail）** | 运行时对输入、计划、工具调用、输出的强制检查点，是原语而非补丁 |
| **自主度（autonomy）** | 允许 Agent 在无人确认下执行的动作等级：只读 / 写入 / 下单 / 支付 |

## 10. 开放问题

- **必备度的判据是否够硬**？§3.3 的"抽掉会不会卡住"依赖主观判断，可能需要引入"没有本文档时，决策延迟与返工成本的量化估计"。
- **18 篇是否过细**？D08（模型层）与 D15（成本性能）存在天然重叠——模型选的直接后果就是成本。可能需要合并为"模型经济学"一篇；也可能因为读者角色不同（算法 vs 平台）而必须拆开。**暂保留拆分，待两篇都起草后回看。**
- **迭代（D17）与评测（D09）的边界**：bad case 回流本身属于评测闭环，D17 是否会退化成 D09 的重复内容？若起草时发现超过 30% 内容重叠，应合并。
- **是否需要"架构决策记录（ADR）"模板**？文档给的是通用答案，但每个项目的取舍理由无处存放，可能导致同一问题反复讨论。
- **标准仍在 Development 期间，本知识库如何避免成为"版本考古现场"**？目前靠 §7.2 的规则缓解，未验证是否有效。
