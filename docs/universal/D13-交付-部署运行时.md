## 0. 总纲

> **部署形态不是运维细节，而是由交互协议与任务时长反推出来的设计结论；先定部署形态再设计交互，几乎必然返工。** `[共识]`

这是本知识库把 D14 排在 D13 之前的原因：**交互协议决定部署形态**，而不是反过来。如果先选好了"异步任务队列 + 轮询"，却发现用户在澄清环节必须实时看到 Agent 的中间推理，那么整套传输、状态机与前端都要重做。

四条支撑判断：

1. **任务寿命必须与资源寿命解耦。** 用户会话、Agent 任务、承载进程三者的寿命数量级完全不同；把任务状态放进进程内存的设计，会在第一次滚动发布时崩掉。
2. **无状态是水平扩缩的前提，而协议正在主动向无状态迁移。** MCP `2026-07-28` 取消 `initialize` 握手与 `Mcp-Session-Id`，把会话状态从服务端移出——直接后果是 MCP 服务端可以像普通 HTTP 服务一样扩容，不再需要会话粘滞 `[已验证]`。
3. **版本不是一个维度，而是四个。** prompt / 模型 / 编排图结构 / 工具契约各自独立演进，组合数呈乘法增长；这是发布管理里最主要的成本来源，也是故障归因最难的一块。
4. **沙箱不是"安全边界"的同义词。** 隔离技术只决定内核层的爆炸半径；网络出口、文件系统范围、凭据范围、工具权限必须同时成立，任何一层有缺口，其余层都白做。这条与 OWASP LLM01（提示注入保持第 1）和 ASI02（工具滥用）直接相关 `[已验证]`。

## 1. 问题定义与边界

### 1.1 本文解决的问题

- 一个已通过评测的 Agent，应该以哪种**运行时形态**对外提供服务（同步、流式、异步、批处理），判据是什么。
- 需要执行模型生成的代码或调用不可信工具时，隔离边界应画在哪一层。
- 并发、排队、长任务、租约与幂等重入如何在部署层实现（机制在 D12，落地在这里）。
- 四个版本维度如何独立发布、灰度、回滚，如何避免组合爆炸。
- 检查点存储（状态快照）如何选型、迁移、备份、设保留期与冷热分层。
- 自建的 MCP 服务端与工具服务如何托管与扩缩。

### 1.2 本文不讨论什么

- **不讨论交互协议本身的设计**（事件类型、澄清机制、审批界面）。那属于 `D14-交付-人机协作.md`；本文只接受其结论作为输入。
- **不讨论可靠性机制的设计原理**（重试、熔断、幂等键、降级阶梯）。机制在 `D12-质量-可靠性.md`，本文讲这些机制在部署面如何落地。
- **不讨论多租户隔离与数据驻留**。那属于 `D16-交付-治理合规.md`；本文讲的是**资源隔离**（CPU/内存/网络/文件系统），不是合规意义上的租户边界。

## 2. 设计思路

### 2.1 第一性原理：三种寿命必须解耦

Agent 系统里同时存在三种寿命，它们相差好几个数量级：

| 寿命 | 典型量级 | 典型中断原因 |
|---|---|---|
| **用户会话** | 分钟到小时 | 用户关闭页面、网络切换 |
| **Agent 任务** | 秒到天（含人工等待、异步回调） | 下游不可用、等待审批 |
| **承载资源的寿命**（进程 / 容器 / Pod） | 分钟到天 | 滚动发布、扩缩容、OOM、节点回收 |

**部署形态的本质，就是决定"任务状态在哪个寿命层级上存活"。**

- 状态存在**请求**里 → 任务寿命被硬性绑死在单次 HTTP 请求上（天然受代理超时限制）。
- 状态存在**进程内存**里 → 任务寿命被绑死在进程上，滚动发布即中断。
- 状态存在**外部存储**里 → 任务寿命与资源寿命解耦，进程变成可丢弃的。

由此，任何"Agent 任务时长超过最外层超时"的场景，都只有一条路：**把任务状态外置，把进程变成无状态的执行器。**

### 2.2 不可回避的约束

| 约束 | 数量级 / 状态 | 对部署形态的强制影响 |
|---|---|---|
| **代理与负载均衡的空闲超时** | 通常是几十秒量级（例如 Cloudflare 对无数据连接约 100 秒后断开）`[共识]` | 长连接必须发心跳；否则连接会被中间层静默切断，表现为"任务跑了但前端断了" |
| **HTTP/1.1 每源连接数限制** | 浏览器侧 6 条/源（业界通用限制，标记为不修复）`[共识]` | 多标签页下的 SSE 会互相挤占；必须走 HTTP/2 多路复用或分域 |
| **协议无状态化** | MCP `2026-07-28` 已移除会话标识 `[已验证]` | 服务端可无粘滞扩缩，但"恢复上次会话"必须由客户端编排层自己实现 |
| **部署单元的不可变性** | 行业默认（容器镜像/不可变制品） | 运行中任务不能依赖本地磁盘；所有持久物必须在外部 |
| **任务状态写入的外部延迟** | 取决于存储选型，可跨数量级 | 写入频率决定了能切多细的检查点粒度 |
| **沙箱启动延迟** | 从毫秒到数百毫秒不等（各来源自报数字差异大）`[待验证]` | 交互式 Agent 每步都新建沙箱会吃掉交互延迟预算，需要池化或长驻会话 |
| **版本四维独立演进** | prompt / 模型 / 图结构 / 工具 | 组合数 = 四个维度取值的乘积；不做显式冻结就无法归因 |

### 2.3 由此推导出的三条核心取舍

**取舍一：宁可把长任务切成可恢复的短步骤，也不把长连接拉到小时级。**

长连接承载长任务会同时踩三个坑：中间层超时、部署时连接被切断、断线后的状态恢复无依据。切步骤的代价是"每步都要写状态"，收益是"进程随便重启"。只有交互本身需要实时感（如流式输出）时才维持长连接，且**连接只承载感知，不承载任务生命周期**。

**取舍二：宁可多花一次状态写入，也不把任务状态放进进程内存。**

进程内状态在开发期"更快"，但它把所有部署操作（发布、扩缩、迁移）都变成了高危操作。这条取舍的判据很简单：**如果滚动发布会让在途任务失败，架构就是错的。**

**取舍三：宁可版本组合显式枚举并冻结，也不隐式跟随最新。**

隐式跟随的表现是：prompt 文件被直接改在生产配置里、工具 schema 改了但没版本号、模型别名指向了会自动升级的通道。后果是"没人改代码但行为变了"，且**无法回滚到上一个已知良好状态**。四个维度必须各自有可寻址的版本，发布时冻结成一个四元组。

## 3. 通用方案

### 3.1 运行时形态选型

#### 形态 A · 同步请求-响应

**机制**：客户端发一次请求，服务端在单次 HTTP 请求内完成整轮 Agent 循环并返回最终结果。
**适用条件**：任务时长显著小于最外层超时（经验上留出 3–5 倍余量）；不需要中途展示过程；不需要中途人工介入。
**代价**：无法展示中间进展，长任务体验差；进程被请求占满，并发能力受限于 worker 数；任何一层的超时都会直接失败。
**不适用场景**：任务含人工审批；任务时长不确定（依赖外部回调）；需要流式反馈的交互。

#### 形态 B · 流式长连接（SSE / WebSocket）

**机制**：一次连接上持续推送事件（token、步骤、工具调用、审批请求、最终结果）；SSE 为单向（服务端→客户端），WebSocket 为双向。
**适用条件**：需要在生成过程中展示进展；单次生成时长在分钟级以内；客户端为浏览器或移动端（SSE 兼容性最好，WebSocket 适合需要客户端随时插话的场景）。
**代价**：连接需心跳维持（否则被中间层静默切断）；HTTP/1.1 下受每源连接数限制；断线重连需要事件序号与补发机制；服务端需要为每个连接保留上下文，扩缩时需要考虑连接排空。
**不适用场景**：时长小时级以上的任务（应改为形态 C，用连接只推送进度）；需要保证不丢事件且可回溯的场景（连接不提供持久性）。

#### 形态 C · 异步任务队列（提交 + 轮询/回调）

**机制**：客户端提交任务，立即获得任务标识；执行在工作进程中异步进行，状态写入外部存储；客户端轮询状态或接收回调。
**适用条件**：任务时长超过交互超时；含人工等待；需要保证"提交了就会执行"；需要按优先级排队。
**代价**：用户看不到"正在思考什么"，只能看到阶段化进度；需要额外的任务状态存储与清理逻辑；重复提交与幂等重入必须显式处理（见 `D12-质量-可靠性.md` §4.2）；端到端延迟增加一个轮询周期。
**不适用场景**：用户对首字延迟敏感的场景（对话式产品）。

#### 形态 D · 定时批处理

**机制**：由调度器周期性触发一批任务，无实时用户在场；失败整体重跑或按项重试。
**适用条件**：任务可幂等重跑；结果通过报告/通知交付；对时效性要求是小时级或天级。
**代价**：无法即时响应；错误发现延迟大；重跑成本可能很高（尤其模型调用）。
**不适用场景**：任何有实时交互需求的产品；含不可逆动作且无法补偿的流程（重跑即重复副作用）。

#### 形态选型判据

| 判断问题 | 若回答为 | 采用 |
|---|---|---|
| 任务含人工审批或异步外部回调？ | 是 | **形态 C**（进度可通过形态 B 的通道推送） |
| 单次任务 P95 时长是否显著小于最外层超时？ | 是（≤ 1/3 超时） | 形态 A 或 B |
| | 否 | 形态 C |
| 是否需要生成过程中的实时反馈？ | 是 | 形态 B（连接只承载感知） |
| 客户端是否需要在一轮生成中多次插话？ | 是 | 形态 B 的 WebSocket 变体；否则优先 SSE |
| 是否完全无实时用户？ | 是 | 形态 D |
| 是否需要按优先级区分任务？ | 是 | 形态 C（带优先级队列） |

### 3.2 沙箱与隔离

隔离的核心问题是：**被隔离对象有多不可信**。这决定了要付出多少启动与运行开销。

#### 方案 A · 容器（共享宿主内核）

**机制**：用命名空间与 cgroups 划分进程、文件系统与资源；与宿主共享内核。
**适用条件**：执行的代码是团队自己写的、经过评审的；工具全部为只读或受控写入；单租户环境。
**代价**：内核漏洞或配置错误即可逃逸；宽泛的挂载、凭据或网络权限会显著放大风险；"看起来隔离了"的心理安全感常导致其余边界被放松。
**不适用场景**：执行模型生成的代码；多租户执行；需要强隔离保证的合规场景。

#### 方案 B · 用户态内核（syscall 拦截，如 gVisor）

**机制**：在用户态实现一个内核来接管系统调用，容器发出的 syscall 不直接到达宿主内核，从而大幅缩小内核攻击面；镜像与容器工具链保持兼容。
**适用条件**：多租户、计算密集但 I/O 不极端的负载；希望复用现有容器镜像与编排。
**代价**：I/O 路径开销明显（各方自报在 10%–50% 区间，差异大，必须用真实负载自测）`[待验证]`；并非所有 syscall 都被完整支持，冷门系统调用可能行为不同。
**不适用场景**：对 syscall 兼容性要求极高的负载；已明确需要硬件级隔离边界的合规场景。

#### 方案 C · 微虚拟机 / 硬件虚拟化（如 Firecracker、Kata Containers）

**机制**：每个执行单元运行在带独立内核的轻量虚拟机里；逃逸需要同时突破客户机内核与 hypervisor。Kata 通过容器运行时接口与 Kubernetes 集成，对应用侧基本无侵入。
**适用条件**：执行不可信代码（模型生成的代码、第三方工具）；多租户；生产环境中的高风险执行路径。
**代价**：启动与内存开销高于容器（各方自报启动时间从百余毫秒到数百毫秒不等）`[待验证]`；需要虚拟化支持（嵌套虚拟化在部分环境不可用）；如果每步都新建沙箱，交互延迟会受影响，需要预热池。
**不适用场景**：纯受信任的内部自动化（成本不成比例）；无法使用 KVM 的环境。

#### 隔离选型判据

| 判断问题 | 若回答为 | 采用 |
|---|---|---|
| 是否执行模型生成或第三方提供的代码？ | 是 | 方案 C（微虚拟机） |
| | 否，但多租户共享执行环境 | 方案 B（用户态内核） |
| | 否，单租户且代码经过评审 | 方案 A（容器）+ 强化配置 |
| 是否允许出网？ | 需要 | 出口白名单（默认拒绝），不要用黑名单 |
| 凭据作用域？ | — | 按会话发放短时、单一用途凭据，不按服务发放长期凭据 |
| 是否需要文件系统持久性？ | 需要 | 用外部存储挂载，沙箱本身按一次性设计 |

> **重要**：以上任何一层都不能单独构成边界。隔离技术、网络出口、文件系统范围、凭据范围、工具权限、运行期监控是**六个必须同时成立的环**，攻击者或"过于字面理解指令"的 Agent 只需要一个缺口。

### 3.3 并发与长任务

#### 方案 A · 租约 + 心跳（Lease / Heartbeat）

**机制**：工作进程领取任务时获得一份带过期时间的租约，并周期性续租；进程崩溃则租约到期，任务被重新分配。
**适用条件**：任务需要独占资源；需要"恰好一个执行者"；执行时间有上界可估计。
**代价**：心跳与租约时长需要调参，两者关系错配会导致任务被反复抢占或故障回收过慢；需要处理"旧持有者仍在运行"的脑裂情况（通常靠外部系统的幂等键兜底）。
**不适用场景**：任务极小、领取与完成在毫秒级（开销大于收益）。

#### 方案 B · 无状态工作进程 + 外部状态

**机制**：进程本身不持有任何任务状态，每次从外部存储读取、执行、写回；同一任务可被任意进程处理。
**适用条件**：步骤足够细；状态可以在步骤边界安全地序列化。
**代价**：每步都有读写往返；需要保证同一任务的并发写不互相覆盖（乐观并发或分片归属）。
**不适用场景**：单步内部有大量不可序列化的中间状态。

#### 方案 C · 持久化执行平台（Durable Execution）

**机制**：把编排逻辑（工作流）与副作用（步骤）分开；工作流的推进由平台上记录的事件历史驱动，进程可任意重启并从中断点继续。
**适用条件**：任务寿命跨越部署；含人工等待；步骤昂贵不能重跑。
**代价**：主流程代码必须确定性（禁墙钟、禁随机、禁裸 I/O），所有非确定性必须封装进步骤；代码升级与在途执行冲突需要版本机制；多一套状态存储的运维。
**不适用场景**：秒级任务；无需恢复的纯计算。

#### 并发判据

| 判断问题 | 若回答为 | 采用 |
|---|---|---|
| 任务是否跨越部署窗口？ | 是 | 方案 C |
| 是否需要限制单资源的并发执行者？ | 是 | 方案 A（租约） |
| 步骤是否天然可序列化且细？ | 是 | 方案 B |
| 是否需要优先级与排队？ | 是 | 队列 + 方案 A 或 C |

### 3.4 版本与灰度

**四个必须独立版本化的维度**：

| 维度 | 变更频率 | 变更风险 | 版本化要求 |
|---|---|---|---|
| **Prompt / 系统指令** | 高（可能每天都在改） | 中：行为漂移，但通常可快速回滚 | 必须有内容寻址版本（哈希或语义版本），禁止直接改生产配置 |
| **模型** | 中 | 高：一次升级会同时改变所有能力与失败模式 | 禁止使用"自动指向最新"的别名；显式固定具体版本 |
| **编排图结构** | 低 | 高：影响状态 schema 与检查点兼容性 | 与状态 schema 版本绑定；变更需考虑在途任务的恢复兼容 |
| **工具契约** | 中 | 高：影响下游系统与权限边界 | schema 变更即破坏性变更；与新版本并存一段时间 |

**四种发布策略**：

| 策略 | 机制 | 适用条件 | 代价 |
|---|---|---|---|
| **影子流量** | 复制真实请求给新版本，结果不返回给用户，只做对比 | 想在不影响用户的前提下比较两个版本；有可靠的对比指标 | 成本翻倍；影子版本的副作用必须被禁止（只读或写沙箱） |
| **金丝雀** | 小比例真实流量走新版本，观察指标后逐步扩大 | 常规发布；指标可实时观测 | 需要一个能按维度切分的指标体系（见 `D11-质量-可观测性.md`） |
| **功能开关** | 代码中就位，通过配置开关启用 | 需要秒级回滚；同一版本需要多套行为 | 开关本身成为状态；长期不清理会形成组合爆炸 |
| **回滚** | 切回上一版本的完整四元组 | 任何发布 | 必须有"上一版本四元组"被完整记录且其依赖未被一并升级 |

### 3.5 选型判据汇总

| 你的处境 | 建议组合 |
|---|---|
| 对话式产品，单轮秒级以内 | 形态 B（SSE）+ 容器（不执行模型代码） |
| 编码/数据分析 Agent，执行生成代码 | 形态 B 或 C + 微虚拟机沙箱 + 出口白名单 |
| 含人工审批的业务流程 | 形态 C + 持久化执行 + 功能开关 |
| 跨天任务（对账、批报告） | 形态 D 或 C + 持久化执行 + 幂等重跑 |
| 多租户 SaaS | 形态 C + 用户态内核或微虚拟机 + 每租户资源配额 |

## 4. 如何设计

### 4.1 步骤序列

```text
① 任务画像          → 产出：任务时长分布（P50/P95/P99）、是否需要中途交互、是否含不可逆动作
② 形态选型          → 产出：运行时形态决策记录（含被否决的形态与理由）
③ 隔离边界设计      → 产出：六环检查表（隔离技术 / 出口 / 文件系统 / 凭据 / 工具权限 / 运行期监控）
④ 状态外置方案      → 产出：检查点存储选型 + 写入粒度 + 保留期策略（回指 D05 §4）
⑤ 并发与租约参数    → 产出：并发度 / 租约时长 / 心跳间隔 / 驱逐策略
⑥ 版本四元组定义    → 产出：ReleaseVector 与冻结流程
⑦ 灰度与回滚路径    → 产出：灰度阶段表 + 回滚演练记录
⑧ 发布门禁对接      → 产出：CI 门禁清单（回指 D09 §8）
⑨ 容量与成本核算    → 产出：单任务资源成本 + 峰值容量结论（回指 D15 §4）
```

### 4.2 数据结构与接口形态

字段名为形态示意，**语义不可省略**（`?` 表示非必填，其余必填）。

```python
from typing import Literal, Optional
from pydantic import BaseModel

class ReleaseVector(BaseModel):
    """发布四元组：四个维度必须同时冻结、同时记录、同时回滚。"""
    prompt_version: str        # 内容寻址（如哈希）或语义版本；禁止 "latest"
    model_id: str              # 显式具体版本；禁止自动升级别名
    graph_version: str         # 编排图 + 状态 schema 版本
    tool_contract_version: str # 工具契约版本（含 schema 哈希）

class DeploymentUnit(BaseModel):
    image_digest: str          # 不可变制品
    release: ReleaseVector
    isolation: Literal["container", "userspace_kernel", "microvm"]
    egress_policy: Literal["deny_all", "allowlist"]   # 禁止 "blocklist"
    credential_scope: Literal["per_session", "per_service"]  # 生产禁止 per_service 长期凭据
    max_concurrency: int
    resource_limits: dict[str, str]   # cpu / memory / disk / pids / network_bandwidth

class TaskLease(BaseModel):
    task_id: str
    holder_id: str             # 持有者标识，用于检测脑裂
    lease_expires_at: str
    heartbeat_interval_ms: int # 必须显著小于租约剩余时间
    attempt: int               # 用于幂等重入判断
    idempotency_key: str       # 恢复重跑时的去重依据

class CheckpointOpsMeta(BaseModel):
    """检查点的运维元数据（内容形态见 D05 §4）。"""
    run_id: str
    seq: int
    created_at: str
    size_bytes: int
    storage_class: Literal["hot", "cold"]     # 冷热分层的显式标记
    retention_until: str                      # 保留期到期时间，用于清理任务
    schema_version: str                       # 迁移用；与 graph_version 联动
```

**接口约定**：

1. `ReleaseVector` 必须写入每条任务记录——否则"行为变了但代码没变"这类问题无法归因（观测字段对齐 OTel GenAI semconv，见 `D11-质量-可观测性.md` §3）。
2. 容器/沙箱镜像必须用 digest 而非 tag，tag 可变且会让回滚指向不确定的内容。
3. `egress_policy` 只允许 `deny_all` 或 `allowlist`；黑名单式出口策略等于没有策略。
4. 检查点写入必须与 `graph_version` 关联，否则迁移在途任务时无法判断兼容性。

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 常见错误取法 |
|---|---|---|
| **运行时形态** | 由任务 P95 时长与最外层超时的比值、是否需要中途交互共同决定；只有比值 ≤ 1/3 时才考虑同步形态 | 按"感觉"选流式，结果中间层超时把长任务切断 |
| **心跳间隔 / 租约时长** | 心跳间隔应远小于租约时长；租约时长必须大于单步最长处理时间的 P99.9，否则正常任务会被反复抢占 | 两者设成同一个值 |
| **并发度** | 由下游配额（模型 RPM/TPM、工具 API 限额）与单任务平均占用时长共同决定，而不是由机器规格决定 | 按 CPU 核数设并发，忽略模型侧速率限制 |
| **沙箱生命周期** | 由隔离启动开销与单任务步数共同决定：交互式多步任务用长驻会话或预热池；一次性代码执行用一次性沙箱 | 每步新建微虚拟机，把交互延迟吃掉 |
| **检查点写入粒度** | 由"重跑一步的代价"与存储成本共同决定（同 `D12-质量-可靠性.md` §4.3） | 只按时间间隔写，导致恢复时回到很远的步骤 |
| **检查点保留期** | 由"最长任务寿命 + 审计要求 + 回放需求"三者取最大值；到期即清理，否则存储无界增长 | 永久保留，半年后存储成本超过模型成本 |
| **灰度比例与观察窗** | 由该维度变更的风险等级与指标收敛速度决定：模型升级需要更长观察窗（失败模式变化慢） | 每次都用固定 5% / 1 小时 |
| **冷热分层阈值** | 由"近 N 天内的访问概率"分布决定；典型是"最近一次任务 + 审计窗口内热存，其余冷存" | 全部热存 |

### 4.4 检查点存储运维

**选型**：

| 类型 | 机制 | 适用条件 | 代价 |
|---|---|---|---|
| **关系库** | 事务 + 结构化查询；检查点作为行/文档 | 需要按条件查询运行状态、需要事务保证、团队已有运维能力 | 高写入频率下成为瓶颈；大字段（长上下文快照）会让表膨胀 |
| **KV 存储** | 按 key 读写，延迟低、扩展简单 | 由 run_id + seq 直接寻址，不需要复杂查询 | 缺少跨键查询能力，运维分析要靠旁路导出 |
| **专用持久化执行平台** | 平台托管事件历史与重放 | 任务需要跨部署恢复、含人工等待 | 引入额外组件与供应商依赖；主流程代码受确定性约束 |

**四项必须提前定好的运维决策**：

1. **迁移**：状态 schema 变更时，在途任务怎么办？三种策略——只读旧版本（旧任务按旧 schema 跑完）、双向兼容（新代码能读旧 schema）、强制终止（代价最低但会丢任务）。**必须先选一个**，否则第一次 schema 变更就会卡死。
2. **备份与恢复**：检查点丢失等于任务丢失。恢复目标（RTO/RPO）应与任务寿命成正比——跨天任务的检查点存储需要真正的备份，秒级任务的可以重建。
3. **保留期与清理**：必须有自动清理任务；清理策略要考虑"任务仍可能被恢复"的窗口（正在等待人工审批的任务，其检查点不能被清理）。
4. **冷热分层**：热存用于活跃任务与最近完成的任务；冷存用于审计与回放。分层键通常是任务状态与完成时间，而不是数据大小。

### 4.5 分阶段实施路径

**最小可行**

1. 完成 §4.1 的 ①②③：任务画像决定形态；隔离边界至少把"执行模型生成代码"的路径单独隔离出去。
2. 状态外置：任务状态写入外部存储，进程可随时重启。
3. 版本显式化：禁止 `latest` 风格的模型与 prompt 引用，四元组写入任务记录。
4. 出口默认拒绝，只放行必需端点。
5. 发布门禁接入 CI：评测门禁（`D09-质量-评测.md` §8）不通过则拒绝发布。

**生产就绪**

6. 四元组的灰度能力：能按比例、按租户或按任务类型切流；影子流量只跑只读路径。
7. 回滚演练：定期做一次完整回滚，验证上一版本四元组的全部依赖仍然可用。
8. 检查点存储完成迁移/备份/保留期/冷热分层四项运维决策，并有自动清理任务。
9. 沙箱池化：交互式路径使用预热池，避免每步冷启动。
10. 自建工具服务的水平扩缩：依靠协议无状态化（MCP `2026-07-28`）去掉粘滞会话，按普通无状态服务扩缩 `[已验证]`。
11. 容量与成本核算：把单任务的资源占用与模型开销合并成单位成本，作为发布门禁的一项（见 `D15-交付-成本性能.md`）。

## 6. 常见陷阱

### 陷阱 1 · 把长任务放在长连接里

**现象**：任务跑到 3 分钟时前端显示"连接断开"，后端却仍在执行；用户重试导致同一任务被提交两次。
**根因**：连接被中间层按空闲超时切断，而任务生命周期与连接生命周期绑在一起。
**埋伏阶段**：**设计**（形态选型时没区分"连接承载感知"与"连接承载任务"）。
**规避**：任务状态外置；连接只推送进度；断线后凭任务标识重新订阅，而不是重新提交。

### 陷阱 2 · 版本组合爆炸导致无法归因

**现象**：表现变差，但四个维度都在最近两周内改过，无法确定是哪一个；回滚时发现"回滚了 prompt 但模型已经被平台自动升级"。
**根因**：四个维度没有独立版本化，也没有在任务记录里冻结四元组。
**埋伏阶段**：**设计**。
**规避**：四元组冻结并写入任务记录；模型禁止使用自动升级别名；一次只变一个维度（与 `D09-质量-评测.md` 的"一次只改一个变量"同源）。

### 陷阱 3 · 沙箱只做了隔离层

**现象**：隔离技术选得很强（微虚拟机），但逃逸或数据外泄仍然发生了。
**根因**：出口策略过宽、凭据按服务长期发放、文件系统挂载了不该挂载的目录、工具权限未按最小化收敛。隔离只防内核级逃逸，不防"合法地调用被允许的东西造成损害"。
**埋伏阶段**：**构建**。
**规避**：六环逐项检查；出口默认拒绝 + 白名单；凭据按会话短时发放；对生成代码与执行代码之间加验证/审批门（回指 `D10-质量-安全护栏.md` §5）。

### 陷阱 4 · 检查点存储被当成业务数据库用

**现象**：半年后存储成本超过模型调用成本；备份窗口越来越长；清理任务误删了仍在等待审批的任务。
**根因**：检查点被永久保留、没有保留期、没有冷热分层，也没有"任务仍可能恢复"的判定条件。
**埋伏阶段**：**运营**。
**规避**：保留期由"最长任务寿命 + 审计窗口"决定；清理前必须排除"仍在等待人工/外部回调"的任务；冷热分层按访问概率而不是数据大小。

### 陷阱 5 · 灰度在生产依赖未就绪时开始

**现象**：金丝雀版本因为缺少某个权限或缓存而表现差，团队据此判断"新版本不行"，实际上只是环境差异。
**根因**：灰度只切流量，没有保证新旧版本运行环境等价（配置、凭据、下游连接、缓存预热）。
**埋伏阶段**：**验证**。
**规避**：发布前做环境等价性检查；金丝雀阶段同时观察**新旧版本**的同一组指标，而不是只看新版本。

### 陷阱 6 · 每步新建沙箱

**现象**：编码类 Agent 的交互体验极差，每步工具调用都要等几百毫秒到数秒的沙箱启动。
**根因**：把"一次性沙箱"的模式套用到多步会话上。
**埋伏阶段**：**设计**。
**规避**：区分两种用法——不可信代码执行用一次性沙箱；多步会话用长驻会话或预热池。启动开销的具体数字必须用真实负载自测，不要照搬外部数字。

## 7. 反例

### 反例 1 · 用同步接口承载 20 分钟的任务

**做法**：把 Agent 任务做成一个 HTTP 接口，靠把负载均衡超时调到很大来"解决"。
**爆掉的方式**：所有中间层（网关、CDN、客户端 SDK、移动网络）都有自己的超时，只调了一层没有用。**爆发时间点是任务时长第一次超过最短的那层超时**；表现为随机比例的"连接重置"，且与任务复杂度相关——团队会误判为"复杂任务本身有问题"。

### 反例 2 · 用"最新"作为模型版本

**做法**：配置里写模型别名，跟随平台的最新版本；理由是"自动获得能力提升"。
**爆掉的方式**：某次平台静默升级后，工具调用格式与失败模式同时改变，评测集通过率下降但没人改过代码。**爆发时间点在升级后的下一次评测或第一次线上异常**；更糟的是回滚无处可回——因为你不知道"上一个版本"是哪个。

### 反例 3 · 把沙箱当成安全边界就收工

**做法**：把 Agent 放进强隔离的微虚拟机，认为安全措施已完成。
**爆掉的方式**：沙箱内可以自由出网、持有长期凭据、可读挂载的共享目录；Agent 被注入后在这个"安全"环境里合法地调用工具完成数据外泄。**爆发时间点通常是一次安全评审或一次真实事件之后**——因为此前的所有监控都显示"没有任何逃逸"。

### 反例 4 · 检查点与业务库共用实例

**做法**：检查点表就建在业务数据库里，"反正都是数据"。
**爆掉的方式**：Agent 高频写检查点把数据库连接池占满，业务查询开始超时；而后为保住业务把检查点写入改成"尽力而为"，长任务恢复能力实际失效。**爆发时间点是并发任务数上量的那一次**。

## 8. 开放问题

**⑴ 无状态运行时与有状态运行时，哪一个应该是 Agent 平台的默认？**

- **无状态派**：进程必须可随意丢弃，状态一律外置；只有这样才能享受成熟的容器编排、真正的水平扩缩和零成本滚动发布。
  前提：任务可以被切成足够细的边界，且每一步的状态可以低成本序列化。
- **有状态派**：Agent 的"工作记忆"很难完全序列化，强行外置会导致每一步都要重新装配上下文，既慢又贵；不如接受有状态运行时，用持久化执行平台来管理状态与恢复。
  前提：任务步数多、单步上下文大，且平台能力足以支撑。
- **未收敛的分歧点**：当单步上下文成本高于状态写回成本时，"无状态"的经济性会反转。行业目前没有公认的拐点。

**⑵ 沙箱隔离强度与交互延迟如何权衡？**

- **强隔离派**：默认使用硬件虚拟化边界，用预热池来抵消启动开销，宁可多花资源。
  前提：多租户或执行不可信代码。
- **轻隔离派**：多数 Agent 执行的其实是受控的工具调用而非任意代码，用容器 + 严格出口与凭据治理的性价比更高。
  前提：代码来源可信、工具面收敛。
- 两派真正的分歧在于**"是否真的需要执行任意代码"**。如果答案是否，争论本身消失。

**⑶ 灰度应该按流量比例，还是按用户/任务类型分层？**

- **流量比例派**：实现最简单，指标最容易聚合。
  前提：流量同质。
- **分层派**：真实流量的长尾分布极端不均，按比例切会长期只覆盖简单用例；应按高风险/高价值切片优先灰度。
  前提：有可靠的任务分类与切片指标能力。
- **分歧点**：分层派能更早发现问题，但会引入选择偏差，指标与全量不可直接比较。

**⑷ 检查点的保留期应该由合规要求还是由工程成本决定？**

- 合规方通常给出下限（必须保留多久），工程方给出上限（保留多久还划得来）。两者冲突时（例如审计要求保留两年而任务平均寿命两小时），目前没有通用的折中方案，只有"热存短期 + 冷存合规期"这类分层做法，其成本模型尚缺少公开的成熟实践。
