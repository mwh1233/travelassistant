## 0. 总纲

> **治理与合规的成败取决于"结构上做不做得到"，而不是"政策上写得好不好"。如果擦除无法落到记忆与检查点的存储结构上，隐私政策就只是一句声明；如果审计记录的是最终输出而不是授权与调用链，任何"不可否认"的承诺都无法兑现。** `[共识]`

可反驳点：对于只读、无个人数据、不对外提供服务的内部工具，治理确实可以停留在政策层，本断言不成立。断言的适用范围是**处理个人数据、或多租户、或需要向第三方举证**的 Agent 系统。

1. **治理要求的可执行性是可检验的**。任何一条治理要求，都必须能被翻译成"系统属性 → 可测断言"；翻译不出来的要求，落地时一定会变成人工承诺。
2. **跨租户泄漏是硬门禁，目标值为 0**。`D09-质量-评测.md` §4.4 已把安全合规列为一等评测目标、§8 把关键安全项设为 0 容忍；本文承接的是**结构上如何保证它为 0**。
3. **擦除的难点在副本，不在主库**。向量索引、检索缓存、检查点、备份、日志、评测数据集都是副本；只删主库等于没删。
4. **Agent 的供应链比传统软件更长**。模型、工具、MCP server、依赖库、prompt 版本共同决定行为，任一项变更都可能改变合规结论，因此需要物料清单而不是部署快照。

## 1. 问题定义与边界

### 1.1 本文解决的问题

- 如何选择并落地**租户数据边界**的隔离级别，使跨租户泄漏在结构上难以发生，并且可被检测。
- 如何设计**审计**：谁在何时授权 Agent 做了什么、是否可不可否认、决策链如何可追溯、保留期与访问控制怎么定；以及如何生成与维护 **AgBOM（Agent 物料清单）**，并与既有供应链风险流程对接。
- 如何把**数据保留与擦除**要求落到分层记忆与检查点上，包括擦除的传播范围与**验证方式**。
- 如何设计**配额与速率限制**，同时服务于成本防护与滥用防护；如何对**第三方模型与供应商**做风险评估（数据使用条款、可用性承诺、变更通知、模型弃用）。
- 如何把外部**合规要求映射**到系统属性，并明确"谁审批、谁负责、例外怎么走"。

### 1.2 本文不讨论什么

- **不讨论运行时技术强制点本身**（输入过滤、权限最小化、沙箱、审批门）——归 `D10-质量-安全护栏.md`；本文讨论的是这些控制点之上的制度、审计与举证。
- **不讨论分层记忆的内部结构与写入策略**——归 `D05-运行时-记忆与状态.md`；本文只要求它提供"可擦除"的结构前提。
- **不讨论 trace 的采集口径与字段命名**——归 `D11-质量-可观测性.md`；本文规定审计所需的额外属性与保留要求。
- **不讨论部署形态与网络隔离的实现**（VPC、命名空间、节点池）——归 `D13-交付-部署运行时.md`；本文只决定"需要哪种隔离级别"。
- **不提供法律意见**，也不做跨境数据流动的完整法律分析。本文给出的是"合规要求 → 系统属性"的翻译方法，具体适用性与解释必须由法务或外部顾问判断。

## 2. 设计思路

### 2.1 第一性原理：治理要求必须能被翻译成三步，翻译不出来的都是空话

任何一条治理或合规要求，只有走完下面三步才算真正落地：

```text
① 法规 / 政策条款      → ② 系统属性（可设计的结构）  → ③ 可测断言（可自动检验）
"用户可要求删除数据"      "每条记忆记录带主体标识，        "对一个测试主体发起擦除后，
                        且所有派生副本可通过该标识枚举"   全部副本中该标识的记录数为 0"
```

**第二步是瓶颈**。多数团队的失败不是在①（知道要求）或③（知道要测），而是在②——他们把要求直接变成流程动作（"收到邮件后人工去删"），而不是结构属性，导致擦除永远是抽查、审计永远是抽样、隔离永远靠自觉。

由此推导出的设计原则：**凡是要求"可证明"的东西，就必须在写入时就把证明所需的字段写进去**。审计字段、主体标识、租户标识、AgBOM 条目都属于这一类——它们在写入时刻的成本几乎为零，在事后补齐的成本极高。

### 2.2 不可回避的六个约束

| 约束 | 性质 | 直接后果 |
|---|---|---|
| **记忆与检索是分层持久化的** | 架构性质 | 擦除必须逐层可达。向量索引里删除一条记录不等于其语义影响消失（同一事实可能存在于摘要、检查点、缓存、备份中） |
| **日志倾向不可变** | 工程权衡 | 一旦追求"不可篡改"，就更难支持"被遗忘"；保留期与访问控制必须在设计期就定，事后无法两者兼得 |
| **隔离级别与成本正相关** | 经济约束 | 行级隔离最省，部署级隔离最贵。选择隔离级别等于选择成本结构，必须先量化泄漏的后果再定级 |
| **第三方模型是不可控依赖** | 供应链性质 | 条款可变、默认值可变、模型可弃用。合规结论依赖于供应商行为，因此必须写成**可复核的假设**而不是结论 |
| **协议身份已与无状态解耦** | MCP `2026-07-28` 取消 `initialize` 与 `Mcp-Session-Id` `[已验证]` | "这个工具是哪来的、谁授权的"不能靠会话推断，必须以清单方式显式登记 |
| **合规时点由外部给定** | 法律性质 | 生效时间不随工程进度调整；只能通过分阶段实施与明确的缺口登记来管理，不能靠"还没查到我们" |

### 2.3 由此推导出的三条取舍

**取舍一：宁可牺牲部分灵活性，也不做跨租户共享的语义缓存。** 语义缓存把一个租户的查询结果复用给另一个租户，是最隐蔽的跨租户泄漏路径——它不产生任何错误日志，只产生"另一个客户的答案"。缓存键必须包含租户边界，或者缓存本身按租户分区。

**取舍二：宁可保留期更短、证据更少，也不留"反正没人查"的日志。** 未定义保留期的日志是负债：既扩大泄漏面，又扩大擦除面。保留期必须由举证需要决定——需要举证多久就留多久，其余到期即删。

**取舍三：宁可拒绝一个供应商，也不接受不可审计的黑箱依赖。** 若供应商无法提供足够的清单信息与变更通知，它在故障与事故中就不可归因。选项有三个：换供应商、把该依赖降级为不可信数据源（`D10-质量-安全护栏.md` 的信任边界）、或显式登记为已知风险并纳入例外流程。**选"忽略"不在选项中。**

## 3. 通用方案

治理在本主题下可拆成四组独立决策。每组给三种以上选项，末尾给组合选型判据。

### 3.1 隔离级别

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 行级隔离** | 所有租户共用表，每行带租户标识；查询强制注入租户条件（推荐用数据库行级安全策略而非应用层拼接条件） | 租户数量大、数据量小、泄漏后果可承受或有合同兜底 | 单条查询写错就可能全量泄漏；需要独立的自动化测试覆盖每一条查询路径 | 处理健康、金融、政务等高敏感数据 |
| **B · schema 级隔离** | 每租户一个 schema / 命名空间，共用同一数据库实例；连接时绑定 schema | 租户数量中量级（数十到数百），需要比行级更强的边界 | 迁移与 schema 变更需要批量执行；连接池与元数据开销上升 | 租户数量上千（元数据管理成本失控） |
| **C · 库级隔离** | 每租户独立数据库实例或独立凭据 | 租户数量较少、需要独立备份与独立擦除 | 运维成本随租户数线性增长；跨租户聚合分析困难 | 长尾小客户占多数的 SaaS |
| **D · 部署级隔离** | 每租户（或每组租户）独立部署单元与独立存储 | 强监管、合同明确要求物理或逻辑专享、或需要独立版本节奏 | 成本最高；需要自动化部署与配置管理；版本碎片化 | 免费或低客单价产品 |

**补充手段（可与任一档叠加）**：每租户独立加密密钥。它把"擦除"转化为"销毁密钥"（crypto-shredding），在密钥不可恢复的前提下，密文残留不再构成可读数据。**前提是该租户的数据与派生索引都用同一密钥体系加密，且密钥销毁有独立的审计记录。**

### 3.2 数据擦除

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 逐层物理删除** | 枚举全部副本（主库、向量索引、缓存、检查点、备份、日志、评测集），对其中的主体记录执行删除 | 副本清单可控、有主体标识贯穿写入链路 | 备份与不可变日志难以物理删除；删除作业本身需要重入与幂等 | 备份为追加不可变、或日志已外出到第三方 |
| **B · 加密擦除（crypto-shredding）** | 每主体或每租户独立密钥，擦除 = 销毁密钥 | 数据以密文形式贯穿全链路；密钥管理已独立 | 密钥粒度越细，密钥管理复杂度越高；加密对检索与缓存的性能有影响 | 存在必须明文持有的副本（如某些报送文件） |
| **C · 定期重建索引 / 缩短保留期** | 不追求单条精确删除，改为周期性从源头重建全部派生索引，并把保留期压到必要下限 | 派生索引可重建、成本可接受 | 擦除有时延（不为 0）；重建窗口内仍存在残留 | 要求"即时擦除"且不可延时的场景 |

**共同要求**：无论哪种方案，都必须能回答"擦除是否完成"——即一次擦除产生一张**擦除凭据**，列出被触及的副本、每条副本的处理结果与时间戳。没有凭据的擦除无法向审计方举证。

### 3.3 审计与不可否认

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 应用日志 + 结构化字段** | 把授权、工具调用、策略判定写入应用日志，与业务日志同库 | 起步阶段、内部举证 | 无防篡改；与应用库同权限，事故方可能同时是日志方 | 需要向外部证明"日志未被修改" |
| **B · 签名事件流** | 每条审计事件带签名或哈希链（前序哈希），形成可验证的追加序列 | 需要防篡改、需要事后证明顺序 | 需要密钥管理与验证工具链；密钥轮换影响验证 | 事件量极大且成本敏感的场景 |
| **C · 双写：OTel 遥测 + OCSF 汇入 SIEM** | 运行期按 OTel GenAI semconv 发 span，审计类事件按 OCSF 输出并汇入企业 SIEM / XDR | 组织已有 SIEM；需要与既有安全流程打通 | 需要两套口径的映射与一致性核对；semconv 仍在 Development，属性名会变 | 没有 SIEM 的小团队（此时方案 B 更合适） |

> **ACS 口径**：OWASP Agent Control Standard 把上述能力组织为"被观测 Agent 暴露声明式钩子 → Guardian Agent（策略权威）返回 allow / deny / modify 三类裁决"，并通过 OTel + OCSF 输出遥测、通过 CycloneDX / SWID / SPDX 输出 AgBOM 的理念 `[共识]`（OWASP Agent Control Standard · 2026-09 · 官方项目说明；第三方分析见 §9）。**注意其成熟度**：规范处于 v0.1 公众预览阶段，参考实现与 AgBOM mapper 分别在后续版本规划中 `[共识]`。**正确用法是把它当作架构方向与勾选清单来规划，而不是当作当下可直接采购/部署的控制措施。**

### 3.4 AgBOM（Agent 物料清单）的生成方式

先明确**必备条目**：模型（含版本与来源）、工具（含 schema 版本与权限）、MCP server（含来源与版本）、依赖库、prompt 版本、检索数据源与版本、护栏策略版本、Guardian / 策略引擎版本。

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 手工清单** | 人工维护一份清单文档，随发布更新 | 组件极少、变更不频繁的起步阶段 | 必然腐化；与实际部署不一致且无人察觉 | 组件数超过一屏、或月变更超过一次 |
| **B · 构建期从配置派生** | 在 CI 中从编排图定义、工具注册表、依赖锁文件、prompt 仓库派生清单，输出 CycloneDX ML-BOM | 已有版本化配置与 CI | 需要把运行时才发现的组件（动态发现的 MCP 工具）也纳入 | 运行期会动态挂载能力的系统 |
| **C · 运行期动态清单（Capability Discovery）** | 运行期发现能力即登记，清单持续更新 | MCP server 动态接入、工具按租户差异化开放 | 清单本身成为高写入负载对象；需要版本化与变更告警 | 对启动延迟敏感的服务（登记扫描有开销） |

**格式选择**：三种格式不是竞品，实践中常并行使用 `[共识]`（第三方对比分析 · 2026 · 见 §9）。**CycloneDX ML-BOM**：OWASP + Ecma TC54 维护，ECMA-424，ML-BOM 自 v1.5 引入、现行 v1.7（2025-10），工具生态最广，适合 **CI/CD 内自动生成与安全工具链消费**。**SPDX 3.0 AI Profile**：Linux Foundation 维护，SPDX 3.0（2024-04）引入 AI Profile，3.0.1 经 OMG（2025-03）通过，模型与数据集是一等元素，适合**监管报送与审计文档**。**SWID**（ISO/IEC 19770-2）：以标签标识软件组件身份，适合**组件身份声明**与既有资产管理体系对接。

**选型判据**：内部自动化为先 → CycloneDX；对外报送与法律合规为先 → SPDX 3.0 AI Profile；两者都需要时用转换工具互通，不必二选一 `[共识]`。

### 3.5 组合选型判据

```text
第一步：量化泄漏后果
  ├─ 涉及人身安全 / 法定义务 / 强监管 → 至少 §3.1 的 C 或 D 档，必配 §3.2 的 A 或 B
  └─ 以商业损失为主                  → 至少 B 档，必配 §3.2 的 C（缩短保留期 + 周期重建）
第二步：外部是否需要举证
  ├─ 需要   → §3.3 选 B 或 C（签名事件流 / 双写 SIEM），且必须有擦除凭据
  └─ 不需要 → §3.3 选 A，但仍须定义保留期与访问控制
第三步：组件是否会被运行期改写
  ├─ 会   → §3.4 选 C，并为清单变更设告警
  └─ 不会 → §3.4 选 B（构建期派生）
第四步：两个否决条件（命中即先修，其余方案都不足以补救）
  ├─ 存在跨租户共享的缓存、索引或微调产物
  └─ 存在无主体标识的持久化副本（无法被擦除枚举）
```

## 4. 如何设计

### 4.1 步骤序列

| # | 步骤 | 产出物 |
|---|---|---|
| 1 | 给每一类持久化数据打三个标签：租户 / 数据主体 / 保留期；并画信任边界，标出哪些依赖是第三方、哪些数据会离开边界 | 数据资产台账（含副本清单）+ 数据流与信任边界图 |
| 2 | 按 §3.1 定隔离级别，并把"租户条件注入"做成不可绕过的机制（优先数据库策略而非应用层约定） | 隔离设计说明 + 跨租户泄漏测试方案 |
| 3 | 定义审计事件的最小字段集（见 §4.2），先在写入侧落地；同时定义保留期与访问控制矩阵 | 审计事件 schema（版本化）+ 保留策略表 |
| 4 | 实现擦除路径：主体 → 副本枚举 → 逐副本执行 → 生成擦除凭据 | 擦除作业 + 凭据模板 |
| 5 | 生成 AgBOM 并与发布流程绑定（每次发布刷新清单并保留历史版本） | AgBOM 产物 + 变更日志 |
| 6 | 建配额与速率限制，区分"成本防护"与"滥用防护"两个目标 | 配额策略 |
| 7 | 对每个第三方依赖做一次风险评估（见 §4.3 的评估项） | 供应商风险台账 |
| 8 | 建治理组织面：审批人、责任人、例外流程与复审周期 | 治理章程（一页即可） |

### 4.2 数据结构与接口形态

```python
from pydantic import BaseModel, Field
from typing import Literal, Optional
from datetime import datetime

class DataAsset(BaseModel):
    # 数据资产与副本登记：擦除的完备性直接取决于这张表是否完整
    asset_id: str                              # 必填
    layer: Literal["state", "working_memory", "session_memory",
                   "episodic", "semantic", "graph", "procedural",
                   "checkpoint", "cache", "log", "backup", "eval_set"]  # 必填：副本类型
    tenant_id: Optional[str]                   # 必填（多租户场景必填，单租户填常量）
    subject_id_field: Optional[str]            # 必填：主体标识所在字段名；为空即"不可擦除"
    retention_days: int                        # 必填：保留期，由举证需要决定
    deletable_online: bool                     # 必填：在线副本=可即时删；离线备份=否
    key_ref: Optional[str]                     # 选填：加密密钥引用，走加密擦除时必填

class AuditEvent(BaseModel):
    # 审计事件：字段对齐 OTel GenAI semconv（Development）与 OCSF 的通用维度
    event_id: str                              # 必填
    occurred_at: datetime                      # 必填
    actor_identity: str                        # 必填：发起者（人 / 服务 / Agent）
    on_behalf_of: Optional[str]                # 选填：代理链上游主体，用于多 Agent 场景
    agent_identity: str                        # 必填：执行动作的 Agent 版本标识
    tenant_id: str                             # 必填：租户边界
    action: Literal["authorize", "tool_call", "policy_verdict",
                    "data_access", "data_erasure", "model_change"]  # 必填
    resource: str                              # 必填：被操作对象
    policy_ref: str                            # 必填：命中的策略版本；缺此项无法复盘
    verdict: Optional[Literal["allow", "deny", "modify"]]   # 选填：策略裁决结果
    trace_id: str                              # 必填：与遥测 trace 关联
    prev_hash: Optional[str] = None            # 选填：哈希链前序，防篡改
    signature: Optional[str] = None            # 选填：事件签名

class AgBOMEntry(BaseModel):
    component_type: Literal["model", "tool", "mcp_server", "library",
                            "prompt", "data_source", "guardrail", "policy_engine"]  # 必填
    name: str                                  # 必填
    version: str                               # 必填：不可用 "latest"
    source: str                                # 必填：来源（供应商 / 内部 / 仓库）
    scope: list[str]                           # 必填：可见范围（租户 / 环境）
    data_classes: list[str]                    # 选填：该组件可接触的数据类别
    known_risks: list[str] = Field(default_factory=list)  # 选填：已登记风险
    added_at: datetime                         # 必填
    supersedes: Optional[str] = None           # 选填：被本条目替换的历史条目

class ErasureReceipt(BaseModel):
    # 擦除凭据：没有它，擦除无法向审计方举证
    request_id: str                            # 必填
    subject_id: str                            # 必填
    tenant_id: str                             # 必填
    requested_at: datetime                     # 必填
    completed_at: Optional[datetime]           # 必填（完成后）
    per_asset_results: dict[str, Literal["deleted", "key_destroyed",
                                         "scheduled", "blocked"]]  # 必填：逐副本结果
    blocked_reason: Optional[str]              # 选填：blocked 项的说明与预计完成时间

class QuotaPolicy(BaseModel):
    tenant_id: str                             # 必填
    purpose: Literal["cost_guard", "abuse_guard"]  # 必填：两个目标分开配置
    window_seconds: int                        # 必填
    max_requests: int                          # 必填
    max_cost_units: float                      # 必填
    on_exceed: Literal["throttle", "degrade", "reject", "notify"]  # 必填
```

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 判据与陷阱 |
|---|---|---|
| **隔离级别** | 泄漏后果的严重度 × 租户数量 × 运维承受力 | 先量化后果再定级。**"我们有行级隔离"不等于安全**——要问的是"隔离条件由数据库强制还是由应用拼接" |
| **加密密钥粒度** | 擦除时效要求 × 密钥管理复杂度 | 要求即时擦除 → 密钥粒度必须细到主体；可接受小时级 → 租户级密钥 + 周期重建即可 |
| **审计事件保留期** | 举证需要（合同、监管、事故复盘周期） | 由举证需要决定，不由存储成本决定。为"以防万一"多留一年，等于多一年的泄漏面 |
| **审计日志访问权限** | 谁能读、读了是否留痕 | 读审计日志本身必须产生审计事件；否则内部滥用无法被发现 |
| **AgBOM 刷新时机** | 组件是否会运行期变化 | 构建期派生 → 每次发布刷新；运行期发现 → 变更即登记并告警。**"latest" 不是版本号** |
| **配额阈值** | 单用户正常峰值的倍数 × 滥用容忍度 | 成本防护与滥用防护的阈值应分别设定：滥用阈值通常远高于成本阈值，且必须有人工复核通道；跨租户泄漏检测则要求每次涉及查询、缓存、索引、检索的变更都跑一遍，不能只做季度审计 |
| **供应商评估复审周期** | 依赖的变更频率与关键度 | 关键依赖（模型、MCP server）按季度或每次变更复审；条款类变更需要显式通知义务写进合同 |

### 4.4 分阶段实施路径

**最小可行（能被审计）**

1. 数据资产台账（含副本清单），每项带租户 / 主体 / 保留期三个标签。
2. 租户条件由数据库策略强制，并有自动化跨租户泄漏测试纳入 CI。
3. 审计事件最小字段集落地（主体、租户、动作、资源、策略版本、trace id）。
4. 擦除路径可用，并产出首批擦除凭据（哪怕部分副本为 scheduled）。
5. 配额与速率限制上线，区分成本与滥用两个目标。

**生产就绪**

6. 审计链路防篡改（签名或哈希链），并与遥测双写对齐。
7. AgBOM 与发布流程绑定，历史版本可查，组件变更产生告警。
8. 供应商风险台账与合同条款挂钩（变更通知、模型弃用提前期、数据使用限制）。
9. 治理组织面固化：审批人、责任人、例外流程、复审周期，且例外有到期日。
10. 合规映射表（§4.6）按辖区维护，每条要求对应一个可测断言与一个系统属性。

### 4.5 落地检查点（中性化）

- [ ] 能回答"这条记忆记录，从写入到被擦除，中间经过几份副本，分别在哪里"。
- [ ] 能回答"上一次跨租户泄漏检测是什么时候跑的，用什么用例，结果如何"。
- [ ] 能回答"审计日志里能不能查到'谁授权了这次高危工具调用'，而不是只有'调用了什么工具'"。
- [ ] 能回答"当前在生产上跑的模型、工具、MCP server、prompt 分别是哪个版本，谁批准的变更"。
- [ ] 能回答"某个供应商明天变更条款或弃用模型，我们多久会知道，由谁处理"。

### 4.6 合规映射：方法与时点（时效性必须核实）

**方法**：把每条外部要求映射为三元组 `<要求条款> → <系统属性> → <可测断言>`，并记录**核实日期**与**核实人**。映射表本身要版本化，因为法规与解释都在变。

**时点核实示例（EU AI Act）**：下表时点来自欧盟官方 AI Act Service Desk 公开问答（欧盟委员会 · 2026 · 官方发布），**但法规可能被修订，且各成员国执行细则仍在演进，因此整体标 `[待验证]`；任何实际合规决策前必须重新核实。**

| 阶段 | 时点 | 内容 | 状态 |
|---|---|---|---|
| 禁止类与定义、AI 素养 | 2025-02-02 | 不可接受风险的禁止性条款适用 | `[待验证]` |
| 治理与通用模型（GPAI）义务 | 2025-08-02 | GPAI 提供方义务适用（强制执行权此前缺位） | `[待验证]` |
| 透明度要求（Art. 50）与执法框架 | 2026-08-02 | 交互式 AI 须告知用户"正在与 AI 交互"；生成/篡改内容须标识；AI Office 与成员国获得完整调查与处罚权限。此前已在市场投放的系统的标识义务有过渡期 | `[待验证]` |
| 新增禁止项 | 2026-12-02 | 非自愿私密影像与儿童性侵害相关内容的生成/篡改禁令 | `[待验证]` |
| Annex III 高风险系统 | 2027-12-02 | 附件三所列高风险系统的规则适用 | `[待验证]` |
| 嵌入受监管产品的高风险系统 | 2028-08-02 | 附件一所列产品中的高风险 AI 系统规则适用 | `[待验证]` |

> 上表结构说明：**AI 治理义务普遍采用"分阶段适用"模式，且同一部法规内部不同条款的时点不同。** 这意味着第 1 天就必须区分"现在适用"与"将来适用"，并把将来适用项写成带到期日的待办，而不是笼统地"以后再说"。为 Agent 系统需要单独核实的其他义务方向（逐辖区核实，本文不预设结论）：与 AI 交互的披露、AI 生成内容的标识与机器可读标记、训练数据摘要、系统性风险评估、高风险场景的技术文档与人工监督、自动化决策的告知与救济。**以上各项是否适用于你的系统、以何种形式适用，必须按辖区与用途单独核实并标 `[待验证]`。**

### 5.1 「最小可行」

- [ ] 每类持久化数据都登记了租户、数据主体、保留期三个标签

## 6. 常见陷阱

| 陷阱 | 现象 | 根因 | 埋伏阶段 | 规避方式 |
|---|---|---|---|---|
| **1 · 隔离靠应用层约定** | 代码评审通过、测试通过，某次新加的查询漏了租户条件，直接全量泄漏 | 隔离条件写在应用代码里，新增代码路径不会自动继承；没有自动化泄漏测试 | 设计 | 把隔离下沉到数据库行级安全策略或平台层；对"所有读取路径"做参数化泄漏测试 |
| **2 · 擦除只删了主库** | 用户要求删除后主库查不到了，但检索仍能召回内容、评测集里还留着原样本 | 未建立副本清单，擦除被当成"一条 SQL" | 构建（`D05-运行时-记忆与状态.md` 未提供可擦除结构前提） | 写入时就带主体标识并登记副本；擦除后自动核验所有副本并出凭据 |
| **3 · 审计只记结果不记授权** | 事故复盘时能查到"调用了某工具"，查不到"谁批准的、按哪版策略批准的" | 审计字段集在设计期就少了授权维度，事后无法补齐 | 定义 | 在审计事件最小字段集中强制包含 actor、policy_ref、verdict；缺任一字段的事件视为无效 |
| **4 · AgBOM 手工维护** | 清单看起来完整，实际比生产落后两个版本；出事故时追踪不到真实组件 | 手工清单没有失败信号——它不会报错，只会过期 | 构建 | 清单从 CI 派生或运行期发现；把"清单与生产不一致"变成可自动检测的告警 |
| **5 · 供应链变更静默传导** | 升级依赖库或某个 MCP server 后，行为变了但合规评估没有重跑 | 变更流程只看代码与测试，没把 AgBOM 条目变更当作合规触发条件 | 运营 | 把 AgBOM 条目变更设为合规复审触发器；A2A 需注意 AgentCard 在 v0.3→v1.0 之间不向后兼容，升级必须两端同步 `[已验证]` |
| **6 · 用"还没查到我们"做合规策略** | 义务时点已到，系统侧没有任何可举证材料 | 把法律时点当成可以用工程进度协商的变量 | 定义 | 把将来适用项写成带到期日的待办并指定责任人；每条义务都要有一个可测断言 |

## 7. 反例

1. **跨租户共享语义缓存** —— 做法：为省成本把语义缓存做成全局共享，理由是"查询内容本身不含敏感信息"。**爆掉的方式**：某个租户的查询结果被返回给另一个租户，不产生错误日志、不触发任何告警，只在客户投诉或抽样审计时暴露。此时无法界定泄漏范围——因为缓存里没有租户维度的查询记录。**这类泄漏只能事后估算，不能事后追溯。**
2. **把"删除"实现为软删除标记** —— 做法：收到擦除请求后置一个 `deleted=true` 标记，认为数据"逻辑上已删除"。**爆掉的方式**：备份照旧、检索索引照旧、导出报表照旧。第一次接受外部审计时，审计方要求现场演示"擦除后从备份恢复一份副本，其中不含该主体数据"——此时才发现整套数据被保留着，且无法在承诺期限内完成真删除。
3. **审计日志与业务库同权限** —— 做法：审计表放在业务库里，读写用同一个数据库账号。**爆掉的方式**：一次误操作或一次被攻陷的应用账号可以同时修改业务数据与审计记录，"不可否认"的承诺在事故当天失效；事后的复盘基于被污染的证据，结论完全不可信。
4. **在没有主体标识的向量索引上承诺擦除** —— 做法：把文档切片后嵌入向量库，切片记录只保留文本与向量，不留原始主体标识。**爆掉的方式**：擦除请求到来时无法枚举该主体的切片，只能重建整个索引；而重建周期长于承诺的擦除时限。更糟的是，即使重建，训练或微调产物中已固化的影响无法回退——**这类影响在写入时刻就已经不可逆。**

## 8. 开放问题

- **AgBOM 的粒度到什么程度才够用？** 一派主张"登记到组件级即可，过度细化会让清单必然腐化"；另一派主张"必须细化到 prompt 版本与策略版本，因为行为由它们决定"。分歧在于对"变更频率"的假设：前者假定行为主要由代码与模型决定，后者假定行为主要由配置决定。目前没有可比的实测证据。 `[待验证]`
- **加密擦除是否等价于删除？** 一派认为在密钥不可恢复的前提下，密文残留不构成可读数据，等价性成立；另一派认为只要密文存在，未来算力或密钥管理漏洞都可能使其恢复，且部分辖区的解释未明确承认这种等价。**这是本文最重要的未决问题**，落地前必须按辖区单独核实。 `[待验证]`
- **ACS 的 Guardian Agent 模式能否成为通用控制面？** 该模式把策略裁决从各框架中抽出，方向清晰；但规范处于 v0.1，参考实现与协议级强制动作（覆盖 MCP / A2A 的 deny / modify）仍在路线图中。在两到三个主流框架原生支持之前，采用者实际上要自己实现一套 Guardian，**这会形成新的锁定**。 `[共识]`
- **审计的"不可否认"在多 Agent 场景下如何定义？** 当一个 Agent 把任务交给另一个 Agent 时，责任主体是委托方、受托方，还是两者？现有审计模型（actor + on_behalf_of）只是形式上的近似，缺少跨主体的责任分配理论。
- **合规映射表由谁维护、义务时点变更如何被系统感知？** 工程团队缺法律判断力，法务团队缺系统认知；两派做法分别是"工程出结构、法务出判据"与"设一个合规工程岗统管"，前者常因语言不通而失效，后者在中小团队不具备条件。法规时点变更通常只能靠人工跟踪，是否需要把"法规变更"也做成一类工程事件（与 AgBOM 变更并列），尚无定论。
