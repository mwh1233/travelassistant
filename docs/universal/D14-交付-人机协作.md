## 0. 总纲

> **审批门是否真正生效，不取决于有没有那个按钮，而取决于人在点击之前能看到什么。信息不充分的审批界面，会把安全控制变成免责声明。** `[共识]`

这个断言可以被反驳：如果 Agent 的动作全部只读、全部可逆，那么"审批界面够不够好"确实不重要。只要存在不可逆动作，下面每一条都成立。

四条支撑判断：

1. **人的纠错能力随监督时长下降，而不是上升。** 多方研究一致指出：当人从"亲自分析"转为"监督自动化结果"时，发现错误的概率会显著下降；工作负荷、时间压力与"长时间无错"都会加剧这一效应（学术文献综述 · 2026 · 多来源一致，具体数值条件依赖强）`[待验证]`。**"有人在看"本身不构成控制。**
2. **更详细的解释可能反而提高接受率。** 有研究综述指出，解释的丰富程度会同时提高人对正确与错误建议的采纳率——即解释改善的是"可信感"，不是"判断力"（多方综述 · 2026 · 二手引用）`[待验证]`。所以"把推理链摊开给人看"不是信任设计的答案。
3. **交互协议是部署形态的输入，而不是输出。** 是否需要中途插话、是否需要服务端主动提问，直接决定了用 SSE 还是 WebSocket、用同步还是异步——这是 D14 先于 D13 的原因（见 `D13-交付-部署运行时.md` §0）。
4. **交互层是信任事故现场。** OWASP Agentic Top 10 中的 ASI09（Human-Agent Trust Exploitation）专门描述"通过利用人对 Agent 的信任来达成目的"这一类风险，它的攻击面完全落在交互层 `[已验证]`。

## 1. 问题定义与边界

### 1.1 本文解决的问题

- 一次 Agent 运行要对外暴露哪些**事件**、事件的 schema 长什么样、如何版本化。
- 什么情况下必须打断用户澄清、什么情况下**绝不该**打断。
- 审批界面上必须呈现的最小信息集是什么（这部分决定了审批门是否有效）。
- 如何展示依据与不确定性，使信任与系统实际可靠性对齐（既不过度信任，也不过度怀疑）。
- 失败如何让用户感知：显式失败、部分成功、恢复路径的三个选项。
- 多轮场景下如何让用户看到"状态"，而不只是看到"聊天记录"。

### 1.2 本文不讨论什么

- **不讨论 HITL 的触发策略**（哪些动作需要审批、自主度给到几级）。策略在 `D02-地基-任务契约.md` §4 与 `D10-质量-安全护栏.md` §5；本文只负责把这套策略实现成可用的界面与事件。
- **不讨论编排拓扑**（谁调用谁、子 Agent 如何交接）。见 `D03-地基-编排模式.md` 与 `D07-运行时-多智能体.md`。
- **不讨论部署形态、副本与资源**。交互协议是它们的输入，结论落在 `D13-交付-部署运行时.md`。
- **不讨论指标定义与阈值**。"用户挫败率""意图衰减率"的计算方式由 `D09-质量-评测.md` §4.3 定义；本文只负责让这些事件**可被检测**。
- **不讨论传输层的实现细节**（反向代理配置、心跳参数调优属于 D13 与具体技术栈）。
- **不讨论安全防护机制本身**（注入防御、权限最小化在 `D10-质量-安全护栏.md`）；本文只讨论这些机制的**人机界面**。

## 2. 设计思路

### 2.1 第一性原理：交互的唯一目的是让信息正确流动

交互设计容易被当成"体验优化"，于是被排到最后。但它的第一性目标其实是**功能性**的：

| 信息方向 | 必须传达的内容 | 失败后果 |
|---|---|---|
| Agent → 人 | 现在在做什么、依据是什么、有多确定、失败了什么、需要人做什么决定 | 人无法判断 → 审批变橡皮图章；或人误以为任务成功 |
| 人 → Agent | 目标、约束、修正、授权/拒绝 | Agent 沿着错误目标长跑，或越权动作 |

而信息流动受三条**不可回避的人因约束**限制：

1. **人的反应时间与注意力是有限预算。** 一次审批请求消耗的不是"一次点击"，而是一段注意力。请求数量超过某个量级后，处理质量必然下降——这不是纪律问题，是生理限制。
2. **人对自动化输出天然有信任倾向。** 自动化偏见（automation bias）表现为两类错误：跟着错误建议做（commission），以及因为系统没提示而不做（omission）。**系统的沉默会被人当成"没问题"。**
3. **信任是不对称的。** 建立信任需要长期正确，摧毁只需一次"说得头头是道但完全错了"。因此交互设计的目标不是"最大化信任"，而是**让信任与实际可靠性对齐**（trust calibration）。

由此得到本文的设计主线：**每一次向用户提问、展示或告知，都要回答"这条信息会改变用户的哪一个判断"，回答不了的就不展示。** 这是"渐进式披露"的真正依据，而不是"界面要简洁"。

### 2.2 不可回避的约束

| 约束 | 性质 | 对交互设计的强制影响 |
|---|---|---|
| **长连接会被中间层切断** | 网络基础设施现状 | 事件必须带序号与可重放语义；断线重连不能导致重复执行副作用 |
| **SSE 单向，WebSocket 双向** | 协议性质 `[已验证]` | 需要"一轮生成中多次插话"（打断、补充信息）的必须上 WebSocket 或双通道 |
| **HTTP/1.1 每源连接数有限** | 浏览器实现（业界通用 6 条/源）`[共识]` | 多标签页场景下纯 SSE 会互相挤占，须走 HTTP/2 |
| **协议交互正在变"回合制"** | MCP `2026-07-28` 的 elicitation/sampling 改为 Multi Round-Trip Requests（SEP-2322）`[已验证]` | 服务端主动提问不再是长驻会话中的一次调用，而是若干次请求-响应；交互实现必须能跨请求保留上下文 |
| **人的阅读速度远低于模型生成速度** | 物理限制 | 流式 token 输出必须做节流与聚合，否则界面在高频重绘下不可读 |
| **不可逆动作无法事后解释** | 物理限制 | 审批必须在动作前完成信息传递；事后"其实我当时是这么想的"没有任何补偿价值 |
| **合规要求"可解释"与"可干预"** | 法规趋势 | 用户必须能看懂、能推翻、能停止、能留痕（这与 D16 的审计要求相连） |

### 2.3 由三重约束推导出的四条核心取舍

**取舍一：宁可少问一次但问对，也不多问一次显得谨慎。**

多余的提问有两个代价：一是消耗注意力预算（挤占真正重要问题的额度），二是训练用户形成"一路点确认"的习惯——**这才是审批门失效的真正原因**。判据：如果一个提问在 90% 的情况下答案都是"是，按你说的做"，它就应该被改成默认行为 + 事后可撤销，而不是一次拦截。

**取舍二：宁可显式失败，也不静默降级后用更自信的措辞掩盖。**

静默失败是评测里最危险的一类失败（见 `D09-质量-评测.md` §4.5）。在交互层的表现是：系统实际用了降级路径，却用与正常路径完全相同的语气给出结果。用户失去了判断依据，也失去了反馈渠道。

**取舍三：宁可少展示推理链，也不把推理链当作信任来源。**

推理链既可能是错的，也可能被注入内容污染；把它当"证据"展示会同时引发两个问题——可信度感的虚假提升，以及**Hidden Context Exposure** 类风险（用户不知道还有哪些上下文被读入）`[已验证]`。正确做法是展示**依据**（来源、时间、范围）而不是**思考过程**。

**取舍四：宁可把"部分成功"说清楚，也不给一个干净的"失败"。**

真实世界里的 Agent 任务经常是部分完成的（3 项里成了 2 项）。把它压缩成"失败"会让用户重做已完成的部分；压缩成"成功"则更危险。部分成功必须是一等表达，它同时也是最好的诊断信号。

## 3. 通用方案

### 3.1 传输形态选型

#### 方案 A · SSE（Server-Sent Events）

**机制**：基于普通 HTTP 的单向流（服务端→客户端），使用 `text/event-stream`；浏览器端 `EventSource` 内建自动重连与 `Last-Event-ID` 续传 `[已验证]`。
**适用条件**：一轮生成内的反馈不需要客户端插话；需要最好的兼容性与最小客户端代码；绝大多数 token 流式输出场景。
**代价**：单向，客户端发消息需要另开请求（打断、补充信息都要走第二条通道）；`EventSource` 不能自定义请求头，鉴权需改用 `fetch` + 流式读取或查询参数（后者有安全代价）；原生客户端处理 POST 流式需要自行解析；HTTP/1.1 下受每源连接数限制。
**不适用场景**：语音打断、多 Agent 实时协作、需要在一轮生成中多次插话的场景。

#### 方案 B · WebSocket

**机制**：HTTP 升级后建立全双工连接，双方可随时发送消息；没有内建重连与续传语义 `[已验证]`。
**适用条件**：客户端需要在一轮生成中主动发消息（打断、修正、实时语音）；消息频率高、对延迟敏感。
**代价**：需要自行实现重连、心跳、消息编号与补发；企业网络中可能被中间设备干扰，需要走 `wss` + 443；没有内建背压，消费慢会导致内存堆积；打开的连接会阻碍浏览器的前进后退缓存。
**不适用场景**：纯单向推送（成本不成比例）；只需偶发客户端信号的场景（用 SSE + 独立 POST 更简单）。

#### 方案 C · 轮询 / 任务状态查询

**机制**：客户端按固定间隔或指数退避查询任务状态；服务端返回阶段化进度。
**适用条件**：任务时长跨越交互超时；含人工等待；客户端可能在查询间歇离线。
**代价**：实时性差（受轮询间隔限制）；空闲查询浪费资源；状态接口需要设计成幂等读。
**不适用场景**：对首字延迟敏感的场景；需要展示逐 token 输出的场景。

#### 传输选型判据

| 判断问题 | 若回答为 | 采用 |
|---|---|---|
| 是否需要在一轮生成中由客户端主动发消息？ | 是 | 方案 B |
| | 否 | 方案 A |
| 任务时长是否超过最外层超时？ | 是 | 方案 C 承载任务状态 + 方案 A/B 承载进度 |
| 客户端是否可能长时间离线？ | 是 | 方案 C（状态可查）+ 事件带序号以便续传 |
| 是否需要跨进程/跨组织的 Agent 交互？ | 是 | 走协议层（A2A `v1.0.1`）而不是自定义消息格式 `[已验证]` |

### 3.2 澄清与追问

#### 方案 A · 阻塞式澄清（停下来问）

**机制**：检测到关键信息缺失或有歧义时暂停执行，向用户提出一个具体问题，等待回答后继续。
**适用条件**：缺失信息会导致方向性错误（例如目标本身有歧义）；错误代价高（不可逆动作、昂贵操作）；问题本身**可以一句话回答**。
**代价**：中断体验；用户不在线时任务停滞；如果问题质量差，就退化成"挤牙膏"。
**不适用场景**：信息可以从上下文或系统内查到（此时应该自己查）；可以先用默认假设推进且可事后修正。

#### 方案 B · 默认假设 + 事后纠正（先走，再改）

**机制**：采用最可能的假设继续执行，同时把假设**显式展示**在界面上，并提供一键修改入口。
**适用条件**：动作可逆或只读；默认假设的分布高度集中；用户更在意速度。
**代价**：一旦默认错，用户需要理解已产生的中间结果并做修正；如果中间结果已经外泄到不可逆路径，代价很高。
**不适用场景**：任何不可逆动作；用户目标本身不确定（此时"最可能的假设"没有意义）。

#### 方案 C · 结构化澄清（表单式一次问全）

**机制**：把需要澄清的项做成一个合并表单（或一次"确认卡片"），一次性收集所有缺失信息。
**适用条件**：缺失项之间有依赖或可以批量回答；用户愿意在开始时花 30 秒换后续顺畅。
**代价**：前期摩擦大；表单项设计不好会被用户误读为"系统不智能"；如果后续又出现新缺失项，体验更差。
**不适用场景**：信息需求在过程中逐步显现的场景（此时应在恰当时机用方案 A）。

#### 澄清选型判据

| 判断问题 | 若回答为 | 采用 |
|---|---|---|
| 缺失信息是否会导致不可逆动作发生在错误目标上？ | 是 | 方案 A 或 C（必须问） |
| 信息能否从上下文/系统内检索到？ | 能 | **不要问**，自己去查（回指 `D04-运行时-上下文工程.md`） |
| 默认假设是否高度集中且动作可逆？ | 是 | 方案 B |
| 缺失项是否 ≥ 3 且彼此独立？ | 是 | 方案 C（一次问全，避免挤牙膏） |
| 用户是否明确表达了"别问了，你决定"？ | 是 | 方案 B + 全程可见的假设清单 |

> **最小必要信息原则**：一次追问只问**当前决策无法继续所必需**的那一条信息，且必须让用户知道"这个答案会被用来做什么"。问"您的预算多少"而不说明用途，是信息采集；问"要筛选 500 元以内的候选，您的预算上限是多少"才是澄清。

### 3.3 审批交互

#### 方案 A · 同步阻塞审批

**机制**：执行到审批门时暂停，向用户呈现完整信息，等待明确决定后才继续。
**适用条件**：动作不可逆或影响面大；用户在线；审批信息可以在一屏内说清。
**代价**：阻塞任务推进；审批请求频繁时直接导致注意力枯竭与橡皮图章；用户离线时任务停滞（需要超时策略）。
**不适用场景**：高频、低风险动作（会把审批变成机械点击，反而削弱高风险审批的效果）。

#### 方案 B · 异步审批 + 超时策略

**机制**：审批请求进入队列，用户可以稍后处理；到达超时后按预设策略（自动拒绝 / 自动降级到只读 / 转人工）处理。
**适用条件**：审批量中等以上；用户不一定在线；动作可以在稍后执行而不失效。
**代价**：需要定义超时默认行为，而这个默认行为本身就是一次风险决策；任务状态需要长时间保留（回指 `D13-交付-部署运行时.md` §4.4 的保留期）；用户可能忘记上下文，导致"看着标题点确认"。
**不适用场景**：时效性强的动作。

#### 方案 C · 事前授权（策略委派 / Pre-authorization）

**机制**：用户事先设定规则（金额上限、允许的动作类型、时间窗口），Agent 在规则内自动执行，超界才触发审批。
**适用条件**：动作类型可枚举、阈值可量化；用户与 Agent 长期协作、行为可预期。
**代价**：规则本身成为攻击目标——**规则必须存放在 Agent 无法修改的地方**，否则"Agent 说服自己提高上限"是必然结果（这是 ASI09 的典型形态）`[已验证]`；规则需要可视化与可审计，否则用户不知道实际授权了什么。
**不适用场景**：一次性任务；规则难以量化的场景。

#### 审批界面必须呈现的最小信息集

这是本节最重要的部分。**缺少其中任何一项，审批都会退化为形式动作：**

| 要素 | 内容要求 | 缺失后果 |
|---|---|---|
| **动作是什么** | 用自然语言 + 具体参数说清楚（写什么、写到哪、影响谁），不写内部函数名 | 用户无法判断 → 机械确认 |
| **影响面** | 影响的对象范围与数量（1 个用户还是 10 万条记录；内部系统还是外部可见） | 用户低估风险 |
| **可逆性** | 明确写"可撤销 / 需要人工补偿 / 不可逆"，并给出撤销窗口 | 用户以为都能撤回 |
| **替代方案** | 至少一个更保守的选项（例如"只生成草稿""只处理前 10 条"） | 用户只有"同意/拒绝"两种选择，往往是无奈同意 |
| **证据与依据** | 目标来源、数据时间、检索到的关键依据（可溯源，不是推理链） | 用户无法核实，只能依赖 Agent 的措辞 |
| **不确定点** | Agent 自己不确定的部分（如"价格数据为 3 天前，可能已变化"） | 不确定被隐藏，用户按确定理解 |
| **超时默认行为** | 超时后会怎样 | 出现"没批也没拒"的黑洞 |

> 强约束：**审批门的信息集必须来自系统结构，不能来自模型的自由生成。** 由模型生成"影响面"这类字段，等于让被审批对象自己写审批材料——这与 D10 的"强制点"设计原则冲突（见 `D10-质量-安全护栏.md` §5）。

### 3.4 可解释、信任与失败表达

#### 可解释的三种做法

| 做法 | 机制 | 适用 | 代价 |
|---|---|---|---|
| **依据展示** | 展示结论所依赖的来源（文档、时间、字段、接口），标注检索与数据的时间 | 事实性结论、有据可查的任务 | 需要系统真的保留溯源信息（`D06-运行时-工具与协议.md` §4 的工具契约五要素之一） |
| **置信度表达** | 用分级词或区间表达不确定性，并在低置信时触发澄清或降级 | 分类、预测、存在歧义时 | 模型自报的不确定度校准差，容易变成"假精确"；用数值概率尤需谨慎 `[待验证]` |
| **反事实提示** | 主动说出"在什么条件下这个结论会不成立" | 高风险决策、方案建议 | 需要额外的推理与验证成本 |

#### 失败表达的三个层次

| 层次 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **显式失败** | 直接告知失败、原因类别、已产生的副作用、可采取的动作 | 默认做法 | 需要系统能区分失败类型（谁失败、是否已产生副作用） |
| **部分成功** | 列出已完成项与未完成项，各自给出下一步 | 多子任务场景 | 需要任务结构可枚举；界面上需要"逐项状态"而非单一结果 |
| **恢复路径三选项** | 固定给出「重试」「修改需求」「转人工」，并说明各自代价 | 所有面向用户的失败 | 需要三条路径都真实可用；"转人工"没有承接资源时会形成二次伤害 |

> **恢复三选项的设计要点**：不要只给"重试"。因为相当一部分失败**重试一定会再失败**（目标本身不可达、权限不足、数据不存在）——此时反复重试只是让用户在同一个坑里多待几分钟。必须让用户能改需求。

## 4. 如何设计

### 4.1 步骤序列

```text
① 事件盘点          → 产出：事件类型清单 + 每种事件的消费者（前端 / 日志 / 评测）
② 传输选型          → 产出：SSE / WebSocket / 轮询决策记录（作为 D13 的输入）
③ 事件契约定义      → 产出：事件信封 schema + 版本化规则 + 有序与去重语义
④ 澄清点设计        → 产出：必须澄清 / 可默认假设 / 禁止打断 三类清单
⑤ 审批信息集设计    → 产出：审批卡片字段表 + 每个字段的数据来源（必须来自系统结构）
⑥ 失败与降级文案    → 产出：失败类型 → 用户可见文案 → 恢复选项 的映射表（回指 D12 §3.4）
⑦ 多轮状态可见性    → 产出：状态视图定义（当前目标 / 已确认约束 / 已完成步骤）
⑧ 埋点与事件上报    → 产出：可被 D09 检测的事件（澄清次数、审批耗时、审批通过率、中断次数）
⑨ 校准与复盘        → 产出：审批质量指标（人工推翻率、审批耗时分布）与定期抽检机制
```

### 4.2 数据结构与接口形态

**事件信封（所有事件共用的外层）**——字段语义不可省略（`?` 表示非必填）：

```python
from typing import Literal, Optional, Any
from pydantic import BaseModel

class EventEnvelope(BaseModel):
    schema_version: str        # 事件契约版本，必须随破坏性变更递增
    event_id: str              # 全局唯一，用于去重
    run_id: str                # 一次运行
    seq: int                   # 单调递增；断线重连后用于续传与排序
    ts: str                    # 服务端时间（ISO8601）
    type: str                  # 见下方事件类型枚举
    data: dict[str, Any]       # 类型专属负载
    replayable: bool           # 断线后是否可重发（含副作用的确认类事件应为 True）
```

**事件类型与必需负载**：

| type | 必需字段 | 语义 | 消费方 |
|---|---|---|---|
| `token` | `text`, `index` | 流式文本片段；**必须可聚合**（客户端丢弃也不影响正确性） | 前端 |
| `step` | `step_id`, `name`, `status`（`started`/`done`） | 编排步骤的开始与结束 | 前端 + 评测 |
| `tool_call` | `call_id`, `tool_name`, `args_digest`, `reversibility` | 即将调用工具；`args_digest` 是可展示摘要而非全量参数 | 前端 + 审计 |
| `tool_result` | `call_id`, `status`, `degraded_from?`, `evidence_ref?` | 工具返回；**失败必须有独立状态，禁止用空结果表示失败** | 前端 + 评测 |
| `approval_request` | `approval_id`, `action`, `impact_scope`, `reversibility`, `alternatives[]`, `evidence[]`, `uncertainties[]`, `timeout_policy` | 审批门（字段与 §3.3 最小信息集一一对应） | 前端 |
| `approval_decision` | `approval_id`, `decision`, `decided_by`, `ts` | 人的决定 | 前端 + 审计 |
| `interrupt` | `reason`, `resumable`, `resume_token?` | 任务被中断（用户取消 / 系统降级 / 外部信号） | 前端 + 评测 |
| `final` | `status`（`ok`/`partial`/`failed`）、`summary`、`artifacts[]` | 终止事件；**必须有且仅有一条** | 前端 |
| `error` | `class`, `user_message`, `recoverable`, `recovery_options[]` | 错误；`user_message` 面向用户，禁止含内部堆栈 | 前端 |

**关键接口约定**：

1. `seq` 单调递增且服务端可重放；客户端发现 `seq` 跳号时必须能请求补发，而不是直接渲染。
2. `token` 事件必须允许丢失（可丢弃、可合并），其他事件不可丢失。
3. `final` 或 `error` 必须出现且仅出现一次；流结束不能靠"静默无消息"表达。
4. `schema_version` 的破坏性变更规则：新增可选字段不算破坏；删除字段、改语义、改枚举值算破坏，必须递增并保证旧客户端不崩（收到未知 type 时应忽略而非报错）。
5. `degraded_from` 非空时，`final` 的 `status` 不得为 `ok`——**降级不能被包装成完全成功**（回指 `D12-质量-可靠性.md` §3.4）。

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 常见错误取法 |
|---|---|---|
| **token 聚合/节流间隔** | 由人的阅读速度与界面重绘成本共同决定：模型 token 速率远高于阅读速度，必须按帧聚合 | 每个 token 一次渲染，高频重绘导致界面卡顿且不可读 |
| **心跳间隔** | 必须小于中间层最短空闲超时（见 `D13-交付-部署运行时.md` §2.2），常见做法是取该值的一半以下；心跳不计入用户可见事件 | 依赖"连接一直有数据"而不发心跳，被静默切断 |
| **澄清超时** | 由"用户回答这个问题通常需要多久"与"任务可等待多久"共同决定；超时后必须给出明确的默认行为 | 默认无超时，任务永久挂起 |
| **审批超时与默认动作** | 由动作的时效性与风险共同决定：高风险 → 超时默认拒绝；低风险可逆 → 超时默认降级执行 | 所有审批统一超时且默认同意 |
| **审批阈值（何时必须问）** | 由 `D02-地基-任务契约.md` 的自主度分级给出，不由交互层决定 | 交互层自己判断"这个要不要问"，导致策略分散在多个地方 |
| **事件保留与回放窗口** | 由任务最长寿命 + 断线重连的最坏情况决定 | 只保留最近 N 条，长任务断线后无法续传 |
| **多轮状态展示的粒度** | 由"用户需要据此做判断的信息"决定，而不是由系统内部结构决定 | 把内部步骤原样罗列，信息量上升而可理解性下降 |
| **不确定性表达方式** | 由任务对精确度的要求决定：可枚举范围用区间，专家场景可用等级词，消费场景用行动化表述（"建议核实"） | 一律显示百分比概率——未经校准的概率是"假精确" `[待验证]` |

### 4.4 分阶段实施路径

**最小可行**

1. 定义事件信封与最小事件集：`token`、`step`、`final`、`error`（四类即可起步）。
2. 传输用 SSE；任务状态用轮询接口兜底。
3. 落地两条硬规则：失败必须有独立状态（不得用空结果表示）；`final` 必须恰好一条。
4. 审批卡片先实现五项：动作、影响面、可逆性、证据、超时行为。
5. 失败必须给出恢复三选项（重试 / 改需求 / 转人工）。
6. 埋点上报：澄清次数、审批请求数、审批决定耗时、中断次数。

**生产就绪**

7. 补齐全部事件类型，含 `approval_request` / `approval_decision` / `interrupt` / `tool_result` 及 `degraded_from`。
8. 事件契约版本化：`schema_version` 变更流程 + 旧客户端兼容策略 + 未知事件忽略规则。
9. 断线重连续传：序号跳号检测 + 补发接口 + 重连后**不重复执行副作用**（回指 `D12-质量-可靠性.md` §4.2）。
10. 部分成功作为一等表达：任务结构可枚举，界面逐项展示状态与下一步。
11. 审批质量治理：控制在合理量级内、拒绝全屏阻断式的高频低风险确认、把低风险动作改为事前授权（规则存放在 Agent 不可修改的位置）。
12. 信任校准机制：定期抽检审批记录，统计"人工推翻 Agent 建议"的比例与审批耗时分布，作为交互层是否退化的信号。
13. 降级与失败的用户可见行为逐级验收（回指 `D12-质量-可靠性.md` §3.4）。

## 5. 检查清单

### 5.1 「最小可行」

- [ ] 存在事件信封定义，含 `schema_version`、`event_id`、`run_id`、`seq`
- [ ] 流式输出做了聚合/节流，不是每 token 一次渲染
- [ ] 失败与"空结果"在事件类型上可区分，不用空结果表示失败
- [ ] 终止事件（`final` 或 `error`）有且仅有一条，且不靠"静默无消息"表示结束
- [ ] 降级结果带 `degraded_from` 标记，且不会被表达为完全成功
- [ ] 澄清清单已区分"必须问 / 可默认假设 / 禁止打断"三类
- [ ] 审批卡片包含：动作、影响面、可逆性、证据、不确定点、超时行为
- [ ] 审批中呈现的"影响面"等关键字段来自系统结构，而非模型自由生成
- [ ] 失败界面固定给出「重试 / 改需求 / 转人工」三选项
- [ ] 用户可见的错误文案不含内部堆栈、字段名与内部标识

### 5.2 「生产就绪」

- [ ] 事件契约有版本化与破坏性变更流程；旧客户端遇到未知事件类型不会崩溃
- [ ] 心跳间隔小于中间层最短空闲超时，且有实测验证
- [ ] 断线重连有续传机制（按 `seq` 补发），且重连不会重复执行副作用
- [ ] 澄清的默认假设在界面上全程可见，并提供一键纠正
- [ ] 追问不出现"挤牙膏"：同一轮任务内的澄清次数有上界与监控
- [ ] 审批请求量在可控范围；高频低风险确认已改为事前授权或事后撤销
- [ ] 事前授权规则存放在 Agent 无法修改的位置，且有可视化与审计
- [ ] 审批质量有指标：人工推翻率、审批耗时分布、超时率；并定期抽检
- [ ] 部分成功有专门界面表达（逐项状态 + 各自下一步）
- [ ] 多轮场景下用户能看到当前目标、已确认约束与进度（不只是聊天记录）
- [ ] 置信度表达方式经过用户验证，不使用未校准的百分比概率
- [ ] 关键交互事件已上报，使 `D09-质量-评测.md` §4.3 的轮次层指标可被计算
- [ ] 降级各级的用户可见行为已逐级验收（回指 D12 §3.4）

## 6. 常见陷阱

### 陷阱 1 · 挤牙膏式追问

**现象**：用户一次性给了需求，Agent 连续追问 6 轮，每轮只问一个字段；用户在第 4 轮开始不耐烦或直接给了错误信息。
**根因**：澄清逻辑是"执行中遇到缺失就问"，没有在开始阶段做一次性缺口分析；也没有"能查到的不要问"的规则。
**埋伏阶段**：**设计**。
**规避**：开始前先做信息缺口盘点，能从上下文/系统查到的自行补齐，≥3 个独立缺失项用一次结构化澄清；对同一轮任务的澄清次数设上界并监控。

### 陷阱 2 · 审批过载导致橡皮图章

**现象**：上线时"每个动作都审批"，两周后用户开始无脑点确认；随后一次真实危险动作被顺利放行。
**根因**：审批被当成越多越安全的控制手段，忽略了人的注意力是有限预算。研究一致指出，工作负荷与提示数量上升会显著降低审查质量 `[待验证]`。
**埋伏阶段**：**定义**（自主度分级过保守）→ 运营期以"用户不看了"的形式爆发。
**规避**：只对高风险/不可逆动作设同步审批；其余改为事前授权或事后可撤销；监控审批耗时分布，耗时的下降是警觉性下降的先兆。

### 陷阱 3 · 把推理链当作信任建设

**现象**：界面上展示完整思维过程，用户反馈"看起来很专业"，但错误结论被同样顺畅地接受；同时暴露了系统读取的内部上下文。
**根因**：把"可解释"等同于"展示内部过程"。推理链的可读性与其正确性无关，且会提高对错误的采纳率 `[待验证]`；同时触发 Hidden Context Exposure 类风险 `[已验证]`。
**埋伏阶段**：**设计**。
**规避**：展示**依据**（来源、时间、范围、可核实的字段）而非思考过程；明确区分"我看到的事实"与"我的推断"；不确定点单独列出。

### 陷阱 4 · 静默失败与"自信的措辞"

**现象**：某步骤失败后系统走了兜底路径，用户收到一个语气正常、甚至更肯定的回答。
**根因**：降级路径复用了正常路径的输出模板与语气；失败信息在事件层就不存在。
**埋伏阶段**：**构建**。
**规避**：降级结果必须带 `degraded_from` 并在界面上体现；`final.status` 不得为 `ok`；把"静默失败率"做成评测指标（回指 `D09-质量-评测.md` §4.2）。

### 陷阱 5 · 断线重连导致重复执行

**现象**：网络抖动后客户端重连，用户看到任务"重新跑了一遍"，或产生了第二笔副作用。
**根因**：把"重连"实现为"重新提交"；事件没有序号，服务端也无法判断是同一次运行的续传。
**埋伏阶段**：**构建**。
**规避**：任务与连接分离；重连只做订阅与补发；提交动作带幂等键（回指 `D12-质量-可靠性.md` §4.2）。

### 陷阱 6 · 只给"重试"一个恢复选项

**现象**：任务因为权限不足或数据不存在而失败，界面只提供"重试"，用户连点五次得到五次相同失败。
**根因**：恢复路径只按"技术失败"设计，没有考虑"目标不可达"这类失败。
**埋伏阶段**：**设计**。
**规避**：失败分类必须映射到不同恢复选项；不可重试的失败直接给出"改需求"或"转人工"（与 `D12-质量-可靠性.md` 的错误分类共用同一份定义）。

## 7. 反例

### 反例 1 · 把审批做成一个"确认"按钮

**做法**：审批卡片只有一句话"Agent 想要执行以下操作，是否继续？"，加上同意/拒绝两个按钮。
**爆掉的方式**：用户无法判断影响面与可逆性，只能依赖 Agent 的措辞——而措辞恰好是被攻击面（ASI09 的典型形态 `[已验证]`）。**爆发时间点是第一次出现"用户认为已审批过、系统认为未授权"，或第一次出现被诱导的高风险动作**。此时无法区分是 Agent 错了还是用户没看清，因为界面从未提供判断依据。

### 反例 2 · 用"生成成功"掩盖"事实错误"

**做法**：只要模型产出了内容就返回 `final: ok`，把"内容是否准确"留给用户自己看。
**爆掉的方式**：用户在一次高风险决策中采信了错误内容，追责时发现系统日志显示"任务成功"。**爆发时间点通常在内容质量首次被认真核查时**，而在此之前，成功率指标一直很好看——因为它衡量的从来不是正确性。

### 反例 3 · 把所有中间过程都推给用户

**做法**：把工具调用参数、检索结果、子 Agent 消息全部实时推到界面上，"让用户看得见"。
**爆掉的方式**：信息过载使界面不可读，用户开始忽略内容只看结论；同时把内部上下文与检索到的原文暴露出去，触发数据暴露类风险。**爆发时间点是用户第一次抱怨"太乱"或第一次安全评审。**

### 反例 4 · 澄清不设超时

**做法**：Agent 提出问题后无限期等待用户回答。
**爆掉的方式**：任务状态长期悬挂，检查点无法清理（回指 `D13-交付-部署运行时.md` §4.4），存储与人工队列逐步塞满；用户回来时已忘记上下文，只能盲选。**爆发时间点是并发任务数上量的那一次。**

## 8. 开放问题

**⑴ 流式展示应该给到多细？**

- **细粒度派**：展示每一步与每次工具调用，用户才有掌控感，也更容易识别错误方向并及时打断。
  前提：用户具备相应的领域知识，且界面上有良好的聚合与折叠设计。
- **粗粒度派**：只展示阶段与结论，过程对多数用户是噪声，反而降低判断质量并泄露内部上下文。
  前提：任务类型以"结果可验证"为主，用户更在意速度。
- **未收敛的分歧点**：这是**用户画像问题而非技术问题**——同一产品对不同专业度的用户可能需要不同的默认粒度。按用户能力动态调整的实践尚不成熟。

**⑵ 不确定性应该如何表达？**

- **数值派**：给出概率或区间，便于用户做量化权衡。
  前提：模型自报的不确定度经过校准。
- **行动派**：不给数字，只给"建议核实 / 建议补充信息 / 可放心使用"这类行动化表述。
  前提：系统能可靠地划分这三档。
- **分歧点**：未校准的概率是假精确（可能比不表达更危险），但校准本身需要标注数据与持续投入 `[待验证]`。目前缺少公开的、跨任务可迁移的校准实践。

**⑶ 审批是否应该强制"冷却时间"（强制延迟）？**

- **支持冷却派**：高风险审批加入强制延迟可以打断反射式确认。
  前提：动作交付存在天然可容忍的延迟。
- **反对冷却派**：延迟会促使用户切换到"批量处理审批"的模式，反而集中降低质量；且延迟在高时效场景直接造成损失。
  前提：审批频率低或时效要求高。
- 双方对"延迟是否真的提升判断质量"都缺少可靠证据。

**⑷ "转人工"这一恢复选项，在没有人可接的场景下是否应该存在？**

- 如果必须存在，就需要真实的人工承接资源与 SLA，否则它只是把失败推给用户。
- 如果不存在，用户就被困在"重试"与"改需求"之间。
- 目前的折中做法是：仅在特定风险等级下暴露该选项，并在无人承接时改为"保存进度并通知"。这一策略的效果缺少公开评测。
