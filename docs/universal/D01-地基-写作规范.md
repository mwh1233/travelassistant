## 0. 总纲

> **通用知识库的失败很少因为写得少，几乎总是因为写得"看起来都对"。一份无法被证伪、无法被照着执行的文档，比没有文档更危险——它会让后来者以为问题已经解决了。** `[共识]`

本文规范解决三个具体问题：

1. **可证伪**：每条结论能追溯到具体版本的具体来源，读错了能发现。
2. **可执行**：读者能据此做出决策或写出第一版实现，而不是只获得"意识提升"。
3. **可维护**：外部标准迭代时，只需改动最小范围就能让文档跟上。

## 1. 问题定义与边界

### 1.1 本文解决的问题

- 如何把"行业上的做法"写成**别人敢照着做**的文档。
- 如何在标准快速迭代（部分标准仍在 Development 状态）时保持文档不失效。
- 如何避免 18 篇文档之间出现术语冲突、内容重叠、责任不清。

### 1.2 本文不讨论什么

- **不讨论具体的 Agent 技术内容**——那是 D02–D17 的职责。
- **不讨论文档工具链**（静态站点、CI 校验脚本、格式检查）——本文只定内容标准，工具化留待后续。
- **不讨论面向非技术读者的科普写法**——本知识库的读者假定为有工程能力的开发者。

### 1.3 与其他文档的边界切线

| 你可能想问 | 去哪篇 |
|---|---|
| 有哪些文档、编号怎么分 | `D00-地基-总纲.md` §3 |
| 每篇文档写什么内容 | 本知识库对应的 D 编号文档 |
| 一篇文档要包含哪些章节、怎么写才合格 | **本文** |

## 2. 设计思路

### 2.1 第一性原理：文档的价值来自"降低他人的决策成本"

一份文档对读者有三种可能的价值：

| 层次 | 读者读完能做什么 | 价值 |
|---|---|---|
| **知晓层** | "哦，原来还有这回事" | 低。不改变任何决策 |
| **判断层** | "在 A 和 B 之间，基于我的约束应该选 B" | 中 |
| **执行层** | "按这五步做，我能在两小时内得到第一版" | 高 |

本知识库要求每篇文档至少达到**判断层**，核心章节必须达到**执行层**。

这直接决定了十三节结构：§5 设计思路服务"为什么"，§6 通用方案服务"选哪个"，§7 如何设计服务"怎么做"。

### 2.2 不可回避的四个约束

| 约束 | 对写法的影响 |
|---|---|
| **标准在变** | 结论必须携带版本号与稳定性标记。不写版本的结论视为无效，因为它可能昨天还是对的 |
| **厂商有利益** | 基准数字可能被挑选、被自报。可信度必须分级，把"官方规范"和"厂商博客"区分开 |
| **Agent 领域未收敛** | 大量问题没有唯一答案。文档必须保留分歧并写清各派前提，而不是合成一个虚假的中立结论 |
| **读者时间有限** | 结论前置。每节开头先给判断，再给论证；不要把答案埋在三千字之后 |

### 2.3 由此推导出的核心取舍

**取舍一：宁可写"两派各有前提"，也不写"最佳实践"。**

"最佳实践"是文档中最有害的短语。它暗示存在一个与约束无关的最优解。正确写法是："方案 A 适合 X 前提，方案 B 适合 Y 前提；当你不确定自己是哪种前提时，先量一个指标 Z。"

**取舍二：宁可标 `[待验证]`，也不省略可信度。**

未标注可信度的结论会被读者按默认最大值理解。标注 `[待验证]` 不会让文档显得弱，反而会让读者信任其余部分。

**取舍三：宁可写短且可执行，也不写长且全面。**

一篇 200 行但能让读者做出决策的文档，价值高于 800 行什么都提到的综述。篇幅不足的问题应在 §5–§7 加深，而不是靠堆砌参考链接解决。

## 3. 通用方案

文档写法本身有三种主流方案，各有代价：

### 3.1 方案 A · 综述型（Survey）

**机制**：按主题全面铺开，尽可能覆盖所有相关技术与论文，引用密度高。

**适用**：读者需要建立全景认知；主题处在快速变化期，尚未形成稳定实践。

**代价**：不产生决策。读者读完知道很多，但仍不知道自己的项目该怎么做。维护成本极高——外部技术一变，全文过时。

**不适用**：需要指导工程决策的场景（正是本知识库的场景）。

### 3.2 方案 B · 手册型（Handbook / Runbook）

**机制**：以"步骤 + 参数 + 命令"为主，假设读者已认同目标，只关心执行。

**适用**：流程稳定、变体少的领域（如部署、运维、故障排查）。

**代价**：不解释原因，读者遇到手册未覆盖的变体就无法迁移。当底层机制变化时，手册需要整体重写。

**不适用**：设计类主题（架构、上下文策略、协议选型），因为这类问题的答案取决于前提。

### 3.3 方案 C · 决策型（Decision-oriented）—— 本知识库采用

**机制**：以"问题 → 约束 → 设计思路 → 方案对比 → 落地步骤"为主干，把知识组织成**决策路径**而非知识目录。

**适用**：领域未收敛、答案依赖前提、读者是需要做技术决策的工程师。

**代价**：要求作者真正理解第一性原理，不能靠罗列资料凑数；篇幅上限受限，必须做取舍。

**不适用**：纯操作类主题（应改用方案 B 作为补充）。

### 3.4 选型判据

| 判断问题 | 若回答为 | 采用 |
|---|---|---|
| 该主题是否存在唯一正确的做法？ | 是，且变体少 | 方案 B 为主 |
| 读者读完后是否需要做选择？ | 需要 | 方案 C |
| 主题是否仍在快速演进、尚未收敛？ | 是 | 方案 C（并在 §11 保留分歧） |
| 是否需要建立全景认知 | 是，且是入门读者 | 方案 A 作为补充章节，不作为主体 |

## 4. 如何设计（本文的落地规范）

### 4.1 一篇文档的产出流程

```text
① 定边界      →  读 D00 §3.2 确认编号/层级/主题词 → 写一句话职责
② 核版本      →  查 D00 §5 对标版本表 → 确认本文涉及的标准及其当前版本
③ 写总纲      →  一句话核心判断（可被反驳）+ 可信度
④ 列问题      →  显式写出"本文不讨论什么"，并画出与相邻 D 文档的边界切线
⑤ 挖原理      →  §5 设计思路：找出第一性原理与不可回避的约束
⑥ 铺方案      →  §6 通用方案：≥3 种，每种四个字段（机制/适用/代价/不适用）
⑦ 落步骤      →  §7 如何设计：步骤序列 + 数据结构 + 参数取值依据
⑧ 补清单与坑  →  §8 检查清单分两档；§9 陷阱带根因与埋伏阶段
⑨ 留开放问题  →  §11 非空
⑩ 自检        →  对 D00 §8 的 13 条验收标准逐条打勾
```

### 4.2 页眉规范

固定八个字段，顺序不可变：

```markdown
> **文档编号**：`D10`
> **层级**：质量
> **文件路径**：`docs/universal/D10-质量-安全护栏.md`
> **适用范围**：<什么场景下该读本文，读者是谁，何时不适用>
> **前置知识**：<读本文前需要掌握的东西；尽量少，越少读者越多>
> **对标版本**：<本文结论所依据的外部标准清单，与下表呼应>
> **最后更新**：YYYY-MM-DD
> **可信度标注**：`[已验证]` … · `[共识]` … · `[待验证]` …
> **来源规范**：数字写成 `数值（来源 · 日期 · 自报/复现）`；厂商自报值不得标 `[已验证]`
```

**反模式**：适用范围写"所有 AI 相关场景"。范围写得越宽，文档越没价值——因为它无法排除任何读者，也就无法帮任何读者判断。

### 4.3 对标版本表规范

紧跟页眉，四列：

| 列 | 要求 |
|---|---|
| 标准 / 方法 | 用**官方名称**，不用俗称（写 "OWASP Top 10 for Agentic Applications"，不写 "OWASP 那个 Agent 榜单"） |
| 版本 | **可核验的版本号或发布日期**。只写"最新"等于没写 |
| 稳定性 | 官方成熟度等级（如 OTel 的 `Development` vs `Stable`）；无官方等级则写"厂商产品" |
| 对应本文 | 该标准主要支撑本文哪几节——这列强制作者把标准真正用起来，而不是文末堆链接 |

### 4.4 可信度分级细则

| 标记 | 判定条件 | 典型来源 |
|---|---|---|
| `[已验证]` | 有**可追溯**的公开来源，且来源本身不是利益相关方的自报 | 官方规范文本、同行评审论文、官方发布公告、可复现的公开基准 |
| `[共识]` | 多个独立来源一致表述，但缺乏可复现的定量证据 | 多个厂商文档的相同结论、工程团队公开实践、标准草案 |
| `[待验证]` | 单一来源、有争议、或条件依赖强 | 单个厂商博客的性能数字、社区讨论、新发布未经检验的方法 |

**硬规则**：

- 厂商自报的基准分数（"我们的方案提升 40%"）**一律不得**标 `[已验证]`。
- 同一结论在多个厂商处出现，仍只是 `[共识]`，不是 `[已验证]`——共识可能只是营销同源。
- 若某项结论来自本知识库自身的推理而非外部来源，标 `[共识]` 并在 §11 说明推理链，不得标 `[已验证]`。

### 4.5 数字与引用写法

```text
✅ 正确
pass@1 在 τ-bench 上普遍低于 50%（τ-bench 论文 · 2024 · 复现）
某厂商报告其记忆方案在 LOCOMO 上约 49%（厂商官方文档 · 2026 · 自报）

❌ 错误
pass@1 只有 50% 左右（无来源）
某方案效果提升显著（无数字、无来源）
业界公认最佳方案是 X（无来源、无前提）
```

### 4.6 §5 设计思路的写法

这一节回答"为什么"，是全文最容易写空的一节。合格的写法必须落到**第一性原理或不可回避的约束**上。

**不合格**：

```text
上下文管理非常重要，因为上下文太长会导致模型效果下降，所以我们要做好上下文管理。
```
问题：这是循环论证，"因为重要所以要做好"。

**合格**：

```text
Transformer 的注意力是两两计算，token 数增加会带来非线性增长的干扰项，
因此上下文越长、特定信息的召回精度越差（context rot）`[共识]`。
这个约束是不可回避的——它是架构性质而非实现缺陷，换模型只能缓解不能消除。
由此推导出的设计取舍是：不追求"装得多"，而追求"装得准"，
具体落地为三条规则：……
```

判断标准：**读者读完这一节，应该能自己推导出后面章节的结论。** 如果不能，说明这节写的是"结果"而不是"思路"。

### 4.7 §6 通用方案的写法

每种方案固定四个字段，缺一不可：

| 字段 | 写什么 | 常见错误 |
|---|---|---|
| **机制** | 它是怎么工作的，用一句话让对方能画出草图 | 只写名字不写机制（"使用 Plan-Execute 模式"） |
| **适用条件** | 什么前提下它是对的 | 写"适合复杂场景"这类无法判断的表述 |
| **代价** | 选择它要付出什么（延迟 / 成本 / 复杂度 / 可观测性 / 一致性） | 只写优点，这是最常见的缺陷 |
| **不适用场景** | 什么情况下它会失败 | 空缺 |

最后必须给**选型判据**——决策树或判断表，让读者能落到自己的场景。

### 4.8 §7 如何设计的写法

必须包含四类内容：

1. **步骤序列**：从零到第一版的可执行步骤，标出每步的产出物。
2. **数据结构或接口形态**：字段名、类型、必填性，用代码块给出。抽象描述（"一个包含对话历史的对象"）不合格。
3. **关键参数与取值依据**：参数不能只写建议值，要写"这个值由什么决定"。例如不要写"top_k 设为 5"，而写"top_k 由单次检索内容的平均 token 数与剩余上下文预算共同决定，典型取值 3–10，超过 10 时应先检查召回质量而非继续加大"。
4. **分阶段实施路径**：最小可行版 → 生产就绪版各做什么。

### 4.9 §8 检查清单的写法

两档，条目必须是**可勾选的客观事实**，不是主观评价。

```text
✅ 「最小可行」：每个工具都有超时设置，且超时值小于该工具下游系统的 P99 延迟
❌ 「最小可行」：工具调用设计得比较合理
```

### 4.10 §9 陷阱的写法

每条陷阱四个字段：**现象 / 根因 / 埋伏阶段 / 规避方式**。

"埋伏阶段"指这个错误是在链路的哪个阶段被引入的（定义 / 设计 / 构建 / 验证 / 运营）。这个字段的价值在于：多数陷阱在引入时毫无症状，只在运营期爆发，标注引入点才能前置拦截。

### 4.11 文档间引用规范

- 引用格式固定为 `` `D06-运行时-工具与协议.md` §4.3 ``——带编号的完整文件名 + 章节号。
- 不使用"见上文""如前所述"等依赖阅读顺序的表述。
- 发现两篇文档内容重叠时：**先改 `D00-地基-总纲.md` 的边界定义，再改文档**，不允许私下协商边界。

## 6. 常见陷阱

### 陷阱 1 · "最佳实践"句式

**现象**：文档中大量出现"最佳实践是……""推荐使用……"，不写前提。
**根因**：作者把某个特定前提下的结论当成了普适结论；或为了显得果断而省略前提。
**埋伏阶段**：写作期（本质是 §5 设计思路缺失）。
**规避**：把每条"最佳实践"改写为"当 X 时做 Y，因为 Z"。写不出 Z 的条目直接删除。

### 陷阱 2 · 版本幽灵

**现象**：结论引用了已变更的标准行为。例如把 MCP 写成"需要先 initialize 建立会话"——这在 `2026-07-28` 之后已不成立。
**根因**：作者的知识来自一年前的教程或模型训练数据，未核官方版本。
**埋伏阶段**：写作期（§2 对标版本表形同虚设）。
**规避**：写每条协议相关结论前，先查 `D00` §5 版本表；表中没有的标准，去官方仓库核当前版本再落笔。

### 陷阱 3 · 抄文档不抄代价

**现象**：方案对比部分洋洋洒洒列了 5 种方案的优点，读者仍然不知道选哪个。
**根因**：作者从各方案的官方文档摘取，而官方文档天然不写自己的缺点。
**埋伏阶段**：写作期（§6 缺"代价"字段）。
**规避**：强制四字段；其中"代价"与"不适用场景"必须由作者独立判断，不得从官方文档摘录。

### 陷阱 4 · 抽象到无法执行

**现象**：§7 写道"应设计合理的状态结构以支持恢复"。
**根因**：作者自己也没想清楚具体形态，用抽象表述掩盖不确定性。
**埋伏阶段**：写作期。
**规避**：强制给出字段名与类型。写不出具体字段，说明该主题尚不适合写文档，应标 `[待验证]` 并留在 §11。

### 陷阱 5 · 通用库被项目细节污染

**现象**：通用文档里出现具体项目的状态类名、业务字段、内部服务名。
**根因**：作者从自己的项目实践出发写作，顺手把上下文带进来了。
**埋伏阶段**：写作期，但**后果延迟到下个项目才暴露**——文档无法复用，且读者会误以为这些名字是行业术语。
**规避**：完稿后逐段自查"这段能否给一个完全不同的项目的工程师看"。项目映射写进项目侧文档，不写进本目录。

### 陷阱 6 · 开放问题留空

**现象**：§11 写"暂无"或直接省略。
**根因**：不是真的没有分歧，而是作者没读到分歧，或为了显得权威而隐藏不确定性。
**埋伏阶段**：写作期。
**规避**：把"找不到开放问题"当作调研不足的信号。可用的发现手段：读该主题下两篇结论相反的论文 / 两个厂商的实现差异 / 社区争论的 GitHub issue。

## 7. 反例

### 反例 1 · 靠堆链接的文档

**做法**：正文只写"关于记忆分层，可参考 Mem0、Zep、Letta"。
**爆掉的方式**：读者点开三个链接，读了两小时，仍然不知道自己该选哪个方案、分几层、每层存什么。三个月后原文档失修，链接失效，文档变成死档。

### 反例 2 · 把项目 README 改名成通用文档

**做法**：把某个项目的架构说明直接搬进通用库，只改了标题。
**爆掉的方式**：下一个项目的工程师读到 `TravelState.current_step` 这类字段，误以为它是行业通用概念，在评审中引用，导致团队形成错误共识。污染传播速度远快于纠正速度。

### 反例 3 · 引用厂商博客的"提升 40%"

**做法**：把厂商发布会的性能数字标为 `[已验证]` 并写入方案对比。
**爆掉的方式**：团队据此做技术选型，实测发现前提不同（厂商的测试集更简单、硬件更强、任务更短），选型复盘时无法归因——因为当时"看起来是有依据的"。

## 8. 开放问题

- **本文的 13 条验收标准是否可自动化校验？** 其中第 2、7、11 条（可反驳的判断、可执行步骤、数字格式）目前只能人工判断。若能用脚本检查出 60% 的项（页眉字段、行数、可信度标记合法性、版本号是否存在），评审成本会显著下降。**待评估。**
- **知识库需要版本化吗？** 外部标准迭代后，旧结论是否要保留？目前的做法是直接改，但读者过去依据旧结论做的决策将失去可追溯性。可考虑"结论级修订记录"或对 `[待验证]` 条目加到期时间。
- **是否允许同一主题跨篇？** 例如"成本"既属于 D15，也是 D08 与 D11 的必需输入。目前规则是"一个主题一篇"，但**"输入型提及"与"主题级展开"的界线未量化**——建议以"超过 30 行即为重叠"作为经验阈值，但未验证。
- **中文术语是否统一？** 例如 context window 有"上下文窗口""上下文长度"两种译法。术语表（`D00` §9）只覆盖了核心概念，边缘术语缺统一口径。
