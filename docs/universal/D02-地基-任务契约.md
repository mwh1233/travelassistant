## 0. 总纲

> **Agent 项目的第一个决策不是"用哪个框架"，而是"这个任务根本不该是 Agent"。凡是步骤可以被事先穷举的任务，用 Agent 循环只会同时换来更高的成本、更差的稳定性和更难归因的失败；而"该不该用 Agent"与"目标 / 边界 / 可用工具 / 完成条件能否写成一句可验证的话"，本质是同一个问题的两面。** `[共识]`

这个断言是可以被反驳的——如果存在一类任务，其步骤可事先穷举但自主体现在"步骤内部的判断质量"而非"步骤的选择"上，那么用 Agent 循环反而可能更优。反驳它的代价是必须先给出这类任务的判据（本文 §8 保留此分歧）。

展开为五条要点：

| # | 判断 | 说明 |
|---|---|---|
| 1 | **定义阶段的门禁是契约，不是文档** | 五阶段链路①的门禁只有一条：契约四要素齐全且能写成一句可验证的话（`D00-地基-总纲.md` §2.2） |
| 2 | **五种 workflow 模式吃掉了大部分"看起来需要 Agent"的需求** | 提示链 / 路由 / 并行 / 编排者-工作者 / 评估者-优化者，控制流由代码决定而非模型决定 |
| 3 | **自主度不是开关，是五级阶梯** | 只读 → 草稿 → 审批后写入 → 额度内自治交易 → 自主循环；L2 到 L3 是可逆性的断点，不是程度的差别 |
| 4 | **HITL 是一组可枚举的触发条件，不是"偶尔问一下"** | 不可逆动作 / 低置信 / 超预算 / 跨权限 / 越出契约，五类，每类都要落到可判定的阈值上 |
| 5 | **过度授权（Excessive Agency）已被列为 LLM 应用第 3 大风险** | OWASP Top 10 for LLM Applications 2026 版（2026-08-03）将 Excessive Agency 由第 6 位升至第 3 位，System Prompt Leakage 退役并替换为覆盖面更广的 Hidden Context Exposure `[已验证]` |

**术语纪律**：任务契约**不是**状态（状态随一次运行变化，契约不随运行变化）、**不是**记忆（记忆跨会话累积高显著度事实，契约是一次性规格）、**也不是**检查点（检查点是状态快照，用于恢复与重放）。三者口径见 `D00-地基-总纲.md` §9。

## 1. 问题定义与边界

### 1.1 本文解决的问题

1. 给定一个业务需求，**用什么判据**决定它是 workflow 还是 Agent？
2. 契约四要素（目标 / 边界 / 可用工具 / 完成条件）各自要写到什么颗粒度，才算"可验证"？
3. 自主度如何分级，每一级对应怎样的风险定价与前置条件？
4. 风险分级如何由"影响面 × 可逆性 × 置信度"推导出运行时门禁？
5. 什么情况下必须停下来问人（HITL 触发条件），由谁决定问还是不问？

### 1.2 本文不讨论什么

- **不讨论编排拓扑**——"谁调用谁、几个循环、是否有中心调度"属于 `D03-地基-编排模式.md`。本文只回答"该不该循环、循环到几级自主"。
- **不讨论上下文策略**——"每次调用装什么、怎么压缩"属于 `D04-运行时-上下文工程.md`。
- **不讨论强制点的实现机制**——"拦截器怎么写、沙箱怎么搭、审批门怎么挂"属于 `D10-质量-安全护栏.md`。本文只产出策略（策略 = 什么时候该拦），D10 产出机制（机制 = 怎么拦得住）。
- **不讨论人机交互的界面与事件契约**——"审批卡片长什么样、流式事件怎么发、澄清话术怎么设计"属于 `D14-交付-人机协作.md`。
- **不讨论评测集与打分器**——"成功标准怎么变成 CI 里的断言与阈值"属于 `D09-质量-评测.md`。
- **不讨论单个行业的具体合规要求**——本文给的是通用分级方法，行业红线由项目侧治理文档承接。

## 2. 设计思路

### 2.1 第一性原理：Agent 的收益来自"处理事先不知道步骤的任务"，代价是引入四类新的不可控

一个任务的解法可以放在一条光谱上：

```text
完全可穷举 ────────────────────────────────────► 完全不可穷举
（步骤固定、分支有限）              （每步取决于上一步的返回，无法预写）
      │                                                  │
   用代码编排                                       用 Agent 循环
（提示链/路由/并行/编排者-工作者/评估者-优化者）      （模型决定步数与工具）
```

**第一性原理**：只有当"下一步做什么"必须依赖运行时才能知道的信息时，把控制流交给模型才有净收益。一旦控制流可以预先写死，模型带来的不确定性就是纯粹的成本——它在做一件代码可以做得更稳、更便宜、更可测的事。

### 2.2 不可回避的约束

| 约束 | 物理/架构性质 | 对契约设计的直接影响 |
|---|---|---|
| **非确定性** | 同一输入多次运行结果可能不同（采样温度、模型版本、工具时序） | 完成条件必须是**可判定**的，不能用"看起来不错"；契约必须能被多次运行验证 |
| **误差复合** | 每步正确率 p，n 步后联合正确率约为 pⁿ。每步 95% 正确，20 步后约 36%（本文算术推导 · 2026-09-29 · 复现） | 必须给循环上界与步数预算；长链路任务应改为"分段可验证"而不是"一次跑到底" |
| **可逆性不可逆** | 一旦动作产生外部副作用（资金、法律承诺、对外可见消息），回滚成本从"代码"变成"人" | 自主度上界由**可逆性**而非数据量决定 |
| **注意力与上下文有限** | 上下文越长关键信息召回越差（context rot，见 `D04-运行时-上下文工程.md`） | 契约必须给出"边界"来裁剪决策空间，边界越窄，Agent 需要装的东西越少 |
| **人的注意力稀缺** | 连续审批会引发告警疲劳，人开始盲批 | HITL 触发条件必须有阈值，且单任务审批密度要有上界，否则 HITL 变成形式主义 |
| **成本上界不可静态计算** | workflow 的成本可静态算出，Agent 的成本依赖步数 | 契约必须携带预算（token / 墙钟 / 调用次数 / 金额），否则无法做门禁 |

### 2.3 由此推导出的核心取舍

**取舍一：宁可把可穷举的步骤写成 workflow，也不为了"看起来智能"而用 Agent 循环。** 因为非确定性与误差复合是架构性质而非实现缺陷——换更强模型只能缓解，不能消除。步骤可穷举时，workflow 在成本、稳定性、可测试性、可归因性四个维度上同时胜出；只有"下一步依赖运行时才可知的信息"时，Agent 的收益才开始为正。

**取舍二：宁可把契约边界写窄（少给工具、短清单），也不给"以防万一"的宽权限。** 因为工具集合是 Agent 的**动作空间**，动作空间越大，出错方式越多，且越难用白名单做横向强制约束。OWASP LLM Top 10 2026 版把 Excessive Agency 排到第 3 位，正是"给得太多"的统计后果 `[已验证]`。边界写窄的代价是可能需要二次补权，远小于越权动作的代价。

**取舍三：宁可在不可逆动作上让 Agent 停下来问人，也不赌置信度。** 因为可逆错误的代价是时间，不可逆错误的代价是钱、法律、信任。回滚成本一旦越过"人"这条线，自主度上界就落到 L2 或以下，与模型置信度无关——置信度只决定**问谁、问多细**，不决定**要不要问**。

读者读完这三条取舍，应能自行推出后文结论：五模式判据表、自主度五级阶梯、风险矩阵三乘三推导、HITL 五类触发条件。

## 3. 通用方案

### 3.1 方案 A · 固定工作流（workflow）

**机制**：控制流由代码写死，LLM 只负责每个节点内部的生成或判断。Anthropic《Building Effective Agents》归纳出五种模式 `[共识]`：

| 模式 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **提示链**（Prompt chaining） | 拆成固定顺序的多次调用，每步输出作为下一步输入，中间可插入程序化校验门 | 任务可稳定分解为前后依赖的固定步骤，且每步可独立验收 | 延迟随步数线性增长；任一中间步的错误向下游传播且难回滚 | 下一步内容依赖中间返回、无法事先确定 |
| **路由**（Routing） | 先分类，再分派到各自的专用下游处理链 | 输入可离散为少数几类，且各类最优处理方式显著不同 | 需要维护分类器与每条分支；误分类会走错整条链且下游无法自救 | 输入类型连续分布、无法离散化；或分类本身就需要多轮 |
| **并行**（Parallelization） | 分段并行（splitting，独立子任务同跑）或投票并行（voting，同一任务多跑取共识） | 子任务互相独立；或需多路独立判断以提升置信度 | token 成本成倍；聚合逻辑本身可能引入新错误 | 子任务之间存在强依赖或共享写操作 |
| **编排者-工作者**（Orchestrator-workers） | 中心 LLM 在运行时**动态**决定拆出哪些子任务，分派给工作者后汇总 | 子任务无法事先枚举，但每个子任务结构简单 | 中心节点是单点瓶颈与单点故障；中心上下文成为复杂度集中地 | 子任务可穷举（此时提示链更便宜且更稳） |
| **评估者-优化者**（Evaluator-optimizer） | 一个角色生成、另一个角色按明确标准评估并给出改进反馈，循环迭代 | 存在可判定的评价标准，且迭代能带来可见改进 | 循环次数不确定，成本不可预测 | 评价标准主观或缺失（缺失时退化为"越改越差") |

**适用条件**：任务步骤可在设计期穷举；分支有限；每步的输入输出契约稳定。

**代价**：灵活性为零——设计期没想到的输入只能进兜底分支；新增分支需要改代码与重测。

**不适用场景**：步骤依赖运行时才能得知的信息（例如"先看查询结果才知道要查什么"）。

### 3.2 方案 B · 单自主 Agent 循环

**机制**：模型在循环中自行决定调用哪个工具、传什么参数、何时停止。控制流由模型在运行时产生（ReAct 式"思考 → 动作 → 观察"是这一形态的最小实现，拓扑细节见 `D03-地基-编排模式.md`）。

**适用条件**：步骤不可事先枚举；任务的成功判定可以被写成一句可验证的话；工具集合可以收敛到一个受控白名单。

**代价**：成本上界不可静态计算（需运行时预算）；失败需轨迹回放才能归因；必须为循环上界、终止条件、每轮预算额外设计。框架映射（仅作形态参考，版本需重新核验）：OpenAI Agents SDK 0.2x、Claude Agent SDK 0.2.x、Pydantic AI V2 均提供最小循环原语 `[共识]`。

**不适用场景**：步骤可穷举（此时方案 A 全面更优）；不可逆动作占比高且无审批门；任务成功标准无法写清（此时连评测都做不了）。

### 3.3 方案 C · 混合：工作流骨架 + 局部 Agent 节点

**机制**：整体用方案 A 的固定骨架保证可预测性，只在"步骤确实不可枚举"的少数节点内部放一个受上界约束的 Agent 循环。骨架负责顺序、门禁与审计点，Agent 节点只负责局部开放性。

**适用条件**：任务大部分可穷举，但存在一到两个天然的开放点（例如"从非结构化材料中抽取一组约束"）。

**代价**：需要同时维护两套心智模型；边界划不好会出现"骨架里的 Agent 做了骨架不该做的事"，需要显式的工具白名单做隔离。框架映射：LangGraph 1.x（1.0 GA 2025-10-22）的状态图模型天然支持"节点内是 Agent、节点间是确定性边"，是这一方案最常见的承载 `[共识]`。

**不适用场景**：任务整体都不可穷举（此时直接方案 B，强加骨架只会限制能力）；团队尚未建立轨迹采集能力（混合形态的调试成本高于纯形态）。

### 3.4 方案 D · 自主度递进（渐进式自治）

**机制**：不把自主度当作一次性开关，而是按五级阶梯逐步放开，每级对应明确的准入条件与风险定价。这是**与方案 A/B/C 正交**的一个维度的选择——无论选哪种拓扑，都需要标定自主度。

| 级别 | 名称 | Agent 被允许做的 | 人做什么 | 准入条件 | 主要风险 |
|---|---|---|---|---|---|
| **L0** | 只读 | 检索、计算、生成草稿，**不产生任何外部副作用** | 无 | 无 | 信息泄露（跨租户/越权读取） |
| **L1** | 草稿 | 产出拟提交内容并给出执行建议，**由人手动执行** | 逐条确认并手动落地 | 无 | 内容事实性错误 |
| **L2** | 审批后写入 | 准备写入操作并请求批准，批准后**自行执行写入** | 单次审批（每动作一次） | 每条写入路径有明确的责任人 | 审批疲劳导致盲批 |
| **L3** | 额度内自治交易 | 在**额度 / 白名单 / 时间窗**内自动执行不可逆动作 | 事后审计 + 异常告警 | 额度上界、白名单、可撤销窗口、回滚预案四者齐备 | 资金 / 法律 / 对客承诺损失 |
| **L4** | 自主循环 | 自主设定子目标、连续执行多轮直至完成条件满足 | 仅在 HITL 触发条件命中时介入 | L3 全部条件 + 循环上界 + 全局预算 + 熔断 | 目标漂移、级联错误、成本失控 |

**关键断点**：**L2 → L3 不是"程度的差别"，是"性质的差别"**——可逆性从"可撤销（成本是时间）"跃迁为"不可撤销（成本是钱/法律/信任）"。因此 L3 的准入条件不是"模型表现足够好"，而是"额度、白名单、撤销窗口、回滚预案四者齐备"。

**适用条件**：任何 Agent 项目，尤其是需要上生产的项目——用递进方式替代"一次放开"。

**代价**：前期需要人工介入，吞吐低于全自主；需要为每一级单独设计监控与门禁。

**不适用场景**：完全无副作用的纯咨询场景（可直接 L0/L1，无需阶梯）；人工介入成本远高于错误成本的一次性内部任务（过度设计）。

### 3.5 契约的三种表达密度

| 表达密度 | 形态 | 谁负责 | 机器可判定 |
|---|---|---|---|
| **一句话契约** | 自然语言"做 X，不做 Y，用这些工具，完成当且仅当 Z" | 本文 | 否 |
| **结构化契约** | 字段化契约对象（见 §4.2） | 本文 | 部分（字段存在性与枚举值可校验） |
| **可执行契约** | 完成条件编译为断言、门禁与评分器 | `D09-质量-评测.md` | 是 |

判据：定义阶段至少产出前两种；第三种是验证阶段的输入，本文不承担。

### 3.6 选型判据

**决策树**（按顺序问，任一问题命中即停）：

```text
① 任务的每一步能否在设计期穷举？
   ├── 能 → ② 步骤之间有前后依赖吗？
   │        ├── 有 → 提示链（方案 A）
   │        └── 无 → 并行（方案 A）
   └── 不能 → ③ 是"分类后走不同链"吗？ → 路由（方案 A）
             │
             └─ ④ 子任务结构简单但数量不可枚举？ → 编排者-工作者（方案 A）
                │
                └─ ⑤ 有明确可判定的评价标准且迭代能改进？ → 评估者-优化者（方案 A）
                   │
                   └─ 以上都不成立 → 单自主 Agent 循环（方案 B）；
                      若只有局部开放 → 混合（方案 C）
```

**自主度判据表**（无论拓扑如何，都要走这张表）：

| 问题 | 回答 | 自主度上界 |
|---|---|---|
| 动作会产生外部副作用吗？ | 否 | L0 或 L1 |
| 副作用可自动回滚吗？ | 是 | L3（仍需额度与白名单） |
| 副作用可回滚但需人工介入吗？ | 是 | L2（逐次审批） |
| 副作用不可回滚吗？ | 是 | **L2 封顶**，除非额度 / 白名单 / 撤销窗口 / 回滚预案四者齐备才可到 L3 |
| 需要自主设定子目标吗？ | 是 | L4，且必须同时具备循环上界、全局预算、熔断三个条件 |

## 4. 如何设计

### 4.1 步骤序列（每步标注产出物）

```text
① 写一句话任务陈述
   产出：一句可被反驳的命题（"让系统在无人确认下完成 X"）
        ↓
② 判定形态：workflow 还是 agent（§3.6 决策树）
   产出：形态判定表（含"为什么不是更简单的那一档"）
        ↓
③ 填契约四要素
   产出：目标 / 边界 / 可用工具 / 完成条件（四者齐全且成一句话）
        ↓
④ 标自主度等级
   产出：自主度矩阵（每个可写动作分别定级，不是整任务一个等级）
        ↓
⑤ 算风险分级（影响面 × 可逆性 × 置信度）
   产出：风险矩阵 + 由它推导的运行时门禁（auto / notify / approve / forbid）
        ↓
⑥ 枚举 HITL 触发条件
   产出：触发条件清单（每类一条可判定阈值 + 触发后动作）
        ↓
⑦ 与 D09 交接
   产出：完成条件 → 交给 `D09-质量-评测.md` §3① 编译为可判定断言
```

> **④ 的注意点**：自主度必须**按动作定级**，不能按任务定级。同一个任务里"读取资料"是 L0、"起草回复"是 L1、"发送回复"可能是 L3。给整任务一个等级是最常见的偷懒写法，后果是把只读动作和不可逆动作绑成同一门禁。

### 4.2 数据结构与接口形态

契约在落地时应是一个**不可变对象**（frozen），因为它在运行期不应被 Agent 自己改写——能被 Agent 改写的契约等于没有契约。

```python
from dataclasses import dataclass
from enum import Enum
from typing import Literal, Optional

class AutonomyLevel(str, Enum):
    L0_READ_ONLY = "read_only"                # 只读，无外部副作用
    L1_DRAFT = "draft"                        # 出草稿，人执行
    L2_APPROVED_WRITE = "approved_write"      # 审批后自行写入
    L3_BOUNDED_TRANSACT = "bounded_transact"  # 额度/白名单内自治执行不可逆动作
    L4_AUTONOMOUS_LOOP = "autonomous_loop"    # 自主设定子目标并连续执行

class Reversibility(str, Enum):
    REVERSIBLE = "reversible"; COSTLY = "costly"; IRREVERSIBLE = "irreversible"
    # 可自动回滚 / 可回滚但需人工或对外可见 / 不可回滚

class ImpactScope(str, Enum):
    SELF = "self"; ORG = "org"; EXTERNAL = "external"
    # 仅本租户内部可见 / 影响组织内部其他人或系统 / 影响外部实体

@dataclass(frozen=True)
class Budget:                             # 四维预算，任一维触顶都收紧门禁
    max_tokens: int; max_wall_clock_s: int; max_tool_calls: int; max_cost_units: float

@dataclass(frozen=True)
class TaskContract:                       # 契约不可变：Agent 不得改写自己的契约
    goal: str                             # 必填：一句话目标，含对象与成功判定
    boundary_exclude: list[str]           # 必填且非空：明确不做的事
    allowed_tools: list[str]              # 必填：工具白名单（显式枚举，禁止通配符）
    done_condition: str                   # 必填：可判定的完成条件
    forbid_conditions: list[str]          # 选填：一旦出现即终止的条件
    autonomy: AutonomyLevel               # 必填：默认自主度（按动作再细化，见下）
    max_steps: int                        # 必填：循环上界
    budget: Budget                        # 必填
    owner: str                            # 必填：契约责任人（L2 审批路由用）

@dataclass(frozen=True)
class ActionDisposition:                  # 按动作定级，而非按任务定级
    action_id: str; autonomy: AutonomyLevel
    reversibility: Reversibility; impact_scope: ImpactScope

@dataclass(frozen=True)
class RiskAssessment:                     # gate 由前三者推导（§4.3 矩阵）
    impact_scope: ImpactScope; reversibility: Reversibility
    confidence: float                             # 0.0–1.0：对该动作正确性的估计
    gate: Literal["auto", "notify", "approve", "forbid"]

@dataclass(frozen=True)
class HITLTrigger:                        # 五类触发条件，阈值见 §4.3
    kind: Literal["irreversible", "low_confidence", "over_budget",
                  "cross_permission", "out_of_contract"]
    threshold: str                                # 必填：可判定阈值表述
    on_trigger: Literal["pause", "ask", "handoff", "abort"]
    fallback: Optional[str] = None                # 无人响应时的兜底，默认必须收紧
```

### 4.3 关键参数与取值依据

参数不写"建议设为 X"，而写"由什么决定"。

| 参数 | 由什么决定 | 典型量级与调整信号 |
|---|---|---|
| `max_steps` | 由**最短必要步数**（人工完成本任务所需的最少外部动作数）的 P95 决定，取 2–3 倍 | 实测步数持续超过最短必要步数的 5 倍，说明是**规划或契约问题**，应先改契约（缩边界、拆任务），而不是继续加大上界 |
| `budget.max_tool_calls` | 由**下游系统的配额与限流**决定，取下游可承受速率的一个保守比例 | 若下游有明确 QPS 配额，上界不应让单任务占用显著份额；否则并发时会互相打死 |
| `confidence` 阈值 | 由**错误的代价**决定，不由模型能力决定 | 不可逆动作的阈值应设到"宁可多问一次"；可逆动作可以低。阈值上调的信号是被问到的人抱怨"这也要问我"——说明阈值过高但错误代价其实不高 |
| `impact_scope` 分级 | 由**出错后谁承担后果**决定，不由数据量决定 | 数据量大但只有本租户可见 = `SELF`；一行数据泄露给外部 = `EXTERNAL` |
| 自主度上界 | 由 `reversibility` 决定（见表） | `IRREVERSIBLE` 天然封顶 L2；`COSTLY` 可到 L2；`REVERSIBLE` 可到 L3（仍需额度与白名单） |
| HITL 审批密度 | 由**告警疲劳**约束决定 | 单任务连续审批次数累积到人开始盲批时即失效（安全运维领域对告警疲劳有长期记录 `[共识]`；具体阈值**必须自测** `[待验证]`）。缓解方式：批前聚合、抽样审计、把逐条审批改为"批量审批 + 事后抽检" |
| 撤销窗口 | 由**下游系统是否支持回滚**决定 | 支持回滚 = 可开 L3；不支持 = 必须 L2 封顶。撤销窗口长度应 ≥ 下游回滚接口的最长处理时间 |

**风险矩阵（影响面 × 可逆性）→ 运行时门禁**：

| 影响面 \ 可逆性 | 可自动回滚 | 可回滚但需人工/对外可见 | 不可回滚 |
|---|---|---|---|
| **仅自身**（`SELF`） | `auto` | `auto` | `approve`（置信度 ≥ 阈值可 `notify`） |
| **组织内部**（`ORG`） | `auto` | `notify` | `approve` |
| **对外**（`EXTERNAL`） | `notify` | `approve` | **`forbid`**（除非 L3 四条件齐备且在额度内） |

`confidence` 作为**修正项**而非独立维度：`confidence` 低于该类动作阈值时，门禁向上一档收紧（`auto → notify → approve`）；`confidence` 高于阈值时**不放松**已定的门禁——高置信度不能把不可逆动作变成可自动执行。这是"取舍三"的直接落地。

**HITL 五类触发条件**：

| # | 触发条件 | 可判定阈值示例 | 触发后动作 |
|---|---|---|---|
| 1 | **不可逆动作** | 该动作的 `reversibility = IRREVERSIBLE` 且不在 L3 白名单内 | `approve`（请求单次批准） |
| 2 | **低置信** | 对该动作正确性的内部估计 < 该类动作阈值 | `ask`（澄清或请求补充依据） |
| 3 | **超预算** | 已消耗 ≥ `budget` 任一维度的某个比例 | `pause`（暂停并汇报剩余可用预算） |
| 4 | **跨权限** | 需要的操作超出 `allowed_tools` 白名单或超出当前身份权限 | `handoff`（移交持有人或拒绝） |
| 5 | **越出契约** | 请求的动作落到 `boundary_exclude` 或命中 `forbid_conditions` | `abort`（终止并说明违反了哪条边界） |

> **运行时强制点**：以上五类只是**策略**。把策略变成"拦得住"的机制（拦截器、沙箱、审批门、guardian agent）属于 `D10-质量-安全护栏.md`。OWASP Agent Control Standard（2026-09-01/02 捐赠入 GenAI Security Project）把这类强制点表述为运行时 guardian，并以 OTel + OCSF 走遥测、以 CycloneDX/SWID/SPDX 出 AgBOM `[共识]`——即"策略可审计"本身也是要求。

### 4.4 分阶段实施路径

**最小可行版（第一次跑通契约）**：① 写一句话契约 + 结构化契约对象（§4.2 的 `TaskContract`），字段可少但四要素不可缺 → ② 走一次 §3.6 决策树，产出形态判定表 → ③ 只标两件事：`allowed_tools` 白名单（禁通配）与 `max_steps` 上界 → ④ HITL 只做一类：不可逆动作必须审批。**不做**：风险矩阵的完整推导、按动作定级、预算多维化。

**生产就绪版**：① 四要素全部落到 `TaskContract` 字段上，`boundary_exclude` 非空且经责任人签字 → ② 自主度**按动作**定级（`ActionDisposition` 列表），而非整任务一个等级 → ③ 风险矩阵三乘三推导完成，每个动作有明确 `gate` → ④ HITL 五类触发条件齐全，每类有可判定阈值与 `fallback` → ⑤ 预算四维化（token / 墙钟 / 调用次数 / 成本）并进入运行时门禁 → ⑥ 完成条件移交 `D09-质量-评测.md`，编译为 CI 断言与发布阈值 → ⑦ 契约进入版本管理，字段变更需评审——契约是接口，不是文档。

## 6. 常见陷阱

每条陷阱保留四字段（现象 / 根因 / 埋伏阶段 / 规避方式），前两者与后两者各合并一列以压缩篇幅。

| # | 陷阱 | 现象与根因 | 埋伏阶段 → 规避方式 |
|---|---|---|---|
| 1 | 用 Agent 循环实现可穷举的流程 | **现象**：步骤固定的多步流程被写成循环，成本高、结果不稳定。**根因**：把"看起来智能"当目标；或团队只有 Agent 框架经验、没有 workflow 经验，工具选择倒逼方案选择 | **定义**。一旦进入设计阶段，拓扑会围绕循环展开，退回 workflow 要重写 → 强制走 §3.6 决策树，并要求写出"为什么不是更简单的那一档"；写不出来的一律降档 |
| 2 | 自主度按任务定级而非按动作定级 | **现象**：整个任务标成 L2，只读检索也要审批，真·不可逆写入与只读操作共用同一门禁。**根因**：把自主度当任务标签而非动作属性，漏掉"同一任务内不同动作的可逆性天差地别" | **定义**（未按动作枚举），在**运营**期爆发：要么审批过密导致盲批，要么不可逆动作因"整体级别不高"被放过 → 用 `ActionDisposition` 按动作枚举；检查清单显式要求"只读与不可逆不在同一门禁下" |
| 3 | 完成条件写成主观描述 | **现象**：完成条件写成"满意的答复""信息足够全面"。**根因**：未区分"人看着满意"与"机器可判定"，把验收标准写成了感受 | **定义**，在**验证**期致命爆发：`D09-质量-评测.md` 无法据此构造断言，评测体系从第一步就建不起来 → 完成条件必须能回答"由谁、依据什么、在什么状态下判定完成"；答不出就回退重写目标 |
| 4 | 工具白名单给成"以防万一" | **现象**：工具集全量开放或使用通配符。**根因**：把工具集当"能力"而非"动作空间"；担心收紧后要二次补权 | **定义**，在**验证/运营**期爆发：越权动作在轨迹里可见但难以事前拦截，OWASP LLM Top 10 2026 版把 Excessive Agency 列到第 3 位正是这一模式的统计后果 `[已验证]` → 白名单显式枚举 + 禁止通配；补权走"请求扩权"的显式路径 |
| 5 | HITL 没有 fallback | **现象**：触发审批后审批人不在，任务无限等待或超时崩溃。**根因**：把 HITL 当成"发个请求就完了"，未定义无人响应时的行为 | **定义**（字段缺 `fallback`），在**运营**期以"任务卡死"或"超时自行放行"爆发，后者更危险，因为绕过了审批 → `HITLTrigger.fallback` 必填；超时默认行为必须是**收紧**（暂停/终止），不能是放行 |
| 6 | 契约可被 Agent 自己改写 | **现象**：Agent 运行中"觉得"目标不合适，自行改边界或扩大工具范围。**根因**：契约与状态混存，Agent 有写状态权限，于是也能写契约 | **设计/构建**（契约未设为不可变），在**运营**期以"越权动作"爆发，且轨迹上看起来像"Agent 自主决策"，极难归因 → 契约对象设为不可变；契约与运行时状态严格分离（`D00-地基-总纲.md` §9） |

## 7. 反例

### 反例 1 · 用一个 Agent 循环覆盖全部业务流程

**做法**：把"接收请求 → 检索信息 → 校验规则 → 生成结果 → 提交下游"整条链路塞进一个 ReAct 循环，不给步骤边界。
**爆掉的方式**：上线后第一个月成本是预算的 3 倍，且失败无法归因——"检索少查了一次"和"校验规则被跳过"在最终回复里长得一模一样。修复时必须先补轨迹采集（`D09-质量-评测.md` §3④），等于把定义阶段欠的债连本带利还回来。

### 反例 2 · 把不可逆动作和只读动作放在同一自主度等级

**做法**：为了"少打扰用户"，把整个任务设为 L3，包含查询与对外发送。
**爆掉的方式**：某次查询返回异常，Agent 在低置信下仍按 L3 自行对外发送了错误内容。复盘发现门禁是按任务定的，不可逆动作从未单独设审批——唯一补救是把自主度回退到 L2，但对外承诺已经发出，回滚成本远高于当初多做一次审批。

### 反例 3 · 契约只写在人看的文档里，代码里没有

**做法**：契约写成设计文档，运行时没有结构化契约对象，边界靠 system prompt 的自然语言描述约束。
**爆掉的方式**：模型在长上下文中逐渐遗忘边界，越界动作出现在轨迹里却没有强制点能拦。更糟的是变更边界时没人知道改哪里——文档与 prompt 会漂移，且没有一处权威。等到做合规审计时，无法回答"某次运行受哪一版契约约束"（`D16-交付-治理合规.md`）。

### 反例 4 · 完成条件依赖"用户满意"

**做法**：契约的完成条件写成"用户对结果表示认可"。
**爆掉的方式**：离线评测无法构造用例（没有可判定的终止状态），团队跳过结果层评测只做人工抽检。"用户没投诉"被当成成功，但真实故障率无法测量；等到客服数据回流才发现某类任务成功率不足一半——而这个问题本可以在定义阶段用一句可判定的完成条件提前暴露。

## 8. 开放问题

- **"可穷举"的判据是否够硬？** 本文用"步骤能否在设计期写出"作为分界，但实际中大量任务处于中间态：主干可穷举、分支不可穷举。此时"混合（方案 C）"的边界划在哪，目前只能靠经验。**待验证**：是否存在可量化的判据（例如"不可穷举的步数占比超过 X% 才值得上 Agent"）？
- **自主度的五级阶梯是否需要更细的分级？** 反对者认为 L2 到 L3 之间的跨度太大（"审批后写入"与"额度内自治交易"之间还有"抽样审计的小额自治"这类中间态）；支持者认为分级过多会导致每个项目自造等级、无法横向比较。**两派前提不同**：前者面向单项目的精细化运营，后者面向跨项目的治理对齐。
- **置信度如何获得？** §4.3 把 `confidence` 作为门禁修正项，但"Agent 对自身动作正确性的估计"目前没有可靠来源——用模型自报置信度存在系统性过度自信（厂商博客与学术讨论均提出过质疑，但结论未收敛 `[待验证]`）。可选替代：用多次采样的一致性（`pass^k` 类）作为置信度代理，但成本成倍。
- **HITL 的密度上界能否量化？** 本文只给出"必须自测"的结论。安全运维领域对告警疲劳有长期记录 `[共识]`，但"Agent 审批疲劳"的阈值是否与告警疲劳同构，尚无公开数据。
- **OWASP Agent Control Standard 的强制点模型会如何影响定义阶段？** 该标准 2026-09-01/02 才捐赠入 GenAI Security Project `[共识]`，工具链跟进中。若其 guardian agent 形态成为事实标准，定义阶段的产出可能需要多一个"强制点映射表"字段。**跟踪中。**
- **契约的变更该走什么流程？** 本文只说"进入版本管理、变更走评审"。但契约变更的语义影响与代码变更不同——它可能让历史评测集整体失效（`D17-迭代-迭代闭环.md`）。这条回边目前未定义。
