## 0. 总纲

> **多 Agent 的收益只有三种：上下文隔离、并行、职责分离。没有其中任何一种收益时引入多 Agent，只会让成本翻倍、把失败归因变成不可解问题，并新增一类单 Agent 不存在的失败源——协调失败。因此判断顺序永远是先问"单 Agent + 工具够不够"，只有回答"不够，且缺口恰好是这三种之一"时才进入多 Agent 设计。** `[共识]`

要点：

1. **多 Agent 不是"更聪明的单 Agent"**，而是"用更多模型调用与通信换取上下文容量或并行度"的工程手段；它不提升单点推理质量。
2. **成本近似与 Agent 数量同阶增长**，而收益只在特定前提下出现——**收益与成本不对称**，这是本主题最容易被忽略的事实。
3. **协调本身是新失败源**：死锁、环依赖、消息丢失、重复执行、互相等待，都是单 Agent 里不存在的模式。
4. **归因难题是结构性的**：失败发生在交接处时，"哪个 Agent 的责任"往往不可判定（回指 `D09-质量-评测.md` §9 开放问题）。
5. **协议分两层**：工具用 MCP（`2026-07-28`），Agent 之间用 A2A（`v1.0.1`），二者互补而非替代。

## 1. 问题定义与边界

### 1.1 本文解决的问题

一句话：**在"已经确定需要多个 Agent"的前提下，确定角色怎么分、它们怎么通信、任务生命周期由谁持有、冲突怎么消解、死锁与预算失控怎么拦。**

**第一道门：要不要多 Agent（先答这个，再读后文）**

| 问题 | 若回答为"否" | 结论 |
|---|---|---|
| 单 Agent 的失败是否**主要**来自上下文被塞满/被稀释？ | 否 | 不是多 Agent 的问题，先查上下文装配（`D04`） |
| 换成多 Agent 是否能带来**真实的并行**（独立子任务同时推进）？ | 否 | 引入多 Agent 只会增加成本 |
| 是否存在**必须隔离**的职责（如互斥的策略校验、互不信任的域）？ | 否 | 用工具 + 提示词约束通常足够 |
| 单 Agent + 工具 + 结构化状态是否已试过并测出瓶颈？ | 否 | **先做这一步**（`D03-地基-编排模式.md` §3） |

任何一行答"否"，都应先回到单 Agent 方案。**多 Agent 的正确性问题通常不是"要不要更多 Agent"，而是"上下文预算与工具设计没做好"。**

三条正当理由（且只有这三条）：

1. **上下文隔离**：子任务的噪音会污染主线推理，隔离后主线上下文显著变小、更准。
2. **并行**：子任务彼此独立，能真并发执行，缩短端到端延迟。
3. **职责分离**：不同角色需要不同的指令/权限/信任级别，混在一个 Agent 里无法独立约束。

### 1.2 本文不讨论什么

- **不讨论"该选哪种编排拓扑"的第一层选型**（含轻量 handoff）——那是 `D03-地基-编排模式.md` 的职责；本文承接其结论，讨论落地细节。
- **不讨论工具协议的实现**（MCP 无状态迁移、工具契约）——归 `D06-运行时-工具与协议.md`。

- **不讨论多租户隔离与跨组织信任边界**——归 `D16-交付-治理合规.md`。
- **不讨论子 Agent 的上下文如何装配与裁剪**——归 `D04-运行时-上下文工程.md`；本文只决定"隔离边界画在哪里"。

## 2. 设计思路

### 2.1 第一性原理：多 Agent 用"复制模型实例 + 隔离上下文"换取容量，代价是引入一个分布式系统

单 Agent 的瓶颈不是"不够聪明"，而是**上下文预算有限且注意力会被稀释**（回指 `D04-运行时-上下文工程.md`）。多 Agent 的本质是：把一个大问题切成若干能被独立上下文容纳的子问题，每个子问题由一个独立模型实例处理。

一旦这么做，就同时获得了一个**分布式系统**的全部难题：通信不可靠、状态需一致、任务可能重复执行、可能互相等待、可能形成环。**这些难题在单 Agent 里不存在，但在多 Agent 里必须显式解决**——而多数多 Agent 失败不是"Agent 不够强"，而是"没人负责这些分布式问题"。

### 2.2 不可回避的约束

| 约束 | 性质 | 对设计的强制影响 |
|---|---|---|
| **上下文隔离是有代价的**：隔离后，子 Agent 看不到主线信息 | 架构性 | 交接必须显式传递"必要且充分"的上下文，多传则失去隔离收益、少传则子 Agent 缺信息 |
| **通信不是零成本**：每次交接都消耗 token、延迟与可观测性 | 工程性 | 交接次数应受预算约束；"频繁小额交接"是典型反模式 |
| **成本随 Agent 数近似同阶增长** | 经济性 | 必须有**跨 Agent 的预算护栏**，否则一次失控的协作会烧掉整轮预算 |
| **并行带来的状态合并冲突** | 分布式 | 共享状态必须有归约语义（回指 `D05-运行时-记忆与状态.md` §3.2），否则覆盖丢数据 |
| **环依赖可能发生**：A 等 B、B 等 A | 图论 | 必须有**环检测 + 深度上限 + 死锁超时**，否则任务永久挂起 |
| **归因困难是结构性的** | 观测 | 交接处必须携带可追溯的关联标识，否则失败无法归口（`D11-质量-可观测性.md`） |
| **过度授权是 Agent 专属高危项** | 安全 | OWASP 2026 版把 Excessive Agency 由第 6 位升至第 3 位 `[已验证]`；多 Agent 会放大它（每个 Agent 都可能被授予过宽权限） |

### 2.3 由此推导出的核心取舍

**取舍一：宁可 Agent 数量少、交接次数少，也不追求"分工看起来很美"。** 每次交接都是一次有损压缩：上下文在传递中被裁剪，语义在角色切换中丢失。**Agent 数与交接数是最直接的复杂度与成本乘数**，能在单 Agent 内用工具或状态解决的问题不应升级为交接。

**取舍二：宁可让任务真相源单一（一个明确持有者），也不让多个 Agent 各自维护"我的版本"。** 多份真相会立刻带来一致性、冲突消解与"谁说了算"的问题。**单一持有者 + 明确读写权限**比"人人可写、最后合并"简单得多，也更可调试。

**取舍三：宁可保守地设深度与预算上限（可能少做一点），也不放任协作自由展开。** 不受限的多 Agent 协作最坏情况是"无限交接 + 无限等待 + 无限成本"。**上限要保守，且必须可观测、可熔断**——宁可任务显式失败并回报，也不要静默烧预算。

## 3. 通用方案

### 3.1 角色划分的三种原则

| 原则 | 怎么分 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **按能力** | 按"会不会做"分（检索型 / 计算型 / 生成型 / 校验型） | 子任务的能力需求差异明显 | 同一领域知识在多个 Agent 重复装配，上下文冗余 | 能力边界重叠、任务高度混合 |
| **按领域** | 按"熟不熟这块"分（领域专家各管一摊） | 领域知识体量大、彼此独立 | 跨领域任务需要额外协调；领域划分过细会碎片化 | 领域知识小、任务跨领域频繁 |
| **按阶段** | 按"流程走到哪"分（规划 / 执行 / 校验 / 收敛） | 流程阶段清晰、各阶段目标不同 | 阶段间强耦合时，交接信息损失大 | 阶段间需要频繁回退的场景 |

> **经验规则**：角色划分的粒度由"上下文能否被独立容纳"决定，而不是由组织架构或人类团队分工决定。**当两个角色必须共享大量上下文才能工作时，它们应该合并。**

### 3.2 通信拓扑（五种）

| 拓扑 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **Supervisor 中心化** | 一个 Supervisor 持有全部决策权，把子任务派给 Worker 并汇总；Worker 之间不直接通信 | 任务可分解为相对独立的子任务、需统一收敛与预算控制 | Supervisor 成为上下文与延迟瓶颈，其失败 = 全系统失败（单点）；大规模下派发开销上升 | 子任务间需大量直接协商；Supervisor 上下文装不下汇总信息 |
| **Hierarchical 分层** | Supervisor 之上再套 Supervisor，形成多层派发树；每层只与直接上下级通信 | 任务可递归分解、规模大、需组织化的权限与预算层层收敛 | 层级越深信息越失真（每层一次有损压缩）；深度与延迟线性增长；归因更难 | 扁平小规模任务（引入层级属过度设计） |
| **Peer 对等** | Agent 平等，可互相直接请求；无中心调度者，靠协议与约定协调 | 角色少（2–4）、能力互补、交互模式简单固定 | 无全局视图，易形成环依赖与互相等待；预算无法集中控制；冲突消解缺仲裁者 | 角色多、交互复杂、需统一治理 |
| **Swarm 去中心** | 无固定角色分工，靠局部规则与共享信号动态分工（如"谁空闲谁接手"） | 任务高度同质、可并行切分、允许近似解 | 行为不可预测、难以复现与评测；成本上限难界定；调试困难 | 要求可复现、可审计、有硬性正确性要求 |
| **Blackboard 共享黑板** | Agent 不直接通信，读写同一共享结构；谁有能力谁在合适时机贡献 | 多角色需对同一状态逐步迭代（多轮校验、增量推断） | 共享结构的并发写需归约（回指 `D05-运行时-记忆与状态.md` §3.2）；黑板膨胀会拖垮上下文；触发规则复杂 | Agent 间不需共享中间状态、任务可完全独立切分 |

### 3.3 A2A `v1.0.1`：Agent 之间的协议

> 版本口径：`v1.0.1`（2026-05-28），首个稳定版 `v1.0.0` 于 2026-03-12；**AgentCard 格式在 v0.3 → v1.0 之间不向后兼容，升级必须两端同改** `[已验证]`。

**四个核心对象（结构性描述属 `[共识]`）**：

| 对象 | 承载什么 | 关键点 |
|---|---|---|
| **AgentCard** | Agent 的元数据与能力声明（标识、能力、技能、端点、鉴权方式） | 是**发现与信任的入口**；版本变更最先冲击它 |
| **Task** | 一次委托的工作单元及其生命周期状态 | 是**跨 Agent 的真相单元**；状态流转必须显式 |
| **Message** | 任务内的消息（含角色与内容分片） | 承载澄清、追问、进度 |
| **Artifact** | 任务的产出物 | 产出与过程分离，便于交付与评测 |

**发现机制**：通过约定的 well-known 端点或注册中心获取 AgentCard（具体路径与注册形态随版本演进，落地时以官方规格为准）`[共识]`。

**鉴权与签名**：AgentCard 声明鉴权方式；跨组织调用需要**可验证的来源身份**（签名/凭据），否则无法区分"可信 Agent"与"冒充者"。信任边界的治理归 `D16-交付-治理合规.md`。

**v0.3 → v1.0 的不兼容性要点**：

- AgentCard 的结构发生变化，**旧解析器无法直接读取新格式**；
- 升级必须**两端同时改**，无法单边灰度；
- 因此**多 Agent 系统上线前必须核对两端的协议版本**，否则表现为"能连通但字段解析失败"或直接握手失败。

### 3.4 选型判据

```
是否需要统一收敛与集中预算控制？
├─ 是 → 任务是否可递归分解且规模大？
│         ├─ 是 → Hierarchical
│         └─ 否 → Supervisor
└─ 否 → 角色数是否 ≤ 4 且交互简单？
          ├─ 是 → Peer
          └─ 否 → 是否需要多角色对同一状态迭代？
                    ├─ 是 → Blackboard
                    └─ 否 → Swarm（仅在允许近似解、可接受不可复现时）
```

| 判断问题 | 若回答为 | 建议 |
|---|---|---|
| 角色数 > 4 且无人统一调度？ | 是 | **不要用 Peer**，先引入 Supervisor |
| 子任务彼此独立、可真并发？ | 是 | Supervisor + 并行 Worker（收益最大的组合） |
| 需要多个角色反复迭代同一份中间状态？ | 是 | Blackboard（必须配归约语义） |
| 要求可复现、可审计、有硬正确性要求？ | 是 | **排除 Swarm** |
| 是否存在跨组织的对端 Agent？ | 是 | 必须先解决身份与信任（`D16`） |

## 4. 如何设计

### 4.1 步骤序列（每步标产出物）

```text
① 先证明"单 Agent 不够"            → 产出：瓶颈证据（上下文/并行/职责，三者之一）
② 选角色划分原则（能力/领域/阶段）  → 产出：角色清单（含"为何不能合并"的说明）
③ 画拓扑与通信边                   → 产出：拓扑图（节点=角色，边=交接） + 交接清单
④ 定任务真相源归属                 → 产出：Task 状态机 + 唯一持有者 + 读写权限表
⑤ 定通信协议（A2A / 内部约定）      → 产出：AgentCard 字段 + Task/Message/Artifact 结构
⑥ 定冲突消解规则                   → 产出：冲突类型 → 消解策略 映射表
⑦ 定死锁/环依赖/预算护栏           → 产出：深度上限 + 环检测 + 熔断阈值 + 预算上限
⑧ 定归因标识（关联 ID 贯穿）        → 产出：跨 Agent 的 trace 关联方案（回指 D11）
```

### 4.2 数据结构与接口形态

**A2A 四个对象的最小形态（示意，字段名中性化）**：

```python
from typing import Literal, Optional
from pydantic import BaseModel

class AgentCard(BaseModel):
    name: str
    description: str
    protocol_version: str                          # 必填：如 "v1.0.1"，两端必须匹配
    capabilities: list[str] = []                   # 声明的能力/技能
    endpoint: str                                  # 调用入口
    auth_scheme: str                               # 鉴权方式声明（强制点归 D10）
    signature: Optional[str] = None                # 跨组织时需可验证来源

class Task(BaseModel):
    task_id: str
    parent_task_id: Optional[str] = None           # 任务树：环检测与预算归集
    state: Literal["submitted", "working", "input_required", "completed", "failed", "canceled"]
    owner_agent: str                               # 真相源归属：唯一持有者
    depth: int                                     # 当前层级深度，用于上限熔断
    budget: "Budget"
    correlation_id: str                            # 贯穿全链路的归因标识

class Message(BaseModel):                           # 任务内消息：承载澄清、追问、进度
    task_id: str
    role: Literal["requester", "responder"]
    parts: list[str]                                # 内容分片（文本/结构化）
    created_at: str

class Artifact(BaseModel):                          # 任务产出物：产出与过程分离
    task_id: str
    kind: str
    content_ref: str                                # 引用而非内联大对象

class Budget(BaseModel):
    max_depth: int                                  # 委派深度上限
    max_agents: int                                 # 参与 Agent 数上限
    max_tokens: int
    max_handoffs: int                               # 交接次数上限
    deadline_ms: int
```

> **设计要点**：`parent_task_id` + `depth` + `correlation_id` 三个字段是**治理三件套**——前者支撑环检测与预算归集，中者支撑深度熔断，后者支撑归因（回指 `D11-质量-可观测性.md`）。缺失任意一个，后续的熔断与归因都做不了。

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 取值信号 |
|---|---|---|
| **委派深度上限** | 任务的信息失真率与延迟预算 | 每层一次有损压缩；深度由"可接受的失真程度"与"延迟预算 ÷ 单层耗时"取较小者 |
| **参与 Agent 数上限** | 成本预算与收益来源 | 由"并行收益是否仍超过协调成本"决定；协调成本随 Agent 数增长，收益常在某点后趋平 |
| **单任务交接次数上限** | 每次交接的 token 与延迟成本 | 由总预算 ÷ 单次交接成本反推；**交接次数比 Agent 数更能预测失控** |
| **任务超时 / 死锁超时** | 正常链路 P99 | 死锁超时应显著大于正常 P99（否则误杀），但小于用户可接受等待 |
| **熔断阈值** | 环依赖发生率与失败代价 | 触发条件示例：深度触顶、同一 Task 重复进入同一 Agent、等待链超过 N 跳 |
| **预算护栏（token/成本）** | 业务成本上界 | 由单次协作的可接受成本决定；**必须在运行时强制扣减，而非事后统计** |
| **广播/协商粒度** | 拓扑与消息成本 | Peer/Swarm 下消息数随角色数超线性增长；由"消息数上限"反向约束角色数 |
| **归因标识粒度** | 需要区分的故障粒度 | 粒度由"是否要能回答'哪个交接点失败'"决定 |

### 4.4 分阶段实施路径

| 阶段 | 做什么 | 不做什么 |
|---|---|---|
| **最小可行** | 固定 2–3 个角色 + Supervisor 中心化 + 单一真相源 + 深度/预算上限 + 关联 ID 贯穿 | 不做 Hierarchical、不做 Peer、不做 A2A 跨组织、不做动态 role 分配 |
| **生产就绪** | 任务状态机显式化；冲突消解规则成表；环检测 + 死锁超时 + 预算护栏全部落地并可观测；A2A 两端版本锁定（`v1.0.1`）；交接信息最小充分性有校验 | 不做 Swarm（除非明确接受不可复现） |
| **规模化** | 分层拓扑 + 每层预算收敛；跨组织信任与签名（`D16`）；多 Agent 失败归因体系（`D09`/`D11`） | 不在缺少归因手段时扩大 Agent 数量 |

### 4.5 冲突消解

多 Agent 的冲突有两类：**事实冲突**（对同一状态/数据的分歧）与**决策冲突**（对下一步做什么的分歧）。四种消解策略：

| 策略 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **仲裁者（Arbiter）** | 指定一个 Agent/规则做最终裁定 | 冲突频繁、需要快速收敛 | 仲裁者成为单点与瓶颈；可能引入偏见 | 仲裁者不具备裁决所需信息 |
| **投票（Voting）** | 多个 Agent 表决，多数/加权多数 | 答案可枚举、Agent 相对独立 | 成本乘以投票人数；平票需兜底规则 | 答案开放、Agent 高度相关（同源错误会一起投错） |
| **优先级（Priority）** | 按预设优先级定谁说了算（如校验角色 > 执行角色） | 角色存在天然的权威差异 | 低优先级方的信息可能被忽略 | 角色无天然权威差异 |
| **证据回收（Evidence Reclaim）** | 冲突双方提交证据（`evidence_ref`，回指 D06 契约），由证据强度裁定 | 冲突可被外部事实仲裁 | 需要证据可追溯；无证据时退化 | 冲突源于判断而非事实 |

> **兜底规则**：任何策略都必须定义"无法判定时怎么办"。常见兜底是**保留双方分歧并上升为 `input_required`**（向人求助），而不是静默取一条——静默取一条会把不确定性藏起来，后续无法归因。

### 4.6 死锁、环依赖、熔断与预算护栏

**环依赖的三种形态**：

| 形态 | 表现 | 检测方式 |
|---|---|---|
| **直接环** | A 等 B，B 等 A | 等待图（wait-for graph）检测环 |
| **间接环** | A→B→C→A | 同上，需全局等待图 |
| **自环 / 重复委派** | 同一 Task 反复回到同一 Agent | 记录 `(task_id, agent_id)` 出现次数，超阈值即熔断 |

**熔断触发条件（建议集）**：

1. `depth` 触达 `max_depth`；
2. 同一 `task_id` 重复进入同一 Agent 超过 N 次；
3. 等待链长度超过 N 跳且无进展（心跳超时）；
4. 累计 token / 成本触达 `budget` 上限；
5. 交接次数触达 `max_handoffs`。

**熔断后的动作**（必须显式定义，不能只"断"）：

```text
熔断 → ①冻结该子树的继续委派
      → ②把当前状态物化为检查点（回指 D05）
      → ③按 Artifact 交付"已完成部分" + 明确未完成部分
      → ④向人上升：input_required 或显式失败
```

> **原则**：熔断的产物必须是**可交付的部分结果 + 明确的未完成项**，而不是"任务消失"。静默停止与静默失败同样危险。

### 4.7 任务生命周期与真相源归属

| 问题 | 必须显式回答 | 后果（不回答时） |
|---|---|---|
| **谁持有真相源？** | 每个 Task 必须有唯一 `owner_agent` | 多份真相 → 冲突消解无从下手 |
| **谁可以写？** | 读写权限表（其他 Agent 只读或只能请求） | 并发写 → 覆盖丢数据 |
| **状态如何流转？** | 显式状态机（submitted → working → input_required/completed/failed/canceled） | 隐式状态 → 无法判断卡在哪 |
| **sub-agent 的状态是否回传？** | 回传"结论 + 证据位置"，而非全部中间状态 | 回传全部 → 隔离收益归零 |

## 5. 检查清单

### 5.1 「最小可行」

- [ ] 有书面证据证明"单 Agent + 工具不够"，且缺口属于上下文隔离 / 并行 / 职责分离之一
- [ ] 每个 Task 有唯一 `owner_agent`（真相源唯一）；任务状态机显式且状态取值可枚举
- [ ] 有委派深度上限与参与 Agent 数上限，且运行时强制
- [ ] 有预算护栏（token/成本/交接次数），且是运行时扣减而非事后统计
- [ ] 跨 Agent 有统一的关联标识（correlation id）贯穿
- [ ] 定义了熔断后的动作（物化检查点 + 交付部分结果 + 上升）

### 5.2 「生产就绪」

- [ ] 交接信息满足"最小充分性"：交接内容有明确来源与用途，不传冗余上下文
- [ ] 冲突消解规则成表，且每种策略都有"无法判定时"的兜底
- [ ] 环依赖检测落地（等待图 / `(task_id, agent_id)` 计数），并有对应熔断
- [ ] 每个 Agent 的权限/工具集是最小化的（OWASP Excessive Agency 已升至第 3 `[已验证]`）
- [ ] 使用 A2A 时，两端协议版本一致（`v1.0.1`），且 AgentCard 解析失败有明确告警
- [ ] 跨组织调用有可验证的身份与签名，信任边界有定义（`D16`）
- [ ] 多 Agent 失败可归因到具体 Agent 或具体交接点（回指 `D11`）
- [ ] 并行分支的共享状态有归约语义（回指 `D05` §3.2）；成本与 Agent 数、交接次数进入监控（`D15`）

## 6. 常见陷阱

### 陷阱 1 · 用多 Agent 掩盖上下文工程问题

**现象**：单 Agent 表现差，就拆成多个 Agent，结果总成本翻数倍、效果无改善。
**根因**：真实瓶颈是上下文装配不当（塞太多/检索不准），拆分只是把问题复制了多份。
**埋伏阶段**：定义（①）——跳过"单 Agent 够不够"的判断。
**规避**：先按 §1.1 的四问自检；只有缺口是三种收益之一时才拆。

### 陷阱 2 · 无唯一真相源

**现象**：多个 Agent 各自维护一份任务状态，出现"两个 Agent 对进度说法不一致"。
**根因**：没有指定 `owner_agent`，把"共享"误解为"人人可写"。
**埋伏阶段**：设计（②）——任务生命周期设计时未定归属。
**规避**：每个 Task 唯一持有者 + 明确读写权限表（§4.7）。

### 陷阱 3 · 交接信息过多或过少

**现象**：过少 → 子 Agent 缺关键约束、重复提问；过多 → 子 Agent 被噪音带偏、隔离收益归零。
**根因**：交接内容没有"最小充分性"标准，凭直觉粘贴上下文。
**埋伏阶段**：构建（③）——实现交接时直接透传全部上下文。
**规避**：交接传"结论 + 范围 + 证据位置 + 下一步"（回指 `D06` 的工具契约思路），不传原始过程。

### 陷阱 4 · 环依赖导致任务永久挂起

**现象**：系统"卡住"，无报错、无超时，任务永不完成。
**根因**：没有等待图检测，也没有深度上限；A 等 B、B 等 A 时双方都在等。
**埋伏阶段**：设计（②）——拓扑设计时未考虑环的可能。
**规避**：等待图环检测 + `(task_id, agent_id)` 重复计数 + 等待链超时（§4.6）。

### 陷阱 5 · 预算无护栏，一次协作烧掉整轮预算

**现象**：某次任务因循环委派或重复交接消耗了远超预期的 token/成本。
**根因**：预算只是"事后统计"，没有在运行时强制扣减与熔断。
**埋伏阶段**：设计（②）——预算被当成监控指标而非治理手段。
**规避**：预算进 Task，运行时扣减，触顶即熔断并交付部分结果（§4.6）。

### 陷阱 6 · A2A 版本不匹配

**现象**：两端能连通但字段解析失败，或直接握手失败。
**根因**：AgentCard 在 v0.3 → v1.0 之间不向后兼容，一端升级另一端没升。
**埋伏阶段**：构建（③）/ 运营（⑤）——接入或升级时未锁版本。
**规避**：两端版本锁定并在 `AgentCard.protocol_version` 显式声明与校验；升级必须两端同改 `[已验证]`。

## 7. 反例

### 反例 1 · "因为单个 Agent 不够聪明，所以拆成五个"

**做法**：把任务切成五个角色，每个角色都配完整工具集与完整上下文。
**爆掉的方式**：成本变成原来的数倍，且由于交接的信息损失，效果不升反降；更糟的是失败时无人能归因到具体环节，团队陷入"到处都在猜"。**在运营期以"成本失控 + 无法归因"的形式爆掉。**

### 反例 2 · "Peer 拓扑 + 无深度上限"

**做法**：四个 Agent 互相自由请求，没有任何深度或次数限制。
**爆掉的方式**：出现 A→B→C→A 的环，任务永久挂起；由于没有超时与熔断，系统表现为"没有错误但是不完成"。**在运营期以"静默挂起"的形式爆掉，且因为不报错而长期不被发现。**

### 反例 3 · "共享黑板人人可写，不定义归约"

**做法**：所有 Agent 都往同一块共享状态写，冲突时后写覆盖。
**爆掉的方式**：并行分支互相覆盖，出现"某 Agent 的贡献凭空消失"；评审时无法复现。**在构建期埋下，在真实并发量上来后以"偶发数据丢失"的形式爆掉。**

### 反例 4 · "跨组织调用直接信任对端 AgentCard"

**做法**：拿到 AgentCard 就按其声明调用，不校验来源身份与签名。
**爆掉的方式**：被冒充的 Agent 接入后，或以合法身份执行越权动作；信任边界形同虚设。**在运营期以"越权/数据外流"的形式爆掉**，这类事件通常由外部发现而非自身监控发现。

## 8. 开放问题

- **多 Agent 失败如何归因？** 一派主张通过强制关联标识 + 每步交接的显式契约，把失败定位到"某个交接点"；另一派认为当失败源于语义损失（信息在传递中被误解）时，归因在原理上不可判定，只能定位到"某段协作"而非某一步。**两派的有效性取决于"失败是否可被分解为步骤级事件"，尚无定论**（与 `D09-质量-评测.md` §9 的同一问题呼应）。
- **Agent 数量是否存在上限？** 一派主张存在一个由协调成本决定的实用上限，超过后收益递减为负；另一派主张通过分层与按需加载可以持续扩展。**分歧在于"协调成本是线性还是超线性"，缺乏可复现的定量证据。** 本库不给数字。
- **A2A 与 MCP 的边界是否会融合？** 一派主张 Agent 本质上也是一种工具，最终可用统一协议表达（A2A 会退化）；另一派主张"有自主意图的对端"需要不同的生命周期与信任模型，二者应长期并存。`v1.0.1` 时点二者并存，未收敛。
- **Swarm 与动态角色分配是否可用于生产？** 一派主张在允许近似解、且不要求可复现的场景（如探索类任务）可用，动态分工能适应任务变化；另一派主张不可复现性使其无法满足任何有审计要求的场景，动态角色的收益不足以抵消可预测性的损失。**前提差异在于"是否需要可复现与可审计"，而非方法优劣。**
