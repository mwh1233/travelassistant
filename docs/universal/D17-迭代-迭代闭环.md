## 0. 总纲

> **迭代不是第六个阶段，而是从⑤运营回到①②③的回边；判断一次迭代是否真正发生的唯一标准，是这条失败是否被永久写进了某个门禁——要么改契约、要么改上下文与编排、要么改工具。"重试一下就好了"不算迭代。** `[共识]`

可反驳点：一次性交付的固定流程系统（步骤完全确定、无 LLM 参与决策）不需要回边，本断言不成立。断言的适用范围是**在真实流量下会产生未预期失败**的 Agent 系统。

1. **回边的目标是"同类问题不再发生"，不是"这一次修好了"**。前者需要在门禁上留下痕迹，后者只需要一次成功运行。
2. **一次失败必须归口，且只能归到一个主要口**。归口决定修复动作，修复动作决定验证方式。无归口的失败会被反复讨论而无法关闭。
3. **门禁是有限资源**。用例无限膨胀会让 CI 慢到无人使用，于是门禁被绕过——这比没有门禁更糟，因为它制造了"有防护"的假象。
4. **评测与迭代的分工是"算"与"用"**。`D09-质量-评测.md` 定义怎么评（坐标系、六环节、维度、打分器、失败标签集）；本文定义**评完之后怎么办**。两者的接口是那张失败标签，不是内容。
5. **外部变更会强制触发迭代**。模型弃用、供应商条款变化、协议版本升级（如 MCP / A2A）都会在未改任何代码的情况下改变行为，因此升级流程必须有"非自愿迭代"这条路。

## 1. 问题定义与边界

### 1.1 本文解决的问题

- 拿到一条**已带标签**的失败之后，如何归因到链路的哪一环，并决定改什么。
- 如何把一次失败变成一条**永久用例 + 断言**，并进入 CI，使它不再复发。
- 如何设计**回归门禁 SOP**（单一变量、baseline 对比、阻断与放行、逃逸分析）。
- 如何设计**版本升级流程**（模型 / prompt / 编排图 / 工具 / 协议），包括影子、金丝雀与回滚判据。
- 如何给 bad case 排优先级，避免"按谁喊得响"排序。
- 如何把失败沉淀为**知识**（文档、清单），使下一个项目不重犯——即本知识库自身的维护机制。
- 如何定义**每次发版的固定动作清单**，使迭代节奏可预期。

### 1.2 本文不讨论什么

- **不讨论怎么评**：评测坐标系、六环节、评测维度清单、打分器设计、失败标签集的定义、基准速览——全部归 `D09-质量-评测.md`。**本文不重复其标签清单与打分器设计，只引用**（`` `D09-质量-评测.md` §4.5 ``）。

## 2. 设计思路

### 2.1 第一性原理：改进速度由反馈回路的带宽决定，而带宽由"归口率"决定

一条失败样本只有三种归宿：

| 归宿 | 定义 | 后果 |
|---|---|---|
| **被消化** | 有归口 → 有修复动作 → 有永久用例 → 进门禁 | 同类问题不再复发，回路的带宽转化为改进速度 |
| **被忽略** | 关单了，但没有归口、没有用例 | 同类问题会以略不同的形式再次出现，且每次都要重新分析 |
| **被误消化** | 未复核就入库，或归错口因此改了错的地方 | **最坏**：门禁里多了一条错误断言，把错误行为固化成标准答案（`D09-质量-评测.md` §7 陷阱 7） |

因此迭代体系的核心指标不是"修复了多少条"，而是**归口率**（有唯一归口的失败占比）与**逃逸率**（进门禁之后仍再次发生的同类失败占比）。这两个数直接刻画回路健康度。

**关键推论**：在归口率低的阶段，增加修复人力不会提升效果——因为修复动作与失败原因是错配的。这正是 §4.1 把"归口"放在"修复"之前的理由。

### 2.2 不可回避的六个约束

| 约束 | 性质 | 直接后果 |
|---|---|---|
| **失败样本非均匀到达** | 统计性质 | 高频低危失败会淹没低频高危失败。按绝对数量排序必然漏掉长尾，必须用频率 × 影响面而非单纯计数 |
| **线上分歧中混有错误行为** | 数据质量约束 | 用户的不安全行为、表述误区、孤例都会被当成"期望行为"。**未经人工复核确认"正确行为应该是什么"的分歧不得入库**（`D09-质量-评测.md` §3 闭环与陷阱 7） |
| **一次改动只能归因一个变量** | 因果推断约束 | 模型、prompt、检索器、工具实现同时换，指标变化无法归因，回退时也不知道该回退哪个 |
| **修复本身可能引入新失败** | 系统性质 | 任何改动都是回归风险；因此"修好一条"与"不弄坏其他"要分别验证 |
| **门禁是有限资源** | 工程约束 | CI 时长与被绕过的概率正相关。用例必须分层（PR 门禁 / 夜间全量），且必须允许退役 |
| **外部依赖会强制变更** | 供应链性质 | 模型弃用、条款变化、协议版本升级（A2A 的 AgentCard 在 v0.3→v1.0 不向后兼容 `[已验证]`）都会在未改代码时改变行为，必须有一条"非自愿迭代"通道 |

### 2.3 由此推导出的三条取舍

**取舍一：宁可慢，也不并行改多个变量。** 需要修十条失败时，正确做法是串行、每条一次改动、每次带 baseline 对比；并行改则全部不可归因。速度来自"每条都能一次修对"，不是来自"同时开工"。

**取舍二：宁可拒绝一条没有归口的修复，也不接受"临时补丁"。** 任何以"先这样，回头再改"开头的修复，事实上都不会回头。没有归口的修复不进门禁，因此它既不留下痕迹，也不带来永久防护。

**取舍三：宁可退役过时用例，也不让门禁无限膨胀。** 上个月写的用例集不包含这个月的新失败模式（`D09-质量-评测.md` §7 陷阱 9），但把全部历史用例都留着会让门禁慢到被绕过。维持"用例总数有上限 + 有退役流程"比"只增不减"更可持续。

## 3. 通用方案

一条失败在归口之后，有四条互斥的修复路径。**先判归口，再选路径**。

### 3.1 方案 A · 用例驱动（改上下文与编排）

**机制**：把失败样本固化为一条带断言的用例，进 CI。对"模型有误解、上下文缺了关键约束、编排在某个分支上走错"这类失败，修复动作是改 prompt / 改上下文装配 / 改图结构，然后由该用例守护。

**适用条件**：失败可被稳定复现；正确行为可被写成断言（确定性断言或带 rubric 的 Judge）；失败根因在模型可见的输入或编排路径上。

**代价**：用例会随时间腐化（外部契约、数据分布变化使旧用例失效）；断言过严会误杀合理的替代路径（必须支持子集 / 包含模式，见 `D09-质量-评测.md` §4.2）。

**不适用场景**：根因在工具契约或权限设计上的失败——此时改用例只是把症状固化，同类问题会换个形式再来。

### 3.2 方案 B · 规则与护栏驱动（改强制点）

**机制**：不修改模型的输入输出，而是在工具调用或输出的强制点上加一条检查（拒绝、改写、要求澄清）。适用于"模型在压力或注入下必然会犯、且不应依赖它自己避免"的失败。

**适用条件**：失败模式可被规则化描述（越权动作、必填字段缺失、禁止的输出形态）；误拦截的代价可接受。

**代价**：规则会累积成难以维护的列表；过严的护栏会把正常能力一起拦掉，制造"该做不做"的新失败（`D09-质量-评测.md` §1.4 的单轴盲区）。

**不适用场景**：失败原因是"模型不知道正确做法"而非"模型越界"——此时护栏只能拦住输出，不能让它做对。

### 3.3 方案 C · 数据与知识驱动（改检索、记忆与样本）

**机制**：修复检索库（补文档、改切片、修索引）、修正记忆层（清理被污染条目、修正写入策略）、或把失败样本补进监督数据。适用于"知识缺失或被污染"类失败。

**适用条件**：失败可归因到"模型看到的内容不对/不全"；知识源可被更新且更新可被验证。

**代价**：知识更新有传播延迟（索引重建、缓存失效）；记忆污染一旦发生，影响面是后续所有决策（OWASP Agentic Top 10 的 ASI06 记忆污染 `[已验证]`），清理比写入难得多。

**不适用场景**：失败根因在于推理能力而非知识——补再多资料也不会让模型学会正确推理。

### 3.4 方案 D · 上游驱动（改契约与工具）

**机制**：承认当前任务契约本身就是错的（成功标准无法判定、边界未定义、工具返回不足以支撑决策），回到 ①定义或 ③构建 修改契约与工具 schema。工具契约应包含 状态 / 结论 / 范围 / 证据位置 / 下一步 五要素（`D06-运行时-工具与协议.md`）。

**适用条件**：失败反复出现在同一类任务上且不同修法都无效；或失败表现为"模型无法判断自己是否做完了"。

**代价**：改动面最大——契约改动会牵动评测集、prompt、工具、下游集成，且需要与消费方重新对齐。周期最长。

**不适用场景**：单点、偶发、可被用例或护栏覆盖的失败——用上游改动去修单点问题是过度工程。

### 3.5 选型判据：先归口，再选路径

```text
拿到一条已复核的失败，按顺序问：
① 正确行为是否已写进契约？（D02 四要素）
  └─ 否 → 方案 D（改契约）。不要先改 prompt。
② 模型是否"知道该怎么做"但没做？
  ├─ 知道但越界 / 不稳 → 方案 B（护栏与规则）
  └─ 不知道 → 方案 A（上下文与编排）或方案 C（知识）
        判据：失败时上下文里是否已包含正确信息？
          ├─ 包含 → 方案 A（它没用好，改装配与编排）
          └─ 不包含 → 方案 C（知识缺失，改检索与记忆）
③ 工具返回是否足以支撑判断？
  └─ 否 → 方案 D（改工具契约）
④ 四项都不成立 → 该失败不可归口，回到①重新定义问题；
   仍无法归口则记入 §8 开放问题，不得用"重试一下"关闭
```

> **D00 §2.2 的门禁**：每条失败都要有归口——要么改契约（`D02`）、要么改上下文与编排（`D03` / `D04`）、要么改工具与协议（`D06`），**不允许"重试一下就好了"**。本文的 §3.5 是这条门禁的可执行版本。

## 4. 如何设计

### 4.1 回流路径：从在线失败到永久用例（九步 SOP）

| # | 步骤 | 动作要点 | 产出物 |
|---|---|---|---|
| 1 | 捕获 | 从在线标注 / 用户反馈 / 事故中捕获失败，保留完整轨迹与上下文 | 失败样本（含 trace id） |
| 2 | 复核 | **人工确认"正确行为应该是什么"**；剔除用户不安全行为、表述误区、孤例 | 复核结论（入库 / 不入库 + 理由） |
| 3 | 打标 | 按 `D09-质量-评测.md` §4.5 的标签集打**唯一主因标签** + 可选次因 | 带标签的失败样本 |
| 4 | 归口 | 按 §3.5 判归口，写入唯一归口与计划修复路径 | 归口判定（含责任人） |
| 5 | 脱敏与最小化 | 去除个人数据、凭证、无关上下文；只保留复现所需的最小输入 | 可入库样本 |
| 6 | 入库 | 作为一条带断言的用例进入数据集（含预期结果与判定方式） | 新用例（版本化） |
| 7 | 修复 | 按归口执行一次改动（**单一变量**） | 变更（可回滚） |
| 8 | 验证 | 新用例通过 + baseline 对比无回归（成功率、`pass^k`、安全项、延迟、成本） | 对比报告 |
| 9 | 固化与沉淀 | 用例进门禁；失败模式写入清单或文档 | 门禁更新 + 知识条目 |

**第 2、4、6 步是"被误消化"的三个高发点**：跳过复核→入库错标准；跳过归口→改错地方；跳过断言→用例只能人工看，不会自动拦截。

### 4.2 数据结构与接口形态

```python
from pydantic import BaseModel, Field
from typing import Literal, Optional
from datetime import datetime

class FailureSample(BaseModel):
    sample_id: str                             # 必填
    trace_id: str                              # 必填：与遥测关联（对齐 OTel GenAI semconv，Development）
    captured_at: datetime                      # 必填
    channel: Literal["online_label", "user_report", "incident", "red_team"]  # 必填
    primary_label: str                         # 必填：取 `D09-质量-评测.md` §4.5 的标签集，本文不重定义
    secondary_labels: list[str] = Field(default_factory=list)   # 选填：仅用于聚类
    reviewed: bool                             # 必填：false 的样本不得入库
    expected_behavior: Optional[str]           # 必填（reviewed=true 时）：正确行为的明确描述
    minimized: bool                            # 必填：是否已完成脱敏与最小化
    rejected_reason: Optional[str]             # 选填：复核未通过时的理由

class TriageDecision(BaseModel):
    sample_id: str                             # 必填
    owner_doc: Literal["D02", "D03_D04", "D06", "D10"]  # 必填：唯一归口
    path: Literal["A_case", "B_guardrail", "C_data", "D_upstream"]  # 必填：修复路径
    priority: float                            # 必填：见 §4.3 排序公式
    single_variable: str                       # 必填：本次只改的那一个变量
    rollback_plan: str                         # 必填
    due: Optional[datetime]                    # 选填

class RegressionGate(BaseModel):
    gate_id: str                               # 必填
    tier: Literal["pr", "nightly", "release"]  # 必填：分层，见 §4.3
    case_ids: list[str]                        # 必填
    blocking: bool                             # 必填：是否阻断发布
    metrics: list[Literal["success_rate", "pass_k", "security_zero_tolerance",
                          "latency_p95", "cost_per_success"]]  # 必填
    baseline_ref: str                          # 必填：对比基线标识
    tolerance: dict[str, float]                # 必填：每项指标的允许劣化幅度

class ReleasePlan(BaseModel):
    version: str                               # 必填
    changed_axes: list[Literal["model", "prompt", "graph", "tool", "protocol", "data_source"]]  # 必填：>1 时需说明为何无法拆分
    strategy: Literal["shadow", "canary", "blue_green", "direct"]  # 必填
    canary_ratio: Optional[float]              # 选填：canary 时必填
    stop_conditions: list[str]                 # 必填：触发自动回滚的条件
    verify_checklist: list[str]                # 必填：发版后必须逐项确认
    involuntary: bool = False                  # 选填：true 表示由外部变更触发（模型弃用等）
```

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 判据与陷阱 |
|---|---|---|
| **用例优先级** | 频率 × 影响面 × 修复成本 | 公式形式：`优先级 = 频率 × 影响面 ÷ 修复成本`。**影响面不能只用"用户数"**——涉及资金、权限、合规的动作，影响面应为最大档（对应 OWASP Agentic Top 10 的 ASI08 / ASI10 类运营期与供应链风险）`[已验证]` |
| **门禁分层** | 用例总时长与改动频率 | PR 门禁只跑"快且稳定"的子集（秒级到分钟级）；夜间跑全量；发布前跑全量 + 安全专项。**不允许把所有用例塞进 PR 门禁** |
| **指标容忍度与 baseline** | 该指标的历史波动幅度；上一个稳定版本 | 容忍度先测出该指标的噪声水平（同版本重复跑的波动范围），再设为噪声的若干倍，凭空设定会把噪声当回归。baseline 必须是**最近一次全量通过的版本**并同样版本化，不能是"上次随便跑的那次" |
| **金丝雀比例** | 失败后果的严重度 | 后果越严重，初始比例越小、观察窗越长；有硬性安全要求的场景先用影子（不接真实流量）再进金丝雀 |
| **回滚判据** | 门禁指标 + 运行期信号 | 必须是**事前写好的可自动判定的条件**；事故当场的争论会推迟回滚。回滚判据与发布判据应共用同一套指标 |
| **用例退役** | 用例的失效判定 | 触发条件：外部契约变更导致用例不再成立、或连续 N 个版本未被任何改动影响。退役需要记录理由，不能静默删除 |
| **升级观察窗** | 该变更轴的历史回归发生率 | 由数据决定，不由"习惯"决定；首次引入某类变更（如首个协议升级）应给最长观察窗 |

### 4.4 版本升级流程

**四类升级轴的评估项（缺一不可）**

| 变更轴 | 必须先回答的问题 | 特殊风险 |
|---|---|---|
| **模型** | 能力面变化是否超出契约边界？成本与延迟是否同向可接受？旧版本何时弃用？ | 同一次 prompt 在新模型上可能失效；缓存前缀与提示格式可能不兼容 |
| **prompt / 上下文策略** | 改动是否破坏了冻结前缀（命中率归零）？是否影响工具定义顺序？ | 缓存命中率骤降不会报错，只会体现为账单 |
| **编排图** | 是否新增了循环分支？步数上界是否仍成立？失败归口是否仍唯一？ | 新增分支可能把某类失败从"可归口"变成"不可归口" |
| **工具 / 协议** | 契约是否向后兼容？消费方是否同步升级？ | **A2A 的 AgentCard 在 v0.3 → v1.0 不向后兼容，必须两端同时改** `[已验证]`；MCP `2026-07-28` 取消 `initialize` 与 `Mcp-Session-Id` 后，任何依赖会话的假设都要重验 `[已验证]` |
| **数据源 / 检索库** | 索引是否重建？缓存是否失效？记忆中的旧结论是否仍成立？ | 污染一旦写入记忆，影响后续全部决策（ASI06）`[已验证]` |

**发布与验证序列**

```text
① 单一变量确认      → 本次只改一个轴；无法拆分时须写明理由并加倍观察窗
② 门禁预跑          → 全量用例 + 安全专项 + 成本/延迟基线对比
③ 影子（可选）      → 新版本对真实流量只做旁路推理，不产生副作用，比对输出差异
④ 金丝雀            → 小比例真实流量；观察窗内比对门禁指标与运行期信号
⑤ 放量              → 逐步提升比例；每档都要重新核对指标
⑥ 回滚判据生效      → 任一 stop_condition 命中即自动回滚；回滚本身也要被验证
⑦ 事后复盘          → 若发生回归，做逃逸分析（见下），并补门禁
```

**逃逸分析（门禁为什么没拦住）**——四种可能，必须落到唯一一种：

| 逃逸类型 | 含义 | 对策 |
|---|---|---|
| **无此用例** | 失败模式从未被写入用例 | 回到 §4.1 第 5–6 步，补用例 |
| **有用例但未跑** | 该用例不在本次触发的门禁分层里 | 调整分层或触发条件 |
| **有用例但容忍度太松** | 跑了但劣化幅度未超阈值 | 用实测噪声水平重设容忍度 |
| **有用例但断言错** | 断言把错误行为当成了正确行为 | 回到 §4.1 第 2 步复核，并检查是否有同类错误断言 |

### 4.5 分阶段实施路径

**最小可行（闭环能跑起来）**

1. 失败样本登记表 + 人工复核环节（复核是硬性前置，不可跳过）。
2. 归口三分法落地：每条失败填写唯一归口与单一变量。
3. 用例数据集版本化，PR 门禁只跑其中的稳定子集。
4. 每类变更有一份"发版前必须回答的问题"清单（§4.4 的表）。
5. 回滚判据事前写好，且至少演练过一次。

**生产就绪**

6. 门禁分层（PR / 夜间 / 发布）与用例退役流程上线，用例总数有上限。
7. 指标容忍度由噪声实测得出，而非经验设定。
8. 影子与金丝雀成为默认发布形态，直接发布需审批并说明理由。
9. 逃逸分析成为回归事件的强制步骤，四类归因必须落到唯一一种。
10. 迭代节奏固定：每次发版有固定动作清单与固定复盘窗口；失败模式写入清单或文档（走 `D01-地基-写作规范.md` 的修订流程），使下个项目不必重犯。

### 4.6 落地检查点（中性化）

- [ ] 能回答"上一条进入门禁的用例来自哪次失败、谁复核的、归口到哪一环"。
- [ ] 能回答"上次发版之后发生回归时，逃逸分析归到四类中的哪一类"。
- [ ] 能回答"当前门禁跑一遍要多久；如果太久，有没有分层，谁在绕过它"。
- [ ] 能回答"某个外部依赖明天弃用，我们的非自愿迭代流程是什么，谁负责"。
- [ ] 能回答"过去三个月退役了几条用例，理由分别是什么"。

### 5.1 「最小可行」

- [ ] 失败样本有登记表，且复核是入库的硬性前置
- [ ] 每条入库失败有唯一主因标签（引用 `D09-质量-评测.md` §4.5 的标签集）、唯一归口与单一变量

### 5.2 「生产就绪」

## 6. 常见陷阱

| 陷阱 | 现象 | 根因 | 埋伏阶段 | 规避方式 |
|---|---|---|---|---|
| **1 · 未复核就入库** | 评测集里出现互相矛盾的用例，同一次运行里两条断言互斥 | 把线上分歧直接当成期望行为；线上分歧里混着用户的不安全行为、表述误区与孤例 | 验证 | 复核是入库硬性前置；未确认"正确行为应该是什么"的样本不得入库（`D09-质量-评测.md` §3 闭环与 §7 陷阱 7） |
| **2 · 用"重试一下就好了"关闭问题** | 工单关闭了，两周后同类失败换个形式再次出现 | 缺少归口判定环节，修复动作与失败原因错配 | 定义 | 强制执行 §4.1 第 4 步：无归口不得关闭；把"归口率"作为迭代体系的健康指标 |
| **3 · 一次改多个变量** | 指标变了，但说不清是哪一项改动的贡献；出问题时也不知道该回退哪个 | 并行修复的排期压力；或"顺手一起改"的工程习惯 | 设计 | 单一变量原则；确需合并时写明理由并加倍观察窗；用 Replay 模式冻结工具层（`D09-质量-评测.md` §3.2） |
| **4 · 断言写成"必须与参考轨迹完全一致"** | 大量合理的替代路径被判为失败，门禁频繁误报 | 忽略了参考路径不唯一；误用严格匹配模式 | 验证 | 断言支持子集 / 包含模式（`D09-质量-评测.md` §4.2）；把"路径不唯一"作为断言设计的前置假设 |
| **5 · 门禁膨胀到被绕过** | CI 时长持续增长，最终有人加白名单或直接跳过 | 用例只增不减，没有退役与分层机制 | 运营 | 分层（PR / 夜间 / 发布）+ 明确退役触发条件 + 用例总数上限；被绕过本身就是最高优先级的失败 |
| **6 · 把外部变更当成"什么都没做"** | 没改任何代码，行为却变了；追踪时发现是依赖项静默升级 | 缺少非自愿迭代通道；依赖的版本固定在"latest"或浮动范围 | 运营 | 依赖版本固定；外部变更（模型弃用、协议升级、条款变化）走同一套 §4.4 评估流程并标记为 involuntary |
| **7 · 只在发现时修复，不做同类扩展** | 同一根因在不同入口反复出现，每条都单独修 | 修复时只针对那一条样本，没有问"还有哪些地方是同一类问题" | 构建 | 归口后增加一步"同类扫描"：按主因标签在历史样本中检索同族失败，一并纳入本次用例集 |

## 7. 反例

1. **把 pending 的线上分歧直接批量入集** —— 做法：为了快速扩充评测集，把线上用户投诉的输入输出对直接导成用例。**爆掉的方式**：三个月后评测集里混入了用户的不安全请求与模型被迫合规拒绝的样本，断言要求模型"满足用户"。团队在门禁上不断调 prompt 去迎合这些断言，把系统的安全行为逐步削弱。诊断成本极高——因为错误断言散布在数百条用例中，没有一处会报错。
2. **修复与验证并轨发布** —— 做法：十条失败一起改（改 prompt、换模型、调检索参数），一次性发布。**爆掉的方式**：指标变好，团队归因到"检索调参起了作用"。两周后其中某项改动引发新的长尾失败，回滚时不知道回滚哪一项，只能整体回退——连带退掉了另外九项真实改善。此后再没人愿意做批量修复，迭代速度反而下降。
3. **没有退役机制的用例池** —— 做法：门禁只增不减，理由是"多测总没坏处"。**爆掉的方式**：CI 时长从数分钟涨到数十分钟，夜间的全量跑不完，于是有人把部分用例标记为不阻断。"不阻断"随后变成惯例——门禁名义上还在，实际已经不再拦截。事故复盘时发现，拦住那次事故的用例早已被标记为不阻断，且没有任何人记得为什么。
4. **把"模型弃用"当突发事件处理** —— 做法：没有非自愿迭代通道，依赖版本用浮动范围跟踪最新。**爆掉的方式**：某天供应商下线旧模型，系统在无代码变更的情况下开始报错或行为漂移。此时才发现：没有任何人负责跟踪弃用公告，也没有做过一次"换模型"的演练，回滚判据里也没有这一项。恢复时间取决于找人的速度，而不是技术准备度。

## 8. 开放问题

- **与 `D09-质量-评测.md` 的重叠程度自检（本节为显式记录）**：本文已把以下内容**排除在外、只做引用**——失败标签集的定义（`D09` §4.5）、打分器与 Judge 校准（`D09` §5）、评测维度清单（`D09` §4）、六环节闭环的数据结构（`D09` §3）。实际重叠集中在两处：① **闭环流程**（`D09` §3 定义了闭环，"回流路径"在本文 §4.1 展开为 SOP）；② **"一次只改一个变量"**（`D09` §3⑥ 与 §7 陷阱 3 提及，本文 §2.3 与 §4.4 给出执行细则）。按 `D01-地基-写作规范.md` §8 的 30 行经验阈值，两处各自的重叠均低于该阈值，**判定为可接受的"输入型提及"与"主题级展开"分工**。**合并建议**：若后续两篇文档任一方新增了对方的主题内容（例如 `D09` 开始写"发版前固定动作清单"，或本文开始定义新的失败标签），应立即触发合并评估——合并形态建议为"评测与迭代闭环"单篇，内部按"算 / 用"两大部分组织，而不是简单叠加。
- **归口率与逃逸率是否可跨团队比较？** 两者都依赖"什么算同类失败"的口径，而该口径由标签体系决定。若标签体系各自演化，跨团队数字不可比——但是否值得为此统一标签体系（代价是各领域被迫使用不贴切的标签），没有结论。
- **门禁应该"快而经常"还是"慢而全"？** 一派主张 PR 门禁必须秒级到分钟级，宁可漏检也要保住"人人都在跑"；另一派主张把全量门禁设为强制，用工程投入（并行化、缓存）来换时长。两派前提不同：前者假定团队会绕过慢门禁，后者假定基础设施投入可无限加。**这决定了 §4.3 中门禁分层的具体阈值，目前只能按团队实测决定。** `[待验证]`
- **外部变更的感知能否自动化？** 模型弃用公告、条款变更、协议版本升级目前依赖人工跟踪；能否把这些做成可订阅的工程事件（与 AgBOM 条目变更联动，见 `D16-交付-治理合规.md`），尚无成熟方案。
- **"同类扫描"的边界在哪？** 按主因标签检索同族失败容易过度扩大范围（一次修复变成大型重构），也容易漏掉标签不同但根因相同的失败。缺少可判定的停止条件。
- **知识回流到什么程度才算生效？** 把失败写进文档是低成本的，但无法验证读者是否真的少犯了同类错误；是否需要给知识条目也配一个"可测断言"（例如对照检查清单核对），尚无实践证据。 `[待验证]`
