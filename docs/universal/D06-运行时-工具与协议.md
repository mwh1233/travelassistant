## 0. 总纲

> **工具的输出不是"数据"，而是 Agent 下一步的决策输入；因此工具的返回值必须是一份契约（状态 / 结论 / 范围 / 证据位置 / 下一步），而不是一个裸结果。与此同时，协议层在 MCP `2026-07-28` 之后已从"有状态会话"翻转成"无状态请求"——任何按旧写法（`initialize` 握手 + `Mcp-Session-Id`）实现的服务端，在迁移时会整体失效而不是局部报错。** `[已验证]`（协议部分）`[共识]`（契约部分）

要点：

1. **工具定义本身占用上下文预算**：工具数量与描述长度直接挤压可用推理空间，工具设计是上下文工程的一部分（回指 `D04-运行时-上下文工程.md`）。
2. **模型只能"读"到工具返回的文本/结构**，读不到你的内部对象；不写进返回内容的语义，对模型等于不存在。
3. **静默失败比报错失败危险得多**：吞掉错误的工具会让 Agent 在错误前提上继续推理（`D09-质量-评测.md` §4.2 已把它列为独立指标）。
4. **协议版本决定架构**：MCP `2026-07-28` 的结论与之前版本可能完全相反，不写版本的协议结论视为无效。
5. **单次工具调用已经不是瓶颈**：BFCL v3/v4 上前沿模型达 88%–94%（官方榜单 · 2026 · 复现），瓶颈在多轮压力下的选择与错误恢复。

## 1. 问题定义与边界

### 1.1 本文解决的问题

一句话：**把"Agent 如何与外部世界对话"定成可评审的接口规范——工具返回什么、schema 怎么写、出错怎么表达、重复执行怎么办、协议怎么接、版本怎么演进。**

具体五件事：

| # | 问题 | 不解决的后果 |
|---|---|---|
| 1 | 工具返回的**语义契约** | 模型拿到裸数据，只能自行猜"这意味着什么、下一步做什么" |
| 2 | 工具 **schema** 的规范与预算 | 描述写太长吃掉上下文，写太短导致误用；枚举/必填缺失导致参数错误率上升 |
| 3 | **错误约定** | 失败被静默吞掉，Agent 在错误前提上继续，最终以"看起来成功"的形式交付错误结果 |
| 4 | **幂等性与副作用标注** | 重试/重放导致重复下单、重复写库；审批门不知道该拦哪个 |
| 5 | **协议选型与迁移** | 在 MCP `2026-07-28` 前后写出两套互不兼容的实现 |

### 1.2 本文不讨论什么

- **不讨论 Agent 之间的通信**——agent↔agent 的协议（A2A）归 `D07-运行时-多智能体.md`；本文只处理 agent↔tool。
- **不讨论权限的强制点**（审批门、沙箱、最小权限的执行拦截）——本文只**声明**权限与副作用属性，强制归 `D10-质量-安全护栏.md`。
- **不讨论状态 schema 本身**——工具如何读写状态归本文，状态有哪些字段归 `D05-运行时-记忆与状态.md`。
- **不讨论模型如何选择工具的内部机制**（路由、微调、推理强度）——归 `D08-运行时-模型推理.md`。
- **不讨论工具调用链路的可靠性策略细节**（超时、重试、熔断、降级分级）——本文只定"可重试性标记"这一契约字段，策略归 `D12-质量-可靠性.md`。
- **不讨论工具执行的部署形态与隔离**（容器、沙箱、并发）——归 `D13-交付-部署运行时.md`。

## 2. 设计思路

### 2.1 第一性原理：工具是"概率模型"与"确定性外部世界"之间的唯一适配层

模型输出是概率性的 token，外部系统要求确定性的输入输出。工具就是这两者之间的适配层，因此工具设计的目标不是"暴露能力越多越好"，而是**把不确定性收敛在工具边界上**：

- 入参用 schema 收敛（枚举、必填、格式约束把模型的自由度压到安全区）；
- 出参用契约收敛（把"发生了什么、意味着什么、下一步能做什么"写成模型可直接用的结构）；
- 错误用结构化表达收敛（把"失败"变成可分类、可重试、可上报的信号，而非丢弃的异常）。

### 2.2 不可回避的约束

| 约束 | 性质 | 对设计的强制影响 |
|---|---|---|
| **工具定义占上下文** | 架构性 | 工具数量与描述长度是**预算**问题：加工具 = 加 token = 挤压推理空间（回指 `D04`） |
| **模型只能看见返回的文本/结构** | 架构性 | 语义必须写进返回值；"隐含在系统里的知识"对模型不存在 |
| **工具选择是概率行为** | 模型性质 | 不能假设"模型一定选对"；名称、描述、参数命名都是**影响选择准确率的设计变量** |
| **外部世界有副作用且不可回滚** | 物理性 | 有副作用的工具必须带幂等键与可重试性标记，否则重试即事故 |
| **协议核心在 `2026-07-28` 变更为无状态** | 规范变更 | 会话式假设（长连接、会话内鉴权、服务端主动推送）整体失效 `[已验证]` |
| **过度授权是 Agent 专属高危项** | 安全 | OWASP 2026 版把 Excessive Agency 从第 6 位升至第 3 位 `[已验证]`，工具集必须做最小化 |

### 2.3 由此推导出的核心取舍

**取舍一：宁可工具少而精，也不追求"能力大而全"。** 工具数量增加会稀释选择准确率，并持续占用上下文预算。多出来的能力若很少被用到，其收益远小于它对主流程的干扰。**先做减法，再用组合补齐能力。**

**取舍二：宁可返回结构化契约（略多 token），也不返回裸数据让模型猜。** 契约字段（状态/结论/范围/证据位置/下一步）会让单次返回变长，但它消除的是模型反复试探与误判造成的多轮成本——**总 token 通常更低**。这一判断属 `[共识]`，需按跟踪际核算。

**取舍三：宁可让工具显式失败（含可重试性），也不让它"看起来成功"。** 静默失败让错误进入后续推理，修复成本随步数放大；显式失败让 Agent 可以重试、改参数或回报，成本被限制在当步。**失败必须在契约里表达，而不是在日志里。**

## 3. 通用方案

工具接入有三条主流路线，另有协议侧的架构迁移必须单独说明。

### 3.1 方案 A · 直接 function calling（进程内工具）

**机制**：工具以函数/方法形式注册在 Agent 进程内，schema 由语言类型或装饰器生成，调用即本地函数调用。**适用条件**：工具与 Agent 同生命周期、无跨语言/跨团队复用需求、调用延迟敏感。
**代价**：与宿主进程耦合，隔离性差（工具崩 = Agent 崩）；难以被其他 Agent 或第三方复用；权限边界只能靠代码审查。**不适用场景**：工具需要独立部署、需要被多个消费方复用、需要不同沙箱级别。

### 3.2 方案 B · 自定义 HTTP API（自有 schema 网关）

**机制**：工具是远端 HTTP 接口，Agent 侧维护一份自有 schema 描述（OpenAPI 子集或自定义），通过网关统一鉴权、限流、审计。**适用条件**：已有成熟 HTTP 资产、需要统一的鉴权/限流/审计、工具由自有团队维护。
**代价**：需要自行定义并维护描述格式与调用约定（等于自建一个小协议）；生态工具不可直接复用；schema 与实现易漂移。**不适用场景**：需要接入大量第三方工具、需要与外部生态互操作。

### 3.3 方案 C · MCP 协议接入（`2026-07-28` 无状态）

**机制**：工具以 MCP Server 形式提供，通过 `tools/list`（结果可缓存）与 `tools/call` 交互；`2026-07-28` 起协议核心为**无状态**，每个请求自包含路由与鉴权信息，服务端可水平扩展。**适用条件**：需要接入多来源工具、需要生态互操作、需要工具与 Agent 解耦部署。
**代价**：引入协议依赖与迁移成本；无状态化后，服务端发起的 elicitation/sampling 需改为 Multi Round-Trip Requests，实现复杂度上升；旧教程与旧实现大量存在，团队需辨别。**不适用场景**：只有一两个内部工具且无复用需求（直接用方案 A 更省）。

### 3.4 MCP `2026-07-28` 无状态迁移（前后两套架构对照）

> 本节结论全部来自官方规范 `[已验证]`。**不写版本号的协议结论一律视为无效。**

| 维度 | 旧架构（`2026-07-28` 之前） | `2026-07-28` 之后 |
|---|---|---|
| 连接模型 | 客户端 `initialize` 握手建立会话，服务端分发 `Mcp-Session-Id` | **取消 `initialize` 握手与 `Mcp-Session-Id`**，协议核心转为无状态请求/响应 |
| 路由 | 依赖会话上下文 | 新增 `Mcp-Method` / `Mcp-Name` 请求头路由（SEP-2243） |
| 服务端发起交互 | 在会话内发起 elicitation / sampling | 改为 **Multi Round-Trip Requests（SEP-2322）** |
| list 结果 | 每次重新获取 | **list 结果可缓存**（SEP-2549） |
| 长任务 | Roots / Sampling / Logging 为常驻能力 | Tasks 转为**正式扩展**（SEP-2663）；Roots / Sampling / Logging 按新的 **12 个月弃用政策**进入弃用期 |
| 鉴权假设 | 会话绑定身份，后续请求复用会话 | **每个请求必须自包含凭据**，会话 ID 不能作为鉴权依据 |

**迁移的性质**：这是一次**架构翻转**，不是参数调整。旧实现会在迁移时"整体失效"——因为会话概念本身被移除，而不是某个字段改名。

### 3.5 选型判据

```
是否需要接入多个来源的工具 / 生态互操作？
├─ 是 → 方案 C（MCP 2026-07-28），并按 §4.7 做无状态迁移
└─ 否 → 是否已有成熟 HTTP 资产 + 统一网关需求？
         ├─ 是 → 方案 B（自有 schema 网关）
         └─ 否 → 方案 A（进程内 function calling）
```

| 判断问题 | 若回答为 | 建议 |
|---|---|---|
| 工具是否只被本项目使用且与 Agent 同生命周期？ | 是 | 方案 A |
| 是否已有统一鉴权 / 限流 / 审计网关？ | 是 | 方案 B（复用网关，不重复造） |
| 是否需要第三方工具或跨团队复用？ | 是 | 方案 C |
| 团队现有实现是否依赖 `initialize` / `Mcp-Session-Id`？ | 是 | **先做 §4.7 的迁移评估再谈接入** |
| 工具总数是否已超过"模型能稳定选择"的范围？ | 是 | 先做工具裁剪（§4.3）与分组，而非继续加 |

## 4. 如何设计

### 4.1 步骤序列（每步标产出物）

```text
① 盘点能力，做减法                → 产出：工具清单（每项含"不做的理由"）
② 定工具边界（一个工具一件事）      → 产出：工具职责表（含合并/拆分决策）
③ 写 schema（类型/枚举/必填/描述）  → 产出：工具 schema（纳入版本管理）
④ 定返回契约（五字段）             → 产出：每工具的返回结构定义 + 示例
⑤ 定错误约定（错误码/可重试性）      → 产出：错误码表 + 重试判定规则
⑥ 标注幂等与副作用                → 产出：副作用分级表 + 幂等键方案
⑦ 选协议并落地（MCP / HTTP / 进程内）→ 产出：协议接入方案（含鉴权与路由）
⑧ 定版本化与灰度                  → 产出：工具 schema 版本策略（回指 D13）
```

### 4.2 数据结构与接口形态

**工具定义（示意，字段名中性化）**：

```python
from typing import Literal, Optional
from pydantic import BaseModel

class ToolSpec(BaseModel):
    name: str                       # 必填：动词_名词，稳定契约，改名=破坏性变更
    description: str                # 必填：一句话说"做什么+何时用"，受描述预算约束
    input_schema: dict              # 必填：JSON Schema；枚举/必填/格式约束在此收敛
    output_contract: "OutputContract"   # 必填：见下
    side_effect: Literal["read_only", "reentrant", "side_effect", "irreversible"]  # 必填
    idempotency_key_field: Optional[str] = None   # 有副作用时必填：幂等键所在入参名
    requires_approval: bool = False               # 声明是否需要审批门（强制点归 D10）
    version: str                    # 必填：工具 schema 语义化版本

class OutputContract(BaseModel):
    status: Literal["ok", "partial", "failed"]   # 状态：这次调用本身的成败
    conclusion: str                 # 结论：一句话结论（不含原始数据）
    scope: str                      # 范围：结论覆盖的数据范围/时间范围
    evidence_ref: Optional[str]     # 证据位置：可回溯到原始记录的位置/ID
    next_step: Optional[str]        # 下一步：建议的后续动作或"无需后续"

class ToolError(BaseModel):
    code: str                       # 结构化错误码，稳定、可分类
    message: str                    # 人类可读，但不得替代 code
    retryable: bool                 # 必填：是否可安全重试
    retry_after_ms: Optional[int]   # 可选：建议退避
    partial_effect: bool = False    # 是否已产生部分副作用（决定能否重试）
```

**契约五字段的来源**：状态 / 结论 / 范围 / 证据位置 / 下一步，取自 Anthropic《Effective Context Engineering》的"工具返回即契约"实践 `[共识]`。

> **要点**：`next_step` 不是"给模型的提示词"，而是**契约的一部分**——它把"这个结果意味着什么"从模型的猜测变成工具提供方的声明。缺失它时，模型只能依据 `status` 与 `conclusion` 自行推断，这正是误判的多发点。

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 取值信号 |
|---|---|---|
| **工具数量上限** | 剩余上下文预算与选择准确率 | 由"工具描述总 token 占预算比例"和"多轮选择准确率实测"共同决定；**先量测再定上限**，不写死数字 |
| **单工具描述长度预算** | 工具总数与预算分配 | 描述预算 = （分配额度 ÷ 工具数）；按此反推每工具可用字数，超出的细节移入参数级描述 |
| **参数级 description 长度** | 参数数量与歧义程度 | 只在"参数值容易理解错"的地方写长（如日期格式、单位、枚举含义） |
| **枚举 vs 自由文本** | 取值空间是否封闭 | 封闭且可穷举 → 枚举（把校验左移到 schema）；开放 → 自由文本 + 运行期校验 |
| **必填字段集** | 是否所有调用都必然需要 | 只有"缺了就一定无法执行"的字段才设必填；可推导/可默认的字段留空 |
| **超时值** | 下游系统 P99 延迟 | 超时必须小于下游 P99（否则超时先于对方失败，重试叠加） |
| **幂等键来源** | 副作用类型 | 由"能唯一标识这一次意图"的业务键决定（如订单号），不由随机 UUID 决定（随机 UUID 无法防重放） |
| **重试上限与退避** | 可重试性与成本 | 策略细节归 `D12-质量-可靠性.md`；本文只要求 `retryable` 字段真实可信 |
| **错误码粒度** | 消费方（Agent / 人 / 告警）需要区分的动作 | 粒度由"不同码是否触发不同动作"决定；触发相同动作的码应合并 |

### 4.4 分阶段实施路径

| 阶段 | 做什么 | 不做什么 |
|---|---|---|
| **最小可行** | 工具清单裁剪到能稳定选择的数量；每工具一份 schema（含必填/枚举）；统一返回五字段；统一错误码 + `retryable`；有副作用工具带幂等键 | 不做 MCP 迁移、不做工具灰度、不做描述预算的量化 |
| **生产就绪** | 描述长度纳入预算核算；错误码按动作归类；副作用四级标注全覆盖；`requires_approval` 声明与 `D10` 的强制点对齐；工具 schema 版本化 + 破坏性变更评审；MCP 迁移完成（若用 MCP） | 不做无审计需求的协议自研 |
| **规模化** | 工具分组/按需加载（把工具集做成可检索的子集，回指 `D04`）；灰度与回滚；工具级 SLO 与成本归因（`D11`/`D15`） | 不追求"工具越多越好" |

### 4.5 错误约定：结构化错误码、可重试性、禁止静默失败

**三条硬规则**：

1. **错误必须以结构化形式返回**，而不是抛出异常或返回空值。`code` 稳定且可分类；`message` 只作补充（回指 `D09-质量-评测.md` §4.5 的 `tool_argument_error` 等标签）。
2. **`retryable` 必须真实**。把不可重试的写操作标成可重试，等于给系统埋了一次重复副作用；把可重试的瞬时错误标成不可重试，则导致本可恢复的任务失败。
3. **禁止静默失败**。工具内部捕获异常后返回"成功 + 空结果"是最危险的反模式：Agent 无法区分"确实没有数据"与"调用失败了"。

**错误分类与建议动作（模板）**：

| 错误类别 | 示例 code 前缀 | retryable | 建议动作 |
|---|---|---|---|
| 入参不合法 | `arg_` | 否（重试无用） | 让模型改参数后重发 |
| 鉴权/权限不足 | `auth_` | 否 | 停止并回报（可能是权限配置问题） |
| 瞬时故障 | `transient_` | 是 | 退避重试（策略归 `D12`） |
| 下游限流 | `rate_limit_` | 是 | 按 `retry_after_ms` 退避 |
| 业务规则拒绝 | `business_` | 否 | 停止并回报（不是错误，是结果） |
| 部分成功 | `partial_` | 视 `partial_effect` | 需人工或补偿流程，**不得自动重试** |

### 4.6 幂等性与副作用标注

副作用分四级，进入工具 schema 并由 `D10-质量-安全护栏.md` 决定强制点：

| 级别 | 含义 | 重试 | 审批门 | 说明 |
|---|---|---|---|---|
| **只读** | 无副作用 | 安全 | 通常不需要 | 检索、查询、计算 |
| **可重入** | 幂等写（同键重放结果一致） | 安全 | 视数据敏感度 | 依赖幂等键 |
| **有副作用** | 非幂等写，可补偿 | 需幂等键 + 补偿 | 常需要 | 创建、更新、发送 |
| **不可逆** | 无法补偿 | **不自动重试** | 必须 | 支付、删除、对外发送 |

> **声明与强制分离**：本文只要求工具**声明**副作用级别与 `requires_approval`；审批门、沙箱、执行拦截的**强制实现**归 `D10-质量-安全护栏.md`。两者必须由同一份 schema 驱动，否则声明会被绕过。

### 4.7 MCP `2026-07-28` 无状态迁移落地

**对服务端实现的影响**：

| 影响面 | 旧写法 | 迁移后必须改成 |
|---|---|---|
| 请求处理 | 先 `initialize`，再在会话内处理后续请求 | 每个请求**自包含**，无会话前置；按 `Mcp-Method` / `Mcp-Name` 头路由（SEP-2243） |
| 状态存放 | 会话内存放上下文 | 迁移到请求内或外部存储；服务端本身保持无状态以便水平扩展 |
| 服务端发起交互 | 会话内直接发 elicitation / sampling | 改为 **Multi Round-Trip Requests**（SEP-2322），需相关性标识关联多轮请求 |
| list 结果 | 每次重新拉取 | 用**可缓存**语义（SEP-2549）设置缓存与失效策略 |
| 长任务 | 依赖常驻能力 | 用 Tasks 扩展（SEP-2663）；Roots / Sampling / Logging 已进入 12 个月弃用期 |
| 负载均衡 | 需会话粘滞（sticky） | **不再需要粘滞**，可任意路由到任一实例 |

**对鉴权的影响**：

- **会话 ID 不再是身份**：`Mcp-Session-Id` 被取消，任何"拿到会话 ID 即视为已认证"的写法都不成立。
- **每请求鉴权**：每个请求必须携带并校验凭据；服务端不得依赖"前一次请求已认证"的状态。
- **与无状态化一致的凭据设计**：优先使用每请求可校验的令牌；令牌的作用域（哪些工具、哪些资源）应最小化（对接 `D10` 的最小权限与 `D16` 的租户边界）。

**如何识别过时的教程/实现**（出现任一即说明是针对旧版本写的）：

1. 要求客户端先调用 `initialize` 才能调用其他方法；
2. 提到 `Mcp-Session-Id`，或"保持会话/长连接"；
3. 服务端"主动推送"或"在会话里抽样"（未提及 Multi Round-Trip Requests）；
4. `tools/list` 被描述为"每次必须重新获取、不可缓存"；
5. 用会话 ID 作为鉴权或路由依据；
6. 把 Roots / Sampling / Logging 当作长期稳定能力。

> 迁移排查法：**grep `initialize`、`Mcp-Session-Id`、`session` 三个词**。命中的地方就是需要重写的地方。

### 4.8 工具版本化与灰度

- **工具 schema 进版本管理**（回指 `D00-地基-总纲.md` §2.2 的"接口冻结"门禁）。命名、参数名、返回字段的变更属于**破坏性变更**，需评审。
- **可加不可改**：优先新增可选参数/新增返回字段；删字段、改语义、改名称必须走版本升级与双写过渡。
- **灰度与回滚**：工具版本灰度、按流量切换、快速回滚的具体机制归 `D13-交付-部署运行时.md`；本文只要求"每个工具带 `version` 且可被路由到不同版本"。
- **契约漂移检测**：工具实现与 schema 的漂移（实现改了、schema 没改）会造成"模型以为的"与"实际发生的"不一致，应纳入 CI 校验。

## 5. 检查清单

### 5.1 「最小可行」

- [ ] 每个工具都有 schema，且**至少一个必填字段**与**至少一个枚举/格式约束**
- [ ] 每个工具的返回都包含五字段（状态 / 结论 / 范围 / 证据位置 / 下一步），缺一不可
- [ ] 每个工具都有结构化错误码，且错误码能映射到"不同动作"
- [ ] 每个错误都带 `retryable` 布尔值，且该值经过验证（可重试的确实可重试）
- [ ] 不存在"捕获异常后返回成功 + 空结果"的静默失败路径
- [ ] 有副作用的工具都有幂等键，且幂等键来自业务语义而非随机值
- [ ] 每个工具有超时，且超时值小于其下游系统的 P99 延迟

### 5.2 「生产就绪」

- [ ] 工具总数与描述总 token 被纳入上下文预算核算（回指 `D04`）
- [ ] 工具命名统一为可预测的模式（如 `动词_名词`），无同义词混用
- [ ] 副作用四级标注完整，且 `requires_approval` 与 `D10` 的强制点同源
- [ ] 不可逆工具在契约中标记后，未出现在任何自动重试路径上
- [ ] 工具 schema 已版本化，破坏性变更走评审并支持双写过渡
- [ ] 若使用 MCP：已按 `2026-07-28` 完成无状态化，代码中不存在 `initialize` / `Mcp-Session-Id` 依赖
- [ ] 若使用 MCP：每请求鉴权独立成立，负载均衡不依赖会话粘滞
- [ ] 工具实现与 schema 的一致性有自动化校验（漂移检测）
- [ ] 工具级成功率、错误码分布、P95 延迟进入监控（回指 `D11`）

## 6. 常见陷阱

### 陷阱 1 · 工具返回裸结果

**现象**：工具返回原始 JSON 数组或长文本，模型需要自行推断"这是什么、下一步做什么"。
**根因**：把工具当成"数据管道"，而非"决策输入的适配层"。
**埋伏阶段**：设计（②）——定义工具时只写了输入，没写返回契约。
**规避**：强制五字段返回；`conclusion` 与 `next_step` 由工具作者提供，不交给模型推断。

### 陷阱 2 · 静默失败（吞掉异常返回空结果）

**现象**：下游报错、超时、返回异常结构，工具捕获后返回"成功 + 空数组"，Agent 据此认为"没有数据"。
**根因**：把"不报错"当成健壮性，或为避免中断流程而吞异常。
**埋伏阶段**：构建（③）——实现工具时为了"稳"而包了一层 catch。
**规避**：错误一律结构化返回；把"空结果"与"调用失败"分成不同 `status`；把静默失败列入评测独立指标（回指 `D09` §4.2）。

### 陷阱 3 · 工具数量膨胀导致选择退化

**现象**：工具从 10 个加到 40 个后，模型开始选错工具、漏调工具，且错误看起来"随机"。
**根因**：把选择准确率当成与工具数量无关的常数；忽略了描述占用的上下文预算与相似工具的干扰。
**埋伏阶段**：定义（①）——没有"不做的理由"，只加不减。
**规避**：工具清单必须带"不做的理由"；相似工具合并或分组按需加载（回指 `D04`）。

### 陷阱 4 · 把不可逆操作标成可重试

**现象**：支付/发货类工具在下游超时后被自动重试，产生重复副作用。
**根因**：`retryable` 由"错误类型"机械推断（超时=可重试），未考虑副作用级别与部分成功状态。
**埋伏阶段**：设计（②）——幂等与副作用标注缺失或未与重试策略联动。
**规避**：`irreversible` 级别不进入自动重试；`partial_effect=true` 时禁止自动重试，转补偿或人工。

### 陷阱 5 · 按旧版 MCP 实现服务端

**现象**：按网上教程实现了 `initialize` 握手与会话保持，迁移到 `2026-07-28` 后服务端整体不可用。
**根因**：知识来自旧教程或训练数据，未核官方版本；把会话式假设当成了协议固有属性。
**埋伏阶段**：构建（③）——接入协议时未核版本。
**规避**：写协议相关代码前核 `D00-地基-总纲.md` §5 版本表；用 §4.7 的六个特征自查旧写法。

### 陷阱 6 · 用会话 ID 当鉴权凭据

**现象**：鉴权逻辑假设"持有会话 ID 即已认证"，无状态化后出现越权或全量拒绝。
**根因**：把传输层的会话标识误当作身份凭证。
**埋伏阶段**：构建（③）——鉴权设计与协议模型不匹配。
**规避**：每请求独立校验凭据；会话标识只用于关联，不用于授权。

### 陷阱 7 · 工具实现与 schema 漂移

**现象**：实现改了字段名/枚举值，schema 未同步，模型按旧 schema 调用失败率上升。
**根因**：schema 被视为文档而非契约，未纳入 CI。
**埋伏阶段**：运营（⑤）——变更时只改实现。
**规避**：schema 与实现的一致性做自动化校验；破坏性变更走版本升级与评审批。

## 7. 反例

### 反例 1 · "把整个数据库表当工具接进来"

**做法**：暴露一个"查询接口"，接受任意 SQL/过滤条件。
**爆掉的方式**：Agent 生成越权查询（跨租户、全表扫描），同时因为入参无约束，参数错误率高、成本不可控。**在验证/运营期以"越权 + 成本爆炸"的形式爆掉**——OWASP 2026 版把 Excessive Agency 升至第 3 位，正是这类设计的高发区 `[已验证]`。

### 反例 2 · "为了减少调用次数，把五个动作合并成一个工具"

**做法**：一个工具用 `mode` 参数切换查询/创建/更新/删除/发送。
**爆掉的方式**：模型对 `mode` 的取值理解不稳，出现"想查询却传了删除"；同时副作用级别无法用一个字段表达，审批门失去判据。**在运营期以"偶发的破坏性误操作"形式爆掉，且难以复现。**

### 反例 3 · "错误一律返回 200 + 空结果"

**做法**：所有失败都返回 HTTP 200，body 为空或空数组。
**爆掉的方式**：Agent 认为"没有数据"并据此继续推理，最终交付基于错误前提的结论；事后只能从日志发现真相，而日志不在模型的推理链里。**在运营期以"结果看起来对但结论错误"的形式爆掉**，且因为不触发任何告警而长期不被发现。

### 反例 4 · "工具描述写得越详细越好"

**做法**：每个工具写 800 字说明，包含使用示例、注意事项、历史背景。
**爆掉的方式**：20 个工具吃掉大量上下文预算，推理空间被挤压；同时关键约束被淹没在冗余信息里，模型反而忽略。**在设计/构建期埋下，在生产负载上来后以"上下文爆、准确率降"的形式爆掉。**

## 8. 开放问题

- **工具数量与准确率的拐点在哪？** 一派主张"能用更少工具就别加"，理由是 BFCL 高分说明单次调用已不是瓶颈，瓶颈在多轮选择与干扰项；另一派主张"按需加载"（工具集可检索）可以突破数量上限，把拐点推后。**两派的差别在于是否接受"检索工具"这一额外步骤**，目前缺乏跨场景的定量证据。本库不给出具体拐点数字。
- **MCP 无状态化后，长任务该由谁编排？** 一派主张由客户端（Agent）持有任务状态、通过 Tasks 扩展表达；另一派主张服务端用外部存储承载任务状态，客户端只做轮询。二者对"无状态"的边界理解不同（服务端无内存 vs 无状态机），未收敛。
- **工具返回契约是否应强制成为协议层标准？** 一派主张五字段应写入 MCP 的返回规范（让所有工具强制遵守）；另一派主张契约是应用层的事，协议只保证传输，强制化会让简单工具变重。**这是"协议该多厚"的老问题，MCP `2026-07-28` 未强制，实践中两派并行。**
- **`retryable` 能否自动推断？** 目前多由工具作者人工声明；能否从错误类型、副作用级别、部分成功状态自动推导出可信的 `retryable`，尚无可靠方法。误标代价不对称（误标可重试 > 误标不可重试），因此默认倾向保守。
- **工具 schema 的反向生成是否可行？** 从已有 HTTP/OpenAPI 自动生成工具 schema 能降低接入成本，但自动生成的描述往往冗长、枚举缺失，可能把上下文预算和准确率同时拉低。**收益与代价的权衡未量化。**
