## 0. 总纲

> **编排模式的选型几乎完全由"共享状态需要被谁看见"决定，而不是由任务复杂度决定。复杂度只决定循环的次数与上界，不决定拓扑；把"任务很复杂"当成选"更重的拓扑"的理由，是 Agent 架构里最常见的一次性错误。** `[共识]`

这个断言可被反驳：如果存在一类任务，其状态可见性极窄但**循环结构本身**必须动态生成（连节点集合都要运行时决定），那么拓扑就确实由复杂度而非状态可见性决定。反驳者需要给出这类任务的实例与频率（本文 §8 保留此分歧）。

展开为五条要点：

| # | 判断 | 说明 |
|---|---|---|
| 1 | **六个模式是三个正交维度的组合，不是六个竞品** | 维度一：计划是事先产出还是边想边做；维度二：控制权是集中的还是转移的；维度三：状态是全局可见还是局部隔离 |
| 2 | **循环上界与终止条件是拓扑的一部分，不是运行时参数** | 拓扑里没有终止节点集合的设计，等于没有设计——`max_iterations` 只是兜底，不是终止条件 |
| 3 | **状态图是唯一内建"暂停/恢复/人机回环"的形态** | 因为它的状态与执行是分离的（检查点），其余形态要暂停就得自己实现持久化 |
| 4 | **Handoff 的代价随深度超线性增长** | 每多一次转移，上下文要重建一次、归因多一跳；转移链长度天然有一个很低的实用上界 |
| 5 | **Swarm / 去中心在单组织内部通常是错误默认值** | 无中心意味着没有单一的事实来源，冲突消解与死锁熔断失去了落脚点（该问题在 `D07-运行时-多智能体.md` 才被系统处理） |

**术语纪律（承接 `D00-地基-总纲.md` §9）**：本文讨论的"节点共享状态"是**一次运行内的结构化事实**（state），不是跨会话持久化的**记忆**（memory），也不是用于恢复重放的**检查点**（checkpoint）。拓扑决定"哪些节点读写同一份状态"；状态 schema 与持久化是 `D05-运行时-记忆与状态.md` 的职责。

1. 已确定"需要 Agent 循环"后，**六个主流编排模式各自的机制、代价与不适用场景**分别是什么？

## 2. 设计思路

### 2.1 第一性原理：编排 = 控制流归属 × 状态可见性 × 上下文边界

任何编排模式都可以用三个问题完全刻画：

```text
① 控制流归谁？    代码写死  ──►  模型运行时决定
② 状态可见性？    全局单份  ──►  每个角色各持一份
③ 计划何时产出？  事先（静态）──►  边做边产（动态）
```

六个模式是这三条轴上的不同落点，而不是六个独立发明：

| 模式 | 控制流 | 状态可见性 | 计划产出时机 |
|---|---|---|---|
| ReAct | 模型（每步） | 单份，全在上下文里 | 边做边产 |
| Plan-and-Execute | 模型（先产计划）+ 代码（执行） | 单份（计划 + 结果） | 事先产计划，可重规划 |
| 状态图 | 代码（边）+ 模型（节点内） | 单份但**分区**（每个节点可读写字段不同） | 边做边产或事先均可 |
| Supervisor | 中心模型 | 中心持全局，工作者持局部 | 中心运行时决定 |
| Handoff | 转移给下一个角色 | 转移时重建上下文 | 边做边产 |
| Swarm | 无中心，各自决定 | 各自一份，共享靠消息 | 边做边产 |

**由此得到关键推论**：选型时真正要问的不是"任务有多复杂"，而是"**共享状态需要被几个节点看到，以及是否需要在中途暂停**"。状态可见性是拓扑的硬约束；复杂度只影响循环上界。

### 2.2 不可回避的约束

| 约束 | 性质 | 对拓扑设计的直接影响 |
|---|---|---|
| **上下文是有界的** | 架构性质（注意力两两计算，越长召回越差） | 每多一个"角色"，就多一份上下文；角色数量受上下文预算约束，不受业务复杂度约束 |
| **非确定性会复合** | 每次模型调用都是一次采样 | 拓扑中的循环必须显式给上界；"靠模型自己判断该停了"不是终止条件 |
| **暂停 = 状态落地** | 要在中断后恢复，状态必须已持久化 | 只有先把状态与执行分离（检查点）才谈得上人机回环；否则"暂停"等于"丢掉重跑" |
| **并行写共享状态需要冲突策略** | 并发写的固有性质 | 状态图的并行节点必须声明写入集，交叠的字段必须有合并策略（`join_policy`） |
| **归因成本随跳数增长** | 每多一跳，失败要多回溯一层 | 转移链长度必须有实用上界，超过后应先怀疑拓扑而不是加强观测 |
| **成本上界不可静态计算（Agent 形态下）** | 步数运行时产生 | 每次迭代的预算必须能累加成一个全局上界，否则无法做发布门禁 |

### 2.3 由此推导出的核心取舍

**取舍一：宁可把状态放成"一份、可见"（显式传参），也不靠"角色各自持有、靠消息同步"。** 因为分散持有会让"当前事实是什么"出现多个答案，冲突消解没有落脚点，且失败无法归因到单一状态。代价是中心节点上下文膨胀，需要用分区读写集来缓解，而不是用"拆角色"来回避。

**取舍二：宁可给循环设一个由数据推导的硬上界，也不依赖模型的自我终止判断。** 因为自我终止是模型输出的一种，它会漂移；而硬上界是可静态验证的。代价是可能截断本该更长的合法路径——因此上界应由"最短必要步数"的分布决定（`D02-地基-任务契约.md` §4.3），而不是拍一个整数。

**取舍三：宁可先不上多角色 Handoff，也用单循环 + 显式状态做到。** 因为每一次 Handoff 都要重建一次上下文、增加一跳归因，而收益（"专注度"）在多数任务上并未被证据支持。只有当**上下文预算明确不允许单循环承载**时，拆分才成为正收益。

读者读完这三条取舍，应能自行推出后文的六模式对比表与决策树：状态可见性窄 + 单循环 → ReAct / Plan-Execute；需要分区与暂停 → 状态图；需要多视角但决策集中 → Supervisor；上下文确实装不下 → Handoff。

## 3. 通用方案

### 3.1 方案 A · ReAct（边想边做）

**机制**：单循环，每轮"思考 → 调用工具 → 观察结果"，把观察追加进上下文后进入下一轮，直到模型输出终止信号或触及上界。

**适用条件**：步骤不可事先枚举；单份上下文足以容纳全部已观察信息；任务深度通常在中短程（十几步以内）。

**代价**：上下文随轮次单调增长，长任务必然触发 context rot（见 `D04-运行时-上下文工程.md`）；没有中途暂停点；失败可见但难定位（错误动作与正确动作在轨迹里形态相似）。

**不适用场景**：需要中途暂停等人审批的流程；上下文预算明显不足以容纳全部观察的长时间任务；需要多个独立视角的决策。

### 3.2 方案 B · Plan-and-Execute（先规划后执行，可重规划）

**机制**：两段式——先由模型产出一份结构化计划（步骤列表，含依赖关系），再由执行器逐步执行；执行中若某步结果与预期不符，触发重规划（重新生成剩余步骤）。

**适用条件**：任务的**主干**可以事先产出计划，但细节需要落地时才知道；需要给用户或审计方展示"将要做什么"（可解释性要求）。

**代价**：多一次模型调用（产计划）；计划的粒度难把握——太粗等于没规划，太细则每步都要重规划，重规划次数本身会失控；重规划需要额外的状态字段记录"已完成的步骤与其结论"。

**不适用场景**：计划本身高度依赖中间结果（此时第一步就无法写对，退化为 ReAct 更划算）；任务足够短（规划开销占比过高）。

### 3.3 方案 C · 状态图（显式节点 / 边 / 检查点 / 人机回环）

**机制**：把编排显式建模成有向图——节点是计算单元（模型调用、工具调用、路由、人类审批、子图），边是转移条件，状态是一份被节点按声明的读写集访问的结构化对象。执行器按边推进，并在每个超级步（superstep）后落检查点。LangGraph 1.x（1.0 GA 2025-10-22）是这一形态最常见的实现 `[共识]`。

**适用条件**：状态需要被多个节点读写但要求分区隔离；需要中途暂停/恢复/人机回环；需要并行分支与汇聚；需要跨版本重放历史轨迹。

**代价**：建模成本最高——图、边、状态 schema 都要显式设计；条件边容易爆炸（`priority` 与互斥性稍不注意就出歧义）；**检查点语义与状态 schema 强耦合**，schema 改动会导致历史检查点不可用（这一问题在 `D05-运行时-记忆与状态.md` 展开）。

**不适用场景**：步骤简单的短任务（图的建模成本高于收益）；拓扑本身需要运行时动态生成（图的节点集合在设计期固定性是其价值来源）。

### 3.4 方案 D · Supervisor（中心调度）

**机制**：一个中心 LLM 持有全局状态与任务队列，按需把子任务分派给若干工作者（可以是模型调用，也可以是被封装的能力单元），收齐结果后决定下一步或结束。

**适用条件**：需要多个**视角或能力域**，但决策应当集中；子任务边界可由中心在运行时划定；需要单一的事实来源来回答"当前进展到哪"。

**代价**：中心节点是单点瓶颈与单点故障；中心上下文成为复杂度集中地，随子任务数量增长而膨胀；工作者之间不能直接协商，任何跨域问题都要绕回中心（增加一跳延迟）。

**不适用场景**：子任务之间需要高频直接协商；中心无法容纳全局状态（此时应先做状态分区，而不是加一层中心）；纯线性任务（中心调度是过度设计）。

### 3.5 方案 E · Handoff（控制权转移）

**机制**：控制权连同会话上下文一起从一个角色转移给另一个角色；任一时刻只有一个角色是活跃的。这是 OpenAI Agents SDK 四原语（Agent / Handoff / Guardrail / Session）中的 Handoff 形态 `[共识]`。与 Supervisor 的区别在于：Supervisor 的中心始终在场，Handoff 是**中心离场、权责移交**。

**适用条件**：任务天然分段且各段需要不同的指令集/工具集/上下文；分段之间的信息可以被**压缩成一份交接摘要**（否则转移没有意义）。

**代价**：每次转移都要重建上下文，需要一份"交接契约"（交接摘要必须包含目标、已完成、未决、约束）；转移链越长，归因越难、跨段约束越容易丢失；转移本身可能成为失败点（转移到一个不合适的角色）。

**不适用场景**：段落之间需要频繁来回（此时就是 Supervisor 或单循环，不是 Handoff）；上下文无法压缩成摘要（转移会丢信息）；转移链预期超过实用上界。

### 3.6 方案 F · Swarm / 去中心

**机制**：没有中心调度，每个角色按本地规则自主决定何时把任务交给谁，共享状态靠消息传递而非单一事实来源。

**适用条件**：角色数量多、任务边界高度动态且无法集中建模；或组织上确实由多个**自治主体**构成（跨组织、跨团队，各自有独立目标与权限）。

**代价**：没有单一事实来源，冲突消解与死锁熔断失去落脚点；可观测性显著下降（无法用一条主线串起执行）；停止条件难以定义（谁来宣布"整体完成"）。

**不适用场景**：单组织内部的生产系统（几乎总是错的默认值）；需要审计与可回放；需要明确的成本上界。

### 3.7 框架映射（`[共识]`，写入时需重新核验）

| 框架 | 版本参考 | 原生承载的模式 | 状态与检查点 |

| LangGraph | 1.x（1.0 GA 2025-10-22） | 状态图（节点 / 条件边 / 子图）、Supervisor、Swarm 式 | 内置检查点与人机回环，是状态图形态的生产默认 |

| Claude Agent SDK | 0.2.x | 单 Agent 循环 + 生命周期钩子 + 原生工具协议接入（MCP 当前规范 `2026-07-28`，见 `D06-运行时-工具与协议.md`） | 钩子式，状态由开发者托管 |
| Google ADK | 2.x（自 1.x 有破坏性变更） | 层级 Agent、原生 A2A 支持（A2A 当前稳定版 `v1.0.1`，2026-05-28） | 会话服务 |

> **框架不改变选型结论**：框架提供的是**承载能力**，不是**选型理由**。先按 §3.8 决策树定模式，再看哪个框架能自然承载该模式所需的状态可见性与暂停语义。反过来（先选框架再让任务适配框架）会稳定地产生"用状态图做线性任务""用 Swarm 做需要审计的流程"这类结构性浪费。

### 3.8 选型判据

**决策树**（按顺序问，任一问题命中即停）：

```text
① 任务需要多轮"观察 → 决策"吗？
   否 → 回 `D02-地基-任务契约.md`：这其实不需要 agent，用 workflow 即可
   是 ↓
② 计划能否在开工前产出，且需要向人/审计方展示？
   能且需要 → Plan-and-Execute（方案 B）；不能 ↓
③ 状态只需要一份、且全程在一个循环里可见？
   是 → ReAct（方案 A）
   否 ↓
④ 需要中途暂停/恢复/人机回环，或有并行分支需要汇聚？
   是 → 状态图（方案 C）
   否 ↓
⑤ 需要多个视角或能力域，但决策集中在一处？
   是 → Supervisor（方案 D）
   否 ↓
⑥ 上下文预算明确装不下单体上下文，且分段间信息可压缩为摘要？
   是 → Handoff（方案 E）
   否 → 重新检查 ②–⑤；仍不成立时才考虑 Swarm（方案 F）
```

**组合判据表**（模式可组合，但有优先级）：

| 场景特征 | 首选 | 可叠加 |
|---|---|---|
| 短链路、单视角、无暂停 | ReAct | — |
| 需要向人解释"打算做什么" | Plan-and-Execute | Supervisor（多域时） |
| 需要审计、暂停、重放 | 状态图 | 任意模式作为节点内部实现 |
| 多域但单一事实来源 | Supervisor | 状态图（作为承载） |
| 分段需不同指令集且可摘要 | Handoff | 状态图（用于承载转移边） |
| 多自治主体（跨组织） | Swarm | — （协议层归 `D07-运行时-多智能体.md`） |

## 4. 如何设计

### 4.1 步骤序列（每步标注产出物）

```text
① 从 D02 的契约取出四要素与自主度
   产出：拓扑设计的输入约束（工具白名单 = 节点可用的能力集合；边界 = 必须存在的门禁节点）
        ↓
② 标注状态可见性：列出全部会被读写的字段，标出"谁能读、谁能写"
   产出：状态可见性矩阵（本文核心产物，直接决定拓扑）
        ↓
③ 走 §3.8 决策树定模式
   产出：模式判定表（含"为什么不是上一档"）
        ↓
④ 画拓扑骨架：节点、边、条件、终止节点集合
   产出：拓扑图（文本或图形）+ 终止条件清单
        ↓
⑤ 给每个循环设上界与每次迭代预算，并汇总成全局上界
   产出：循环上界表 + 全局预算（必须 ≤ D02 契约里的预算）
        ↓
⑥ 标注暂停点与恢复语义
   产出：检查点位置清单（哪些超级步之后必须落盘）
        ↓
⑦ 与 D05 交接状态 schema
   产出：`D05-运行时-记忆与状态.md` 的输入（字段清单 + 读写集 + 恢复要求）
```

> **② 是最关键也最常被跳过的一步。** 如果状态可见性在开工前没有被显式列出，模式选择就退化成了直觉，而直觉在这种问题上稳定偏向"更重的拓扑"。

### 4.2 数据结构与接口形态

拓扑规格应当是一份**可校验的数据**，而不是散落在代码里的调用关系——只有可校验才能回答"终止节点集合是否非空""是否存在无出边的非终止节点"这类问题。

```python
from dataclasses import dataclass
from typing import Literal, Optional

@dataclass(frozen=True)
class NodeBudget:                      # 单节点的每次迭代预算
    max_iterations: int                # 必填：该节点内循环上界（非循环节点填 1）
    max_wall_clock_s: int              # 必填
    max_tool_calls: int                # 必填
    max_cost_units: float              # 必填

@dataclass(frozen=True)
class NodeSpec:
    node_id: str
    kind: Literal["llm", "tool", "router", "human", "subgraph"]
    reads: list[str]                   # 必填：可读的共享状态字段（空列表 = 无依赖）
    writes: list[str]                  # 必填：可写的共享状态字段
    budget: NodeBudget                 # 必填
    # 校验规则：两个并行节点的 writes 交叠时，必须声明 merge_keys

@dataclass(frozen=True)
class EdgeSpec:
    src: str; dst: str
    condition: Optional[str]           # None = 无条件边
    priority: int                      # 必填：同一 src 出多条条件边时的互斥判定顺序

@dataclass(frozen=True)
class LoopGuard:                       # 循环上界与终止条件，属于拓扑而非运行时参数
    max_supersteps: int                # 必填：状态图级总循环上界
    terminate_conditions: list[str]    # 必填且非空：必须同时含"成功终止"和"失败终止"两类
    repeat_action_threshold: int       # 必填：相同动作重复多少次判定为打转
    on_exhaust: Literal["abort", "escalate", "summarize"]  # 上界耗尽后的行为

@dataclass(frozen=True)
class TopologySpec:
    nodes: list[NodeSpec]
    edges: list[EdgeSpec]
    entry: str                         # 必填：入口节点
    terminal: list[str]                # 必填且非空：终止节点集合
    loop_guard: LoopGuard              # 必填
    join_policy: Literal["all", "any", "quorum"]   # 并行汇聚策略
    merge_keys: dict[str, str]         # 选填：并行写入字段 → 合并函数名
```

**最小校验集**（应作为 CI 断言存在）：

1. `terminal` 非空，且每个非终止节点至少有一条出边。
2. 每个循环节点（`max_iterations > 1`）所在的强连通分量必须有可达的 `terminal` 节点。
3. 所有节点的 `budget.max_cost_units` 之和 ≤ 契约 `budget.max_cost_units`。
4. 并行分支的 `writes` 交叠字段必须出现在 `merge_keys` 中。
5. `terminate_conditions` 同时包含成功与失败两类表述。

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 调整信号 |
|---|---|---|
| `max_iterations`（单节点） | 由该节点承担的子任务在 `D02` 中估出的**最短必要步数** P95 决定，取 2–3 倍 | 实测持续顶格 → 先怀疑契约边界过宽或该节点承担了不适合的子任务，而不是加大上界 |
| `max_supersteps` | 由图深度 × 平均分支因子估出，且必须 ≤ `D02` 契约里的 `max_steps` | 与单节点上界之和不一致时以契约值为准（契约是上位约束） |
| `terminate_conditions` | 由 `D02` 的**完成条件**（成功终止）与 `forbid_conditions`（失败终止）逐条映射而来 | 只有成功终止没有失败终止，是最常见的缺陷——失败会退化为"上界耗尽" |
| `repeat_action_threshold` | 由**动作的幂等性**决定：非幂等动作设为 1（第二次相同调用即熔断），幂等只读动作可放宽到 2–3 | 熔断误报多 → 说明判定"相同动作"的指纹过于粗糙（应含关键参数，而非只有工具名） |
| `join_policy` | 由"子任务是否可独立判定完成"决定：任一分支成功即达成 → `any`；必须全部完成 → `all`；需多路共识 → `quorum` | `any` 下出现"半成品被当作完成" → 应检查分支的成功终止条件是否够强 |
| 每次迭代预算 | 由**下游配额**、**全局剩余预算**、**该节点历史 P95 消耗**三者取最小值 | 单节点反复吃完全局预算 → 该节点应被拆成独立子图并单独设预算 |
| 检查点位置 | 由"暂停最可能发生在哪里"决定：人机回环节点前必落盘；幂等性差的工具调用后必落盘 | 恢复后出现重复副作用 → 落盘点在副作用之后而不是之前 |
| Handoff 转移链上界 | 由归因成本与上下文重建成本决定 | 具体数值**必须自测** `[待验证]`；经验上超过 3 次转移后，失败归因所需的信息量显著上升 |

### 4.4 分阶段实施路径

**最小可行版**：① 只画"节点 + 无条件边 + 终止节点集合"，不定并行；② 每个循环节点设 `max_iterations`，全局设 `max_supersteps`；③ `terminate_conditions` 至少写一条成功、一条失败；④ 与人机回环相关的位置留出（但暂不实现检查点）；⑤ **不做**：并行分支、Handoff 转移契约、拓扑校验 CI。

**生产就绪版**：① 状态可见性矩阵完整（每个字段标出读写节点）；② `TopologySpec` 作为代码资产进入版本管理，§4.2 的五条最小校验进入 CI；③ 并行分支的 `join_policy` 与 `merge_keys` 齐备；④ 检查点位置清单确定，恢复语义（幂等/重放）已验证；⑤ 循环上界、重复动作熔断、上界耗尽行为（`on_exhaust`）全部落地；⑥ 拓扑与 `D05` 的状态 schema 对齐，schema 变更流程已定义；⑦ 拓扑骨架与 `D11-质量-可观测性.md` 的 span 层级一一对应，保证每条边可观测。

## 6. 常见陷阱

| # | 陷阱 | 现象与根因 | 埋伏阶段 → 规避方式 |
|---|---|---|---|
| 1 | 用任务复杂度选拓扑 | **现象**：复杂任务一律上状态图或多角色，简单任务也照搬。**根因**：把状态可见性与复杂度混为一谈，把"更重的拓扑"当成"更可靠" | **设计**，在**运营**期以"建模成本与调试成本远超收益"的形式爆发 → 强制先填状态可见性矩阵再选模式；决策树从最简单的模式开始问 |
| 2 | 没有失败终止条件 | **现象**：只定义了"任务完成"，失败时只能靠 `max_iterations` 耗尽退出。**根因**：把终止条件等同于成功条件，失败路径被默认成"重试" | **设计**，在**运营**期表现为"超时退出"占了失败的大头，且错误信息无意义 → `terminate_conditions` 强制同时包含成功与失败两类；失败终止要说明失败原因 |
| 3 | 循环没有预算，只有次数 | **现象**：限制了循环次数，但每次迭代可以花掉任意 token。**根因**：把"循环上界"当成成本控制，忽略了单次迭代成本可差一两个数量级 | **设计**，在**运营**期以"次数没超但账单超了"的形式爆发 → 每次迭代预算由下游配额 / 全局剩余 / 历史 P95 三者取最小值；全局上界必须可累加验证 |
| 4 | 并行节点写同一字段 | **现象**：两个并行分支都写状态里的同一个字段，结果取决于完成顺序，表现为"偶发不一致"。**根因**：把状态当成共享内存，没有显式声明读写集与合并策略 | **设计**，在**验证/运营**期以低概率、不可复现的差异爆发（最贵的一类故障） → 并行前置条件：`writes` 不交叠，或交叠字段必须有 `merge_keys` |
| 5 | Handoff 当万能解 | **现象**：任务一分段就加一个角色并转移控制权，转移链越来越长。**根因**：把 Handoff 当成"分工"的同义词，忽略了每次转移都要重建上下文并增加归因跳数 | **设计**，在**运营**期以"跨段约束丢失""失败无法定位到哪一段"的形式爆发 → 转移前先问"信息能否压缩成一份交接摘要"；转移链长度设上界并监控 |
| 6 | 状态图建模过细 | **现象**：把每个模型调用都画成节点，图有几十个节点和上百条条件边。**根因**：把"显式"当成价值本身，忽略了条件边的组合爆炸与维护成本 | **设计**，在**迭代**期以"每加一个需求就要重画图"的形式爆发 → 条件边应表达**语义分支**而非"每一步"；同一语义内的多步收敛到一个节点内部用循环处理 |
| 7 | 用 Swarm 做需要审计的流程 | **现象**：去中心设计上线后无法回答"整体什么时候算完成""某次异常是谁的决定"。**根因**：把"自主"当成目标，忽略了审计需要单一事实来源 | **运营**期爆发，且此时重构拓扑代价最高 → 单组织内部默认排除 Swarm；跨组织场景才进入候选，且协议层归 `D07-运行时-多智能体.md` |

## 7. 反例

### 反例 1 · 线性三步流程建成状态图

**做法**：一个"检索 → 生成 → 校验"的固定流程，用状态图 + 检查点实现，理由是"以后可能变复杂"。
**爆掉的方式**：三个月后需求确实变了，但变的是"每步的 prompt"，图结构一次没用上；而维护成本已经付出——每个新同学要先读懂图结构和状态 schema 才能改一行 prompt。真正需要检查点的需求（中途暂停）从未出现。

### 反例 2 · 只有 `max_iterations = 25` 的循环

**做法**：单循环的 ReAct，终止条件只有"模型输出 FINISH"，外加上界 25。
**爆掉的方式**：上线后 30% 的失败轨迹是"第 25 步退出"，日志里只有一句"达到最大迭代次数"。团队无法判断是模型在打转、任务确实需要更多步、还是某个工具持续返回错误——因为没有失败终止条件，所有失败都被压成了同一种形态。

### 反例 3 · 用 Handoff 链做五段流程

**做法**："收集 → 校验 → 决策 → 执行 → 汇报"五个角色，每个角色把控制权交给下一个。
**爆掉的方式**：某次执行失败，排查发现"决策"阶段依赖的一条约束在校验阶段被摘要时丢了，而交接摘要本身没有被版本化，无法回放当时的摘要内容。修复方向是把交接契约显式化（目标 / 已完成 / 未决 / 约束四字段必填），这等于把定义阶段欠的债还回来。

### 反例 4 · 并行分支各自写共享进度字段

**做法**：两个并行的子任务分支都往状态里的 `progress` 字段追加自己的进展。
**爆掉的方式**：单跑时正常，并发跑时概率性丢失一方记录（后写覆盖先写）。这类故障复现率低、影响面大，团队往往先怀疑模型不稳定，浪费数周排查；根因其实是拓扑里缺少 `merge_keys` 声明。

## 8. 开放问题

- **拓扑能否由模型在运行时生成？** 有一派主张"元编排"——让模型根据任务动态决定节点集合与连接（即拓扑本身也成为运行时产物）；另一派认为这会同时失去可校验性、可观测性与成本上界，与 §2.2 的约束直接冲突。**两派前提不同**：前者面向一次性、探索性任务，后者面向需要审计与 SLA 的生产系统。目前没有公开证据表明前者在生产环境下的净收益为正 `[待验证]`。
- **Handoff 的实用上界是多少？** 本文只给出"必须自测"。是否存在与任务类型无关的经验值，尚无公开数据；反对"设上界"的一派认为限制转移次数会迫使单角色上下文膨胀，代价只是换了个地方付。
- **状态图与代码编排的边界会消失吗？** 若未来主流框架把"隐式的调用链"也能自动导出为可校验的图，那么手写状态图的必要性下降。目前这一方向仍以厂商实现为主，无跨框架标准 `[共识]`。
- **ReAct 是否会被"原生长上下文"淘汰？** 如果上下文足够大且召回不退化，ReAct 的"上下文单调增长"这一代价就消失，Plan-and-Execute 与 Handoff 的动机也随之减弱。但 context rot 目前是架构性质（Anthropic《Effective Context Engineering》· 2025-09 · 工程博客），该假设是否可被根本性缓解尚不确定。
- **多 Agent 的收益是否被高估？** 本文 §2.3 取舍三倾向于"先不上多角色"，但这依赖"上下文预算允许"这一前提。当子任务的上下文需求真实冲突时，拆分是必需的——**这条分界线（"预算不允许"的判定标准）尚未量化**。
- **拓扑与状态 schema 的耦合怎么解？** 状态图形态下，schema 变更会让历史检查点失效（本文 §3.3）。是否应该把拓扑与 schema 的版本绑定为同一个版本号，目前各框架做法不一。
