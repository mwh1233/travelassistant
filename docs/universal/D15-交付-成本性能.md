## 0. 总纲

> **一次 Agent 任务的成本由步数决定，而不是由请求数决定；因此"单次模型调用变便宜"与"任务变便宜"之间没有必然联系。一个无法按步归因成本的系统，任何成本优化都只是猜测。** `[共识]`

可反驳点：对单轮、单步、一次调用即完成的确定性任务（分类、固定字段抽取），成本确实随请求数线性增长，本断言不成立。断言的适用范围是**含循环、含工具调用、含重试**的 Agent 任务。

1. **成本随步数增长，步数由拓扑决定**。同一个任务在 ReAct 下可能 5 步、在 Plan-Execute + 反思下可能 25 步。拓扑选型（`D03-地基-编排模式.md`）是第一杠杆，模型单价只是第二杠杆。
2. **失败是乘数而不是加数**。一次重试不是"多花一倍"，而是"重跑整条轨迹外加清理成本"。
3. **成本必须在评测阶段就有位置**。`D09-质量-评测.md` §4.4 已把成本列为横切维度，并要求直接成本 / 人工复核成本 / 错误返工成本三项分开算；本文承接的是**怎么算准、怎么压下去**。
4. **延迟与成本不是两个独立目标**。缓存既降本又降延迟，批处理降本却升延迟，流式升成本感知却降体感延迟。当成两个 KPI 分别优化，必然互相拆台。

## 1. 问题定义与边界

### 1.1 本文解决的问题

- 如何把一次运行的成本**拆到可归因的粒度**（步 / 工具 / 缓存层 / 模型），而不是只知道月度账单总额。
- 如何用**结构手段**（路由、缓存、批处理、上下文冻结）压成本，而不是"少调用几次"这种不可执行的指令。
- 如何设定**延迟预算**并按阶段分摊，使 SLO 可被分解到具体环节。
- 如何计算**单位经济学指标**（每任务 / 每成功任务 / 每用户成本），并把失败与重试成本放进正确的分子与分母。
- 如何设置**成本护栏**，使一次失控循环不会烧光当月预算。

### 1.2 本文不讨论什么

- **不讨论模型能力对比与选型**——归 `D08-运行时-模型推理.md`。
- **不讨论 trace 的采集口径与字段定义**——span 怎么发、属性怎么命名、采样怎么做，归 `D11-质量-可观测性.md`；本文只规定"从归因角度需要哪些字段"。
- **不讨论并发容量与资源编排**（实例数、连接池、长任务队列）——归 `D13-交付-部署运行时.md`。
- **不讨论阈值的业务标定**（"低于多少不能发版""上限设多少"）——归 `D09-质量-评测.md` §8 的门禁流程。
- **不讨论定价谈判、采购与自建算力的总拥有成本**——属商业与基础设施决策。
- **不讨论模型提供方的缓存内部实现**（KV cache 物理结构、命中判定算法）——只讨论其对调用方可见的契约与计费后果。

## 2. 设计思路

### 2.1 第一性原理：任务成本是一个乘积，不是一个求和

```text
每成功任务成本 ≈ [ Σ_步 (模型token成本 + 工具/外部API成本 + 持久化成本) ] × (1 + 失败重试放大率) ÷ 成功率
                 └────────── 分子：单条轨迹成本 ──────────┘   └── 失败放大项 ──┘
```

这个式子决定了优化的全部方向：

- **减少项数（步数）**：拓扑简化、循环收敛、把多步合并为一次结构化输出。
- **降低单价**：上下文冻结以命中前缀缓存、模型分级路由、工具结果缓存。
- **降低失败放大率**：幂等重试、只在可重试错误上重试、熔断避免死循环重试。
- **提高分母**：成功率从 90% 提到 95%，等价于成本下降约 5%，通常比压单价更容易。

**关键推论**：只压单价（换便宜模型）会让成功率下降，分母变小，乘积可能反而变大——这就是 §7 反例 1 的机制。

### 2.2 不可回避的六个约束

| 约束 | 性质 | 对本主题的直接后果 |
|---|---|---|
| **注意力是两两计算** | 架构性质，换模型只能缓解 | 上下文长度直接决定单步 prefill 成本；"把全部历史都带上"是持续计费的负债，不是一次性开销 |
| **前缀缓存有最小 token 门槛与 TTL** | 提供方契约 | 低于门槛**静默不缓存**（不报错）；超 TTL 未命中则按写价计费。收益与流量密度强耦合，低 QPS 场景的缓存几乎必亏 |
| **协议核心已无状态化** | MCP `2026-07-28` 取消 `initialize` 与 `Mcp-Session-Id` `[已验证]` | 每轮都要重传上下文，**步数 × 上下文 = token 总量**的关系被强化 |
| **外部 API 有配额与限流** | 物理限制 | 重试不是免费的：既消耗配额，又可能触发更长退避，直接击穿延迟预算 |
| **模型输出非确定** | 架构性质 | 成本是分布不是常数，用均值做预算必被长尾击穿，必须用 P95/P99 |
| **单位经济学的分母是成功任务** | 会计口径要求 | 失败、重试、人工复核、返工必须计入分子；否则算出的是"每请求成本"，无法用于定价与容量决策 |

### 2.3 由此推导出的三条取舍

**取舍一：宁可付缓存写入溢价，也不打破冻结前缀。**
前缀缓存的价值来自"多轮之间前缀完全一致"。在前缀里插入时间戳、按会话动态拼系统提示，会让命中率归零，把本该 0.1 倍的读取成本变成全额输入成本。冻结机制归 `D04-运行时-上下文工程.md`，本文只承接其成本后果：**冻结前缀是成本决策，不只是工程整洁度决策。**

**取舍二：宁可降级能力，也不做无限重试。**
重试本质是"用成本换成功率"。当失败源于不可重试的原因（参数错误、权限不足、输入本身不合规）时，重试只是重复付费。做法是按错误类别区分并设重试预算上限，超出即熔断并降级（`D12-质量-可靠性.md` 的降级分级）。

**取舍三：宁可报"每成功任务成本"，也不只报"每任务成本"。**
只报每任务成本的系统，会在成功率下滑时给出"成本很稳定"的假象——它把失败也算成了完成的一次。

## 3. 通用方案

以下四种方案不是互斥选项，而是**四个可独立叠加的杠杆**。选型判据见 §3.5。

### 3.1 方案 A · 前缀冻结 + prompt cache 命中最大化

**机制**：把上下文切成稳定前缀（系统指令、工具定义、固定示例）与易变后缀（本轮输入、最新工具返回）。前缀置于消息序列最前且保持不变，由提供方侧 prompt cache 复用；提供方按缓存写 / 缓存读 / 普通输入三类分别计费。

**适用条件**：同一前缀在会话内被反复使用（Agent 循环天然满足）；前缀长度达到提供方的最小可缓存 token 门槛；调用足够密集，能在 TTL 内再次命中。

**代价**：前缀必须真正冻结，个性化只能放到后缀。缓存写入有溢价，若前缀只被用一次则净亏。

**不适用场景**：一次性批处理（每个请求前缀都不同）；前缀低于门槛；调用间隔远大于 TTL 且无后续流量。

> 倍率参考：某厂商官方文档给出 5 分钟 TTL 写入 `1.25×`、1 小时 TTL 写入 `2×`、缓存读取 `0.1×` 基础输入价（Anthropic 官方文档 · 2026 · 自报）`[共识]`。**倍率是商业条款而非技术常量，落地前必须回查当前官方计费页。**

### 3.2 方案 B · 模型分级路由与降级

**机制**：按步骤的能力敏感度分配档位。规划、最终答复、歧义消解用高档位；分类、字段抽取、格式修复、结果摘要用低档位；同档位内再按推理强度分档。同时定义**降级链**：主模型超时或限流时落到次档位，并在 trace 记录降级事实。

**适用条件**：任务中存在明显异质的多类步骤；不同步骤对能力的要求差异大于一个档位；步骤分类已稳定（否则路由本身成为新失败源）。

**代价**：路由判断出错会产生"该用强模型却用了弱模型"的静默质量下降；每档模型的能力边界、prompt 适配、结构化输出约束都要单独验证；缓存前缀因模型而异，可能抵消部分缓存收益。

**不适用场景**：步骤同质的任务；总步数很少（3 步以内，路由开销占比过高）；成功率尚未稳定（此时先解决成功率）。

> 能力面与档位划分依据见 `D08-运行时-模型推理.md`；本文只把路由当成本杠杆。

### 3.3 方案 C · 批处理与异步化

**机制**：把非交互路径（评测集重跑、标注、夜间批量任务、非实时摘要与归档）从同步 API 移到提供方批处理通道，以更长完成时延换折扣；系统层用队列把"用户不等结果"与"用户等结果"的工作分开。

**适用条件**：任务不在用户交互路径上；业务允许分钟到小时级时延；批量作业可幂等重跑。

**代价**：延迟大幅上升且完成时点不可控；错误处理从"立刻重试"变成"整批事后核查"，需要批次结果对账机制；折扣通常不可与其他优惠叠加。

**不适用场景**：交互路径上的调用（首 token 延迟直接决定体验）；有硬时限的任务；需要人在回路逐步确认的流程。

> 折扣参考：某厂商官方文档给出 Batch API 对输入与输出 token 的 `50%` 折扣（Anthropic 官方文档 · 2026 · 自报）`[共识]`。条款会变，需回查。

### 3.4 方案 D · 多层缓存：语义 / 结果 / 工具结果

**机制**：在提供方侧 prompt cache（按前缀精确匹配）之外，由调用方再维护三层缓存：

| 层 | 命中条件 | 典型收益 | 主要失效风险 |
|---|---|---|---|
| **语义缓存** | 新查询与历史查询向量相似度超阈值 | 高（把整条 Agent 运行压成一次向量检索） | **假命中**：语义相近但约束不同（日期、地点、身份、数量）被当作同一问题，返回错误答案且极难发现 |
| **结果缓存** | 输入完全一致 + 依赖的外部状态未变（版本号 / ETag / 数据时间戳校验） | 中高 | **陈旧命中**：价格、库存、政策已变但缓存未失效 |
| **工具结果缓存** | 同一工具 + 同一参数 + 幂等标记 + 时效窗口内 | 中（对只读工具效果好） | 对**有副作用**的工具不可用；写操作缓存直接导致状态不一致 |

**适用条件**：相同或高度相似请求重复出现；工具只读且时效性可作为显式参数表达。

**代价**：每层都要有自己的失效策略、可观测性与正确性论证；语义缓存的阈值直接影响正确率，必须纳入评测（`D09-质量-评测.md` §4.1）。

**不适用场景**：输入几乎不重复的长尾任务；约束高度个性化的任务；有副作用的工具调用。

> 协议层支撑：MCP `2026-07-28` 引入可缓存的 list 结果 `[已验证]`，使工具清单、资源清单类元数据可以合法缓存而不必每轮重拉；这是"什么可以被缓存"在协议层的明确边界。

### 3.5 选型判据

```text
第一步：成本能不能归因到步？
  ├─ 不能 → 停止优化，先做 §4.1 步骤 1–3（归因基线）
  └─ 能   → 第二步
第二步：四项分解里最大项是谁？
  ├─ 模型 token > 60%      → 方案 A（前缀冻结）；仍有缺口再加方案 B
  ├─ 工具/外部 API > 40%   → 方案 D 的工具结果缓存；检查有无可批处理的调用（方案 C）
  ├─ 存储与检查点 > 20%    → 先看 D05 的遗忘策略，再看检查点粒度
  └─ 人工复核与返工 > 20%  → 根因在成功率，回到 D09，不要在这里压
第三步：叠加时检查两个否决条件
  ├─ 缓存命中率 < 由 TTL 与调用间隔算出的下限（§4.3）→ 放弃缓存，改为缩短前缀
  └─ 引入后成功率下降 > 门禁容差 → 该方案在偷换质量，回退
```

## 4. 如何设计

### 4.1 步骤序列

| # | 步骤 | 产出物 |
|---|---|---|
| 1 | 定义"一个任务"的边界与成功判定 | 任务定义（与 `D02-地基-任务契约.md` 的完成条件一致） |
| 2 | 建立四项分解账本：模型 token / 工具与外部 API / 存储与检查点 / 人工复核与返工 | 成本分解表 |
| 3 | 按步采集：token 四分类、工具耗时与费用、是否降级、是否重试 | 归因数据集（字段见 §4.2） |
| 4 | 算基线：每任务 / 每成功任务 / 每用户成本；延迟 P50 / P95 / P99 | 基线报告 |
| 5 | 按"步 × 成本"排序，定位前 20% 的热点步 | 热点步清单 |
| 6 | 对热点步套用 §3 的杠杆，一次只改一个变量 | 变更清单 + 预期收益 |
| 7 | 在评测集上回归：成本下降时成功率是否守住门禁 | 对比报告（含 `pass^k`，见 `D09-质量-评测.md` §4.4） |
| 8 | 设护栏：单任务成本上限、单用户日配额、月度预算熔断，并定义触发后的降级行为 | 护栏配置 |

**步骤 7 不可跳过**：不伴随成功率校验的成本下降不可信（见 §7 反例 1）。

### 4.2 数据结构与接口形态

```python
from pydantic import BaseModel
from typing import Literal, Optional

class ModelStepCost(BaseModel):
    """单步模型调用成本；字段口径对齐 OTel GenAI semconv（Development，属性名可能变动）。"""
    step_index: int                                  # 必填
    node_id: str                                     # 必填：编排图节点，用于拓扑归因
    provider: str                                    # 必填：对应 gen_ai.provider.name
    model: str                                       # 必填：实际应答模型，非请求模型
    input_tokens: int                                # 必填
    output_tokens: int                               # 必填
    cache_write_tokens: int = 0                       # 选填
    cache_read_tokens: int = 0                        # 选填
    reasoning_tokens: int = 0                         # 选填
    cache_ttl_seconds: Optional[int] = None           # 选填：命中/写入所用 TTL
    is_degraded: bool = False                         # 必填：本步是否走到降级档位
    retry_of: Optional[int] = None                    # 选填：重试时指向原始 step_index
    cost_amount: float                                # 必填
    cost_source: Literal["provider_api", "rate_table"]  # 必填：金额来源，防止估算被读成实测

class ToolStepCost(BaseModel):
    tool_name: str                                    # 必填
    cache_layer: Literal["none", "semantic", "result", "tool_result"]  # 必填：命中层
    cache_hit: bool                                   # 必填
    external_fee: float = 0.0                         # 选填：外部服务费用
    duration_ms: int                                  # 必填

class LatencyBudget(BaseModel):
    """延迟预算按阶段分摊；合计不得超过端到端 SLO，超出即需重新分配。"""
    total_p95_ms: int                                 # 必填：端到端 P95 上限
    ttft_ms: int                                      # 必填：首 token（流式的主体验指标）
    model_ms: int                                     # 必填：全部模型调用合计，非单次
    tool_ms: int                                      # 必填：全部工具调用合计
    cache_lookup_ms: int                              # 必填：各级本地缓存查询合计
    human_gate_ms: int = 0                            # 选填：人在回路等待，通常不计入 SLO 分子
    headroom_ratio: float = 0.2                       # 必填：为长尾预留的余量比例

class RoutingPolicy(BaseModel):
    tier_high: str                                    # 必填
    tier_low: str                                     # 必填
    step_tier_map: dict[str, Literal["high", "low"]]  # 必填：节点 → 档位
    degrade_on: list[str]                             # 必填：触发降级的错误类别
    max_cost_per_task: float                          # 必填：单任务成本上限，超出即熔断
    max_steps: int                                    # 必填：步数上界
```

### 4.3 关键参数与取值依据

| 参数 | 由什么决定 | 判据与陷阱 |
|---|---|---|
| **缓存前缀长度** | 必须 ≥ 提供方的最小可缓存 token 门槛 | 门槛按模型不同；**低于门槛不报错**，只表现为命中率恒为 0。先量命中率再下结论 |
| **缓存 TTL 选择** | 同前缀平均调用间隔 `T` 与写入溢价 | 写入溢价需 `N` 次命中回本（`N = 写入倍率 ÷ (1 − 读取倍率)`）。`T` 远大于 TTL 时短 TTL 必亏，应选长 TTL 或放弃缓存 |
| **上下文长度上限** | 单步 prefill 成本与 context rot 拐点的交集 | 取两者较小值，不是"窗口多大就填多少"。质量侧拐点见 `D04-运行时-上下文工程.md` |
| **高档位步骤比例** | 各步骤能力敏感度分布 | 先全高档位跑出成功率基线，再逐节点降到低档位并观察掉点，**不要一次全降** |
| **重试预算** | 可重试错误占比 × 单步成本 | 上界 = 允许的额外成本 ÷ 单步成本；必须按错误类别区分，对不可重试错误重试是纯浪费 |
| **单任务成本熔断阈值** | 单位经济学目标 × 安全系数；与 `D02-地基-任务契约.md` 契约中的预算要素一致 | 设为"P95 任务成本 × 1.5~2"，使正常长尾不误杀、异常循环被拦住；熔断机制本身归 `D12-质量-可靠性.md`，本文只提供金额口径；熔断后必须有明确定义的降级行为 |
| **语义缓存相似度阈值** | 假命中代价 vs 未命中代价 | 不可拍脑袋：取一批"语义相近但约束不同"的对抗样本，调阈值到假命中率为 0，再看未命中率是否可接受 |
| **批处理适用占比** | 是否在交互路径上 | 判据是"用户是否在等这次返回"，不是"业务上是否重要" |
| **延迟指标的采集与口径** | 由 SLA 反推；首 token / 每步 / 总时长分开算 | 采集字段与采样归 `D11-质量-可观测性.md`；**均值不可作门禁**（`D09-质量-评测.md` §4.4）；人机回路等待单列，不混进模型延迟比较 |

### 4.4 分阶段实施路径

**最小可行（能把账算清）**

1. 每步记录 token 四分类与耗时并落库，离线可聚合即可。
2. 建立四项分解的月度账本。
3. 只在交互路径之外的调用上开批处理（改动局部、收益确定）。
4. 冻结系统提示与工具定义的顺序，保证前缀在会话内不变。
5. 设单任务成本上限与步数上限，超限即终止并在 trace 打标。

**生产就绪**

6. 路由策略入库（决策树或判断表），节点级档位映射版本化并与模型版本绑定。
7. 缓存分层上线，每层独立暴露命中率、假命中率（抽样人工核查）与净收益。
8. 单位经济学进入常规报表：每任务 / 每成功任务 / 每用户 / 每租户四口径，按模型版本与拓扑版本切片。
9. 成本护栏进入发布门禁，与 `D09-质量-评测.md` §8 的门禁合并执行。
10. 成本异常告警：单任务成本 P99 突破、命中率骤降、降级率骤升。

## 6. 常见陷阱

| 陷阱 | 现象 | 根因 | 埋伏阶段 | 规避方式 |
|---|---|---|---|---|
| **1 · 用单次调用价格做选型** | 对比"每百万 token 多少钱"选了便宜模型，上线后月成本反而更高 | 只看单价，没看完成任务所需步数与重试率；弱模型往往步数更多、格式修复轮次更多、失败率更高 | 设计 | 对比单位改为**每成功任务成本**，并在固定评测集上测（用 `D09-质量-评测.md` §3.2 的 Replay 模式冻结工具层，使差异只归因到模型） |
| **2 · 缓存命中了但命错了** | 语义缓存上线后成本显著下降，同时出现零星的"答案看着对但约束不对"投诉 | 相似度阈值只管"像不像"，不管"约束是否一致"；日期、地点、身份、数量在向量空间中距离很小 | 构建（阈值调参时没有对抗样本集） | 把约束字段从语义匹配中剥离，作为**精确匹配的缓存键前缀**，只对无约束部分做语义匹配；建立"相近但约束不同"的对抗用例集进入回归 |
| **3 · 成本与延迟互相拆台** | 为降本引入批处理，P95 延迟击穿 SLA；或为降延迟加大并行度，成本同比例上升 | 把两者当独立 KPI 分别优化，没有共同的预算约束 | 定义（没有把延迟与成本放进同一个预算框架） | 建立**联合预算**：给定端到端 P95 上限与单任务成本上限，一起分摊到步；任何变更必须同时报告成本与延迟两个数 |
| **4 · 检查点与记忆的隐性成本** | 模型成本控制得很好，账单仍然很高，最后发现是存储与状态序列化 | 检查点粒度太细（每步全量快照）、记忆层无遗忘策略、trace 全量落库且带完整 prompt 内容 | 构建（`D05-运行时-记忆与状态.md` 的遗忘策略缺位） | 把"存储与检查点"作为四项分解中的独立一项持续监控；检查点区分增量与全量；trace 内容字段按需采样（`D11-质量-可观测性.md`） |
| **5 · 步数失控消耗的不只是钱** | 某类输入触发循环，单次运行调用数十次模型与工具 | 缺步数上界与循环检测；重试策略对所有错误一视同仁 | 运营 | 设三道闸：最大步数、单任务成本上限、同一工具同参数重复调用检测；任一触发都记入失败标签（`D09-质量-评测.md` §4.5 成本类标签） |
| **6 · 把成本下降当成功（Goodhart 式陷阱）** | 成本报表一路向下，投诉量缓慢上升，三个月后才发现成功率已经掉了 | 成本劣化的反馈比质量劣化快得多——成本当天可见，质量要等数据积累；成本被当成唯一优化目标 | 验证（成本优化未纳入同一套门禁） | 成本与质量同表报告、同门禁阻断；任何成本下降的变更，若没有附带成功率与 `pass^k` 对比数据，视为未验证 |

## 7. 反例

1. **只换便宜模型** —— 做法：把主模型整体换成低一档，成本立刻下降。**爆掉的方式**：两周内成本回弹到原水平甚至更高，因为失败率上升带来更多重试与格式修复轮次；更隐蔽的爆法是成本没有回弹，但成功率从 92% 悄悄掉到 84%，且失败集中在最复杂的那 10% 任务上，直到人工复核成本（第四项）翻倍才被发现。
2. **为了"个性化"动态拼接系统提示** —— 做法：在系统提示里插入用户名、当前时间、最近一次会话摘要，让每次调用都不同。**爆掉的方式**：前缀缓存命中率归零，输入 token 全额计费，延迟中位数同时上升（每轮都要重新 prefill 整个前缀）。这个变化不产生任何报错、告警或指标异常——除了账单。
3. **用均值给成本做预算** —— 做法：统计出平均每任务 X 元，据此估算月度预算与对外报价。**爆掉的方式**：成本呈长尾分布，5% 的任务吃掉 40% 的成本；按均值估的预算在月中就被击穿，若报价基于均值则每一单长尾任务都在亏钱。正确做法是按 P95/P99 与分布形态定价，并给长尾设熔断。
4. **把失败任务从成本报表里剔除** —— 做法：统计单位成本时只算"成功的那些运行"，理由是失败没有产生产品价值。**爆掉的方式**：指标看起来很漂亮且持续改善，但失败的成本真实发生了（`D09-质量-评测.md` §4.4 要求错误返工成本单独计入）。剔除后得到的数字无法用于任何容量与定价决策——它描述的是一个不存在的高成功率世界；当成功率波动时，这个指标会给出完全错误的信号方向。

## 8. 开放问题

- **语义缓存的阈值能否通用化？** 一派主张通用层只提供机制不提供阈值，因为约束语义无法脱离领域表达；另一派主张按约束字段的显式程度自动判定，因为多数任务已有结构化约束字段。两派前提不同——前者假定输入以自然语言为主，后者假定输入已结构化，目前无收敛结论。 `[待验证]`
- **按步归因是必做还是选做？** 归因需要埋点与存储，低流量场景下归因成本可能高于被优化掉的成本，缺少可量化的门槛。
- **缓存收益能否跨供应商移植？** 各家的门槛、TTL、倍率、断点数量与自动管理策略都不同；"前缀冻结"这一设计在换供应商后是否需要重做，缺乏稳定抽象。
- **成本与质量的联合优化是否是伪命题？** `D09-质量-评测.md` §9 已记录"缺少统一的联合指标"。本文提出的"每成功任务成本"对 P99 长尾不敏感，可能掩盖单次极端昂贵且失败的任务；是否要引入"P99 成功任务成本"作为互补指标尚无定论。
- **熔断触发的降级算不算一次失败？** 算失败，熔断会污染成功率统计；不算失败，熔断会掩盖真实的容量与质量不足。两种口径都会在某处失真。
