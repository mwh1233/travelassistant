## 0. 总纲

> **Agent 的可靠性不是"给它加一层重试"，而是把**可重试动作**与**不可逆动作**在结构上分开；做不到这一点，任何重试策略都会把偶发故障放大成事故。** `[共识]`

这个断言可以被反驳：如果 Agent 只做只读检索，那么"加一层重试"确实就是全部答案。所以在读本文之前，先确认你的 Agent 会不会写入外部系统——只要会，下面每一条都成立。

支撑它的四条事实：

1. **Agent 是非确定性控制器**。重试在这里不是"重放同一条指令"，而是"让模型基于新信息重新做一次决策"。同一份输入重跑，可能选出不同工具、不同参数。分布式系统里"重试 = 幂等重放"的直觉，在 Agent 里直接失效。 `[共识]`
2. **它调用的下游系统整体不可靠**。一次 Agent 循环通常包含 3–20 次远程调用（模型 + 工具 + 检索 + 记忆）。任何一次调用的失败率即使只有 1%，整轮失败率也会被乘法放大——这是部分失败（partial failure）问题，不是 bug。 `[共识]`
3. **失败会被写进上下文，污染后续决策**。工具报错信息一旦作为工具结果进入下一轮上下文，模型很可能把它当成"事实"，进而编造出"因为 X 不可用，所以我改用了 Y"这类看似合理的错误路径。**失败信息在 Agent 里不是中性的。** `[待验证]`
4. **级联失败是 OWASP 明确收录的 Agent 风险**：ASI08 Cascading Failures 与 ASI10 Rogue Agents 都指向同一件事——单个组件的异常放大会让系统在无人干预的情况下持续恶化 `[已验证]`。

因此本文的结论是：**先做"可逆性分级"，再做超时与重试；先做"隔离与预算"，再做降级分级。**

## 1. 问题定义与边界

### 1.1 本文解决的问题

- 一次 Agent 运行中，某个工具/模型/外部服务失败时，如何**不把局部失败放大成整轮失败**。
- 哪些错误**可以**重试、哪些**绝不可以**；不可重试的判断如何写进代码而不是写进注释。
- 长时任务（分钟到数天）在进程重启、部署、人工等待之后如何**继续**。
- 当依赖整体不可用时，系统如何**分级降级**，以及每一级对用户意味着什么。
- 可靠性目标如何量化（SLO / 错误预算）并进入发布门禁。

### 1.2 本文不讨论什么

- **不讨论多 Agent 拓扑层面的死锁与环依赖**。那属于编排结构问题，见 `D07-运行时-多智能体.md` 的熔断小节；本文只讲与拓扑无关的通用可靠性机制。
- **不讨论部署形态、副本、资源配额、灰度策略**。那属于 `D13-交付-部署运行时.md`；本文给出的机制在 D13 里被"落到部署面"。
- **不讨论可靠性指标的具体阈值标定**。指标定义与评测口径见 `D09-质量-评测.md`；本文只讲"哪些量必须进指标"。
- **不讨论安全边界**（注入防御、权限最小化、审批门）。那些在 `D10-质量-安全护栏.md`；本文会引用审批门作为降级链的最后一环，但不定义它。
- **不讨论提示词技巧**。本文对幻觉的立场是工程性的：见 §2.3 与 §3.4，不通过 prompt 抑制。

## 2. 设计思路

### 2.1 第一性原理：Agent 把"部分失败"变成了常态

经典分布式系统的核心难题是：**你无法区分"请求没到"和"请求到了但响应丢了"和"请求还在处理中"**。这三者对应完全不同的后果——重试第一次是安全的，重试第二次会重复副作用，第三次可能没有任何效果。

Agent 让这个问题变得更糟，原因是三重叠加：

| 叠加项 | 后果 |
|---|---|
| 每一轮循环包含多次独立远程调用 | 失败概率相乘，而不是相加 |
| 决策者（模型）本身非确定 | 重试 = 重新决策，不保证收敛到同一结果 |
| 动作带外部副作用（下单、发信、改数据） | 重试的代价从"浪费一次调用"变成"重复一次真实世界的后果" |

**由此得到本文最重要的一条设计原则：可靠性设计的顺序是"先分级可逆性，再设计重试"，而不是反过来。** 可逆性决定了允许的语义（至少一次 / 至多一次），语义决定了机制。

### 2.2 不可回避的约束

| 约束 | 性质 | 对设计的强制影响 |
|---|---|---|
| **超时不可判定** | 物理限制，不可消除 | 任何超时都可能"误杀"一个实际成功的调用 → 必须配合幂等键，否则重试即重复副作用 |
| **重试会放大负载** | 正反馈，数学性质 | 重试必须在**全栈某一点**收敛，多层各重试会把 1 次请求放大成 4³ 次（Google SRE 的经典示例：3 层各配 3 次重试 = 最多 64 次到达数据库） `[共识]` |
| **模型的非确定性** | 架构性质 | 重试必须由**编排层策略**驱动，不能由模型"自己决定再试一次"，否则无法上界、无法归因 |
| **token 与延迟预算有限** | 经济约束 | 退避等待、重复调用、降级后的多轮追问都在烧预算 → 重试必须有总预算上限 |
| **MCP 无状态化** | 协议约束 | MCP `2026-07-28` 取消了 `initialize` 握手与 `Mcp-Session-Id`，会话不再由服务端持有 → "重连后恢复会话"这类重试语义必须由**客户端编排层**实现，不能指望协议层 `[已验证]` |
| **用户注意力稀缺** | 人因约束 | 降级的最后一级是"人工接管"，而人的处理吞吐是有限的 → 降级必须尽量在前面几级被吸收掉 |

### 2.3 由此推导出的四条核心取舍

**取舍一：宁可"快速失败 + 明确降级"，也不"无限重试直到成功"。**

无限重试在单机上是耐心，在系统上是攻击。需要区分两类失败：**瞬态失败**（单个组件抖动，重试有用）与**系统性失败**（由负载、相关性行为、bug 引起，重试有害且会把系统推进不可恢复状态）。AWS 的立场很直接：用 token bucket 做自适应重试，让整个故障期间的负载被限制在正常水平的约 101%，而"3 次裸重试"会放大到约 400%（AWS re:Invent ARC403 · 2024 · 自报） `[共识]`。

**取舍二：宁可让不可逆动作"结构上不可重试"，也不靠注释与规范约束。**

"这个接口不要重试"写在文档里，三个月后一定会有人加上 `@retry`。可行的做法是把可逆性写进**类型/枚举**，让重试器在编译期或运行期就能拒绝（见 §4.2 的 `reversibility` 字段）。

**取舍三：宁可把失败做成"用户可见的状态"，也不"用兜底默认值掩盖失败"。**

兜底默认值会让失败变成静默失败——这是评测里最危险的一类标签 `D09-质量-评测.md` §4.5。**降级的每一级都必须有用户可见行为**，否则降级就退化成撒谎。

**取舍四：宁可多花一次状态写入，也要把"已经执行到哪"持久化。**

Agent 任务的典型寿命是分钟级到小时级（等待人工审批、等待外部回调）。进程生命周期远短于任务寿命，二者必须解耦——这是 §3.3 检查点续跑存在的全部理由。

## 3. 通用方案

以下四种方案不是替代关系，而是**同一套可靠性栈的四层**，绝大多数生产系统都会同时用到其中三到四种。

### 3.1 方案 A · 无状态重试（超时 + 退避 + 抖动 + 幂等键）

**机制**：为每次远程调用设置超时；失败后按 `min(cap, base × 2^n)` 等待并加入抖动后重试；对写操作附加幂等键，使下游能够识别并忽略重复请求。推荐组合是**上限退避（capped exponential backoff）+ Full Jitter**，即等待 `random(0, min(cap, base × 2^n))`。

**适用条件**：失败是瞬态且彼此独立的；动作是只读或幂等的；下游支持幂等键或自带天然幂等（如"设置地址"而非"追加记录"）。

**代价**：

- 超时会误杀慢成功，产生重复调用与额外成本。
- 退避等待直接吃任务总延迟预算，用户感知为"卡住了"。
- 抖动使延迟不可预测，压测与容量估算更难。
- 幂等键需要在下游落地，跨组织时常常推不动。

**不适用场景**：不可逆动作（支付、发货、删除）；错误属于**客户端错误**（参数非法、鉴权失败、资源不存在）——重试只是浪费；下游整体过载（此时重试是加压，应改走熔断或降级）。

> 关键判据：**抖动不是可选优化。** 无抖动的指数退避在大量客户端同时失败时仍会造成同步重试波次（thundering herd）。Marc Brooker 的早期模拟给出一组对照：无抖动场景 P99 约 2600ms、错误率约 17%，加入 Full Jitter 后 P99 约 1400ms、错误率约 6%（AWS Architecture Blog · 2015 · 自报模拟） `[共识]`。

### 3.2 方案 B · 熔断与舱壁隔离

**机制**：
- **熔断（Circuit Breaker）**：按错误率/慢调用率统计下游状态，达到阈值后**快速失败**（不再发起真实调用），经过冷却窗口后放行少量探测流量决定是否恢复。
- **舱壁（Bulkhead）**：按依赖或按租户划分独立的并发池/连接池/队列，使一个下游的故障最多耗尽其自己的那份容量，而不是拖垮全部。

**适用条件**：依赖数量多、且各依赖的"坏"是独立事件；系统已能区分"这个依赖坏了"与"整个系统坏了"。舱壁在**多租户与多工具**场景收益最大。

**代价**：

- 熔断阈值难以标定——一个正常波动 ±10% 的下游若设 5% 阈值，会把正常抖动变成保护性中断。
- 对分片系统可能**扩大爆炸半径**：4 个分片挂 1 个时下游失败率 25%，天真熔断会把它变成 100%（AWS re:Invent ARC403 · 2024 · 自报） `[共识]`。
- 舱壁需要容量规划与按分区观测，运维复杂度显著上升。
- 熔断开启期间的失败是"人为制造"的，会被误读成真实故障率上升。

**不适用场景**：依赖只有一条且没有降级路径时（此时熔断只是"快一点地失败"，必须先设计 fallback 才有意义）；错误是业务性的而非可用性的（如"该用户无权限"不应计入熔断统计）。

### 3.3 方案 C · 检查点续跑（Durable Execution）

**机制**：把 Agent 运行切成可记录的步骤；每步完成时把**状态快照**持久化到外部存储（如 append-only 事件历史）；进程崩溃、被部署替换或等待人工审批后，新进程从最后一条记录之后继续。语义上：**工作流本身获得"执行一次"的效果，而具体步骤（Activity）是至少一次执行**，因此每一步仍需幂等键。

**适用条件**：任务寿命显著长于进程寿命；存在外部等待（人工审批、异步回调、隔夜处理）；步骤代价高（一次长模型调用、一次昂贵的检索）不能重跑。

**代价**：

- 工作流代码必须**确定性**——不能用墙钟时间、随机数、裸 I/O，否则重放时会与历史不一致，产生非确定性错误并让工作流卡死。所有非确定性必须被关进"步骤"里。
- 代码变更会与在途执行冲突：在流程中间插入一步，会让按旧版本记录的运行在重放时对不上，必须用版本分支/补丁机制过渡。
- 需要额外运维一套状态存储（见 `D13-交付-部署运行时.md` §4.4）。
- 存储的增长很快：每步都写一次快照，长任务会产出大量历史。

**不适用场景**：秒级以内的短任务（写检查点的开销可能大于任务本身）；完全无副作用的纯推理任务（重跑成本低，不值得引入复杂度）。

> Temporal 类实现的官方语义描述：默认 Activity 重试为无限次，即"至少一次"；把 `maximumAttempts` 设为 1 并使用普通 Activity 可得到"至多一次"——但此时**零次也是可能结果**（Temporal 官方文档 · 2026 · 厂商文档） `[共识]`。这个取舍不可回避：至少一次要付幂等成本，至多一次要付"可能没做"的成本。

### 3.4 方案 D · 降级分级与人工接管

**机制**：定义一个有序的降级阶梯，每级有明确的**触发条件**与**用户可见行为**，且只能单向下降（自动恢复需显式条件）：

| 级别 | 名称 | 触发条件（示例判据） | 系统行为 | 用户可见行为 |
|---|---|---|---|---|
| **L0** | 全功能 | 依赖健康 | 正常执行 | 无差别 |
| **L1** | 缩减功能 | 非关键依赖劣化（增强排序、二次校验、富媒体生成失败） | 关闭增强项，保留主路径 | 结果"朴素但正确"，附一行说明 |
| **L2** | 只读/受限 | 写路径依赖不可信，或错误率超阈值 | 禁止写入与不可逆动作，只允许查询与草稿 | 明确告知"当前只能查看与生成草稿，暂不能提交" |
| **L3** | 人工接管 | L2 仍无法满足，或风险等级为高 | 暂停自动执行，把已收集的事实与建议动作放入人工队列 | 进入人工流程，用户看到"已转人工"与预计响应 |

**适用条件**：所有会被用户直接触达的 Agent 产品；尤其是带外部副作用的场景。

**代价**：每一级都要单独实现用户提示、日志与测试用例（成本约为线性增加）；级别越多，状态机越容易出 bug；L2/L3 会让业务指标（完成率）在故障期显著下降——这需要业务方提前接受，否则会被迫"降级也不敢用"。

**不适用场景**：内部批处理任务（失败直接重跑更简单）；没有人工可接管资源的场景（L3 形同虚设，应把资源投入 L1/L2）。

### 3.5 选型判据

| 判断问题 | 若回答为 | 采用 |
|---|---|---|
| 该动作是否可逆、是否幂等？ | 可逆或幂等 | 方案 A（重试） |
| | 不可逆 | **禁止重试**（`max_attempts = 1`），改走审批（`D10-质量-安全护栏.md` §5） |
| 依赖数量是否 ≥ 3 且故障相互独立？ | 是 | 方案 B（熔断 + 舱壁） |
| 任务寿命是否显著长于进程寿命？ | 是（分钟级以上或含人工等待） | 方案 C（检查点续跑） |
| | 否（秒级） | 不引入方案 C，改用 A + B |
| 是否面向最终用户且有外部副作用？ | 是 | 方案 D 必选 |
| 是否存在单点依赖且无替代？ | 是 | 先补降级路径，再考虑熔断 |

## 4. 如何设计

### 4.1 步骤序列

```text
① 动作可逆性盘点      → 产出：动作清单（动作名 / 读或写 / 是否幂等 / 副作用等级 / 可补偿方式）
② 失败分类            → 产出：错误分类表（可重试 / 不可重试 / 未知），每类给出判定依据
③ 超时与预算分层      → 产出：超时预算表（每层超时值 + 上游剩余预算 + 假超时率目标）
④ 幂等键设计          → 产出：幂等键生成规则与下游契约（回指 D06 §4）
⑤ 隔离划分            → 产出：舱壁划分表（按依赖 / 按租户 / 按优先级）
⑥ 检查点与语义选择    → 产出：步骤划分 + 每步语义（至少一次 / 至多一次）+ 补偿动作
⑦ 降级阶梯与触发条件  → 产出：L0–L3 状态机 + 每级的用户可见文案与埋点
⑧ 可观测对接          → 产出：失败事件字段（对齐 OTel GenAI semconv，见 D11 §3）
⑨ SLO 与错误预算      → 产出：SLI 定义 + SLO 目标 + 预算耗尽后的冻结规则
```

### 4.2 数据结构与接口形态

以下为**形态示意**，字段名可按项目规范调整，但**字段语义不可省略**（`?` 表示非必填，其余为必填）。

```python
from enum import IntEnum
from typing import Literal, Optional
from pydantic import BaseModel, Field

class Reversibility(str):
    """动作可逆性——决定是否允许重试。这是可靠性设计的第一等字段。"""
    READ = "read"                     # 只读：重试永远安全
    WRITE_IDEMPOTENT = "write_idempotent"  # 写但幂等：重试安全（需幂等键）
    WRITE_COMPENSABLE = "write_compensable" # 写且可补偿：重试后需执行补偿动作
    IRREVERSIBLE = "irreversible"     # 不可逆：max_attempts 必须为 1

class RetryPolicy(BaseModel):
    max_attempts: int                      # 由可逆性 + 总预算决定；IRREVERSIBLE 恒为 1
    base_delay_ms: int
    cap_delay_ms: int                      # 退避上限，不得超过总预算
    jitter: Literal["full", "equal", "decorrelated", "none"]  # 生产环境禁用 "none"
    retryable: list[str]                   # 可重试的错误类别（白名单，不是黑名单）
    non_retryable: list[str]               # 显式列出，避免"没写就当可重试"
    total_budget_ms: int                   # 单次工具调用允许消耗的时间上限
    idempotency_key_from: Optional[str]    # 幂等键来源字段；WRITE_* 时必填

class ToolAttempt(BaseModel):
    call_id: str
    tool_name: str
    attempt: int
    reversibility: Reversibility
    outcome: Literal["ok", "retryable_error", "terminal_error",
                     "timeout", "circuit_open", "shed"]
    side_effect_committed: bool            # 必填：副作用是否已落到外部系统
    compensable: bool                      # 若已提交，是否可补偿
    evidence_ref: Optional[str]            # 证据位置（工具契约五要素之一，见 D06 §4）
    degraded_from: Optional[str]           # 若非空，说明这是降级后的替代结果

class CheckpointRecord(BaseModel):
    """状态快照，用于恢复与重放；不是记忆（口径见 D00 §9）。"""
    run_id: str
    seq: int
    kind: Literal["plan", "step_result", "approval_decision", "compensation"]
    state_digest: str                      # 状态内容的摘要，用于检测中途篡改
    pending_effects: list[str]             # 已提交但尚未确认的外部副作用
    created_at: str

class DegradeState(BaseModel):
    run_id: str
    level: IntEnum                        # L0=0 全功能 / L1=1 缩减 / L2=2 只读 / L3=3 人工
    reason_code: str                      # 触发降级的判据编号，必须可追溯
    entered_at: str
    user_visible_notice: str              # 必填：降级必须对用户可见，不允许空
    auto_recover_condition: Optional[str] # L0 的恢复条件；为空则只允许人工恢复
```

**接口约定（比字段更重要）**：

1. `side_effect_committed` 必须由**执行器**填写，不允许由模型生成——模型不知道真实世界发生了什么。
2. `outcome` 为 `terminal_error` 或 `circuit_open` 时，**不得**进入重试队列，必须走降级或补偿。
3. `degraded_from` 非空的结果，在最终输出里必须可被下游识别，否则就是静默失败。
4. 所有可靠性事件必须同时发一条 trace（对齐 OTel GenAI semconv，见 `D11-质量-可观测性.md` §3），否则 §8 的开放问题无法回答。

### 4.3 关键参数与取值依据

**不要照抄推荐值。** 每个参数都由具体条件决定，下表给出的是"由什么决定"。

| 参数 | 由什么决定 | 常见的错误取法 |
|---|---|---|
| **单层超时** | 由下游延迟分布的某个高分位反推：先定一个可接受的**假超时率**（Amazon 的做法是以 0.1% 假超时率为目标，取对应分位延迟），再**逐层向内收紧**，保证内层超时之和 < 上游剩余预算（AWS Builders' Library · 2023 · 厂商工程指南） `[共识]` | 对所有调用统一设 30s；内层超时大于外层超时（等于内层超时永远不生效） |
| **`max_attempts`** | 由可逆性（IRREVERSIBLE → 1）× 总预算 ÷ 单次 P95 耗时共同决定；工程上很少需要超过 4 | 全站统一 3 次，包括支付类调用 |
| **退避上限 `cap`** | 由任务总预算与上游超时决定，必须使"最坏情况下所有重试之和"仍然可接受；没有 cap 的 10 次指数退避可达半小时量级 | 用默认 cap 而不检查它是否已超出上游超时 |
| **抖动模式** | 由系统类型决定：**封闭系统**（工作由内部产生，如 worker 池）中退避很有效；**开放系统**（流量来自外部，如面向公网的 API）中退避几乎无效，抖动是必需项（AWS re:Invent ARC403 · 2024 · 自报） `[共识]` | 在开放系统里指望"让调用方退避"来降低到达率 |
| **重试预算** | 由"重试不再是例外"这一判断反推。Google 的经验值：单请求最多 3 次尝试；单客户端出站请求中重试占比超过 10% 即停止重试；进程级每分钟重试次数设上限（SRE Book · 2016） `[共识]` | 只设单次调用重试次数，不设全局速率上限 → 重试风暴 |
| **熔断阈值** | 由下游的**错误率基线与其正常波动范围**决定：阈值必须显著高于正常波动上界，否则会把正常抖动判成故障 | 对基线 2%、波动 ±3% 的下游设 5% 阈值 |
| **熔断半开探测量** | 由"恢复需要多少样本才能判断"决定，通常远小于正常流量；探测流量必须计入统计但不应影响用户请求 | 半开放行全量流量，直接造成二次冲击 |
| **租约/心跳间隔** | 心跳间隔 ≪ 租约时长，且租约时长 > 单步最长处理时间；两者共同决定"进程崩溃后多久任务才会被回收重跑" | 心跳与租约同值，导致正常处理中的任务被反复判定超时 |
| **检查点写入频率** | 由"重跑一步的代价"与存储成本共同决定：代价高（长模型调用、昂贵检索）则每步写；代价低则按阶段写 | 每个 token 写一次（存储爆炸）/ 整轮结束才写（等于没有检查点） |

### 4.4 分阶段实施路径

**最小可行（第一周即可完成）**

1. 完成 §4.1 的 ①②③④：动作清单、失败分类、分层超时、幂等键。
2. 落一条硬规则：`IRREVERSIBLE` 动作的 `max_attempts = 1`，且**在代码层校验**而非文档说明。
3. 每种失败都必须产出结构化 `ToolAttempt`，并带上 `side_effect_committed`。
4. 加一个最小降级：只做 L0 → L2（无法写入时明确告知用户），不做 L1。
5. 定义两条 SLI：**任务级成功率**、**静默失败率**（工具报错但流程继续）。

**生产就绪**

6. 引入舱壁：按依赖划分并发池，至少把"用户请求"与"后台批处理"分开。
7. 引入熔断，阈值按下游基线标定；对分片系统改用自适应算法（如目标速率调节），避免把分片故障放大为全量熔断。
8. 长任务改为检查点续跑，明确每一步的语义（至少一次 / 至多一次）与补偿动作；对至少一次步骤全部补齐幂等键。
9. 实现完整 L0–L3 阶梯，每一级都有用户可见文案、埋点与独立的回归用例。
10. 定义 SLO 与错误预算，并**把预算耗尽后的行为写死**（例如：冻结高风险变更、只允许修复类发布）。
11. 把 `pass^k` 与级联失败场景加入回归评测（见 `D09-质量-评测.md` §4.4）。
12. 定期做故障注入：随机让某个工具超时/返回 500/返回畸形数据，验证降级是否按阶梯触发。

## 5. 检查清单

### 5.1 「最小可行」

- [ ] 有一份动作清单，每个动作标注了可逆性（read / write_idempotent / write_compensable / irreversible）
- [ ] 每个不可逆动作的 `max_attempts` 为 1，且该约束在代码中有强制校验
- [ ] 每个远程调用都有超时，且内层超时小于其上游的剩余预算
- [ ] 重试策略使用指数退避 + 抖动，且设置了退避上限
- [ ] 重试错误类别是**白名单**（显式列出可重试项），未知错误默认不重试
- [ ] 所有写调用携带幂等键，且下游契约中明确该字段（见 D06 §4）
- [ ] 每次工具调用都记录 `side_effect_committed`
- [ ] 至少存在一级降级路径，且降级时有明确的用户可见提示
- [ ] 任务级成功率与静默失败率两个指标已接入监控

### 5.2 「生产就绪」

- [ ] 重试在全栈只有一处生效，其他层明确"失败透传"
- [ ] 存在全局限速的重试预算（请求级 / 客户端级 / 进程级至少一项）
- [ ] 舱壁已按依赖或租户划分，单依赖故障不会耗尽共享池
- [ ] 熔断阈值基于下游真实基线标定；对分片依赖不使用开关式熔断
- [ ] 熔断/降级状态被显式记入 trace 与指标，可与真实故障率区分
- [ ] 长任务使用检查点续跑，每个步骤标明语义（至少一次 / 至多一次）与补偿动作
- [ ] 至少一次语义的步骤全部具备幂等键或天然幂等性
- [ ] 检查点恢复有回归用例：进程被杀后能继续，且不产生重复副作用
- [ ] L0–L3 四级降级阶梯已实现，每级有触发条件、用户可见文案、埋点与用例
- [ ] 有 SLO 定义与错误预算，且预算耗尽后的冻结规则被写死并被执行
- [ ] 故障注入（工具超时 / 5xx / 畸形返回）已纳入常规回归
- [ ] 级联失败场景（一个子调用失败）有专门的回归用例

## 6. 常见陷阱

### 陷阱 1 · 对不可逆动作重试

**现象**：偶发性的重复下单、重复退款、重复发信。日志里"两次调用都成功"，用户侧只有一次操作。
**根因**：重试策略按"接口"配置而不是按"动作语义"配置；或者超时被当成失败，但实际请求已经在下游成功，重试造成第二次副作用。
**埋伏阶段**：**设计**（可逆性没有成为一等字段）→ 运营期爆发，且通常以低频、难复现的方式出现。
**规避**：把可逆性写进类型并在重试器里强制；不可逆动作一律 `max_attempts = 1`，失败走人工而不是重试。

### 陷阱 2 · 多层重试造成的重试风暴

**现象**：上游一次抖动，下游流量瞬间放大约 3–4 倍，系统从"部分不可用"进入"完全不可用"，恢复时间远长于故障本身。
**根因**：网关、SDK、编排层、Agent 循环各配了重试，且都认为自己只重试 3 次"很保守"。乘法的结果是爆炸。
**埋伏阶段**：**设计**（没人负责全局重试预算）。
**规避**：明确规定"重试只在某一层发生"，其他层失败透传；引入重试预算（请求级 / 客户端级 / 进程级）与 token bucket 式自适应限流。

### 陷阱 3 · 让模型决定是否重试

**现象**：模型看到工具报错后"自己想办法"再调一次，有时换个参数再试、有时换一个工具，行为不可预测，成本与延迟无上界。
**根因**：把重试当成决策问题交给非确定性控制器，而不是编排层的确定性策略。
**埋伏阶段**：**设计**。
**规避**：重试策略固定在编排层；交给模型的只有"失败事实 + 可选动作"，且动作集合中不含"原样重试"，只含"换策略"（如缩短查询范围）或"上报"。

### 陷阱 4 · 熔断把部分故障放大成全局故障

**现象**：4 个分片只挂了 1 个（25% 失败率），客户端熔断整体打开后变成 100% 不可用。
**根因**：熔断按"接口整体错误率"判定，忽略了下游是分片/多副本结构。
**埋伏阶段**：**设计**。
**规避**：对分片依赖使用按分片粒度的统计或自适应算法（随下游容量调节速率），避免"开/关"二值熔断；上线前用 4 分片挂 1 个的场景做验证。

### 陷阱 5 · 静默失败被兜底值掩盖

**现象**：检索失败后返回空列表，模型据此回答"没有找到相关信息"，用户以为是真的没有；监控上成功率 100%。
**根因**：错误被转换成"合法的空结果"，失败信息在类型上与正常结果不可区分。
**埋伏阶段**：**构建**（错误处理写成 `except: return []`）→ 运营期几乎不可见。
**规避**：失败必须与"空结果"在类型上可区分；降级结果必须带 `degraded_from` 标记；把静默失败率单独设成指标并进门禁（见 `D09-质量-评测.md` §4.2）。

### 陷阱 6 · 检查点续跑把副作用重放一遍

**现象**：进程重启后任务继续，但用户收到了第二封邮件 / 仓库里出现了第二笔记录。
**根因**：误以为"检查点 = 只执行一次"。实际语义是**工作流执行一次效果、步骤至少一次执行**；崩溃点恰好在"副作用已提交、记录未写入"的毫秒窗口内时，步骤一定会重跑。
**埋伏阶段**：**构建**。
**规避**：所有带副作用的步骤必须幂等（幂等键）或可补偿；检查点记录里维护 `pending_effects`，恢复时先核对副作用是否已落地。

### 陷阱 7 · 降级没有用户可见行为

**现象**：系统已经降到只读模式，但界面仍然显示"提交"按钮并提示成功（实际未写入）。
**根因**：降级被实现为后端开关，没有同步到交互层；或产品认为"告知降级会影响体验"。
**埋伏阶段**：**设计**（降级阶梯只定义了技术条件，没定义用户可见行为）。
**规避**：每一级都必须定义用户可见文案并纳入验收；无用户可见行为的降级不算实现（交互实现见 `D14-交付-人机协作.md` §3.4）。

## 7. 反例

### 反例 1 · "全站统一重试 3 次"

**做法**：在 HTTP 客户端统一配置"超时 30s、重试 3 次、指数退避"，包括写操作。
**爆掉的方式**：第一次真实故障发生在支付类调用上：下游实际成功但响应超时，重试造成重复扣款。**爆发时间点是第一次下游抖动**，而不是压测时；因为压测里下游永远不会"成功了但不回包"。

### 反例 2 · 用"整轮重跑"作为长任务的恢复策略

**做法**：任务失败就从头再来一遍，理由是"反正结果应该一样"。
**爆掉的方式**：任务跑到第 12 步（已发出 3 封通知、已创建 2 笔外部单据）失败，重跑把它们全部重做一遍。**爆发时间点在任务时长超过几分钟之后**——短任务下这个做法确实从来没出过问题，所以它在评测阶段是"通过"的。

### 反例 3 · 把降级做成"静默换模型"

**做法**：主模型不可用时自动切到更弱的小模型，但对用户与日志都不标注。
**爆掉的方式**：故障期内输出质量整体下降，用户投诉"变笨了"，而监控显示"成功率 100%、无错误"。归因时既找不到降级记录，也不知道影响面有多大——**故障已经结束，证据已经丢了**。正确的做法是把 `degraded_from` 写进结果与 trace，让降级可统计。

### 反例 4 · 熔断阈值照抄别人的数字

**做法**：看到某处写"错误率超过 5% 就熔断"，直接照搬到自己的下游。
**爆掉的方式**：该下游的基线错误率本来就是 2%–8%（业务性失败，不是可用性失败）。上线后熔断频繁误触发，被团队当成"熔断没用"而整体关闭，于是真正的故障失去保护。**爆掉时间点是上线后第一个流量高峰。**

## 8. 开放问题

**⑴ 重试应由编排层还是由模型负责？**

- **派 A（编排层负责）**：重试是可上界、可归因、可测试的确定性策略，必须由编排层持有；模型只输出"意图"与"失败事实"。
  前提：工具语义稳定、错误分类清晰、编排层能拿到结构化错误。
- **派 B（模型参与重试决策）**：某些失败的正确应对是"换个思路"（改查询范围、换数据源、降级目标），这是决策而非策略，编排层写不出穷举规则；交给模型可以在长尾上显著提升完成率。
  前提：有严格的成本与步数上界、可观测性足以回放、且模型能拿到"为什么失败"的结构化信息。
- **不合成结论**：两派的实际分歧在于**"长尾完成率"与"可预测性"哪个更值钱**。可操作的做法是：把不可逆动作与写操作强制划归派 A，把只读探索划归派 B，并给派 B 设独立预算。

**⑵ 降级阶梯应该由系统自动触发，还是必须人工确认？**

- **自动触发派**：故障期的每一秒人工延迟都是损失；且人工确认的转人工链路本身可能故障。
  前提：降级动作**保守且可逆**，且用户被清晰告知。
- **人工确认派**：降级改变了业务语义（例如从"可提交"变成"只读"），属于产品决策，不应由可靠性代码单方面决定。
  前提：有 7×24 的响应能力，且降级频率不高。
- **实际分歧点**：触发条件是**可用性信号**（自动）还是**业务语义变化**（人工）。目前行业未收敛。

**⑶ 幻觉能否通过"结构约束 + 验证环节"工程性抑制，还是必须靠模型能力提升？**

- **工程派**：把"有依据"变成可校验的结构——每个结论性输出必须带证据位置，验证环节只做"证据是否存在、是否支持结论"的机械检查。前提：存在可供校验的证据源。
- **能力派**：验证环节自身也是模型调用，会引入二次幻觉与数倍成本，且它无法验证"证据源本身是否过期/被污染"。前提：任务为开放式生成，缺少可枚举的证据。
- **可观察的判据**：如果任务的成功标准能写成系统状态断言（见 `D09-质量-评测.md` §3），工程派可行；否则退回能力派。

**⑷ 至少一次 vs 至多一次，在 Agent 场景下的默认值应该是什么？**

- 分布式系统的默认答案是"至少一次 + 幂等"，因为它不丢事。但 Agent 的动作常常**无法幂等**（发消息、通知第三方、影响人的决策），此时"至少一次"的代价由外部承担，而"至多一次"的代价由系统承担。默认值应否偏向至多一次，目前缺少工程共识。
