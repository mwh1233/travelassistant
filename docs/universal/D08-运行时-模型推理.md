## 0. 总纲

> **在 Agent 里，模型选型不是"挑一个最强的模型"，而是"为每一类子任务配一个能力下限刚好够用的推理档位"。把最强模型开在最高推理档位跑完所有步骤的系统，失败形式不是"答错"，而是"延迟与成本不可预算、且事后无法定位是哪一步贵"。** `[共识]`

- **成本与延迟是步数的乘积，不是单次调用的线性叠加。** 15 步任务里每步 2 倍成本、3 倍延迟，会变成整体的数量级差异。单步档位选择被循环结构放大——这是模型层最大的杠杆，也最先被忽略。
- **能力不可外推。** 能拿国际数学奥林匹克金牌的模型，读模拟时钟的正确率只有 50.1%（Stanford AI Index 2026 · 2026-04 · 复现）。"用总分最高的模型"在 Agent 场景里是没有依据的启发式。`[已验证]`
- **路由是架构决策，不是运维调优。** 它同时决定前缀缓存命中率、可观测性归因口径、回归覆盖矩阵，必须随接口一同冻结（`D00-地基-总纲.md` §2.2）。
- **结构化输出的可靠性来自约束机制，不来自祈使句；名义上下文窗口 ≠ 有效上下文窗口。**

一句话：**决定"哪一步配哪个档位"，并让这个决定可观测、可预算、可回归。**

## 1. 问题定义与边界

### 1.1 本文解决的问题

1. **分档**：一个任务含规划、抽取、分类、改写、校验、总结等异质子步骤，如何为每类配置能力档位。
2. **预算**：单步推理强度（reasoning effort / thinking budget / 测试时计算）开到多少，及其与延迟成本的非线性关系如何进入预算。
3. **约束**：如何让结构化输出从"通常能解析"变成"必然可解析"，以及这个必然性牺牲了什么；同时确定用什么证据判断某模型"够用"（选型）。
4. **命中**：前缀缓存命中率如何被模型路由与上下文装配共同决定（机制归 `D04-运行时-上下文工程.md`，本文只讲模型侧差异与路由影响）。

## 2. 设计思路

### 2.1 第一性原理：一次推理调用只有四个可交易量

不存在同时改善四者的选项：**能力**由模型档位、推理档位、可用上下文决定，提高它要付出延迟与成本；**延迟**的下界由输出 token 数决定（自回归串行解码），降低它要牺牲能力或增加并行成本；**成本**由输入 token（含缓存折扣）与输出 token（含 reasoning token）构成，降低它要牺牲能力或延迟；**确定性**由温度、约束解码与模型版本决定，提高它要削掉模型的自由度。

**关键推论：延迟的下界由输出 token 数决定。** 自回归解码是串行的，输出 N 个 token 的墙钟时间近似随 N 线性增长。因此"提高推理档位"在物理上等价于"生成更多 token"，延迟必然上升，且上升幅度与思考长度成正比，而不是与"难度提升幅度"成正比。

### 2.2 六个不可回避的约束

| 约束 | 性质 | 对设计的影响 |
|---|---|---|
| **测试时计算收益递减，曲线未知** | 结构性。思考 token 增加时正确率先升后平，拐点因任务类型而异 | 不能设全局"高推理档位"，必须按任务类型找拐点；不要照搬外部预算值 `[待验证]` |
| **能力是参差的（jagged frontier）** | 语料与训练目标的产物，非实现缺陷 | 不能用总分排序选模型，必须按**自己的子任务类型**分别测 |
| **注意力是两两计算的** | 架构性质（回指 `D04-运行时-上下文工程.md`） | 名义窗口不是有效窗口；塞满窗口同时拉高成本与降低召回 |
| **约束解码改变输出分布** | 解码机制性质 | 换来解析必然性，代价是约束之外的自由度被削掉（§3.2） |
| **供应商不可控** | 商业与运维现实 | `latest` 别名静默解析到新快照；函数调用与 JSON 模式的边界行为跨版本会变 |
| **前缀缓存要求字节级稳定的前缀** | 缓存机制性质 | 路由一旦改变系统提示或工具集，命中率归零。**路由与缓存必须同时决策** |

### 2.3 由此推导出的三条取舍

**取舍一：宁可让某一步能力不足并显式失败，也不要让每一步都用最强档位以致整体不可预算。** 显式失败可被观测、重试、降级（归 `D12-质量-可靠性.md`）；不可预算的成本与延迟只能事后削减，而削减时你无法知道砍掉的是哪一档。**可归因的失败优于不可归因的成功。**

**取舍二：宁可让结构化输出靠 schema 约束 + 校验重试兜底，也不要靠 prompt 里的格式要求再事后正则解析。** 正则解析把失败推迟到解析层并丢失失败原因；校验重试把失败变成一个可计数的指标（重试率），并能定位到具体字段。**把概率性约束转换为结构性约束，是模型层性价比最高的改动。**

**取舍三：宁可锁定模型版本并承担一次升级回归的成本，也不要让 `latest` 别名在生产上漂移。** 别名漂移不产生告警，只产生"最近好像不太稳"这类无法行动的报告。**版本锁定把一次不可观测的漂移换成一次可观测的回归**（流程归 `D17-迭代-迭代闭环.md`）。

### 2.4 由此推导出的五条结论（不另行论证）

① **路由必须显式**（由"供应商不可控"推出，任何"让模型自己选档位"的设计都不可回归）；② **每一档位必须有独立评测锚点**（由能力参差推出，`D09-质量-评测.md`）；③ **路由粒度不得细于可观测性粒度**（否则降级造成的损失不可归因，`D11-质量-可观测性.md`）；④ **能被规则判定的步骤不应消耗推理**（与 `D02-地基-任务契约.md` "先穷尽最简方案"同源）；⑤ **缓存命中率是架构指标而非运维指标**（由"前缀需字节级稳定"推出，上线后调不回来）。

## 3. 通用方案

四类子问题，每个方案固定四字段：**机制 / 适用条件 / 代价 / 不适用场景**。

### 3.1 路由方案

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 静态单模型单档位** | 全链路同一模型、同一推理强度，无路由逻辑 | 步数 ≤5；子任务同质（如全是抽取）；原型阶段 | 能力与成本只能二选一：按最强配则简单步骤严重超配，按最低配则规划步骤静默失败（计划本身错，但每步执行都"成功"） | 步数随任务长度变化的开放式任务；有成本或延迟预算的生产系统 |
| **B · 任务类型静态路由** | 按**预定义步骤类型**（分类/抽取/规划/工具选择/总结/校验）静态映射到不同模型档位；映射表构建期冻结，运行时不做动态判断 | 拓扑已固定（`D03-地基-编排模式.md`）；步骤类型可枚举；流量可预测 | 需维护映射表并随模型迭代重测；对"看起来像分类实则是规划"的模糊步骤会误配。**映射表是配置，必须进版本管理** | 动态生成计划的拓扑（步骤类型在运行时才产生） |
| **C · 难度自适应路由（级联）** | 先用轻档位处理，由**可自动判定的置信信号**（解析失败、schema 校验失败、多次采样不一致、预算余量）决定是否升级到重档位 | 存在**廉价且可靠的下游验证器**（schema 校验、可执行代码、可查的事实源） | 升级判定有假阴（该升没升 → 静默错误）与假阳（不该升却升 → 成本反超方案 B）。**升级必须由验证器触发而非模型自评触发**——自评校准差是常见失败源 `[共识]` | 无法构造自动验证器的开放语义任务；对 P99 延迟敏感的场景（一次请求可能跑两次） |
| **D · 并行集成 + 仲裁** | 同一子任务多模型/多档位并行，再由规则或第三个模型仲裁（多数投票、最优选择、字段级合并） | 高风险且可判定的子任务（金额、日期、ID 类关键字段、安全分类）；调用成本占整体预算低 | 成本与延迟近似按并行度线性增加；仲裁环节引入新失败模式（仲裁器偏好、位置偏见，见 `D09-质量-评测.md` §5.2） | 开放式生成（仲裁器无法判断哪个更好）；长链路的每一步（成本乘法放大） |

### 3.2 结构化输出方案

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 仅 prompt 约束** | 指令里写"只输出 JSON，字段为…"，靠提示遵循 | 原型、内部工具、输出仅人工阅读 | 失效是概率性的；失败时表现为**下游解析崩溃**而非模型报错。长输出、复杂嵌套时失败率显著上升 | 有机器消费者的任何生产链路 |
| **B · 约束解码 / grammar** | 解码阶段用语法（JSON Schema / 正则 / CFG）掩蔽非法 token，使输出结构必然合法 | 字段结构固定、枚举已知、需要极高解析率 | **牺牲自由度**：模型无法在约束之外表达；"值本身需要推理"的字段可能出现格式正确而内容劣化的结果；部分实现嵌套/联合类型支持有限，并可能抑制思考过程 `[待验证]` | 需要自由推理再归纳结构的任务；思考型字段不应被强约束 |
| **C · 工具调用即 schema** | 把结构化输出写成一次工具调用的参数，复用 function calling 的 schema 校验（MCP `2026-07-28` 下工具 schema 即契约，归 `D06-运行时-工具与协议.md`） | 已接工具调用；输出与某动作绑定 | 受供应商函数调用实现质量影响；参数名成为对外持久契约，改名成本高 | 纯数据抽取、不希望触发动作语义的场景 |
| **D · 校验 + 修复回环** | 自由输出 → schema 校验 → 失败则把**校验错误原文**回灌要求修复，限次重试 | 用作 A/B/C 的兜底；字段少、修复成本低 | 增加 1+ 次模型调用；必须设重试上限，否则形成隐性循环 | 无法在 1–2 次修复内收敛的高复杂度结构 |

**组合惯例**：以 C 或 B 作主约束（结构性），以 D 作兜底（可计数），并对**修复重试率**单独设指标——它直接读出"约束设计是否合适"。

### 3.3 推理档位与预算方案

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 全局固定档位** | 所有步骤统一推理强度 | 原型；任务同质 | 无法匹配异质步骤，整体延迟被拉高 | 有延迟或成本约束的生产系统 |
| **B · 按步骤类型定档** | 规划/校验用高档位，抽取/改写/分类用低档位或关闭思考 | 步骤类型可枚举（与 §3.1 方案 B 配套） | 需为每类步骤实测拐点；定档表随模型升级失效 | 步骤类型动态生成 |
| **C · 按不确定性动态升档** | 以验证器失败、多次采样不一致、字段缺失等信号触发提高档位重试 | 有可自动判定的失败信号 | 延迟出现长尾（少数请求跑多次）；升档判据需与路由日志联合调试 | 无验证器的开放任务 |
| **D · 预算封顶 + 主动截断** | 为单任务设思考 token 与总步数上限，触顶即降档或转人工 | 长时任务、无人值守任务 | 截断语义不完整，可能产出"半成品但看起来完整"的答案，必须配显式失败标记（归 `D12-质量-可靠性.md`） | 单步任务（封顶无意义） |

**存档口径**：无论选哪种，**"本次调用实际使用的模型标识与推理档位"必须成为 trace 的一等属性**（实现归 `D11-质量-可观测性.md`），否则后续的成本与质量分析无法归因。

### 3.4 缓存命中方案

> 缓存机制、前缀冻结、TTL 与失效策略归 `D04-运行时-上下文工程.md`；此处只列**模型侧差异与路由影响**。

| 方案 | 机制 | 适用条件 | 代价 | 不适用场景 |
|---|---|---|---|---|
| **A · 无缓存** | 每次调用发送完整上下文 | 上下文短、调用次数少 | 成本与延迟随上下文长度线性上升 | 长系统提示 + 多步循环（最常见的 Agent 形态） |
| **B · 前缀缓存（provider-side）** | 供应商缓存前缀 KV，命中部分按折扣计价并降低首 token 延迟；要求前缀**字节级稳定** | 系统提示 + 工具定义 + 固定示例构成的可冻结前缀，且被反复调用 | **脆弱**：任何前缀变更（工具集增删、提示里插入时间戳、路由切换模型）都会击穿；命中率下降不产生告警，只表现为成本与首 token 延迟上升 | 前缀频繁变化（如每步重写系统提示） |
| **C · 应用侧语义缓存** | 对语义等价请求复用上一条结果（通常配向量相似度） | 高重复、低时效敏感的问法 | 相似度阈值难定：偏低→返回错误答案且**无错误信号**；偏高→命中率接近 0。对时效或个性化依赖强的任务风险极高 | 依赖实时状态、用户上下文或有可写副作用的调用 |
| **D · 分层组合** | 前缀缓存打底 + 语义缓存仅用于明确的只读子任务 + 结果缓存按会话隔离 | 生产系统 | 需要一份"哪些子任务可缓存"的白名单，并随功能演进维护 | 多租户未隔离的系统（跨租户命中＝数据泄漏，归 `D10-质量-安全护栏.md`） |

**路由破坏缓存的方式**（本文特有的关注点）：路由把流量分散到不同模型/不同工具集后，**同一业务路径可能组装出不同的前缀**，于是每个变体的命中次数都低于阈值，缓存实际失效而无人察觉。判断方法：**按路由标签切分命中率，而不是看全局值**（切分口径归 `D11-质量-可观测性.md`）。

### 3.5 选型判据

**决策表：按子任务类型定档**

| 子任务类型 | 失败代价 | 档位 | 结构化输出 | 路由方式 |
|---|---|---|---|---|
| 规则可判定的校验、格式检查 | 低 | 不用模型 | — | — |
| 分类、意图识别、路由判定 | 中（错误放大到后续全部步骤） | 最低可用档位 | 枚举约束 | 静态或级联 |
| 抽取（字段、实体、参数） | 高（错值进入副作用） | 中档位 | schema 约束 + 校验 | 静态；关键字段可并行仲裁 |
| 规划与任务分解 | 极高（下游无法修复） | 高档位 | 自由文本 + 结构校验 | 静态高档位，不参与降级 |
| 工具选择与参数生成 | 高 | 中高档位 | 工具 schema 即约束 | 静态 |

**决策树：是否需要动态路由**

```text
子任务的正确性能否被廉价、自动地判定？
├── 不能 → 用静态路由（方案 B）。不做自适应，因为"该不该升级"本身无法被验证
└── 能 ──> 单次调用成本占整体预算是否可忽略？
          ├── 是 → 优先并行集成（方案 D），直接换正确率
          └── 否 → 用级联（方案 C），并强制：升级由验证器触发、且设升级次数上限
```

**禁用项（本文硬结论）**

- **禁止用 MMLU / HumanEval 类分数选 Agent 模型**——基于这类分数为 Agent 选型，是 2026 年明确不成立的赌注（`D09-质量-评测.md` §6 · `[已验证]`）。
- **禁止用单一总分比较模型**——能力参差意味着相对强弱不稳定（Stanford AI Index 2026 · 2026-04 · 复现）；选型必须在**自己的子任务切片**上测。
- **禁止在生产使用会静默解析到新快照的模型别名。**

## 4. 如何设计

### 4.1 步骤序列

| # | 步骤 | 产出物 |
|---|---|---|
| 1 | **拆出子任务清单**：把拓扑里每个需要模型参与的步骤写成一行，标注输入、输出、是否有副作用 | 子任务清单（`task_id` / 输入摘要 / 输出类型 / 副作用标记） |
| 2 | **为每个子任务定"最大可承受代价"**：先写延迟与成本上限，再选模型（顺序不可颠倒） | 子任务代价上限表 |
| 3 | **初配档位**：按 §3.5 决策表填入模型与档位，宁可先保守 | 路由表 v0（配置文件，进版本管理） |
| 4 | **为每个档位建最小验证集**：每类子任务 30–50 条自带判定条件的样本（建设方法归 `D09-质量-评测.md`） | 分档验证集 |
| 5 | **实测拐点**：对规划类与抽取类扫推理档位，记录正确率与延迟/成本的联合曲线 | 拐点表 |
| 6 | **定结构化输出方案**：按 §3.2 选主约束与兜底，写死修复重试上限 | schema 定义 + 重试上限 |
| 7 | **验证缓存前提**：确认各路由变体下的前缀字节稳定性，按路由标签测命中率 | 命中率分变体基线 |
| 8 | **把路由标签写进遥测**，随后**冻结并登记**：路由表、schema、档位表进版本管理，改动需评审 | 遥测属性清单（实现归 `D11-质量-可观测性.md`）+ 冻结记录（`D00-地基-总纲.md` §2.2） |

### 4.2 数据结构与接口形态

路由表最小可用形态（`!` 标注必填）：

```yaml
version: "1.3.0"                               # ! 路由表版本，必须与调用记录一同上报
defaults:                                      # ! 兜底策略
  model_id: "<provider>:<model>@<snapshot>"    # ! 显式快照，禁用 latest 别名
  reasoning_effort: "low"                      # ! 枚举随供应商而异：none|low|medium|high
  max_output_tokens: 1024                      # ! 硬上限，防失控输出
  temperature: 0.0                             # ! 抽取/规划应为 0；开放生成才调高
  timeout_ms: 30000                            # ! 必须小于上游整体超时
  max_repair_attempts: 1                       # ! 结构化校验失败后的修复次数上限
routes:
  - task_type: "plan"                          # ! 取自 §4.1 步骤 1 的子任务清单
    model_id: "<provider>:<model>@<snapshot>"
    reasoning_effort: "high"
    output_spec:
      mode: "json_schema"                      # ! none|json_schema|grammar|tool_call
      schema_ref: "schemas/plan.v2.json"       # ! 与 mode 配套；none 时省略
      strict: true                             # ! 是否启用约束解码
      free_text_fields: ["rationale"]          # ! 豁免约束的字段，避免思考被压死
    fallback:
      escalate_to: "plan_heavy"                # ! 升级目标；最多两级
      degrade_to: "plan_light"                 # ! 降级目标
    budget:
      max_thinking_tokens: 8192                # ! 单次推理的硬上限
      max_retries: 0                           # ! 规划步骤不重试，失败即降级或转人工
```

调用结果的返回形态（调用方必须能拿到这些字段，否则无法归因）：

```python
from dataclasses import dataclass
from typing import Literal, Any

@dataclass
class ModelCallResult:
    ok: bool                       # ! 是否满足契约（含 schema 校验通过）
    value: Any | None              # 解析后的结构；ok=False 时可为 None
    task_type: str                 # ! 回填路由标签，用于切片统计
    model_id: str                  # ! 实际生效的模型快照
    requested_model: str           # ! 请求值；与 model_id 不同即说明别名漂移
    reasoning_effort: str          # ! 实际档位
    route_version: str             # ! 路由表版本
    latency_ms: int                # !
    repair_attempts: int           # ! 修复重试次数（0 表示一次通过）
    constraint_mode: Literal["none", "json_schema", "grammar", "tool_call"]  # !
    input_tokens: int              # ! token 口径归 D11-质量-可观测性.md
    output_tokens: int             # !
    cache_read_input_tokens: int | None       # 可空：供应商可能不返回
    cache_creation_input_tokens: int | None   # 可空
    reasoning_output_tokens: int | None       # 可空：思考 token 常单独计价
    failure_kind: str | None       # ! schema_violation|timeout|empty_output|
                                   #   refusal|transport_error|budget_exceeded
```

> `requested_model` 与 `model_id` 分离是刻意的：这是别名漂移唯一的可观测痕迹（同 `gen_ai.request.model` 与 `gen_ai.response.model` 的思路，属性口径归 `D11-质量-可观测性.md`）。

### 4.3 关键参数与取值依据

> 原则：**写"由什么决定"，不写"建议设为 X"。**

| 参数 | 由什么决定 | 误用后果 |
|---|---|---|
| **模型档位** | 由该子任务的**失败代价**与**可否被下游修复**共同决定：不可修复 → 高档位；可被校验重试 → 低档位 | 按"哪个模型更强"整体升档，简单步骤严重超配且延迟长尾 |
| **推理档位** | 由该子任务的**拐点位置**决定，拐点必须自测（§4.1 步骤 5）。它通常落在"任务需要多步内部推理"的临界处 | 全局最高档：延迟与成本上升而正确率不变；全局关闭：规划类静默失败 |
| **max_thinking_tokens** | 由 P95 延迟预算反推：单步允许墙钟时间 ÷ 每 token 解码耗时 | 不设上限 → 少数请求产生极长思考，P99 不可控 |
| **max_output_tokens** | 由输出结构的最大合理体积决定，而非模型上限 | 设成模型上限等于没设，是账单异常的主要来源 |
| **temperature** | 由"该子任务是否存在多个同样正确的输出"决定：抽取/分类/规划取 0，创意生成才取正数 | 抽取类用高温 → 同输入产生不同字段值，破坏幂等（`D06-运行时-工具与协议.md`） |
| **max_repair_attempts** | 由 schema 复杂度与字段数决定；超过 2 次边际收益很小且会掩盖 schema 设计问题 | 无穷 → 隐性循环；为 0 → 把可修复的失败直接暴露为事故 |
| **单步超时** | 由上游整体 SLA 减去其他步骤预算得出 | 单步超时 > 整体超时 → 上游已放弃，下游仍在计费 |

### 4.4 分阶段实施路径

**最小可行（能跑通且能归因）**

- 单一模型 + 单一档位；路由机制就位但只填一条规则。
- 结构化输出走 `json_schema` 严格模式 + 1 次修复重试。
- 每次调用记录 `requested_model` / `model_id` / `reasoning_effort` / token 用量 / `repair_attempts` / `latency_ms`。
- 模型快照号显式写在配置里，禁止别名。
- 接受成本与延迟未优化，但**任何异常都能定位到具体一次调用**。

**生产就绪**

- 按 §3.5 完成分档；规划类与抽取类各有拐点实测数据。
- 路由表进版本管理并随 trace 上报 `route_version`，改动走评审。
- 缓存命中率按路由变体分开监控，低命中变体有定位路径。
- 有降级/升级链，每次跳转被计数与告警，不被静默吞掉。
- 模型版本升级有回归与回滚流程（`D17-迭代-迭代闭环.md`），升级前后在分档验证集上对比。
- 有"哪些子任务不该用模型"的白名单，并定期审查。

## 5. 检查清单

### 5.1 「最小可行」

- [ ] 每次模型调用都记录 `requested_model` 与 `model_id`，且二者分开存储
- [ ] 配置里没有 `latest` / `default` / 无快照号的模型别名
- [ ] 每个子任务有 `task_type` 标签，且该标签进入每次调用的记录
- [ ] 所有面向机器的输出都有显式 schema，校验失败会产生可计数的失败事件
- [ ] 修复重试有硬上限，重试次数被计入指标
- [ ] 单步超时严格小于上游整体超时

### 5.2 「生产就绪」

- [ ] 路由表有自身版本号并随调用记录上报；改动需评审
- [ ] 规划类与抽取类子任务有各自的**推理档位拐点实测数据**，不是照搬外部建议值
- [ ] 缓存命中率按路由变体切分监控，每个变体的前缀字节稳定性有验证手段
- [ ] 存在升级/降级链，链上每次跳转都被计数与告警
- [ ] 失败在**子任务切片**上统计，而不是只看全局成功率
- [ ] 模型版本升级有回归流程与回滚路径（`D17-迭代-迭代闭环.md`）
- [ ] 选型依据来自自建分档验证集，全文没有一处用 MMLU / HumanEval 类分数作为 Agent 选型理由
- [ ] 存在"不使用模型"的白名单（规则 / schema 校验可覆盖的步骤）

## 6. 常见陷阱

### 陷阱 1 · 用排行榜分数选 Agent 模型

**现象**：选型会上用综合能力分或编码基准分排序，第一名直接上生产。
**根因**：把"通用能力"当成可外推的标量；而能力是参差的，且所有固定基准都会饱和（`D09-质量-评测.md` §6）。
**埋伏阶段**：设计。
**规避**：选型证据必须来自**自己的子任务切片**；公开基准只用于把候选集从几十个筛到 3–5 个。硬规则：基于 MMLU / HumanEval 类分数为 Agent 选型是明确不成立的赌注 `[已验证]`。

### 陷阱 2 · 把推理档位当"质量旋钮"

**现象**：线上效果不好 → 全局调高推理档位 → 成本与延迟上涨，正确率无明显变化。
**根因**：测试时计算收益递减且拐点因任务类型而异。分类/抽取不需要内部推理，加思考 token 基本无收益；规划类档位不足则是灾难性的。一个全局旋钮无法同时满足两类。
**埋伏阶段**：构建。
**规避**：按子任务类型分别测拐点（§4.1 步骤 5），把档位写进路由表而不是全局配置。

### 陷阱 3 · 约束解码压死了思考

**现象**：开启严格 JSON 约束后，需要推理的字段质量大幅下降；值"格式完美但内容平庸"。
**根因**：约束解码在解码阶段掩蔽非法 token，模型无法在结构之外展开中间推理；对"值本身需要推理"的字段，约束越早介入自由度损失越大。
**埋伏阶段**：构建（引入时无症状）。
**规避**：把需要推理的字段显式列入 `free_text_fields` 豁免约束（§4.2），或改两阶段——先自由推理，再用约束解码做结构化归纳。注意这种劣化**不产生解析错误**，格式指标看不到。

### 陷阱 4 · 前缀缓存被路由与动态内容击穿

**现象**：缓存已启用但命中率长期偏低且无人追查；成本与首 token 延迟高于预期。
**根因**：前缀缓存要求前缀**字节级稳定**。常见破坏源：提示里插入当前时间；工具集按需增减；按难度路由到不同模型（缓存不互通）；路由使同一业务路径组装出多个前缀变体，每个变体重复次数都低于缓存生效阈值。
**埋伏阶段**：设计（路由与上下文装配是同一决策的两面）。
**规避**：把可冻结前缀当契约冻结；路由变更与缓存命中率联动评审；按路由变体分别监控命中率。

### 陷阱 5 · 静默的模型漂移

**现象**：某天开始"整体感觉不稳定"，成功率降几个点，但没有任何部署变更记录。
**根因**：使用 `latest` 类别名，供应商在服务端换了快照；函数调用与 JSON 模式的边界行为跨版本会变，且不产生项目侧事件。
**埋伏阶段**：运营（引入点在建置期的配置里）。
**规避**：显式快照号 + 记录并比对 `requested_model` 与 `model_id`，不一致即告警。升级流程归 `D17-迭代-迭代闭环.md`。

## 7. 反例

### 反例 1 · 全链路最高档位

**做法**：所有步骤统一最强模型 + 最高推理档位 + 最大输出上限，理由是"质量优先"。
**爆掉的方式**：上线初期效果最好、一切正常；流量上来后 P99 延迟首先失控（长尾来自少数长思考请求），随后成本按步数放大。此时任何削减都要先做分档评测——而立项时没做——于是只能凭感觉逐档下调，每次下调都伴着一次"不知道会坏在哪"的发布。

### 反例 2 · prompt 里写"请输出 JSON" + 事后正则

**做法**：为不引入 schema 机制，在指令里强调格式，下游用正则抠字段。
**爆掉的方式**：演示集上通过率很高。生产中少量输出被 markdown 代码块包裹、字段顺序变化、字符串含未转义引号，正则抠出**错误但合法**的值（例如把备注里的数字当成金额）。这类错误没有异常、没有日志，只有错误的下游副作用。爆点通常在第一次真实的资金或状态变更操作上。

### 反例 3 · 语义缓存没做租户隔离

**做法**：为降低重复提问成本，对"看起来相似"的请求直接复用上一条结果。
**爆掉的方式**：跨租户复用时把 A 的结果返回给 B。相似度阈值越低命中率越高、错配越频繁。**这类泄漏不触发任何解析错误或超时**，只会在某次审计或用户投诉时一次性暴露。缓存隔离与租户边界归 `D10-质量-安全护栏.md` 与 `D16-交付-治理合规.md`。

## 8. 开放问题

- **路由判据用什么？** 一派主张**验证器触发**（只有下游可自动判定的失败才触发升级），理由是判据自证、可回归；另一派主张**学习式路由器**（用历史轨迹训练难度预测器），理由是能在尝试前选对档位、不浪费一次调用。前者的前提是"存在廉价可靠的验证器"，后者的前提是"有足够历史轨迹且分布稳定"。**分歧本质是"验证成本 vs 预测成本"谁更低，目前没有跨任务通用的答案。**
- **reasoning trace 该不该回灌上下文？** 一派认为保留上一步的思考能显著改善长任务连贯性；另一派认为思考内容会污染上下文、拉高成本并放大 context rot。争点在于"思考是否构成状态的一部分"。**待跨任务的对照实验。**
- **多模型并行仲裁值得吗？** 支持方给出高风险字段的收益，反对方指出成本近线性增加且仲裁器引入新偏见。缺的是**按失败代价分布**的判据，而不是按任务类型的经验规则。
- **没有验证器的开放任务怎么办？** "最小够用档位"的判定依赖"能否被下游验证器救回"；该判据失效时，是否只能退回最高档位？**本文未收敛。**
